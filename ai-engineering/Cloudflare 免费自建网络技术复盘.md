# Cloudflare 免费自建网络技术复盘

从 Pages 部署、Clash Verge 接入，到间歇断网的排查与优化

实践时间：2026 年 10 月 23 日至 26 日。文中时间均为北京时间。

**最终结论：这套方案能够使用，但网络连接不稳定。本次排查和配置优化改善了部分显示、配置和故障发现行为，没有解决持续稳定使用的问题。**

## 1. 背景与目标

我最初想搭建一套免费的自建代理，使用 Cloudflare Pages 运行 edgetunnel，通过 KV 保存配置，再把订阅导入 Windows 上的 Clash Verge。搭建参考了[这篇教程](https://www.freedidi.com/23618.html)。

最初的目标是能正常访问网页。实际使用后，我又希望节点名称清楚、出口地区直观、尽量保持地区一致，并解决时好时坏、Timeout、Error 和网页打不开的问题。

这篇文章记录整个搭建和排查过程：从显示名称改造、固定入口，到主备切换、DNS、传输方式、网络对照和故障记录。有效的局部调整和失败尝试都会保留。

判断结果时，我区分三件事：配置是否改成功、测试当时能否连通、实际使用是否持续稳定。这三者不能互相替代。不同时间窗口的测试也分别列示，不合并成一个所谓的长期可用率。

## 2. 实际搭建了什么

### 2.1 资源与职责

下文用 pages.example.com 表示 Pages 默认域名，用 proxy.example.com 表示自定义域名，便于说明两类入口。

| 组成 | 本次实际情况 | 作用 |
|---|---|---|
| Cloudflare | 已有账号，能够进入控制台 | 承载 Pages 项目及相关资源 |
| GitHub | Fork 了上游 edgetunnel 仓库 | 保存项目代码来源 |
| 服务程序 | edgetunnel，来源于 [cmliu/edgetunnel](https://github.com/cmliu/edgetunnel) | 提供管理页面、订阅及代理处理 |
| 初始 Pages 项目 | 第一次创建的项目 | 部署后遇到平台封锁 |
| 后续 Pages 项目 | 使用 Pages 默认域名访问 | 后续管理、订阅和代理测试使用的站点 |
| ADMIN | 生产环境管理员变量 | 管理页面认证 |
| KV | 绑定变量名为大写 KV | 为程序提供配置存储 |
| 免费域名 | 初期已经注册，尚未配置 DNS | 用于后续域名接入测试 |
| 后续测试的自定义域名 | proxy.example.com | 能到达登录页，另做过真实代理对照 |
| 客户端 | Windows、Clash Verge | 导入订阅、选择线路和策略 |
| 测试时内核 | Mihomo Meta v1.19.32 | 实际处理客户端代理连接 |

初始 KV 命名空间名为“边缘隧道-kv”。命名空间显示名称可以不同，但程序读取的绑定变量名需要配置为大写 KV。

### 2.2 搭建路径及实际发生的事情

实际搭建的主线是：准备免费域名、创建 Pages 与 KV、配置 ADMIN 和 KV 绑定，再把生成的订阅导入客户端。[参考教程](https://www.freedidi.com/23618.html)

**步骤一：准备资源。** 准备 Cloudflare 账号、免费域名和 Fork 的项目代码。初期域名已经注册，但 DNS 尚未配置，节点也还没有完成验证。

**步骤二：创建初始 Pages 项目。** 创建项目，配置生产环境 ADMIN，并建立 KV 命名空间。初期出现过 404、项目被封锁、管理页面提示未绑定 KV 等问题。

**步骤三：检查绑定并重试部署。** 当时实际进入控制台，核查生产环境 ADMIN、大写 KV 与命名空间绑定，执行了“重试部署”。平台明确拒绝重试，返回项目被封锁的信息。

这一步没有完成解封，也没有证明原项目重新部署成功。最初的 404、KV 提示和平台封锁是不同现象，不能只用其中一个概括全部原因。

**步骤四：使用后续搭建好的站点。** 后续管理、订阅、浏览器验证和网络测试，都围绕另一个能够访问的 Pages 项目进行。这里并不是原项目解封成功，而是后续有了能工作的部署。

**步骤五：通过管理页面生成订阅并导入 Clash Verge。** 测试到的实际客户端节点使用 VLESS、WebSocket 和 TLS，并启用了 ECH；证书校验保持开启。后台页面能够打开，是管理面可达的证据，代理是否能上网仍需单独测试。

**步骤六：测试原生域名及自定义域名。** 后续两者的 /admin 都曾跳转到 /login，并返回登录页面。自定义域名还进行了真实代理测试，结果没有优于原生入口，未加入最终固定候选。

搭建时需要注意：CNAME 应指向自己的实际 Pages 项目，不能照抄教程示例；Pages 的 KV 绑定变更需要重新部署才能生效。管理页面提示未绑定 KV 时，要检查绑定名称、生产环境和部署是否已更新。[Pages 绑定说明](https://developers.cloudflare.com/pages/functions/bindings/)

### 2.3 理解这条连接链路

下面是用于理解故障位置的逻辑示意，不是每一次请求的完整抓包还原。

~~~mermaid
flowchart LR
    C["Clash Verge / Mihomo"] -->|"VLESS + WebSocket + TLS，启用 ECH"| E["Cloudflare 入口"]
    E --> P["Pages 中的 edgetunnel"]
    P --> T["目标网站"]
    P -. "依目标及策略，可能使用" .-> X["反代 / 出口"]
    X --> T
    K["KV：保存配置"] -.-> P
    A["ADMIN：管理认证"] -.-> P
~~~

这条链路说明了三件事：

1. 管理页面可打开，只说明其中一部分链路可用。
2. 修改节点名字，不会改变连接质量。
3. 多个入口 IP 如果仍指向同一个 Pages 项目，不等于多套彼此独立的服务。

## 3. 最先遇到的问题：名字、地区和 IP 都不直观

### 3.1 原始页面为什么难用

原始代理页出现“自动选择”“故障转移”“负载均衡”“漏网之鱼”“全球直连”等名称。我很难从这些名字直接理解它们的作用，也看不出节点对应的国家。

实际做过的第一轮改造是把这些名称改成更直接的说明：

| 原名称 | 调整后的含义 |
|---|---|
| 节点选择 | 手动指定线路或策略 |
| 自动选择 | 自动选快线，可能切换线路 |
| 故障转移 | 断线后按顺序换备用 |
| 负载均衡 | 多条线路按网站分担 |
| 漏网之鱼 | 未匹配网站的默认上网方式 |
| 全球直连 | 直连规则，默认不走代理 |
| 全球拦截 | 拦截规则，默认阻止连接 |

早期还在名称中显示连接 IP、检测日期、历史地区说明。实际使用时感觉太长、不直观，后来简化为“编号｜国家·城市”。这些是界面可读性改造，不是网络性能修复。

### 3.2 地区检测实际得到什么

当时对 16 条节点进行过检测，记录的结果是：10 条显示美国加州、1 条显示中国香港、5 条未测通。随后又遇到订阅从 16 条变成 50 条、连接地址全部变化的情况，旧检测结果无法再匹配新入口，页面因而大量显示“地区未知”。

后续一批 20 条候选中，记录了 13 条查到地区、7 条未测通。地区检测只反映当时的查询结果，不能作为长期固定地区的保证。

**早期实现只覆盖了已测入口，没有完整处理订阅更新后的重新检测。** 后来补上了自动地区查询，但它又会在检测开始和结束时重载配置。

配置重载可能影响正在使用的连接。后来明确说明了这一影响，并停用了会反复重载配置的早期自动检测程序。没有证据证明全部断网都由它引起，也不能把它引入的干扰全部归给线路。

### 3.3 日本、美国等显示为什么不能直接比较

本次需要区分三种信息：

| 信息 | 能说明什么 | 不能说明什么 |
|---|---|---|
| 节点连接地址 | 客户端尝试连接哪个域名或 IP | 不等于网站看到的出口地址 |
| 网站检测到的出口 IP | 当次访问该目标时，对方看到的地址 | 不保证其他目标、其他时刻相同 |
| IP 地区数据库 | 查询服务对该 IP 的地区标注 | 不精确证明机房物理位置，也不是永久标签 |

后台检测曾显示日本，另一些查询又显示美国。早期一次浏览器出口查询并未同步确认 Clash 实际选中的订阅，因此不能把那次结果直接当作自建节点的出口。

后续还多次发现桌面已经切换到另一个现有订阅。**如果不先确认当时的路由，比较两个页面上的国家名称，很容易把不同线路的结果混在一起。**

本次没有完成“同一个节点、同一个目标、跨较长时间”的完整地区一致性验收，因此既不能说它必然一直跨国跳转，也不能保证它永久固定在某个国家。历史地区名称仅保留为识别标签。

## 4. 从显示问题转向真实断网

实际使用中，问题不只是测速变红，网页也确实打不开。

这改变了排查目标。需要判断实际请求失败的位置，不能只解释 Timeout、Error 的含义。

还需要避免一个误判：REJECT 本来就用于拒绝连接，它显示失败不代表代理节点坏了；DIRECT 成功也不代表自建代理成功。本文对“自建失败”的判断，来自实际节点请求与故障日志，不是把页面所有红色卡片都算成故障。

后续测试主要使用以下固定目标：

- Google 的 generate_204。
- YouTube 的 robots.txt。
- ChatGPT 的 robots.txt。
- 部分早期测试还使用 gstatic、example.com、Cloudflare 页面或下载请求。

这些小请求可以检查代理连通性，但 robots.txt 返回成功不等于完成登录、对话、视频播放或长连接。真正的浏览器对话验证另列，不和这些检测混为一谈。

## 5. 优化与排查过程

下面按主要阶段展开。同一类重复试验合并列示，分别说明修改目的、测试结果和局限。

### 5.1 固定候选入口，减少订阅更新带来的变化

**问题：** 初期候选数量、地址和端口会随订阅变化；某次测过的好入口，下次更新后未必还在。

**操作：**

1. 查看后台的入口、端口、传输、ECH、反代等设置。
2. 对多个入口和端口做实际请求测试。
3. 从随机候选逐步收敛到少量固定候选，先固定三条，后续加入原生域名入口形成四条。
4. 停用早期反复重载配置的地区自动检测。

早期记录中，固定三条后的一组 36 次网页请求全部成功。后来的真实断网说明，这个结果只适用于当时的窗口，不能作为持续稳定的证明。

后续使用的四条逻辑节点如下。国家、城市名称是历史检测标签。

| 编号 | 连接地址 | 说明 |
|---|---|---|
| 01 | pages.example.com:443 | 原生域名入口 |
| 02 | 104.17.156.19:443 | 固定入口 IP |
| 03 | 104.17.151.40:443 | 固定入口 IP |
| 04 | 104.17.144.7:443 | 固定入口 IP，后来多次作为主线候选 |

这些节点使用同一个自建站点相关配置。**固定候选减少了配置漂移，没有消除入口连接本身的失败。**

### 5.2 加入自动主备，但没有把它当成独立服务备份

**问题：** 手动固定到某一条坏线路后，可能一直留在该线路。

**操作：** 增加 fallback 主备组，主选择器指向主备组，节点按顺序选择。做过主线故障模拟、备用切换和下载验证。

早期有过 30 秒检查的版本，后续实验又出现 300 秒、惰性检查的版本；不是从头到尾只有一套参数。后面还针对故障计数窗口和检查方式分别做了验证。

**局部结果：** 模拟主线不可用时，可以切到备用并完成请求。

**没有解决：** 如果候选入口都不可用，或者健康检查误判，自动主备仍可能无法恢复。共用同一套后端的几个入口，也不能等同于几套独立备用服务。

### 5.3 对照端口、传输方式和指纹

**目的：** 判断是不是端口或客户端握手设置导致当前组合失败。

| 试验 | 实测结果 | 处理 |
|---|---|---|
| 一个入口的 443、2053、2083、2087、2096、8443 对照 | 每个候选该轮均为 6/6 成功 | 无法据此证明换端口更好，未持续改端口 |
| 02 的同类端口对照 | 443 为 6/6，2053 为 4/6，其余该轮为 6/6 | 没有建立优于 443 的可靠收益 |
| WebSocket 基线、早期数据、Firefox 指纹对照 | 各自该组均为 9/9 成功 | 同时成功不等于候选更优，未据此全面换指纹 |
| Chrome 与 native 指纹分入口对照 | 主入口两者各 6/6；另一入口分别 1/6 和 3/6 | 不能证明改指纹能普遍修复，未推广 |
| XHTTP 候选 | 0/9 成功，WebSocket 对照为 9/9 | 未采用 |
| 具名 gRPC 候选 | 0/9 成功，基线为 9/9 | 未采用 |

这些结果只适用于本次客户端、服务端配置和网络窗口，不能推导成 XHTTP 或 gRPC 在所有环境中都不可用。

另一个窗口中，WebSocket 基线为 6/9、增加早期数据后为 7/9、gRPC 为 0/9。这些结果同样没有建立持续可靠性，不能只保留表格中全通的窗口。

早期数据只在测过的 04 上保留了 2048 字节设置。后来给原生域名入口单独做对照：基线 4/12，增加早期数据后 6/12，两者都不可靠，因此没有推广到 01。该功能没有被证明能根治断网。

### 5.4 调整 ECH 的 DNS 查询路径，保留加密与证书校验

**操作：** 为 cloudflare-ech.com 设置直接访问的加密 DNS 策略，使用阿里与腾讯的 DoH 地址，保留 TLS、ECH 和证书校验。

~~~yaml
nameserver-policy:
  cloudflare-ech.com:
    - https://223.5.5.5/dns-query#DIRECT
    - https://doh.pub/dns-query#DIRECT
~~~

**结果：** 对应的一组检查能够完成，但后续仍发生断网。

**边界：** 这证明调整后的查询路径在当时能工作，不能单凭它认定所有故障来自 DNS，也不能说 ECH 是提速开关。没有通过关闭证书校验来换取“测试成功”。

### 5.5 用更长的请求记录重新评价节点

在一次扩展测试中，对四条节点各做 36 次请求，合计 144 次：

| 节点 | 成功 | 失败 |
|---|---:|---:|
| 04 | 35/36 | 1 |
| 02 | 24/36 | 12 |
| 03 | 33/36 | 3 |
| 01 | 36/36 | 0 |
| 合计 | 128/144 | 16 |

当时 01 表现较好，后续阶段曾把原生域名入口放在主位。此后又被新的对照和真实故障推翻。

上表按逐请求记录重新计数，合计 16 次失败。

部分明确错误记录为：

~~~text
dial tcp 104.17.156.19:443: i/o timeout
dial tcp 104.17.151.40:443: i/o timeout
pages.example.com:443 connect error: context deadline exceeded
~~~

前两类明确涉及入口 TCP 连接超时。后一类只说明建立代理外层连接超过截止时间，单凭这行不能进一步区分 TCP、TLS/ECH 或 WebSocket 的具体阶段。

### 5.6 修正主备的故障计数窗口

**问题：** 连接一次失败本身就可能花约 5.2 秒。原先 5 秒窗口太短，后续失败到来时，计数可能已被重置。

**操作：** 使用实际安装的 Mihomo 内核，在本地可控 SOCKS 服务上比较 5000 毫秒与 10000 毫秒设置。这里的主线故障是人为模拟，不是公网故障。

| 设置 | 观察到的行为 |
|---|---|
| 5000 毫秒 | 仍留在坏主线，最终请求失败，没有触发对应主动检查 |
| 10000 毫秒 | 触发检查，选择备用，最终返回 204 |

据此将后续配置中的 timeout 调到 10000 毫秒。

这里修改的是主备健康检查及相关故障判定行为，不是延长 Cloudflare 服务的生命，也不是修复公网数据包丢失。

后来还比较了 max-failed-times 为 2 与 1 的情况，首次恢复分别约 21.691 秒与 21.613 秒，没有显示有意义的改善，因此没有把“改成 1”作为进一步修复。

### 5.7 家庭网络与手机热点对照

**目的：** 判断是否只有家庭网络能触发故障。

实际做过同一组自建节点的网络对照；手机使用移动流量，测试完成后恢复原网络。

| 网络窗口 | 结果 |
|---|---|
| 第一次移动热点 | 12/12 成功 |
| 家庭网络 | 12/12 成功 |
| 再次移动热点 | 04 为 0/3、03 为 0/3；02 与 01 各为 3/3 |

热点下也能复现失败，因此不能只把原因归给家庭路由器或单一家庭宽带。两种网络都可能失败，也不等于已经证明它们失败于同一个原因。

这些窗口没有同步覆盖完整运营商路径，不能据此断言某一家运营商就是根因。

### 5.8 查看 Cloudflare 指标与实时日志

**操作：**

1. 在已登录的 Cloudflare 控制台查看 liu 项目的指标。
2. 控制台实时日志出现 WebSocket 建立失败后，改用官方 Wrangler 工具。
3. 观察代理测试与服务端日志，区分客户端入口失败、服务端执行结果和流中断。

日志查看命令的基本形式如下：

~~~powershell
wrangler pages deployment tail <生产部署标识> --project-name <项目名> --format json
~~~

保存的一份“过去 24 小时”指标快照为：

| 指标 | 数量 |
|---|---:|
| 成功 | 55,190 |
| 错误 | 8,979 |
| Internal errors | 8,969 |
| Exceeded CPU | 10 |
| Script threw exception | 0 |
| Exceeded memory | 0 |

这些是平台统计窗口中的计数，不是个人网页访问次数，也没有和每一次断网完成一一对应。

**可得到的结论：** 平台上存在错误记录。

**得不到的结论：** 所有断网都由 CPU、免费额度、脚本异常或平台封锁引起。尤其不能把 8,979 个错误全部写成 CPU 超限，因为该快照对应的 CPU 超限只有 10 次。

CPU 执行耗时与连接持续时间也不是同一概念。官方限制文档可以解释这些指标，但本次没有证据把某个统一资源上限认定为全部故障的根因。[平台限制说明](https://developers.cloudflare.com/workers/platform/limits/)

日志管理流量与自建代理数据流量在测试中作了区分，已有的其他订阅没有接成自建节点的上游。

### 5.9 真实浏览器验证：确认它确实能用过

曾临时启用自建订阅，核对实际连接链路包含自建节点和主备组，并在浏览器中完成一次 ChatGPT 对话：

~~~text
发送：网络连接测试，请只回复：测试成功。
收到：测试成功。
~~~

测试后恢复原订阅及原选择。

这比只访问 robots.txt 更强，证明当时确实完成过实际应用请求。**它依然只是一次成功，后来发生的真实失败不能被这次成功抵消。**

### 5.10 两分钟定向抓包：没有复现完整断网

使用 Windows 管理员权限，运行了约两分钟的定向诊断：

- 限定五个目标 IPv4 的 TCP 流量。
- 使用 54 字节截断和大小上限。
- 采集结束后停止跟踪，管理员辅助进程退出。

该窗口中，15 次基础 TCP 连接与 12 次代理请求全部成功。确认过一次 SYN 重传，对应一次连接约 1224 毫秒后成功。

但捕获点的接收方向 Wi-Fi 帧处于受保护状态，无法按当时的截断数据解码入站 TCP 握手。因此：

- 没有解码到 SYN-ACK，不代表网络没有返回 SYN-ACK。
- 一次 SYN 重传，不能定位究竟是哪段链路造成延迟。
- 没复现断网，不能把这次抓包写成已经定位根因。

抓包未修改网络或安全设置。

随后尝试用无需管理员权限的 SIO_TCP_INFO 获取本进程自建 socket 的统计。这不等同于抓取整个系统的流量。一次三分钟观察得到 29 次入口控制检查成功、15 次自建检测请求成功，但仍只是当时没有复现故障。

### 5.11 阅读服务端重试逻辑，但没有据此盲改

本地保存的源码中发现：

- 一个 1000 毫秒的出站连接超时设置。
- 已收到数据与尚未收到数据的连接，后续重试行为有区别。
- 显式设置 PROXYIP 会改变自动兜底行为。

**关键限制：这份本地源码与线上部署的逐字一致性没有完成核验。** 而且部分客户端日志已经明确失败于入口 TCP 建连，发生在这些出站逻辑之前。

因此该阶段只做只读审计，没有把“看到了 1 秒”当作根因，没有宣称已经修改线上超时，也没有贸然固定反代导致丢失原有兜底能力。

### 5.12 尝试 IPv6 与 TCP 并发，没有可靠收益就不采用

**IPv6：** 原生 IPv4 和两个 IPv6 候选在短测中各为 12/12 成功；但模拟旧候选不可用、只能依赖 IPv6 备用时，两组复测分别只有 3/9 和 5/9 成功，未达到可用要求。因此未加入日常配置。

该过程有一次测试加载了旧配置，当时已明确判定结果无效，修正加载路径后重新测试。无效结果没有作为采用 IPv6 的依据。

**TCP 并发：** 成对比较中，对照为 17/24 成功，并发候选为 16/24 成功，没有显示可靠收益，因此没有启用。

这里保留失败尝试，是为了避免以后把相同选项重新包装成已经验证的“稳定优化”。

### 5.13 把低频检查改为每 30 秒主动检查

**问题：** 在 300 秒、lazy 为 true 的版本中，曾测失败的备用恢复后，可能较久没有重新识别；偶发成功的主线仍可能占据优先位置。

**操作：** 用本地可控故障，比较：

- 原设置：interval 为 300，lazy 为 true。
- 候选设置：interval 为 30，lazy 为 false。
- 使用当前 10000 毫秒超时设置复测。

**结果：** 在“主线失效、备用恢复”的模拟中，候选约 40 秒后选到备用，最终请求成功；原设置在约 55 秒观察窗口结束时仍留在主线，最终请求失败。

据此保存了 30 秒主动检查配置。

**这个修改有机制层面的实测收益，但边界很明确：** 30 秒是检查间隔，不是承诺 30 秒内恢复；还需考虑检查耗时、失败条件和是否存在可用备用。

另外，某个 Google 检查成功，并不代表同一节点访问其他目标都成功。本次后续真实测试就出现了这种情况。fallback 的顺序选择行为应按其实际健康状态理解，不能把它当成逐请求必成功的重试器。[fallback 说明](https://wiki.metacubex.one/config/proxy-groups/fallback/)

### 5.14 再次比较 01 与 04，调整主线优先级

同一时间段内，分别固定到 01 与 04，成对测试实际目标：

| 节点 | 成功 | 请求耗时中位数 |
|---|---:|---:|
| 04 | 15/15 | 935 毫秒 |
| 01 | 13/15 | 3165 毫秒 |

这一窗口中，04 表现更好。于是把保存的主备顺序由 01、04、03、02 调整为 04、01、03、02。只修改自建订阅覆盖脚本，保留所有原节点参数，并验证其他正在使用的订阅未被重载。

新配置单独复测 9/9 成功。但后续真实使用中，04 仍然失败。**因此这次调整只能写成阶段性优先级优化，不能写成找到永久稳定主线。**

### 5.15 连续观察推翻了“短测正常就算修好”

另开独立进程，对当时已物化的“01 优先、30 秒主动检查”版本进行 15 轮观察。开始时间为 10 月 26 日 08:59:05，结束时间为 09:15:47，约 17 分钟。

- 合计 45 次检测。
- 成功 36 次，失败 9 次。
- 曾出现 Google 成功，YouTube 与 ChatGPT 失败。
- 曾从 01 切到 04 后恢复。
- 01 被重新判为健康后，顺序策略又会优先选择它，随后仍有卡顿或失败。

这组长观察使用的是 01 优先版本，不是后来保存的 04 优先版本，不能误标为“04 优先连续运行 17 分钟”的成绩。

同样，不能仅凭每轮开始和结束的组选择，断言这一轮每一个请求都走过同一节点。逐节点比较应看前面的固定节点成对测试。

### 5.16 补上断网也能运行的本地记录器

在线排查有一个现实限制：网络断开后，在线工具可能同时失去访问能力，故障信息无法及时传回来。因此需要让电脑在断网时也能自行保存记录。

于是实现本地记录器：

1. 读取当前订阅、模式和选择链。
2. 仅在自建订阅且为全局模式时发起自建检测。
3. 检测失败后保存请求结果、选择状态及定向入口控制检查。
4. 使用其他订阅时只记录等待状态，不对其进行探测。
5. 日志只保留当前与上一份轮转文件，体积约限制在 4 MiB 加单条记录以内。
6. 本次启动限时八小时，没有添加系统开机启动任务，不需要保持在线对话。

验证覆盖了非自建时不探测、模拟失败落盘、切换订阅后的结果排除、成功路径、日志轮转和重复启动保护。

重复启动保护最初触发了 Windows 锁定字节读取异常，后续修正为直接拒绝第二个实例，并复测确认不会再额外启动探测。这里的模拟只验证记录器行为，不代表复现了真实网络根因。

### 5.17 捕获 09:23 的真实故障

本地记录器捕获了一次实际使用中的故障：

- 时间：10 月 26 日约 09:23。
- 当次 Google、YouTube、ChatGPT 三个请求全部失败。
- 均出现 SSL: UNEXPECTED_EOF_WHILE_READING，耗时约 5 秒。
- 随后的独立入口检查中，04 的 104.17.144.7 和 03 的 104.17.151.40 TCP 连接超时。
- 同一组后续控制检查中，两个原生域名入口地址与 02 地址又能完成基础检查。

控制检查是随后新建的独立 socket，不是前一条失败连接的延续。前一次代理失败、后一次基础检查成功，可以同时成立，不能互相抵消。

还发现当次采样的 GLOBAL 直接指向 04，绕过了主选择器中的自动主备。但保存的自建默认选择仍指向自动主备。

这只能说明：**采样瞬间的运行选择与保存默认不同。** 它能解释那段请求为什么没有按预期经过主备；不能把它当成全部断网的原因，也不能用它解释四个入口各自的失败。不同采样并非同一瞬间，不能混为一谈。

### 5.18 重新测四条线路，再测自定义域名

该次故障后的四节点重测为：

| 节点 | 成功 |
|---|---:|
| 04 | 2/3 |
| 02 | 0/3 |
| 03 | 2/3 |
| 01 | 2/3 |

**四条都至少失败过一次。** 这直接否定了“只要把 04 放首位就能稳定”的推断。

随后检查已有自定义域名。管理页能打开，并不意味着它适合做可靠代理入口，因此进行了与原生域名同时段的成对测试：

| 候选 | 成功 | 失败 |
|---|---:|---:|
| 原生域名入口 | 12/15 | 3 |
| 自定义域名入口 | 9/15 | 6 |

自定义域名没有改善，因此没有加入最终固定候选。没有通过降低 TLS 校验来让它“通过”。

还查阅过[项目上游的类似超时反馈](https://github.com/cmliu/edgetunnel/issues/1566)。其中有人报告 DNS 调整有效，但那是其他环境的结果，不能替代本次固定入口 TCP 超时与代理失败的证据，所以没有据此直接照抄设置。

## 6. 最终保存到什么状态

最后核对的自建配置如下。这是最终保存的设置，实际生效情况仍需要结合运行时的选择链检查。

| 项目 | 保存状态 |
|---|---|
| 候选入口 | 四条保留 |
| 自动主备优先顺序 | 04 → 01 → 03 → 02 |
| 检查目标 | https://www.gstatic.com/generate_204 |
| 检查间隔 | 30 秒 |
| timeout | 10000 毫秒 |
| lazy | false，主动检查 |
| max-failed-times | 2 |
| 主要传输 | VLESS + WebSocket + TLS |
| 证书校验 | 保持开启 |
| ECH | 保持开启 |
| ECH 查询 DNS | 直接加密 DNS 策略 |
| 早期数据 | 仅 04 保留 2048 字节 |
| 原生域名额外早期数据 | 没有推广 |
| TCP 并发候选 | 没有启用 |
| IPv6 备用候选 | 没有加入日常配置 |
| 自定义域名候选 | 对照失败，未加入最终固定候选 |

主备组配置的核心部分如下：

~~~yaml
proxy-groups:
  - name: 自建主备
    type: fallback
    proxies:
      - 04｜美国·圣何塞
      - 01｜美国·洛杉矶
      - 03｜美国·圣何塞
      - 02｜美国·圣何塞
    url: https://www.gstatic.com/generate_204
    expected-status: 204
    interval: 30
    timeout: 10000
    lazy: false
    max-failed-times: 2
~~~

预期的选择链为：

~~~text
GLOBAL
  → 上网线路
    → 自建主备
      → 当前选中的自建节点
~~~

如果 GLOBAL 直接选择某条节点，上述主备组即使存在，也不在这条实际链路中。这是配置验收必须同时检查“保存值”和“运行值”的原因。

## 7. 现在能确认的原因，与不能确认的原因

### 7.1 已确认的故障机制

**第一，确实有入口建连失败。** 部分日志明确为目标入口 IP 的 TCP i/o timeout。对这些请求，问题发生在入口 TCP 建立阶段，不能先归为管理页面、规则名字或应用对话的问题。

**第二，健康检查不能覆盖所有实际请求。** 一次检查成功时，其他目标仍可能失败，因此“显示一个延迟数字”不等于稳定上网。

**第三，切换机制曾有配置层面的不足。** 过短的失败计数窗口、低频惰性检查、顺序策略反复回到偶发恢复的主线，以及一次实际运行绕过主备，都会影响恢复行为。但这些不能解释全部入口故障。

**第四，早期自动地区补查引入了配置重载。** 这是本次改造增加的潜在干扰，后来已停用，不能隐去。

**第五，短测试给过过强信心。** 出现过 36 次请求全成功、真实对话成功、IPv6 短测全成功、04 固定对照全成功，随后仍然失败。它们都只证明某个时间窗口可用。

### 7.2 尚未唯一定位的部分

本次没有完整证明：

- 具体是哪一段运营商路径或哪个网络设备导致每一次超时。
- 每次外层连接截止时间究竟发生在 TCP、TLS/ECH 还是 WebSocket 的哪一步。
- 历史平台 Internal errors 与某次实际断网的精确对应。
- 全部故障是否有一个共同根因。
- 同一节点未来是否始终保持同一个国家、城市或出口 IP。

因此不能把这些故障简单归因于“DNS 污染”“ECH 有问题”“CPU 不够”“被封锁”“家庭路由器差”或“人多拥堵”。这些可能是排查方向，未被本次证据统一证实。

## 8. 这套方案在本次使用中的缺点

| 缺点 | 本次实际表现 |
|---|---|
| 搭建成功与持续可用是两回事 | 管理页、订阅和实际请求曾成功，后续仍频繁断网 |
| 入口候选不是独立服务 | 四条都指向这套自建站点，不能据节点数量认定有完整冗余 |
| 自动选择不等于稳定 | 健康检查可能通过，实际目标仍然失败 |
| 出口地区不易作永久承诺 | 不同检测、路由和历史标签需要区分，没有完成长期一致性验收 |
| 免费平台和公网连接有不可控部分 | 客户端参数不能直接修复公网入口不可达；本次也未锁定一个可修复的平台根因 |
| 维护成本高于最初预期 | 要检查入口、DNS、传输、运行选择、日志、热点对照和真实故障 |
| 优化本身可能增加干扰 | 早期自动地区检测的配置重载就是实例 |

这些结论限定于本次配置、客户端、网络环境和观察窗口，不推导成所有使用同一项目的人都一定失败。

## 9. 可以沉淀为技术资产的方法

### 9.1 保留的排查顺序

1. 先记录实际运行的订阅、模式和选择链，避免测错线路。
2. 区分界面状态、管理页可达、基础 TCP/TLS 和真实代理请求。
3. 固定候选、目标与配置，一次改变一个主要变量。
4. 同时保留成功和失败记录，不只展示通过的轮次。
5. 将本地模拟、独立进程测试和桌面实际使用分开标注。
6. 改完后检查配置是否保存、是否生效、是否真的改善了目标行为。
7. 长期观察必须能在断网时继续本地落盘，不依赖在线联系。

### 9.2 这次排查的教训

- 不把一次 204、几轮全通或一次对话成功写成“稳定了”。
- 不把改了配置、保存成功、能够回退，写成故障已修复。
- 不把其他订阅的正常表现当作自建成功。
- 不把未采用的 XHTTP、gRPC、IPv6、并发或自定义域名候选写成最终配置。
- 统计按逐请求记录计数，参数按实际配置核对。
- 不把“没有抓到故障”解释成“没有故障”。

测试数据需要按逐项记录重新计数，参数则以实际配置为准，避免旧记录或手工汇总造成误判。

## 10. 最终结论

**这套 Cloudflare 免费自建方案确实能够工作。** 已经完成过真实浏览器对话和多组成功请求，因此不能简单说它完全不能用。

**但本次实际使用不稳定。** 实际发生过网页打不开，也记录到了逐请求失败、入口超时和连续观察中的故障，不能用先前短测成功来否定。

**本次优化没有达成持续稳定使用。** 显示名称更清楚了，候选更固定了，部分故障切换行为经过验证，断网记录也补上了；但四条候选都曾出现失败，自定义域名对照也未改善，底层间歇故障没有得到可验证的根治。

本次实践的最终评价是：

> **能用，但不好用，因为不稳定。**

继续调整入口顺序、检查频率和客户端参数，并没有让这套方案达到日常稳定使用的要求。因此，我最终转向了自己管理 VPS 的方式，使用 Xray + VLESS REALITY 搭建代理服务，并接入 Clash。

后续的服务器部署、电脑和手机接入，以及运行中的故障处理，已经单独整理在[《自建代理服务器：Xray + VLESS REALITY + Clash 实战》](https://github.com/lyj012/tech-notes/blob/main/ai-engineering/%E8%87%AA%E5%BB%BA%E4%BB%A3%E7%90%86%E6%9C%8D%E5%8A%A1%E5%99%A8%EF%BC%9AXray%20%2B%20VLESS%20REALITY%20%2B%20Clash%20%E5%AE%9E%E6%88%98.md)中，这里不再重复展开。
