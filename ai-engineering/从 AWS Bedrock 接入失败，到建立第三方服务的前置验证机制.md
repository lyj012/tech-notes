# 从 AWS Bedrock 接入失败，到建立第三方服务的前置验证机制

> **文章定位**：真实项目复盘 + AI 辅助开发方法论补充 + 可复用检查清单  
> **事件时间**：2026 年 10 月  
> **项目背景**：`living-room-quest`，Java 后端、Fire TV 黑客松、AI 内容生成  
> **证据范围**：本次操作记录、CloudTrail 事件历史 CSV、AWS Support 的实际回复、Codex 的项目反馈。本文不将推测写成事实。

## 一、这次真正要解决的是什么问题

我参加 Amazon Developer Hackathon，想让 `living-room-quest` 的 Java 后端调用 Amazon Bedrock 上的 Nova 2 Lite，用于游戏里的动态叙事、危机和选项生成。

**真正的成功标准**不应该是“账户注册完成”“领到 API 额度”“控制台能看到模型”或“SDK 已能发出请求”，而应该是：

1. 当前账户具有使用该模型的资格；
2. Java 后端可以完成至少一次真实、合法且可观测的调用；
3. 知道调用成本和失败处理方式；
4. AI 输出能被游戏业务正确消费，且故障时不破坏游戏流程。

实际情况是，我先完成了大量 AWS 环境、权限和预算配置，最后才发现：**核心服务被 AWS 账户准入策略限制，个人账户的这次申请未能获批。**

这不是一篇关于“如何配置 AWS”的教程，而是一次关于**如何避免把工程投入放在未验证的前提之上**的复盘。

## 二、事实时间线：已经验证到哪一层

| 阶段 | 真实发生的事 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| 账户与额度 | AWS Paid 账户激活；黑客松 **150 美元**促销额度兑换成功，另有新账户 **100 美元** Credit | 额度真实存在，且当时状态为 Active | 不能证明 Bedrock 调用已获准，也不代表额度耗尽会自动停机 |
| 产品适用范围 | 黑客松 Credit 的 Applicable products 包含 `Amazon Bedrock`、`AmazonBedrockFoundationModels` 等 | 这笔额度的适用服务范围包含 Bedrock 相关收费项 | 不能证明所有 Bedrock 功能、账户和模型均有准入资格 |
| 控制台 | 在 `us-east-1` 的 Model Catalog 中看到 Nova 2 Lite，能打开 Playground | 目录可见，控制台页面可访问 | **不能证明 Runtime 可以成功推理** |
| 身份与权限 | 配置 Root MFA、专用 IAM 用户 `living-room-quest-dev`、用户 MFA、最小模型调用权限 | 建立了隔离的项目身份与权限边界 | 不能解除 AWS 服务端的账户级准入限制 |
| 本地调用 | 使用 AWS CLI 临时登录；Java 21 + AWS SDK for Java `2.55.11` 发起 `Converse` | 本地认证、网络到 Runtime 的调用链已实际运行 | 不能单凭“请求到达”断言参数、模型或准入都正确 |
| 运行时错误 | CloudTrail 记录 **4 次** `Converse` 失败，均为 `ValidationException` | AWS 确实收到并拒绝了这几次请求 | 单凭错误类型还不能判断具体原因 |
| 原始证据 | 查到完整 `errorMessage`，要求验证 corporate customer，并给出 `bedrock-allowlisting` 支持入口 | **当前请求受账户准入审核限制** | 不能推出 AWS 在所有时间、所有地区都不开放个人使用 |
| 官方回复 | AWS Support 对这次账户申请表示：目前不向个人用户开放，企业申请需提供商业注册证 | **当前账户以个人身份无法按该工单路径获准** | 不能推断其他账户、其他产品或未来政策必然相同 |
| 替代方案 | Codex 报告第三方中转站的 `gpt6soi` API 已测试可调用 | 存在不依赖 Bedrock 的可行候选 | 不能由此证明整个 Java 游戏已经完成正式集成与验收 |

CloudTrail 最新一次失败调用的关键字段是：

```text
2026-10-07 05:18:29（北京时间）
eventName: Converse
eventSource: bedrock.amazonaws.com
awsRegion: us-east-1
userIdentity: living-room-quest-dev
userAgent: aws-sdk-java/2.55.11 ... Java 21
errorCode: ValidationException
```

真正决定诊断方向的是完整错误消息，而不是 `400` 或 `ValidationException` 这两个表象：

> To access Amazon Bedrock, you must provide further information so we can verify you are a corporate customer ...

随后 AWS Support 的回复进一步明确了本次账户的资格问题。**至此，继续修改 Java 请求结构、重复调整 IAM、反复换模型，不再是有证据支持的优先动作。**

注意：CloudTrail 这条事件的 `requestParameters` 为 `null`，因此不能凭事件记录反推 Java 请求中的全部参数，也不能声称已从 CloudTrail 验证实际使用的 inference profile ID。

## 三、这次真正的失误：验证顺序反了

原来的投入顺序接近于：

```text
注册账户 / 绑定付款方式
    → 领取 Credit
    → 设置 MFA、IAM 与本地临时凭证
    → 配置预算及自动拒绝策略
    → 修改 Java SDK 调用
    → 首次实际访问 Bedrock Runtime
    → 遇到账户级准入限制
    → 再去找 AWS Support 确认资格
```

问题不是这些工程化操作本身没有价值。**身份隔离、MFA、费用保护都合理；不合理的是，在尚未证明核心能力可用之前，就把它们全部做成了完整工程。**

我和 AI 都犯了同一个判断错误：把“服务显示在控制台里、额度列表里包含该服务”过早地当成“当前账户有资格调用该服务”。

这次浪费的主要资源并不是模型费用，而是**数小时不可恢复的注意力与操作时间**。更重要的是，大量控制台点击没有推动核心产品能力实现。这种机会成本不会体现在 AWS 账单里。

因此，新原则是：

> **越靠近关键前提的验证，越应该提前；越昂贵、越复杂、越可延期的工程化工作，越应该放在核心可行性确认之后。**

但“先验证”不等于用 Root 密钥、关闭保护、冒险扣费。必要的账户安全和最小金额控制，仍必须在第一次真实调用之前完成。

## 四、形成可复用的四道验证关卡

这套方法适用于 AI 模型 API、云计算、支付、短信、OCR、地图、语音、海外 SaaS 等任何外部依赖。

### G0：资格关——我是否真的被允许使用？

任何安装 SDK、创建资源、调整架构之前，先确认：

- **主体资格**：个人还是企业？是否要求营业执照、实名认证或人工审批？
- **地区资格**：中国大陆个人是否可以合法注册、支付并使用目标 API？
- **功能资格**：免费额度、试用名额、Model Catalog 可见性，是否与实际 API 调用权限分离？
- **审核状态**：有没有账号刚注册时不可用、需等待或必须工单审核的情况？
- **退出条件**：一旦发现主体资格不符合，是否立即停止投入并转向替代方案？

**产物**：一句明确结论——“可用 / 不可用 / 尚未验证”，并附证据来源。不能拿“理论支持”替代“当前账户已获准”。

### G1：成本与安全关——最小验证的风险能否承担？

在首次产生费用之前确认：

- 是否绑定信用卡，额度用完后是否继续计费；
- Credit 是否适用于目标服务，以及是否存在其他非抵扣收费；
- 是否可以限制单次请求大小、调用次数与最大费用暴露；
- 是否有最小权限身份，避免使用 Root API Key；
- 失败、超时和自动重试是否可能产生额外费用。

本次配置过**每月 10 美元预算、80% 实际成本告警，以及自动附加 Bedrock 显式 Deny 策略**。这类措施能降低风险，但必须严格区分：

1. **预算不是实时硬上限**，费用数据与执行动作可能延迟；
2. 预算是否排除 Credit，不能只看“未混合成本”就认定，必须核实实际 CostTypes 配置；
3. 这次配置的 Deny 针对专用 IAM 用户，不等于整个 AWS 账户绝对不能产生其他费用；
4. **没有真实触发演练，不能声称自动拒绝策略已经端到端验证成功。**

**产物**：最大可接受损失、最小身份权限、一次性测试范围，而不是提前建设复杂费用平台。

### G2：核心能力关——先跑通最小真实闭环

用**足够小、已经获得授权的真实请求**验证：

```text
真实身份 → 真实凭证 → 真实 API → 合法响应 → 记录成本与错误信息
```

例如 AI 模型接入，只要完成一次结构合法的输入与响应，记录实际 model ID、区域、延迟、Token 用量或返回的计量数据即可。**不需要先完成整个业务界面、通用模型网关和长期费用账本。**

成功标准是外部能力实际可用，不能用“网页能打开”“CLI 安装成功”“Access Token 有效”替代。

如果失败，优先保存完整服务端错误，而不是盲目多调用几次。

### G3：工程化与交付关——可用后再扩大投入

只有通过 G0～G2，才进入：

- 完整 Java SDK / Provider 适配；
- 超时、降级、重试与幂等边界；
- 结构化输出校验与领域规则隔离；
- 日志链路、监控、用量统计和限额；
- 自动化测试、Demo、部署和文档交付。

对复杂项目可以完整执行原有《AI 辅助开发技术验证清单》；对简单功能则只保留相关条目，避免把流程本身变成新的成本。

## 五、遇到 API 错误时，先找证据，不要让 AI 靠关键词猜

这次最有价值的 Debug 转折点，是从“只拿到 `400 / ValidationException`”变成“拿到 CloudTrail 中的完整 `errorMessage`”。

以后第三方接口失败，要求 AI **一次性提供最小诊断证据包**：

| 证据 | 用途 |
|---|---|
| HTTP Status + 具体异常类 | 定位错误大类，但不能直接当作根因 |
| **完整 error message** | 识别平台明确给出的限制或修复方向 |
| Request ID、失败时间 | 对齐平台控制台与支持记录 |
| 实际 endpoint、Region、model ID | 确认调用目标是否正确 |
| 脱敏后的请求结构和关键配置 | 查参数不兼容或调用方式错误 |
| 当前调用身份、实际权限 | 排除认证及授权问题 |
| 已经验证与尚未验证的内容 | 防止“调用过了”被误报成“功能正常” |

分类排查时，**同一个 `ValidationException` 既可能是请求参数问题，也可能是账户资格问题**。要读完整信息，而不是预设成“模型 ID 填错”或者“权限不足”。

同样，排障时不要把独立故障强行联系起来。本次项目还出现过“重启后测试存档缺失”，但没有证据表明它与 Bedrock 账户拒绝有关，应单独按本地持久化问题排查。

## 六、AI 和我应该如何分工

原则并不是“所有事情都由我亲自操作”，也不是“AI 自己一路做到底”。合理的边界是：

| 我负责 | AI / Codex 负责 |
|---|---|
| 定义业务目标、成功标准和可接受成本 | 只读检查项目、官方限制和当前环境 |
| 判断是否值得继续投入、设置止损节点 | 给出可验证事实、风险、最低成本验证路径 |
| 本人身份验证、付款及高风险授权 | 自动完成可授权的机械配置、代码修改和非付费测试 |
| 对首次付费调用、权限扩大作最终确认 | 在证据不足时停止猜测，保留日志并提出下一项最小验证 |
| 验收业务结果、决定上线与否 | 提供修改范围、测试结果、失败记录和回滚依据 |

特别要防止一种低质量的 AI 协作方式：AI 明明不了解真实代码，却提前指定大量文件、SQL 和架构改法。给 Codex 的应当是**目标、已知事实、必要约束、验收标准和授权边界**；具体实现应先由它阅读真实项目再决定。

还有一条需要加给 AI 的强制规则：

> **任何第三方平台集成，未完成 G0 资格验证与 G2 最小真实调用前，不得把“接入完成”作为事实汇报，也不要未经确认扩大配置和开发范围。**

## 七、止损规则：不为已经投入的时间继续追加成本

这次 AWS 事件触发了一个清楚的停止条件：**官方明确表示当前个人账户不符合 Bedrock 准入要求，而且没有可验证的自助解除办法。**

此时继续投入时间修改 IAM、换模型或反复尝试，并不会提高当前项目成功率。更合理的操作是：

1. 保留 Bedrock 已有代码与故障证据，不删除可复用成果；
2. 把实际不可用的 Provider 隔离或关闭，保留本地 fallback；
3. 验证其他合法可用的模型 API。Codex 已报告 `gpt6soi` 中转站接口可测试调用，但底层模型真实性、服务稳定性以及 Java 项目正式接入仍须分别验证；
4. 把精力重新投入可交付的游戏体验，而不是继续为 $150 Credit 消耗时间；
5. 若未来准入政策变化，再重新评估，不将“也许有一天能用”作为当前项目依赖。

这不是放弃工程质量，而是**在证据发生变化后及时修改技术路径**。

## 八、可直接复制的「外部服务接入验证卡」

以后接任何新 API，先填这张卡，再决定是否交给 Codex 开发。

```text
服务 / 功能：
业务目标：
为什么必须引入该外部依赖：
现有可替代方案：

G0 资格
- 账号主体：个人 / 企业 / 未知
- 地区 / 合规要求：
- 个人是否可用及证据链接：
- 审核、白名单、配额前提：
- 资格结论：可用 / 不可用 / 尚未确认

G1 风险
- 是否绑卡、额度用尽后是否继续扣费：
- 最坏可接受金钱损失：
- 最小调用与权限范围：
- 失败时如何停止调用：

G2 最小真实验证
- 实际请求的时间、身份、Region、endpoint：
- 返回：成功 / 失败
- 响应或完整报错（脱敏）：
- Request ID / 日志证据：
- 真实调用成本、用量或预计计费方式：

投入决策
- 继续 / 暂停 / 放弃：
- 理由及已验证证据：
- 本轮实际花费时间：
- 下一个最小动作：
- 触发停止的条件：
```

**执行要求**：

- 优先由 AI 自动搜集平台政策和项目现状；只有真实登录、MFA、付款及敏感授权才交给人；
- 资格尚不清楚时，不把推断写成“已验证可用”；
- 每轮验证只为消除一个关键不确定性，不做无关扩建；
- 不因“赠送额度”“已经花了几个小时”而改变止损标准。

## 九、把一次失败变成可复用资产

这次经历至少沉淀出三个不同层次的东西：

**事实资产**：CloudTrail 证明 Java SDK 的 `Converse` 请求到达 Bedrock，并由完整错误信息和 Support 回复确定本次账户准入阻塞。

**方法资产**：建立 **G0 资格 → G1 风险 → G2 最小真实调用 → G3 工程化** 的技术接入关卡，避免未经验证就做大量配置。

**判断资产**：重新识别三种不同的“可用”：**文档支持、账户获准、业务闭环跑通**。它们不能相互替代。

真正能形成长期复利的，不是把这件事写成“我学会了 AWS IAM”，而是以后每次接支付、AI、OCR、云资源、第三方 SaaS，都能用同一套方法更早排除不可行方案，减少无效劳动，保护时间、现金和注意力。

**一句话总结：先确认“有资格、能调用、付得起”，再讨论“怎么设计、怎么扩展、怎么工程化”。**
