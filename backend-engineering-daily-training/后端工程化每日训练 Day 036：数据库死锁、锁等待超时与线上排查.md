# 后端工程化每日训练 Day 36：数据库死锁、锁等待超时与线上排查

## 一、今天学习的知识点

今天学习的是：

**数据库死锁（Deadlock）、锁等待（Lock Wait）、锁等待超时（Lock Wait Timeout）、统一加锁顺序、短事务设计，以及线上死锁的排查思路。**

一句话理解：

> 死锁不是“某个事务等锁等得很久”，而是多个事务之间形成了锁等待闭环；工程上要优先从事务边界、SQL、索引和加锁顺序中寻找根因，有限重试只能作为偶发死锁的兜底手段。

Day 34 学习了悲观锁，Day 35 学习了事务隔离级别。今天把两部分连接起来：

```text
数据库锁本身不是问题
↓
真正危险的是
不同事务以不一致的顺序获取相同资源
+
事务持锁时间过长
+
SQL / 索引导致锁竞争范围扩大
↓
最终可能形成死锁或大量锁等待
```

今天重点解决以下问题：

```text
什么是数据库死锁
死锁和普通锁等待有什么区别
Lock Wait Timeout 和 Deadlock 有什么区别
为什么统一加锁顺序可以降低死锁概率
为什么“统一顺序”并不意味着没有锁等待
为什么长事务会放大锁竞争
为什么不能在持锁事务里调用 AI / HTTP 30 秒
为什么线上每天几百次死锁不能靠增加重试次数解决
三个甚至更多事务能不能形成死锁
SQL 和索引为什么也会影响锁竞争
线上出现 Deadlock 应该按照什么顺序排查
```

## 二、死锁到底是什么

假设有两个事务。

事务 A：

```text
锁住 order_1001
↓
准备锁 inventory_2001
```

事务 B：

```text
锁住 inventory_2001
↓
准备锁 order_1001
```

执行到一半后：

```text
事务 A：
已经持有 order_1001
正在等待 inventory_2001

事务 B：
已经持有 inventory_2001
正在等待 order_1001
```

关系变成：

```text
A 等 B
B 又等 A
```

也就是：

```text
A → B → A
```

形成一个闭环。

这才叫：

**死锁（Deadlock）。**

因此今天最重要的判断标准不是：

```text
有没有人在等锁
```

而是：

> **锁等待关系有没有形成闭环。**

---

## 三、锁等待、锁等待超时和死锁必须分开

今天一开始最大的混淆点，是把：

```text
一个事务长时间不释放锁
```

也理解成：

```text
死锁
```

这是错误的。

### 1. 普通锁等待

例如：

```text
A 等 B
B 正在正常执行
```

只要 B 最终：

```text
COMMIT / ROLLBACK
↓
释放锁
```

A 就可以继续执行。

这只是：

**锁等待。**

---

### 2. 锁等待超时

如果：

```text
A 一直等 B
B 没有等待 A
```

但是 B 执行太久，A 等待超过数据库允许的时间，就可能出现：

```text
Lock wait timeout exceeded
```

这叫：

**锁等待超时（Lock Wait Timeout）。**

它仍然没有形成循环。

---

### 3. 死锁

如果：

```text
A 等 B
B 又等 A
```

形成：

```text
A → B → A
```

才是：

**Deadlock。**

最小判断模型：

```text
单向等待
= 锁等待

单向等待太久
= 锁等待超时

循环等待
= 死锁
```

---

## 四、为什么数据库必须主动处理死锁

普通锁等待理论上可以继续：

```text
A 等 B
↓
B 执行完成
↓
B 释放锁
↓
A 继续
```

但死锁不同：

```text
A 等 B
B 等 A
```

如果谁都不主动退出：

```text
A 无法继续
B 也无法继续
```

因此数据库检测到死锁后，通常需要选择其中一个事务作为牺牲者：

```text
ROLLBACK
```

打破等待环，让另一个事务继续执行。

所以线上看到：

```text
Deadlock found when trying to get lock
```

不能理解成：

```text
数据库坏了
```

更应该理解成：

> **至少有一组并发事务对锁资源形成了循环依赖。**

---

## 五、最典型的死锁来源：加锁顺序不一致

假设转账业务需要同时锁两个账户。

请求 1：

```text
A → B 转账
```

请求 2：

```text
B → A 转账
```

如果代码按照：

```text
先锁付款方
再锁收款方
```

那么可能出现：

```text
请求 1：
锁 A
↓
等待 B

请求 2：
锁 B
↓
等待 A
```

于是：

```text
请求 1 → 请求 2
请求 2 → 请求 1
```

形成死锁。

---

## 六、统一加锁顺序为什么可以降低死锁概率

更合理的规则是：

```text
永远先锁 ID 小的账户
↓
再锁 ID 大的账户
```

例如：

```java
long first = Math.min(fromId, toId);
long second = Math.max(fromId, toId);
```

然后所有转账事务都执行：

```text
SELECT first FOR UPDATE
↓
SELECT second FOR UPDATE
```

无论业务方向是：

```text
A → B
```

还是：

```text
B → A
```

数据库加锁顺序都保持：

```text
A
↓
B
```

这样第二个事务可能仍然要等待：

```text
事务 A：拿到 A 锁
事务 B：等待 A 锁
```

但事务 B 在拿不到第一把锁时，还没有机会先拿住后面的 B 锁。

所以不会轻易形成：

```text
A 等 B
B 又等 A
```

今天这里最重要的纠正是：

```text
统一加锁顺序
≠
不发生锁等待
```

真正作用是：

> **统一加锁顺序主要是在破坏循环等待条件，而不是消灭所有等待。**

---

## 七、死锁不一定只有两个事务

今天进一步练习了三个事务的情况。

```text
事务 A：
持有 row_1
等待 row_2

事务 B：
持有 row_2
等待 row_3

事务 C：
持有 row_3
等待 row_1
```

关系是：

```text
A → B → C → A
```

仍然形成闭环。

所以：

```text
A ↔ B
```

可以死锁。

同样：

```text
A → B → C → A
```

也可以死锁。

甚至更多事务也可能参与同一个等待环。

因此判断死锁时，不要只检查：

```text
是不是两个事务互相等
```

而应该检查：

> **整个锁等待图中是否存在环。**

---

## 八、没有形成环，就算很多事务在排队也不是死锁

例如：

```text
A：锁住 row_1，等待 row_2
B：锁住 row_2，正在正常执行
C：等待 row_1
```

等待关系是：

```text
C → A → B
```

但 B 没有继续等待 C 或 A。

所以没有形成：

```text
C → A → B → C
```

这就不是死锁。

只要 B 最终执行完成：

```text
B 释放 row_2
↓
A 继续执行
↓
A 释放 row_1
↓
C 继续执行
```

整个等待链就会逐步消失。

因此：

```text
等待链很长
≠
死锁

形成等待环
=
死锁
```

---

## 九、长事务为什么危险

假设事务 A：

```text
BEGIN
↓
锁住订单
↓
调用 AI 接口
↓
等待 30 秒
↓
更新库存
↓
COMMIT
```

最直接的问题是：

```text
事务执行 30 秒以上
↓
订单锁至少被长时间持有
↓
其他事务更容易撞上这个锁
↓
锁等待增加
↓
并发吞吐下降
```

如果多个事务还存在交叉加锁关系，就进一步提高形成死锁的机会。

同时长事务通常还会占用：

```text
数据库连接
应用线程
事务上下文
```

如果大量请求都这样执行，就可能继续出现：

```text
连接池长期占用
↓
新请求拿不到连接
↓
接口响应时间上升
↓
请求继续堆积
↓
系统压力进一步扩大
```

因此应该把下面这句话固定下来：

> **事务越长，锁持有时间通常越长；锁持有越久，锁竞争和锁等待越严重。**

---

## 十、为什么不能持锁调用 AI / HTTP / 第三方接口

危险设计：

```text
BEGIN
↓
SELECT ... FOR UPDATE
↓
拿到数据库锁
↓
调用 AI / HTTP / 支付接口
↓
等待 30 秒
↓
UPDATE
↓
COMMIT
```

外部调用存在很多不可控因素：

```text
网络抖动
第三方超时
服务拥堵
限流
重试
接口故障
响应时间不可预测
```

如果这些操作发生在持锁事务中，就相当于：

```text
把外部系统的不确定时间
转换成数据库锁的持有时间
```

更合理的原则是：

```text
数据库事务
只包住必须保证原子性的本地数据库操作
```

而把：

```text
AI 调用
HTTP 调用
OSS 上传
支付网关
长时间计算
```

尽量移出长事务。

---

## 十一、长事务和死锁不是完全等价的关系

今天练习中还有一个容易混淆的点。

假设两个事务严格统一顺序：

```text
A：先锁订单 → 再锁库存
B：先锁订单 → 再锁库存
```

但是每个事务都执行 30 秒。

这时：

```text
锁等待
```

仍然可能非常严重。

例如：

```text
A 拿到订单锁
↓
执行 30 秒

B 一直等待订单锁
```

这更容易导致：

```text
Lock Wait Timeout
```

而不是最典型的：

```text
Deadlock
```

因为等待关系可能只是：

```text
B → A
```

并没有：

```text
A → B
```

所以需要区分两个主要风险来源：

```text
事务太长
→ 更直接放大锁等待、连接占用、吞吐下降

加锁顺序不一致
→ 更直接制造循环等待和死锁条件
```

长事务会增加整体锁竞争，并可能放大死锁概率，但：

> **事务长并不等于一定死锁。**

---

## 十二、SQL 和索引为什么也属于死锁排查范围

例如：

```sql
UPDATE orders
SET status = 'DONE'
WHERE user_id = 100;
```

如果：

```text
orders 有几百万行
user_id 没有合适索引
```

数据库可能需要扫描大量记录才能找到目标数据。

这里不能简单记成：

```text
没有索引
=
一定锁住几百万行
```

更准确的是：

```text
缺少合适索引
↓
扫描范围可能扩大
↓
SQL 执行时间增加
↓
事务持锁时间可能增长
↓
多个事务操作相交数据时
锁竞争风险上升
```

不同数据库、隔离级别、执行计划和 SQL 形式会影响实际锁行为，所以线上不能只凭 SQL 文本猜：

```text
到底锁了哪些记录
```

而应该结合：

```text
执行计划
索引
死锁日志
实际锁等待信息
```

一起判断。

---

## 十三、一次更新大量数据为什么危险

例如：

```sql
UPDATE orders
SET status = ?
WHERE create_time < ?;
```

如果一次处理几十万行，可能带来：

```text
事务持续时间很长
锁数量增加
锁持有时间增长
与其他在线事务的数据范围相交
数据库日志量增加
回滚代价变大
```

如果其他事务也在同时更新相交的数据范围，锁竞争会更加明显。

因此大批量更新通常需要评估：

```text
是否可以分批
每批多少行
是否有合适索引
事务能否缩短
是否会影响在线请求
失败后如何继续
```

核心不是简单地：

```text
一条 SQL 能改完
就一次全改完
```

而是要控制单个事务的影响范围。

---

## 十四、为什么每天几百次死锁不能靠增加重试解决

假设线上每天已经出现：

```text
几百次 Deadlock
```

错误处理方式：

```text
原来重试 3 次
↓
改成重试 10 次
```

这没有解决：

```text
为什么会形成循环等待
```

反而可能产生：

```text
死锁
↓
事务回滚
↓
重新执行 SQL
↓
再次竞争同一批锁
↓
再次死锁
↓
继续重试
```

结果可能是：

```text
数据库 QPS 上升
锁竞争增加
连接占用增加
事务耗时继续上升
请求堆积
```

严重时可能形成恶性循环，进一步拖慢甚至拖垮系统。

所以今天的判断是：

> **高频死锁首先是需要定位和修复的并发设计 / SQL 问题，不是一个简单的“重试参数太小”问题。**

---

## 十五、重试什么时候才合理

重试并不是完全不能用。

复杂高并发系统里，即使事务设计已经比较合理，也很难保证永远没有偶发死锁。

对于确实不可完全避免的偶发死锁，可以考虑：

```text
有限次数重试
+
适当退避
+
业务幂等
```

例如：

```text
最多重试 1~3 次
```

但前提是先确认：

```text
不是稳定复现的锁顺序错误
不是超长事务
不是 SQL / 索引明显有问题
```

而且重试业务必须考虑：

```text
重复扣款
重复退款
重复创建订单
重复发送消息
```

等副作用。

因此：

> **重试是兜底，不是根治。**

## 十六、线上出现 Deadlock 应该先查什么

今天最终形成的排查顺序：

```text
发现 Deadlock
↓
找到参与死锁的事务
↓
找到每个事务执行的 SQL
↓
确认各自已经持有什么锁
↓
确认各自在等待什么锁
↓
画出等待关系
↓
检查是否存在加锁顺序不一致
↓
检查事务是否过长
↓
检查是否在事务内调用远程服务
↓
检查 SQL / 索引 / 执行计划
↓
检查单次更新范围是否过大
↓
修复根因
↓
最后再考虑有限重试
```

这比第一反应：

```text
重启数据库
调大连接池
调长超时时间
增加重试次数
```

更接近真正的工程排障。

## 十七、MySQL / InnoDB 下可以先看什么

如果线上使用 MySQL InnoDB，出现死锁后可以先查看 InnoDB 状态：

```sql
SHOW ENGINE INNODB STATUS\G
```

重点寻找最近一次死锁相关信息，例如：

```text
LATEST DETECTED DEADLOCK
```

关注：

```text
参与事务
事务执行 SQL
持有的锁
正在等待的锁
数据库最终回滚了哪个事务
```

在 MySQL 8 中，也可以结合 `performance_schema` 中的锁信息进一步分析当前锁等待关系，例如：

```text
data_locks
data_lock_waits
```

但工具只是帮助获取证据。

真正目标仍然是还原：

```text
事务 A 持有什么
事务 A 等什么

事务 B 持有什么
事务 B 等什么

最终在哪里形成环
```

## 十八、一个最小的死锁分析案例

假设日志最终还原出：

```text
事务 A：
UPDATE orders ... id = 1001
↓
持有 order_1001
↓
接下来 UPDATE inventory ... id = 2001
↓
等待 inventory_2001
```

同时：

```text
事务 B：
UPDATE inventory ... id = 2001
↓
持有 inventory_2001
↓
接下来 UPDATE orders ... id = 1001
↓
等待 order_1001
```

可以直接画成：

```text
A 持有 order_1001
A 等 inventory_2001
        ↓
        B

B 持有 inventory_2001
B 等 order_1001
        ↓
        A
```

形成：

```text
A → B → A
```

这时修复方向就非常明确：

```text
统一两个业务的加锁顺序
```

例如统一成：

```text
订单
↓
库存
```

而不是：

```text
Service A：订单 → 库存
Service B：库存 → 订单
```

## 十九、今天几个错误判断的纠正

### 易错点 1：认为“对方一直不释放锁”就是死锁

错误理解：

```text
A 等 B 很久
=
死锁
```

正确判断：

```text
A 等 B
B 没等 A
```

仍然只是锁等待。

如果等太久：

```text
Lock Wait Timeout
```

只有形成：

```text
A → B → A
```

才叫死锁。

---

### 易错点 2：认为统一顺序是为了“不再等待”

统一：

```text
订单 → 库存
```

以后，第二个事务仍然可能：

```text
等待订单锁
```

所以统一顺序不能消灭锁等待。

它主要解决的是：

```text
不同事务交叉持有不同锁
↓
再互相等待
```

也就是降低形成循环等待的概率。

---

### 易错点 3：把长事务直接等同于死锁

长事务更直接导致：

```text
持锁时间增长
锁等待增加
连接占用增加
吞吐下降
```

如果没有等待闭环，就不能叫死锁。

---

### 易错点 4：认为没索引就一定锁住几百万行

更准确的工程表达应该是：

```text
缺少合适索引
↓
可能扫描大量数据
↓
SQL 更慢
↓
事务和锁竞争窗口扩大
```

实际锁范围要结合数据库实现、隔离级别和执行计划判断。

---

### 易错点 5：高频死锁先增加重试次数

如果每天几百次死锁，说明应该优先检查：

```text
事务边界
SQL
索引
加锁顺序
批量更新范围
```

盲目增加重试只会放大数据库压力。

---

## 二十、面试怎么表达

如果面试官问：

### 什么是数据库死锁？

可以回答：

> 数据库死锁通常发生在多个事务以不同顺序获取相同资源锁时。例如事务 A 先锁订单再等待库存，而事务 B 先锁库存再等待订单，就会形成循环等待。数据库检测到死锁后，一般会主动回滚其中一个事务来打破等待环。

---

如果继续问：

### 死锁和锁等待超时有什么区别？

可以回答：

> 普通锁等待通常是单向的，例如事务 A 等待事务 B，B 本身没有等待 A；如果等待时间超过限制，就可能出现 Lock Wait Timeout。死锁的关键是多个事务之间形成循环等待，例如 A 等 B、B 又等 A。

---

如果继续问：

### 如何降低数据库死锁概率？

可以回答：

> 我会优先统一多个业务访问相同资源时的加锁顺序，同时缩短事务范围，避免事务内执行 HTTP、AI、支付等不可控远程调用；对于大批量 SQL，还会检查索引和更新范围，减少锁竞争窗口。对于确实无法完全避免的偶发死锁，可以在保证幂等的前提下进行有限重试。

---

如果继续问：

### 线上出现大量死锁怎么排查？

可以回答：

> 我不会先调大重试次数，而是先通过数据库死锁日志找到参与事务和 SQL，分析各事务持有什么锁、等待什么锁，把等待关系还原出来。然后重点检查加锁顺序、事务边界、长事务、SQL 执行计划和索引。如果根因修复后仍存在少量偶发死锁，再考虑有限重试和退避策略。

```text
事务越长

```
