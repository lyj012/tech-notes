# 后端工程化每日训练 Day 73：TCP 重传、网络质量与业务抖动排障复盘

## 一、今天学习什么

今天学习一种线上非常常见、但又很容易被“Ping 能通”掩盖的问题：

**TCP 重传（Retransmission），以及“网络能通、端口也通，但 Java 接口偶发变慢甚至 timeout”应该怎么排查。**

典型现象：

```text
Ping 正常
端口正常监听
Java 服务也没有挂

但是：
接口原来 100ms
现在偶尔 1s / 3s
文件上传变慢
JDBC 偶发 timeout
Collector 偶发超时
```

今天最核心的目标不是看到 TCP 重传后直接判断“网络坏了”，而是建立一条完整证据链：

```text
业务现象
↓
TCP 重传
↓
本机网卡
↓
交换机端口
↓
中间链路
↓
必要时抓包
↓
修复
↓
重新验证
```

最重要的一句话：

> **网络可达不等于网络质量正常，请求最终成功也不等于中间传输过程没有发生异常。**

---

## 二、为什么请求成功仍然可能存在网络问题

假设一个接口原来：

```text
100ms
```

现在偶尔：

```text
3000ms
```

最后仍然成功返回。

这不能证明网络没有问题。

TCP 是可靠传输协议。

简化过程：

```text
客户端                         服务端

数据1  ---------------------->
       <---------------------- ACK

数据2  --------X
          丢失 / 未及时确认

        等待

数据2  ---------------------->
       <---------------------- ACK
```

如果某段数据没有被正常确认，发送方可能重新发送。

这就是：

```text
TCP Retransmission
TCP 重传
```

因此可能出现：

```text
第一次发送
↓
异常
↓
等待确认
↓
重传
↓
最终成功
```

从 Java 应用看：

```text
请求成功
```

但耗时可能已经从：

```text
100ms
```

变成：

```text
3s
```

所以：

> **请求成功只能证明最终成功，不能证明整个 TCP 传输过程健康。**

如果情况继续恶化：

```text
发送
↓
未正常确认
↓
重传
↓
再次异常
↓
继续等待
↓
超过应用超时时间
↓
timeout
```

需要注意：

```text
timeout ≠ 一定是 TCP 重传导致
```

数据库慢、线程阻塞、服务端卡顿、防火墙丢包、链路异常等都可能造成 timeout。

---

## 三、Ping 0% 丢包为什么不能证明业务网络正常

执行：

```bash
ping 10.0.0.20
```

看到：

```text
0% packet loss
```

只能说明：

> **本次 ICMP 探测报文正常收到回复。**

Ping 使用的是：

```text
ICMP
```

而 Java HTTP/JDBC 等业务通常建立在：

```text
TCP
```

之上。

因此不能写成：

```text
Ping 正常
→ HTTP 一定正常
```

更不能写成：

```text
Ping 0% 丢包
→ TCP 业务一定不存在抖动和重传
```

正确理解：

```text
Ping 正常
↓
说明基础 IP/ICMP 可达性目前没有明显问题

但：
↓
不能代表真实业务 TCP 传输质量完全正常
```

所以遇到：

```text
Ping 通
端口通
业务偶发慢
```

排查问题应该从：

```text
通不通？
```

继续升级为：

```text
质量怎么样？
```

## 四、TCP 重传指标怎么看

Linux 可以查看 TCP 统计：

```bash
nstat -az | grep -i retrans
```

常见关键指标：

```text
TcpRetransSegs
```

它是一个累计 Counter。

例如：

```text
TcpRetransSegs = 580000
```

单独这个数字不能证明：

```text
现在正在严重丢包
```

也不能直接证明：

```text
以前曾经发生过一次严重丢包
```

因为它只是累计值，没有告诉你这些重传是什么时候发生的。

可能是：

```text
很长时间缓慢累计到 580000
```

也可能是：

```text
绝大部分集中发生在最近几分钟
```

所以真正有价值的是观察：

```text
增量
速率
趋势
```

例如：

```text
10:00  TcpRetransSegs = 580000
10:01  TcpRetransSegs = 588000
```

一分钟增加：

```text
8000
```

计算：

```text
重传增量
=
后一次计数 - 前一次计数
```

进一步可以计算：

```text
平均每秒重传量
=
重传增量 / 采样间隔秒数
```

需要同时注意：

- Counter 是否发生重置；
- 系统是否重启；
- 当前整体 TCP 流量规模；
- 平时正常基线是多少。

例如一分钟多了 8000 个重传段，在流量极大的机器和流量很小的机器上，含义可能完全不同。

因此：

> **监控累计值的意义有限，真正应该重点监控的是增量、速率以及相对基线的变化。**

## 五、TCP 重传上涨能够证明什么

假设：

```text
10:00  TcpRetransSegs = 580000
10:01  TcpRetransSegs = 588000
```

同时：

```text
Java 接口 RT 明显上涨
```

现在可以确认：

> **这一分钟内 TCP 重传计数增加了 8000，确实发生了大量 TCP 重传现象。**

这里已经不是：

```text
可能发生重传
```

而是：

```text
已经存在重传证据
```

同时：

```text
接口 RT 上涨
+
TCP 重传同步上涨
```

会让：

```text
网络传输质量异常
```

成为重点排查方向。

但是目前仍然不能直接证明：

```text
接口变慢一定就是 TCP 重传造成的
```

也不能直接证明：

```text
一定是网络丢包
```

更不能直接证明：

```text
一定是网线坏了
```

---

## 六、重传不完全等于丢包

TCP 发生重传，常见原因确实包括：

```text
数据包丢失
```

但不能简单写成：

```text
重传上涨
=
已经证明严重丢包
```

可能还存在：

```text
ACK 到达过慢
报文严重乱序
网络时延突然增加
发送方错误判断报文丢失
中间链路异常
```

因此正确说法应该是：

> **重传说明 TCP 传输过程存在异常现象，但真正原因需要继续向下定位。**

这也是今天非常重要的判断边界：

```text
现象
≠
根因
```

---

## 七、本机网卡怎么继续排查

查看网卡统计：

```bash
ip -s link show eth0
```

重点关注：

```text
RX errors
RX dropped
TX errors
TX dropped
```

假设：

```text
TCP 重传快速上涨

RX errors  = 0
TX errors  = 0
RX dropped = 0
TX dropped = 0
```

不能得出：

```text
网络没有问题
```

它最多说明：

> **目前没有直接证据指向这台服务器本机网卡发生 error/drop。**

网络路径可能是：

```text
服务器
↓
交换机端口
↓
交换机
↓
路由器
↓
防火墙
↓
VPN
↓
目标服务器
```

本机网卡正常，只排除了一部分嫌疑，不能证明整条链路正常。

所以下一步应该继续看：

```text
交换机对应端口
↓
CRC
Input/Output Error
Drop / Discard
接口利用率
```

然后再根据证据决定是否继续查：

```text
防火墙
路由
VPN
ACL
中间网络设备
```

如果仍然无法判断，再进行抓包。

## 八、Output Drop 和 CRC 分别代表什么

今天重点区分了两个非常重要的交换机指标。

### 1. Output Drop

可以简单理解为：

> **设备想把包发出去，但出口队列塞不下了，只能把包丢掉。**

常见场景：

```text
接口利用率很高
↓
数据发送速度超过链路承载能力
↓
队列持续堆积
↓
队列满
↓
Output Drop
```

因此：

```text
高利用率
+
Output Drop 快速增加
```

更像：

```text
网络拥塞
带宽打满
突发大流量
队列问题
```

---

### 2. CRC

CRC 可以简单理解为：

> **收到的数据帧校验失败，帧在物理传输过程中出现损坏。**

如果：

```text
接口利用率并不高
+
Output Drop = 0
+
CRC 快速增加
```

更应该怀疑：

```text
网线
光纤
光模块
交换机端口
网卡物理接口
速率 / 双工协商
```

可以先记一句非常简单的：

```text
Drop
→ 包太多，来不及发

CRC
→ 包传坏了
```

## 九、两个场景怎么判断

### 场景 A

```text
接口利用率 99%
Output Drop 快速增加
CRC = 0
```

证据链：

```text
链路几乎跑满
↓
发送队列压力很大
↓
Output Drop 上涨
↓
CRC 没有异常
```

更像：

> **链路拥塞 / 带宽不足 / 突发大流量导致的队列丢包。**

排查重点：

```text
谁在制造大量流量
带宽是否真的跑满
是否存在突发流量
QoS / 队列策略
链路容量是否不足
```

应用代码可能是流量来源之一，但不能看到高利用率就直接认定：

```text
一定是 Java 代码问题
```

---

### 场景 B

```text
接口利用率 20%
Output Drop = 0
CRC 快速增加
```

证据链：

```text
链路没有跑满
↓
出口没有队列丢包
↓
CRC 却快速上涨
```

更像：

> **物理链路质量问题。**

重点排查：

```text
网线
光纤
光模块
交换机端口
网卡接口
速率 / 双工协商
```

因此两个场景虽然最后都可能导致：

```text
TCP 重传
接口变慢
timeout
```

但是根因方向完全不同。

## 十、完整故障场景：从 Java 慢定位到物理链路

现象：

```text
Java CPU 正常
内存正常
GC 正常
数据库没有明显异常

但是接口持续抖动
```

首先不能直接得出：

```text
Java 服务完全正常
```

更准确的判断是：

> **目前没有明显应用资源瓶颈证据，需要继续寻找其他方向。**

建立假设：

```text
是否存在网络传输质量问题？
```

继续观察：

```text
TcpRetransSegs 快速上涨
```

说明：

```text
当前 TCP 传输存在明显重传现象
```

再检查服务器网卡：

```text
RX errors  = 0
TX errors  = 0
RX dropped = 0
TX dropped = 0
```

说明：

```text
本机网卡没有直接异常证据
```

继续检查交换机对应端口：

```text
接口利用率：20%
Output Drop：0
CRC：持续快速上涨
```

此时证据链已经明显收敛：

```text
Java 接口 RT 抖动
↓
应用侧暂未发现明显资源瓶颈
↓
TCP 重传快速增加
↓
服务器网卡 error/drop 正常
↓
交换机端口 CRC 持续上涨
↓
服务器与交换机之间的物理链路嫌疑大幅上升
```

下一步优先检查：

```text
网线 / 光纤
光模块
交换机端口
网卡物理接口
速率 / 双工协商
```

而不是重新从：

```text
ARP
路由
防火墙
```

全部无差别查一遍。

排障最重要的能力之一就是：

> **根据已有证据不断缩小范围，而不是每获得一个新证据后仍然从头检查所有可能性。**

---

## 十一、修复以后必须验证

假设最终发现：

```text
光模块异常
```

更换以后不能只说：

```text
已经换好了
```

必须重新观察：

```text
CRC 是否停止上涨
TCP 重传增量是否明显下降
接口 RT 是否恢复稳定
timeout 是否消失
```

只有：

```text
故障现象消失
+
异常指标恢复
```

才能形成完整证据闭环：

```text
现象
→ 假设
→ 证据
→ 缩小范围
→ 根因
→ 修复
→ 验证
```

## 十二、必要时使用 tcpdump 抓包

如果交换机、网卡等指标仍然无法定位，可以抓包：

```bash
tcpdump -nn -i eth0 host 10.0.0.20 and port 8082 -w /tmp/app.pcap
```

然后通过 Wireshark 等分析：

```text
TCP Sequence
ACK
Retransmission
Duplicate ACK
乱序
时延
RST
```

如果条件允许，两端同时抓包价值更高。

例如：

```text
A 端确认发出了数据
↓
B 端完全没有抓到
```

则问题更可能位于：

```text
A 与 B 之间的网络链路
```

如果：

```text
B 端已经收到完整请求
↓
但是很久没有响应
```

则排查方向应重新回到：

```text
B 服务器
B 应用
数据库
线程
下游依赖
```

抓包的价值不是“看起来专业”，而是进一步回答：

> **包到底在哪一段消失、延迟或被重新发送。**

## 十三、Java 服务网络质量监控应该怎么设计

如果只监控：

```text
Ping 通不通
+
8082 端口通不通
```

只能较好发现：

```text
彻底断网
端口彻底不可用
```

但发现不了很多“还活着，但质量正在恶化”的阶段。

更合理的是分层监控。

### 第一层：基础可用性

```text
Ping
TCP 端口探测
```

回答：

```text
彻底断没断？
```

---

### 第二层：业务质量

监控：

```text
接口 RT
P95 / P99
timeout 数量
请求失败率
```

回答：

```text
业务有没有开始变慢或失败？
```

---

### 第三层：TCP 质量

监控：

```text
TcpRetransSegs 增量
重传速率
相对历史基线
```

回答：

```text
TCP 传输过程是否正在恶化？
```

---

### 第四层：服务器网卡

监控：

```text
RX errors
TX errors
RX dropped
TX dropped
```

回答：

```text
本机网卡是否存在明显异常？
```

---

### 第五层：交换机端口

监控：

```text
接口利用率
CRC
Input Error
Output Drop
Discard
```

回答：

```text
更像物理链路问题？
还是网络拥塞？
```

## 十四、多指标关联比单指标告警更有价值

例如：

```text
接口 RT ↑
timeout ↑
TCP 重传 ↑
```

说明：

```text
网络传输质量嫌疑明显上升
```

进一步：

```text
网卡 error/drop ↑
```

则本机网卡或本机链路嫌疑提高。

如果：

```text
网卡正常
CRC ↑
```

重点查：

```text
网线
光纤
光模块
交换机端口
```

如果：

```text
网卡正常
CRC = 0
接口利用率 99%
Output Drop ↑
```

重点查：

```text
带宽打满
网络拥塞
突发大流量
流量来源
```

所以比起：

```text
TcpRetransSegs > 某个固定数字就报警
```

更合理的是：

```text
接口 RT 连续升高
+
TCP 重传速率明显高于基线
+
timeout 同步增加
```

触发：

```text
网络质量劣化告警
```

这样可以在：

```text
Ping 还通
端口还通
服务也没有彻底挂
```

的时候提前发现质量问题。

## 十五、今天容易混淆的几个点

### 1. Ping 0% 丢包

错误：

```text
Ping 没丢包
→ HTTP 没问题
```

正确：

```text
Ping 主要证明 ICMP 探测正常
不能直接代表真实 TCP 业务质量
```

---

### 2. TcpRetransSegs = 580000

错误：

```text
58 万这么大
→ 现在网络一定很差
```

正确：

```text
这是累计值
要看一段时间内的增量 / 速率 / 趋势
```

---

### 3. TCP 重传上涨

错误：

```text
重传上涨
→ 已经证明网线坏了
```

正确：

```text
重传上涨
→ 说明 TCP 传输存在异常现象
→ 继续根据网卡、交换机、链路和抓包定位根因
```

---

### 4. 网卡 error/drop = 0

错误：

```text
本机网卡正常
→ 整个网络正常
```

正确：

```text
只说明本机网卡暂时没有直接异常证据
中间交换机 / 路由 / 防火墙 / VPN 等仍可能有问题
```

---

### 5. CRC 和 Output Drop

```text
Output Drop
→ 更关注拥塞、带宽、发送队列

CRC
→ 更关注物理链路质量
```

不能把两个指标混成同一种问题。

## 十六、今天形成的排障模型

以后遇到：

```text
Ping 正常
端口正常
但 Java 接口偶发慢 / timeout
```

可以按下面这条链排查：

```text
1. 先确认业务现象
   ↓
   接口 RT / timeout / 失败率

2. 排除明显应用瓶颈
   ↓
   CPU / 内存 / GC / SQL / 线程

3. 看 TCP 重传
   ↓
   重点看增量 / 速率 / 基线

4. 看本机网卡
   ↓
   RX/TX error/drop

5. 看交换机对应端口
   ↓
   CRC / Drop / Discard / 利用率

6. 看中间链路
   ↓
   防火墙 / 路由 / VPN / ACL

7. 必要时两端抓包
   ↓
   确认数据在哪一段异常

8. 找到根因并修复

9. 重新验证
   ↓
   RT
   timeout
   TCP 重传
   CRC / Drop
```

## 十七、今天的最终结论

今天最需要记住的是：

```text
Ping 通
≠
网络质量正常

请求成功
≠
传输过程没有异常

TcpRetransSegs 总数很大
≠
当前正在严重丢包

TCP 重传上涨
→
说明传输出现异常现象
→
但不能直接判断真正根因

高利用率 + Output Drop
→
更像拥塞 / 队列丢包

低利用率 + CRC 上涨
→
更像物理链路异常
```

最终排障思路：

```text
业务现象
→ TCP
```
