# 后端工程化每日训练 Day 29：接口超时、超时预算与级联故障保护

## 一、今天学习的知识点

今天学习的是：

**接口超时（Timeout）设计、超时预算（Timeout Budget），以及超时与限流、熔断、线程池、重试、Outbox Pattern 的组合使用。**

一句话理解：

> 超时不是为了“多等一会儿提高成功率”，而是给不可控操作设置明确的资源占用上限，在下游变慢或故障时及时失败、释放线程和连接，防止局部故障演变成整个系统的级联故障。

今天重点解决以下问题：

```text
为什么第三方 AI 变慢，会拖慢整个 Java 服务
为什么 AI 慢首先耗尽的是线程，而不一定是数据库连接
Connect Timeout、Read Timeout、Overall Timeout 分别解决什么问题
数据库、Redis、HTTP、对象存储为什么都需要自己的超时策略
为什么超时后不能立即重试很多次
什么是重试风暴（Retry Storm）
为什么不同接口不能统一配置一个超时时间
什么是 Timeout Budget（超时预算）
限流、熔断、线程池、超时、重试分别保护哪一层
Outbox Pattern 在异步 AI 任务中负责什么，不负责什么
如何把长耗时 AI 请求改造成更稳定的异步任务链路
```

---

## 二、问题背景：一个慢 AI 接口为什么能拖垮整个服务

假设一个 AI 平台存在下面的同步调用链：

```text
用户请求
↓
查询数据库
↓
调用第三方 AI
↓
上传结果到 OBS
↓
返回结果
```

正常情况下：

```text
AI 响应：2 秒
```

异常情况下：

```text
AI 响应：40 秒
```

如果系统没有合理的超时策略，一个请求进入 Tomcat 后可能长期占用工作线程：

```text
请求进入
↓
Tomcat 分配工作线程
↓
线程调用 AI
↓
AI 40 秒不返回
↓
当前线程持续等待
↓
线程无法处理其他请求
```

假设 Tomcat 最大工作线程数为：

```text
200
```

当大量请求都卡在 AI 调用上时：

```text
请求 1   → 占用线程 1
请求 2   → 占用线程 2
...
请求 200 → 占用线程 200
```

第 201 个以及后续请求只能进入等待队列，或者在队列、连接器等资源达到上限后被拒绝。

最终可能形成：

```text
第三方 AI 变慢
↓
单个请求处理时间变长
↓
Tomcat 活跃线程数持续升高
↓
可用工作线程越来越少
↓
新请求开始排队
↓
接口响应时间进一步上升
↓
客户端开始重试
↓
请求量被进一步放大
↓
线程池、HTTP 连接池等资源被耗尽
↓
整个服务不可用
```

这里需要注意一个表述：

```text
Tomcat 线程数持续增加
```

不一定准确。

如果线程池已经配置了最大线程数，更准确的是：

```text
Tomcat 活跃 / Busy 线程数持续接近上限
请求排队数量增加
平均响应时间增加
```

## 三、为什么请求处理时间会直接影响吞吐量

系统吞吐量不仅取决于线程数量，也取决于每个请求占用线程的时间。

可以用一个非常粗略的方式理解：

```text
吞吐量 ≈ 可用并发数 / 单请求平均处理时间
```

假设有 200 个工作线程。

### 正常情况

每个请求平均占用线程：

```text
1 秒
```

理论上每秒可以完成的请求数量大约为：

```text
200 / 1
≈ 200 req/s
```

### AI 变慢以后

每个请求平均占用线程：

```text
40 秒
```

理论完成速率会下降到：

```text
200 / 40
≈ 5 req/s
```

虽然这个计算忽略了 CPU、网络、连接池、队列等实际限制，但它说明了一个核心规律：

> 请求执行时间越长，同样的并发资源能够提供的吞吐量越低。

因此，下游系统即使只是“变慢”而不是完全宕机，也可能对上游造成严重影响。

## 四、AI 变慢首先占用的是什么资源

今天需要修正的一个理解是：

```text
第三方 AI 没有释放数据库连接
↓
数据库连接池耗尽
```

这个因果关系并不总是成立。

AI 调用通常通过 HTTP 访问第三方服务，它首先长期占用的是：

```text
当前请求线程
HTTP Client 连接
Socket
内存中的请求上下文
```

如果 AI 调用没有放在数据库事务中，并且数据库查询结束后连接已经归还连接池，那么 AI 等待 40 秒并不会天然占用数据库连接。

更准确的链路是：

```text
AI 变慢
↓
请求线程被占用
↓
HTTP 连接长期占用
↓
请求完成速度下降
↓
新请求不断进入
↓
线程池和 HTTP 连接池压力增加
```

### 什么情况下会进一步拖垮数据库连接池

如果代码是：

```java
@Transactional
public AiResult executeTask(Long taskId) {
    AiTask task = taskMapper.selectById(taskId);

    AiResult result = aiClient.call(task);

    taskMapper.updateResult(taskId, result);
    return result;
}
```

执行第一条 SQL 后，事务可能已经获取了数据库连接。

随后：

```text
进入事务
↓
执行 SQL
↓
获取数据库连接
↓
调用 AI 等待 40 秒
↓
事务仍未结束
↓
连接迟迟不能归还
```

此时才会出现：

```text
AI 变慢
↓
事务持续时间变长
↓
数据库连接持有时间变长
↓
连接池可用连接减少
↓
新请求获取数据库连接开始等待
↓
连接池超时
```

所以更准确的结论是：

> AI 调用本身不直接使用数据库连接，但如果长耗时网络调用位于数据库事务中，就会把事务持有的数据库连接一起拖住。

这也和 Day 28 的事务边界设计直接关联。

## 五、超时真正解决什么问题

很多人第一次接触超时时，会理解为：

```text
超过 10 秒没有成功
↓
那就报错
```

这只是表现。

超时真正解决的是：

```text
限制一次不可控操作最多占用资源多久
```

例如：

```text
AI 服务故障
```

如果没有超时：

```text
一个线程可能等待很久
```

配置 15 秒超时后：

```text
最多等待 15 秒
↓
结束当前调用
↓
释放当前调用占用的线程和网络资源
↓
让系统还有能力处理其他请求
```

因此：

> 超时的核心目标不是提高成功率，而是控制故障影响范围。

## 六、三类核心超时

### 1. Connect Timeout

连接超时解决的是：

```text
客户端能不能在规定时间内和服务器建立连接
```

例如：

```text
Java 服务
↓
AI 服务
```

如果目标服务宕机、网络路由异常、防火墙阻断或连接建立过慢：

```text
2 秒仍然没有建立连接
↓
Connect Timeout
↓
快速失败
```

示例：

```text
connectTimeout = 2s
```

它保护的是：

```text
建立 TCP / TLS 等连接阶段不能无限等待
```

---

### 2. Read Timeout / Response Timeout

连接已经建立，但服务端迟迟没有返回需要的数据时，需要读取或响应超时。

例如：

```text
连接 AI 成功
↓
请求已经发送
↓
AI 一直没有返回数据
↓
等待超过阈值
↓
Read / Response Timeout
```

示例：

```text
readTimeout = 15s
```

需要注意：不同 HTTP Client 对 `read timeout`、`response timeout` 的定义可能不同。

特别是流式 AI 接口：

```text
SSE / Streaming
```

只要服务端持续返回少量数据，某些客户端的单次读超时可能不断被刷新。

因此复杂调用不能只依赖 Read Timeout，还需要 Overall Timeout 或业务 Deadline。

---

### 3. Overall Timeout / Request Deadline

整体超时限制的是：

```text
一次完整业务调用最多允许执行多久
```

例如：

```text
查询数据库
↓
调用 AI
↓
上传 OBS
↓
返回结果
```

业务规定：

```text
整个同步请求最多 20 秒
```

即使单个步骤还没有触发自己的超时，只要整体 Deadline 已经到达，就应该停止继续执行无意义的后续工作。

例如：

```text
整体预算 = 20 秒

数据库已经用了 2 秒
AI 已经用了 16 秒
剩余预算只有 2 秒
```

这时再启动一个预计需要 10 秒的 OBS 上传通常已经没有意义。

---

## 七、Timeout Budget：为什么不能给所有步骤都配置 30 秒

假设整个接口 SLA 希望控制在：

```text
20 秒
```

错误做法：

```text
数据库查询超时 = 20 秒
AI 超时       = 20 秒
OBS 超时      = 20 秒
```

理论最坏情况可能变成：

```text
20 + 20 + 20
= 60 秒以上
```

所以需要设计：

> **Timeout Budget（超时预算）**

例如：

```text
数据库查询       1s
AI 建连           2s
AI 响应          12s
OBS 上传          3s
业务处理          1s
预留              1s
--------------------
Overall Timeout  20s
```

核心思想是：

```text
一个请求的总时间是有限预算
每个下游调用只能消耗其中一部分
```

并且：

```text
越靠后的步骤
越应该感知剩余 Deadline
```

否则前面的调用已经耗光时间，后面继续执行只会浪费资源。

## 八、不同组件应该配置什么超时

### 1. 数据库

数据库至少要关注两类超时。

#### 获取连接超时

例如 HikariCP：

```text
connectionTimeout
```

含义是：

```text
从连接池获取一个数据库连接
最多允许等待多久
```

如果连接池已经全部占满：

```text
等待 1 秒仍然拿不到连接
↓
快速失败
```

而不是无限排队。

#### SQL 查询超时

用于控制：

```text
一条 SQL 最多允许执行多久
```

例如慢 SQL、锁等待等情况下，避免业务线程长时间卡死。

数据库本身还可能存在：

```text
锁等待超时
事务超时
Socket 超时
```

具体名称和语义取决于数据库、驱动和连接池实现。

---

### 2. AI / 第三方 HTTP 接口

主要关注：

```text
Connect Timeout
Response / Read Timeout
Overall Timeout
```

例如：

```text
Connect Timeout = 2s
Response Timeout = 15s
Overall Timeout = 18s
```

具体值不能机械照抄，要根据：

```text
正常 P50 / P95 / P99 延迟
业务 SLA
第三方稳定性
调用成本
是否允许异步
```

进行设计。

---

### 3. OBS / OSS / S3 对象存储

对象存储调用同样属于外部网络调用。

需要关注：

```text
Connect Timeout
Socket / Read Timeout
Request Timeout
上传耗时上限
```

某些 SDK 还会暴露：

```text
Write Timeout
Call Timeout
Request Timeout
```

具体名称取决于 SDK。

大文件上传不能简单使用和普通 JSON HTTP 请求相同的超时时间，应结合：

```text
文件大小
上传带宽
分片上传
断点续传
```

设计。

---

### 4. Redis

Redis 调用也不能无限等待。

通常需要关注：

```text
连接超时
命令执行 / Socket 超时
连接池获取连接超时
```

Redis 一旦变慢，如果大量业务线程都阻塞在缓存调用上，同样会造成级联故障。

---

### 5. MQ

生产者发送消息可能涉及：

```text
连接建立
消息发送
Broker ACK / Confirm
```

这些阶段同样需要有明确的等待上限。

消费者执行任务时也应该限制：

```text
单条任务最大执行时间
```

否则一个卡死任务可能长期占用 Consumer Worker。

---

### 6. Future / CompletableFuture / 线程池任务

异步任务不代表可以无限执行。

例如：

```java
future.get(10, TimeUnit.SECONDS);
```

本质上也是：

```text
给等待异步结果设置上限
```

但还需要注意：

```text
调用方不再等待
≠
底层任务一定已经真正停止
```

如果需要取消任务，还要结合：

```text
Future.cancel
线程中断
下游客户端取消请求能力
任务本身是否响应中断
```

进行设计。

---

## 九、为什么不同接口不能统一使用一个超时时间

错误做法：

```text
所有接口统一 30 秒
```

因为不同业务的正常耗时完全不同。

例如：

```text
登录接口：       1~3 秒
支付查询：       3~5 秒
普通数据库查询： 1~2 秒
OCR：           10~30 秒
AI 推理：        10~60 秒甚至更长
大文件上传：      取决于文件大小和带宽
```

如果登录接口也允许等待 30 秒：

```text
异常时会长时间占线程
```

如果大模型调用只允许 2 秒：

```text
正常请求也会大量失败
```

所以超时时间应该基于：

```text
业务 SLA
历史延迟分布
依赖方稳定性
用户可接受等待时间
并发量
资源容量
失败后的恢复方式
```

进行配置。

## 十、为什么超时后不能立即重试很多次

假设：

```text
100 个用户请求
每个请求调用 AI 1 次
```

原始下游流量：

```text
100 次 AI 请求
```

如果每次超时以后都最多再重试 10 次：

```text
100 × 最多 11 次尝试
```

理论上可能产生超过 1000 次下游调用。

于是形成：

```text
AI 已经变慢
↓
大量请求超时
↓
客户端立即重试
↓
下游流量继续增加
↓
AI 压力更高
↓
AI 更慢
↓
更多请求超时
↓
更多重试
```

这就是：

> **Retry Storm（重试风暴）**

它带来的风险包括：

```text
线程占用增加
HTTP 连接增加
网络带宽增加
CPU 和内存压力增加
第三方 API 调用次数增加
AI Token 成本增加
下游服务恢复速度变慢
系统整体雪崩
```

所以“浪费 Token”只是其中一个成本，更严重的是资源和流量被成倍放大。

## 十一、正确的重试策略

重试适合处理：

```text
短暂网络抖动
瞬时连接失败
部分 5xx
临时限流
短暂服务不可用
```

不适合无脑重试：

```text
参数错误
认证失败
权限不足
业务校验失败
明确的 4xx
已经持续故障的服务
```

通常需要同时具备：

```text
有限次数
指数退避
随机抖动 Jitter
只重试可恢复错误
整体 Deadline
幂等保护
```

例如：

```text
第一次失败
↓
等待 500ms

第二次失败
↓
等待约 1s

第三次失败
↓
等待约 2s
```

再加少量随机抖动：

```text
避免大量实例在完全相同的时间点一起重试
```

更重要的是：

> 重试次数不能脱离 Overall Timeout 独立设计。

如果整个请求只剩 1 秒预算，就不应该再发起一个预计需要 10 秒的重试。

## 十二、超时和熔断有什么区别

超时解决的是：

```text
单次调用最多等多久
```

熔断解决的是：

```text
已经发现下游持续失败以后
是否还要继续调用
```

没有熔断时：

```text
请求 1 → 等 15 秒 → 超时
请求 2 → 等 15 秒 → 超时
请求 3 → 等 15 秒 → 超时
请求 4 → 等 15 秒 → 超时
```

即使已经明显知道 AI 服务不可用，每个请求仍然要浪费 15 秒。

加入熔断后：

```text
短时间失败率超过阈值
↓
Circuit Breaker OPEN
↓
后续请求不再真正访问 AI
↓
快速失败 / 降级 / 转异步等待
```

一段时间后进入：

```text
HALF_OPEN
```

只放少量请求测试下游是否恢复。

如果成功：

```text
CLOSED
```

重新恢复正常调用。

因此：

```text
Timeout
→ 限制一次调用的等待时间

Circuit Breaker
→ 限制持续故障期间还要发起多少无意义调用
```

## 十三、线程池在 AI 调用链中负责什么

线程池不是为了让 AI 调用变快。

它主要负责：

> **限制同时执行的 AI 任务数量，并把 AI 故障隔离在有限资源范围内。**

例如：

```text
Tomcat 最大线程：200

AI 专用线程池：
corePoolSize = 10
maximumPoolSize = 20
queueCapacity = 100
```

即使突然进入：

```text
1000 个 AI 任务
```

也不是：

```text
1000 个任务同时调用 AI
```

而是：

```text
最多 20 个并发执行
100 个左右进入有限队列
其余触发拒绝 / 降级 / 延迟处理
```

这样做的意义是：

```text
AI 服务挂了
↓
AI 专用线程池被占满
```

不应该直接演变成：

```text
整个 Java 服务所有线程都被 AI 拖死
↓
登录接口也挂
用户查询也挂
文件下载也挂
管理后台也挂
```

这种模式通常称为：

> **Bulkhead（舱壁隔离）**

就像船舱被分隔，即使一个区域进水，也尽量不让整艘船一起沉没。

---

## 十四、限流在这套链路中负责什么

限流保护的是入口。

例如：

```text
系统最大允许 100 req/s
```

如果瞬间进入：

```text
1000 req/s
```

系统不能把所有请求都无条件放进内部资源池。

可以按照：

```text
用户
API Key
IP
租户
接口
模型
套餐等级
```

设置不同限额。

用户今天提出：

```text
AI 长时间不可用时
只供应给管理者和付费用户
```

这个方向属于：

```text
优先级限流 / 分级降级
```

但要进一步区分：

```text
管理者是否真的应该拥有更高 AI 调用优先级
```

如果管理接口只是运维用途，更合理的策略可能是：

```text
保证核心管理接口不受 AI 故障影响
而不是让管理员继续大量调用故障中的 AI
```

付费用户则可以根据业务价值设置：

```text
更高配额
更高队列优先级
备用模型
更少降级
```

但仍然不能绕过系统总容量上限。

---

## 十五、Outbox Pattern 在这里负责什么

Outbox Pattern 不直接解决：

```text
AI 超时
AI 变慢
线程池耗尽
```

它解决的是：

> **数据库业务状态已经提交，但 MQ 消息没有可靠发送的问题。**

例如 AI 平台不采用同步等待，而改为异步任务：

```text
用户提交任务
↓
数据库事务
├─ INSERT ai_task，状态 PENDING
└─ INSERT outbox_event
↓
提交事务
```

这两个数据库操作由同一个本地事务保证：

```text
要么都成功
要么都失败
```

随后：

```text
Outbox Publisher
↓
读取未发送事件
↓
发送 Kafka
↓
收到 Broker 确认
↓
更新 Outbox 状态
```

这样即使：

```text
数据库提交成功
↓
应用立即宕机
```

消息仍然保存在 Outbox 表中，后续可以继续发送。

但 Outbox 不能替代：

```text
AI Timeout
Circuit Breaker
线程池隔离
AI 调用重试
OBS 上传补偿
消费者幂等
```

它们负责的是不同故障边界。

---

## 十六、把长耗时 AI 请求改造成异步任务

对于可能执行几十秒甚至几分钟的 AI 任务，与其让用户 HTTP 请求一直等待，更稳定的设计通常是：

### 阶段一：接收任务

```text
用户 POST /ai/tasks
↓
入口限流
↓
参数校验
↓
短事务
├─ 创建 task：PENDING
└─ 创建 outbox_event
↓
事务提交
↓
立即返回 taskId
```

返回：

```json
{
  "taskId": 10001,
  "status": "PENDING"
}
```

用户可以通过：

```text
轮询任务状态
SSE
WebSocket
消息通知
```

获取最终结果。

### 阶段二：可靠投递任务

```text
Outbox Publisher
↓
Kafka
↓
Worker Consumer
```

Kafka 负责：

```text
异步解耦
削峰
任务缓冲
```

### 阶段三：Worker 执行

```text
Consumer 收到任务
↓
幂等校验
↓
状态更新 PROCESSING
↓
进入 AI 专用线程池
↓
检查熔断器
↓
调用 AI
```

AI 调用配置：

```text
Connect Timeout
Response / Read Timeout
Overall Timeout
```

### 阶段四：失败处理

如果是瞬时可恢复错误：

```text
有限重试
+
指数退避
+
Jitter
```

如果持续失败：

```text
熔断
↓
任务进入 RETRY_WAIT / FAILED
↓
记录错误原因
↓
必要时告警
```

### 阶段五：结果保存

```text
AI 成功
↓
上传 OBS
↓
短事务
├─ 保存 objectKey
└─ 更新 task = SUCCESS
```

整个过程避免了：

```text
一个用户 HTTP 请求
长期占用 Tomcat 工作线程 40 秒甚至更久
```

## 十七、限流、线程池、超时、熔断、重试、Kafka、Outbox 的责任边界

可以把今天和前几天学习的知识串成下面这张表。

| 机制 | 主要解决的问题 |
| --- | --- |
| 限流 | 控制进入系统的请求量，避免入口过载 |
| 线程池 | 控制本机同时执行的任务数量，隔离资源 |
| 超时 | 限制单次操作最多占用资源多久 |
| 熔断 | 下游持续故障时停止大量无意义调用 |
| 重试 | 处理少量、瞬时、可恢复故障 |
| Kafka | 异步解耦、削峰、缓冲任务 |
| Outbox | 保证数据库业务状态与 MQ 事件最终一致 |
| 幂等 | 抵消重复消息、重复请求和重复重试产生的副作用 |
| 状态机 | 明确任务当前阶段，并为失败恢复提供依据 |
| 补偿 | 跨系统失败后恢复到可接受的一致状态 |

它们不是互相替代关系，而是：

```text
不同层次
解决不同故障
共同组成稳定性体系
```

---

## 十八、一套更稳定的 AI 调用链

把 Day 23、Day 24、Day 25、Day 27、Day 28 和今天的 Day 29 串起来：

```text
用户请求
↓
【限流】
控制入口流量
↓
参数 / 权限 / 配额校验
↓
【短数据库事务】
INSERT task(PENDING)
INSERT outbox_event
↓
COMMIT
↓
立即返回 taskId
```

异步部分：

```text
Outbox Publisher
↓
Kafka
↓
Consumer
↓
幂等校验
↓
【AI 专用线程池】
限制执行并发
↓
【熔断器】
判断当前是否值得继续访问 AI
↓
【Timeout】
Connect Timeout
Response / Read Timeout
Overall Timeout
↓
AI 调用
```

成功路径：

```text
AI 成功
↓
OBS 上传（有自己的超时）
↓
短事务
↓
保存 objectKey
更新 task = SUCCESS
```

失败路径：

```text
AI 超时
↓
判断错误是否可重试
↓
有限重试 + 指数退避 + Jitter
↓
仍然失败
↓
task = RETRY_WAIT / FAILED
```

大面积故障：

```text
失败率达到阈值
↓
Circuit Breaker OPEN
↓
快速失败 / 延迟执行 / 切换备用模型
↓
减少继续攻击故障下游
```

这套链路的核心不是让每个请求都成功，而是：

> 在部分组件故障时，系统仍然能够控制资源消耗、保留恢复能力，并避免一个下游故障拖垮全部业务。

## 十九、常见错误设计

### 错误一：完全不设置超时

```text
第三方不返回
↓
线程一直等
```

风险：

```text
线程耗尽
连接耗尽
请求堆积
级联故障
```

---

### 错误二：所有接口统一 30 秒

问题：

```text
没有根据业务 SLA 和正常延迟设计
```

结果可能是：

```text
快接口失败时占资源太久
慢接口正常请求却频繁超时
```

---

### 错误三：只设置 Connect Timeout

连接建立成功以后：

```text
服务端仍然可能一直不返回
```

所以只设置连接超时远远不够。

---

### 错误四：只设置 Read Timeout，没有 Overall Deadline

复杂请求存在多个串行步骤：

```text
DB
↓
AI
↓
OBS
```

每一个步骤都没有单独超时也许不算很长，但加起来可能已经超过整体 SLA。

---

### 错误五：超时后立即重试很多次

结果：

```text
故障流量被放大
↓
下游更难恢复
```

---

### 错误六：在 @Transactional 中等待第三方超时

```text
事务开始
↓
执行 SQL
↓
调用 AI 等待 30 秒
↓
事务才结束
```

数据库连接和锁可能被长期持有。

正确思路：

```text
短事务
↓
提交并释放数据库资源
↓
事务外执行外部调用
```

---

### 错误七：认为异步线程池可以自动解决所有问题

如果线程池配置成：

```text
无限线程
无限队列
```

只是把压力从 Tomcat 转移到另一个地方。

稳定的线程池需要：

```text
明确最大线程数
有界队列
拒绝策略
监控
超时
```

## 二十一、最小代码示例

下面只用于理解思想，不强调具体 API。

### HTTP Client 超时

伪代码：

```java
HttpClient client = HttpClient.builder()
    .connectTimeout(Duration.ofSeconds(2))
    .responseTimeout(Duration.ofSeconds(15))
    .build();
```

再为一次完整调用设置：

```text
Overall Timeout = 18 秒
```

重点不是 API 名称，而是明确：

```text
连接阶段有上限
等待响应有上限
整个调用生命周期也有上限
```

---

### CompletableFuture 超时

```java
CompletableFuture<AiResult> future =
    CompletableFuture.supplyAsync(
        () -> aiClient.call(request),
        aiExecutor
    );

AiResult result = future
    .orTimeout(15, TimeUnit.SECONDS)
    .join();
```

仍然需要注意：

> `orTimeout` 让等待方超时，不代表第三方 HTTP 调用一定已经被真正取消；底层 Client 自己仍然应该配置网络超时和取消机制。

## 二十二、今天思考题的回答与修正

### 问题一：为什么第三方 AI 慢，会导致整个系统越来越慢

原回答：

```text
第三方没有释放，占用了连接池没有被释放
新的请求过来也没有得到释放
连接池耗尽导致整个系统响应变慢
```

需要修正。

更准确的是：

> 第三方 AI 变慢首先会让调用它的 Tomcat 或业务线程长期阻塞，线程释放速度下降。在固定线程数量下，请求完成吞吐下降，新请求开始排队，响应时间继续增加。如果客户端又开始重试，流量会被进一步放大，最终可能耗尽线程池和 HTTP 连接池。

只有在下面情况中：

```text
AI 调用位于数据库事务内
```

才可能进一步出现：

```text
事务持有数据库连接时间变长
↓
数据库连接池耗尽
```

---

### 问题二：哪些步骤应该配置什么超时

原回答：

```text
查询、调用、上传都应该配置超时
但不知道具体类型
```

修正后：

#### 数据库

```text
连接池获取连接超时
SQL Query Timeout
必要时锁等待 / 事务超时
```

#### AI HTTP

```text
Connect Timeout
Response / Read Timeout
Overall Timeout
```

#### OBS 上传

```text
Connect Timeout
Socket / Read Timeout
Request / Overall Timeout
必要时 Write Timeout
```

并且整个接口还应该设置：

```text
Overall Deadline
```

避免各阶段超时时间简单相加后远超业务 SLA。

---

### 问题三：AI 超时以后重试 10 次有什么问题

原回答提到：

```text
浪费 Token
大规模请求下资源来不及释放
可能导致系统崩溃
```

这个方向正确，但需要补充最核心的问题：

> 大量重试会产生 Retry Storm，把原始故障流量成倍放大。

除了 Token 成本，还会增加：

```text
线程占用
HTTP 连接
CPU
内存
网络带宽
下游服务压力
恢复时间
```

正确策略是：

```text
少量重试
+
指数退避
+
Jitter
+
只重试可恢复错误
+
受 Overall Deadline 约束
```

---

### 问题四：AI 长时间不可用如何组合稳定性机制

原思路：

```text
先限流
只供应给管理者和付费用户
失败达到一定次数后熔断
线程池和本地消息表没有思路
```

补完整以后：

```text
入口限流
↓
按用户 / 套餐 / 租户进行配额和优先级控制
↓
任务写数据库 + Outbox
↓
快速返回 taskId
↓
Outbox 可靠投递 Kafka
↓
Kafka 削峰
↓
Worker 消费
↓
AI 专用线程池限制最大执行并发
↓
熔断器判断是否继续访问 AI
↓
Connect / Read / Overall Timeout
↓
有限重试 + 指数退避
↓
失败进入 RETRY_WAIT / FAILED
```

其中：

```text
限流
→ 防止入口流量超过容量

线程池
→ 防止本机 AI 并发无限增长

超时
→ 防止一个任务无限占资源

熔断
→ 防止持续调用已经故障的 AI

重试
→ 恢复瞬时故障

Kafka
→ 削峰和异步解耦

Outbox
→ 保证任务创建与 MQ 事件可靠一致

状态机 + 补偿
→ 让失败任务可恢复
```

## 二十三、面试表达

可以这样表达：

> 在调用 AI、支付、对象存储等外部依赖时，我不会只关注接口是否能调用成功，而会给不同阶段配置合理的超时，包括连接超时、响应或读取超时，以及必要的整体 Deadline。超时的核心目的是限制一次不可控调用占用线程和连接的时间，避免下游慢请求持续堆积后拖垮上游服务。
>
> 如果是长耗时 AI 任务，我倾向于通过任务表、Outbox 和 Kafka 改造成异步执行，由独立 Worker 和专用线程池限制 AI 并发，并结合限流、熔断、有限重试、指数退避和幂等设计。数据库事务只负责短时间内必须原子提交的数据库操作，不会把几十秒的 AI 或对象存储调用放在事务里。这样即使第三方长时间不可用，也能把故障限制在可控资源范围内，而不是拖垮整个系统。

## 二十四、今天的核心结论

```text
AI 变慢首先占用的是请求线程和 HTTP 连接
不一定直接占用数据库连接
```

```text
AI 位于数据库事务中
才可能因为长事务进一步拖住数据库连接
```

```text
Connect Timeout
解决“连不上”
```

```text
Read / Response Timeout
解决“连上了但迟迟不返回”
```

```text
Overall Timeout / Deadline
限制整个调用链最多执行多久
```

```text
超时控制单次调用的资源占用时间
熔断控制持续故障时是否继续调用
限流控制进入系统的请求量
线程池控制本机并发量
```

```text
重试不是越多越可靠
大量立即重试会形成 Retry Storm
```

```text
Outbox 不解决 AI 超时
Outbox 解决数据库业务状态与 MQ 消息可靠投递之间的一致性
```

```text
长耗时 AI 业务更适合：
短事务 + Outbox + Kafka + Worker + 专用线程池 + Timeout + Circuit Breaker
```

今天最重要的系统设计认识是：

> 高可用不是让所有外部调用永远成功，而是在依赖变慢、超时、失败甚至长时间不可用时，让系统能够快速止损、限制资源消耗、隔离故障，并保留后续恢复能力。
