## 二、今天学习什么：为什么 Cache 能加速访问？

### 1. Cache 的位置与作用

CPU 与主存（RAM）之间存在速度差异。CPU Cache 是更小、通常更快的硬件缓存，用于保留近期可能用到的数据，减少访问较慢存储层的等待。

简化访问路径：

~~~text
CPU
 ↓
L1 Cache（小、快）
 ↓ 未命中
L2 Cache（通常比 L1 大、慢）
 ↓ 未命中
主存 RAM
~~~

实际处理器可能还有 L3、多种缓存组织和并行/重叠访问，本轮只采用串行教学模型。**Cache Miss 表示当前层找不到所需数据，不表示数据丢失。**

### 2. 两种局部性

| 概念 | 判断重点 | 示例 |
|---|---|---|
| 时间局部性（Temporal Locality） | 刚访问过的**同一位置**可能再次被访问 | 100 → 500 → 100 |
| 空间局部性（Spatial Locality） | 刚访问过的位置**附近**可能接着被访问 | 100 → 101 → 102 |

两种局部性可以同时存在。例如反复读取彼此靠近的 a、b、c，既可能有相邻数据访问，也可能多次访问同一数据。

示例：

~~~java
int[] arr = new int[10000];
int sum = 0;
for (int i = 0; i < arr.length; i++) {
    sum += arr[i];
}
~~~

在数组物理布局连续且其他条件相近时，顺序遍历通常比访问相隔很远的随机下标更能利用**空间局部性**。这里讨论的是数据访问模式，不是说循环本身就自动产生某一种局部性。

### 3. Cache Line：为什么取回一整块？

Cache 通常按 **Cache Line（缓存行）** 为单位组织和传输数据，而不是每次只缓存一个 Java int。

假设缓存行为 64 字节、一个 int 为 4 字节：

~~~text
64 ÷ 4 = 16
~~~

一条完整的 64 字节缓存行最多可覆盖 16 个相邻的 4 字节 int 槽位。读取 arr[100] 发生未命中时，可取回包含该元素的一整条缓存行。如果 arr[101] 恰好也在这一行、该行未被替换，下一次读取它就有机会命中。

**精度边界：** 不能无条件声称 arr[100] 和 arr[101] 必在同一缓存行；是否跨边界还受数组起始地址与缓存行对齐影响。实际 Java 代码中的局部变量也可能被 JIT 优化到寄存器，因此讲解中的 a、b、c 是为理解缓存原理设定的简化内存访问情景。

### 4. 本段真实问答与纠错

**首次判断：顺序读取数组 A 还是随机读取 B 更易利用空间局部性？**

- 用户首次选择 B，认为“随机访问更需要缓存，而循环主要是算术”。
- **纠正：** 两种访问都可能查询 CPU Cache；关键是相邻数据是否已随缓存行进入缓存。顺序遍历通常更有利于空间局部性。
- 随后用户在“已加载 arr[100]，再读 arr[101]”的情景下能够选择相邻数据并解释原因，**纠错后的简单迁移通过**。

**时间局部性与空间局部性：**

- “100 → 500 → 100”：用户指出第一次读入后第三次可能命中，最终判断为时间局部性；中途短暂混入“附近”的说法，经辨析明确。
- 单个 price 变量在循环里反复被使用：用户首次误认为空间局部性，把循环变量 i 自增与被访问的 price 数据位置变化混为一谈；经拆解后理解同一位置反复访问属于时间局部性。
- a、b、c 位于同一缓存行且循环重复访问：用户能区分**不同近邻位置访问＝空间局部性；同一位置反复访问＝时间局部性**。
- 单次依次访问 a、b、c：用户独立判断主要体现空间局部性；补充说明代码若反复读写 total，也可能有时间局部性。

**缓存行机制：** 用户能够解释 64 字节一行、4 字节一个 int、一次取回一整行后相邻数据更易命中，属于**讲解后的机制解释通过**。

## 三、Cache 命中率、未命中代价与平均访问时间

### 1. 基本概念

- **命中（Hit）：** 目标数据在当前缓存层中找到。
- **未命中（Miss）：** 当前缓存层未找到，需继续访问下一级。
- **命中率（Hit Rate）：** 命中次数 ÷ 总访问次数。
- **未命中率（Miss Rate）：** 未命中次数 ÷ 总访问次数；等于 1 − 命中率。
- **未命中代价（Miss Penalty）：** 某层未命中后产生的**额外**处理或访问代价。

命中率高通常有利于性能，但不是充分条件；必须同时考虑命中耗时、未命中耗时或额外未命中代价。

### 2. 两种容易混淆的耗时口径

**口径 A：题目给出“命中总耗时”和“未命中总耗时”。**

~~~text
平均访问时间
=（命中次数 × 每次命中总耗时
 + 未命中次数 × 每次未命中总耗时）
 ÷ 总访问次数
~~~

如果题目给的是比例，也可以写：

~~~text
平均访问时间
= 命中率 × 命中总耗时
+ 未命中率 × 未命中总耗时
~~~

**口径 B：题目给出“命中时间”和“未命中额外代价”。**

~~~text
平均访问时间
= 命中访问时间 + 未命中率 × 未命中额外代价
~~~

口径 B 中“额外代价”不应再当成“未命中全过程总耗时”重复计算。计算前先判断题干采用哪种口径。

### 3. 实际训练的计算记录

**题 1：** 100 次数据访问，80 次命中，每次命中 2 ns；20 次未命中，每次未命中总耗时 12 ns。

~~~text
(80 × 2 + 20 × 12) ÷ 100
= (160 + 240) ÷ 100
= 4 ns
~~~

用户独立给出了正确算式，并能解释分母 100 是访问总次数。

**题 2：** 同样的两种耗时，命中次数提高到 90：

~~~text
(90 × 2 + 10 × 12) ÷ 100 = 3 ns
~~~

用户说明：命中次数增加，则高成本的未命中次数减少，总耗时与平均耗时随之下降（前提是其他成本不变）。

**题 3：** 原命中率 90%，命中总耗时 2 ns，未命中总耗时 22 ns；优化后命中率 95%。

~~~text
优化前：(90 × 2 + 10 × 22) ÷ 100 = 4 ns
优化后：(95 × 2 + 5 × 22) ÷ 100 = 3 ns
减少：1 ns（相对于优化前降低 25%）
~~~

用户独立列出两组正确算式。这里用 100 次作为便于计算的等比例示例。

**反例：命中率更高未必更快。**

| 指标 | A | B |
|---|---:|---:|
| 命中率 | 95% | 99% |
| 命中总耗时 | 2 ns | 2 ns |
| 未命中总耗时 | 12 ns | 100 ns |
| 平均访问时间 | 2.5 ns | 2.98 ns |

A：0.95×2 + 0.05×12 = 2.5 ns。  
B：0.99×2 + 0.01×100 = 2.98 ns。

用户能够解释不能只看命中率，必须比较总体耗时；当命中率已很高而未命中代价很大时，也可以考虑降低单次未命中代价。

## 四、多级 Cache：L1 Miss、L2 Hit 和局部命中率

### 1. 逐级访问

~~~text
L1 Hit → 从 L1 获得数据
L1 Miss、L2 Hit → 从 L2 获得数据，不必向主存获取
L1 Miss、L2 Miss → 继续向更低层（教学模型中为 RAM）获取
~~~

“这次算 Hit 还是 Miss？”不能脱离具体层级：应该准确说 **L1 Miss、L2 Hit**，而不是笼统把所有层级都称为命中。

用户最初说“整体算命中”，经提醒后明确应分别描述各级结果。

### 2. 局部命中率：分母是到达该级的请求数

100 次访问：90 次 L1 命中；剩下 10 次进入 L2，其中 8 次 L2 命中、2 次继续访问主存。

~~~text
L1 命中率：90 ÷ 100 = 90%
L2 局部命中率：8 ÷ 10 = 80%
最终访问主存比例：2 ÷ 100 = 2%
~~~

另一个练习：200 次访问，160 次 L1 命中，40 次进入 L2，其中 30 次 L2 命中。

~~~text
L2 局部命中率 = 30 ÷ 40 = 75%
~~~

用户能独立计算并解释为什么不能除以 200。连续同构算术题的增量学习价值低，用户明确提出不要继续重复简单题，因此后续转向综合性能判断。

### 3. 两级 Cache 平均访问时间：中文公式

在**串行访问、下级成本按额外耗时计算**的简化模型中：

~~~text
平均访问时间
= 一级缓存访问时间
+ 一级缓存未命中率 × (
    二级缓存访问时间
    + 二级缓存局部未命中率 × 主存额外访问代价
  )
~~~

关键因果：

1. 每次都要检查 L1，付出一级访问时间。
2. 只有 L1 没找到，才额外付出访问 L2 的时间。
3. 只有 L1、L2 都没找到，才额外付出主存访问代价。

| 参数 | 方案 A | 方案 B |
|---|---:|---:|
| 一级缓存访问时间 | 1 ns | 1.2 ns |
| 一级未命中率 | 10% | 5% |
| 二级缓存访问时间 | 6 ns | 8 ns |
| 二级局部未命中率 | 20% | 30% |
| 主存额外访问代价 | 80 ns | 80 ns |

~~~text
方案 A = 1 + 0.10 × (6 + 0.20 × 80)
       = 1 + 0.10 × 22
       = 3.2 ns

方案 B = 1.2 + 0.05 × (8 + 0.30 × 80)
       = 1.2 + 0.05 × 32
       = 2.8 ns
~~~

虽然 B 的 L1 检查更慢、L2 访问也更慢、L2 局部未命中率更高，但 B 的一级未命中率更低：

~~~text
A 到达主存的概率 = 10% × 20% = 2%
B 到达主存的概率 =  5% × 30% = 1.5%
~~~

因此在给定模型下 **B 的平均访问时间更短**。

真实训练中，用户计算出方案 A 的 3.2 ns；方案 B 由讲解者示范。不能把“讲解者算出 B”记录为用户独立完成两方案计算。用户能解释需要综合多个变量，但首次看到公式时出现理解负担；改为中文名称和逐级成本解释后能够跟上。

## 五、三种 Cache 映射方式：数据应该放到哪里？

### 1. 为什么需要映射？

主存中的数据块数量远多于 Cache 可用的缓存行数量。映射方式决定：**某个主存数据块允许被放入哪些缓存行**。

### 2. 三种规则对照

| 映射方式 | 放置规则 | 关键特点 |
|---|---|---|
| 直接映射（Direct Mapped） | 每个主存块只能放在一个固定缓存行 | 简单，但可能发生位置冲突 |
| 全相联映射（Fully Associative） | 任意空闲缓存行均可放置 | 灵活，硬件比较/管理复杂 |
| 组相联映射（Set Associative） | 只能进入固定组，组内任选一行 | 在位置灵活性与硬件成本之间折中 |

### 3. 直接映射

~~~text
缓存行编号 = 主存数据块编号 % 缓存行总数
~~~

符号 %（MOD）表示整数除法取余数。Cache 只有 4 个缓存行时：

~~~text
1 % 4 = 1
5 % 4 = 1
~~~

数据块 1 和数据块 5 都只能放在缓存行 1。先加载 1、再加载 5，会在该行发生替换；即使其他行空着也无法避免这种位置冲突。

本次用户在理解 MOD 后能独立解释“块 5 替换块 1”的结果，**直接映射简单迁移通过**。

### 4. 全相联映射

如果缓存行 0 放数据块 1、缓存行 1 放数据块 5、缓存行 2 和 3 为空，那么需要加载数据块 9 时，可以直接放进空闲的行 2 或行 3，不必替换已有数据。

本次用户能准确说明“全相联可以放到任意空位置”，**基础机制通过**。硬件代价只作概念介绍，尚未训练标签比较电路等细节。

### 5. 2 路组相联

最重要的区分：

- **路数：每一组有多少个缓存行。**
- **组数：整个 Cache 一共分为多少组。**

~~~text
组数 = 缓存行总数 ÷ 每组缓存行数（路数）
组号 = 主存数据块编号 % 组数
~~~

例一：4 个缓存行、2 路组相联。

~~~text
组数 = 4 ÷ 2 = 2

第 0 组：缓存行 0、1
第 1 组：缓存行 2、3

块 4 % 2 = 0  → 第 0 组，可放在行 0 或 1
块 5 % 2 = 1  → 第 1 组，可放在行 2 或 3
~~~

用户初次把“块 4 取余得到组号 0”理解为“只能进入缓存行 0”，因此误判需要替换已有块 2；经纠正“组号不等于缓存行号”后，在块 3、块 5 的第 1 组案例中独立判断块 5 可以放入空闲行 3。

例二：组已经满了怎么办？

第 0 组的两个缓存行分别放块 2、块 4；块 6 % 2 = 0，也必须放第 0 组。即使第 1 组还有空位，也不能跨组放置，必须在第 0 组中替换一行。

用户能独立说明不能放到其他组；回答“随机找个缓存行替换”时，需要补充：**替换必定限制在目标组，但挑选哪一行取决于替换策略，不一定随机**。LRU 和随机替换本轮仅提及，未系统学习。

### 6. 最后一道题暴露的薄弱点：把“2 路”当“2 组”

**题目：** Cache 有 8 个缓存行、2 路组相联，初始全空，依次加载主存数据块 0、4、8。读取块 8 时是否必须替换？

正确计算：

~~~text
缓存行总数 = 8
每组缓存行数 = 2（2 路）
组数 = 8 ÷ 2 = 4

0 % 4 = 0
4 % 4 = 0
8 % 4 = 0
~~~

三个数据块全部属于第 0 组。但第 0 组只有两个缓存行，放入 0、4 后已经满了。加载 8 时必须替换组内一个数据块，即使其他组有空位也不行。

**用户真实表现：** 已掌握“组内可放任意行、不能跨组”的规则，但这道题错误地用 2 作为取模分母，并推测只要某组有足够多行就无需替换。经过讲解已指出错误，不过**尚未对另一道“给出总行数和路数、自行求组数”的题进行独立复测**。

因此不能把组相联的定量迁移标记为全部通过。

## 七、Day 107 间隔回忆：业务规则放在哪一层？

在 Day 108 新知识训练完成后，才按规则进行上一正式训练日回忆。

**题目：** HTTP Controller 和 MQ Consumer 都能创建订单。创建前必须检查下单业务权限。只在 Controller 写权限检查是否合理？应如何设计？

**用户回答（整理）：**

> 不合理。Controller 是接口层，Service 应处理业务逻辑，Mapper 负责数据访问。放 Service 可以让职责清晰、修改方便，不要把业务逻辑写在 Controller。

**本轮评价：主体结论正确，但遗漏了最直接的风险。**

关键的因果关系是：MQ Consumer 可以直接调用业务服务而不经过 Controller。如果下单业务权限只在 Controller 校验，MQ 入口可能绕过它。共同的业务规则应由 Service 或受其统一调用的业务组件负责，保证所有创建订单入口执行一致检查。

注意区分 HTTP 入口的身份认证（例如 Filter、Security）与“是否具有创建订单资格”的业务授权校验；不能把所有认证、协议解析都粗暴地塞到 Service。

**回忆结果：** 独立选择 Service 正确；对“跨入口绕过业务规则”的机制没有主动展开，经补充后理解，**尚未针对这个遗漏点再次独立复测**。
