# 后端工程化每日训练 Day 78：容量规划、排队效应、资源池联动与 MQ 积压复盘

## 一、今天学习什么

今天学习主题：

**容量规划、排队效应与资源池联动：为什么 QPS 没有上涨，线程池、连接池、数据库和 MQ 仍然可能一起进入过载。**

最近几天的训练更多是在回答：

> 某个组件出问题以后，怎么沿调用链定位？

今天开始补一个更上层的能力：

> **系统为什么会从正常突然进入排队、超时甚至雪崩？真正限制吞吐的资源在哪里？**

今天建立的核心因果链：

~~~text
下游变慢
↓
请求执行时间增加
↓
同时在途请求增加
↓
线程被占用更久
↓
数据库连接被占满
↓
请求开始排队
↓
整体 RT 继续上涨
↓
更多请求滞留在系统中
↓
Timeout
~~~

今天最重要的两个判断：

> **增加并发，不等于增加吞吐。**

> **系统容量由最紧的瓶颈决定。**

---

## 二、QPS、响应时间、并发量必须分清

### 1. QPS / 吞吐量

表示系统单位时间内处理多少请求。

例如：

~~~text
500 QPS
=
每秒约 500 个请求
~~~

### 2. 响应时间

表示一个请求从进入到完成需要多久。

例如：

~~~text
100ms
500ms
1s
~~~

### 3. 并发量

表示某一时刻有多少请求还留在系统内部，没有处理完成。

---

## 三、今天最重要的公式：Little's Law

在稳定系统中，可以做一个非常实用的近似：

~~~text
并发量 ≈ 吞吐量 × 响应时间
~~~

即：

~~~text
L = λ × W
~~~

例如：

~~~text
QPS = 500
平均响应时间 = 100ms = 0.1s

并发量 ≈ 500 × 0.1
       = 50
~~~

这意味着：

~~~text
入口 QPS 不变
≠
系统内部并发压力不变
~~~

只要响应时间上升，并发需求就会一起上涨。

今天最重要的认知之一：

> **“慢”本身就可以制造高并发。**

---

## 四、为什么 QPS 没涨，数据库变慢也能拖垮 Java 服务

第一道训练题：

~~~text
Spring Boot

入口流量：
500 QPS

Tomcat 最大工作线程：
200

HikariCP 最大连接数：
50

每个 HTTP 请求：
平均执行 1 次 SQL
~~~

正常情况下：

~~~text
SQL = 50ms
~~~

数据库抖动以后：

~~~text
SQL = 500ms
~~~

入口仍然只有：

~~~text
500 QPS
~~~

### 正常情况下

数据库并发需求近似：

~~~text
500 × 0.05
= 25
~~~

连接池有：

~~~text
50
~~~

所以大约需要 25 个数据库并发，连接池够用。

### SQL 从 50ms 变成 500ms 后

数据库并发需求变为：

~~~text
500 × 0.5
= 250
~~~

但是连接池仍然只有：

~~~text
50
~~~

于是：

~~~text
500 QPS 不变
↓
SQL 变慢 10 倍
↓
连接被占用时间变长
↓
数据库并发需求约 25 → 250
↓
HikariCP 只有 50
↓
连接池打满
↓
其余请求等待连接
↓
Tomcat 线程也被等待请求占住
↓
新请求继续排队
↓
整体 RT 继续上升
↓
Timeout
~~~

所以：

> **不是流量上涨制造了高并发，而是请求停留时间变长制造了更多在途请求。**

## 五、排队为什么会形成正反馈

最危险的不是“连接池满了”本身，而是后续反馈：

~~~text
SQL 变慢
↓
连接持有时间增加
↓
连接池利用率升高
↓
等待连接的请求增加
↓
请求 RT 增加
↓
线程占用时间增加
↓
Tomcat 线程越来越满
↓
新请求排队
↓
RT 再次增加
↓
更多请求同时滞留
~~~

最终形成：

~~~text
慢
↓
排队
↓
更慢
↓
更多排队
↓
更慢
~~~

这就是典型的：

**Queueing Effect（排队效应）**。

## 六、为什么 Tomcat 200 → 500 不一定有用

第二道训练题：

~~~text
500 QPS
Tomcat = 200
HikariCP = 50
SQL = 500ms
~~~

有人提出：

~~~text
Tomcat：
200 → 500
~~~

问题在于：

~~~text
Tomcat 线程
↓
仍然需要 HikariCP 连接
↓
才能真正执行 SQL
~~~

HikariCP 还是：

~~~text
50
~~~

因此增加 Tomcat 线程并没有创造：

~~~text
更多数据库连接
更多数据库 CPU
更高磁盘 IO
更高 SQL 执行能力
~~~

反而可能增加：

~~~text
等待线程
上下文切换
内存占用
请求堆积
Timeout
~~~

可以理解成：

~~~text
银行只有 50 个窗口

原来大厅最多进 200 个人
现在允许进 500 个人

窗口还是 50 个
~~~

办业务的真实能力没有提高，只是大厅里等待的人更多。

所以：

> **增加线程数，不等于增加系统吞吐量。**

---

## 七、为什么 HikariCP 50 → 300 也不一定解决问题

第三道训练题继续往下一层：

> 既然连接池只有 50，那直接改成 300 不就行了吗？

判断应该是：

~~~text
可能有效
但绝不能说一定有效
~~~

因为还必须继续问：

> **数据库本身吃不吃得消？**

连接池扩大，本质上只是允许更多请求同时进入数据库。

如果数据库还有大量余量，连接池过小确实可能是瓶颈。

但如果 SQL 从 50ms 变成 500ms 的原因本来就是：

~~~text
数据库 CPU 接近打满
磁盘 IO 很高
锁竞争
慢 SQL
执行计划异常
数据库内部资源争用
~~~

这时：

~~~text
HikariCP 50 → 300
↓
Java 等连接的问题减少
↓
更多请求同时进入数据库
↓
数据库 CPU / IO / 锁竞争进一步恶化
↓
SQL 更慢
↓
整体系统更慢
~~~

也就是说：

> **瓶颈没有消失，只是从 Java 连接池移动到了数据库。**

连接池不仅是资源池，也是一道保护数据库的并发边界。

~~~

> **哪个资源最先达到极限，哪个资源就是当前瓶颈。**

## 九、为什么系统经常不是线性变慢，而是突然崩

第四道训练题：

~~~text
500 QPS：正常
600 QPS：正常
700 QPS：正常
800 QPS：稍微变慢
850 QPS：大量 Timeout
~~~

真实系统经常不是：

~~~text
QPS 增加 10%
性能就下降 10%
~~~

### 还有容量余量时

~~~text
500
600
700
~~~

关键资源还有余量，请求大多可以直接执行，排队很少。

### 接近极限后

到了 800 QPS，资源利用率已经很高，但还有少量：

~~~text
capacity headroom
容量余量
~~~

所以开始稍微变慢。

继续增加到临界点：

~~~text
资源接近 / 达到极限
↓
新请求不能立即处理
↓
开始排队
↓
排队时间进入 RT
↓
RT 上升
↓
在途请求进一步增加
↓
队列继续增长
↓
Timeout
~~~

所以：

> **系统从“直接执行”进入“需要排队”以后，性能状态发生了质变。**

生产系统不能长期让：

~~~text
CPU 100%
连接池 100%
线程池 100%
~~~

然后认为资源利用得非常充分。

更准确的判断是：

> **系统已经没有能力吸收正常波动。**

需要注意：临界点不一定是数据库连接池，也可能是 CPU、Tomcat、数据库 IO、锁、Pika、IoTDB 或外部 HTTP。

## 十、Fan-out：入口 QPS 不等于数据库 QPS

第五道训练题：

接口：

~~~http
GET /dashboard
~~~

一个请求内部执行：

~~~text
查询主机信息     1 SQL
查询监控项       1 SQL
查询告警         1 SQL
查询权限         1 SQL
查询面板配置     1 SQL
~~~

也就是：

~~~text
1 个 HTTP 请求
→ 5 个数据库请求
~~~

入口：

~~~text
1000 QPS
~~~

数据库请求量可能是：

~~~text
1000 × 5
= 5000 SQL/s
~~~

这就是：

**Fan-out（扇出 / 请求放大）**。

所以容量分析不能只问：

> Java 服务入口有多少 QPS？

还要继续问：

~~~text
一次请求产生多少次 SQL？
多少次 Pika？
多少次 IoTDB？
多少次外部 HTTP？
~~~

因此：

> **入口 QPS 只是流量入口，不等于各个下游真正承受的 QPS。**

## 十一、MQ 不会创造处理能力

第六道训练题切换到监控采集场景：

~~~text
Collector
↓
MQ
↓
Consumer
↓
IoTDB
~~~

生产速度：

~~~text
20,000 条/s
~~~

消费能力：

~~~text
15,000 条/s
~~~

每秒净积压：

~~~text
20,000 - 15,000
= 5,000 条/s
~~~

于是：

~~~text
1 秒：5,000
1 分钟：300,000
10 分钟：3,000,000
1 小时：18,000,000
~~~

所以：

> **MQ 能吸收峰值，但不能消灭长期容量不足。**

只要长期：

~~~text
生产速度 > 消费速度
~~~

队列就会持续增长。

---

## 十二、MQ 真正解决什么问题

今天答题时有一个需要纠正的点：

> **MQ 本身不等于限流。**

MQ 更主要解决：

~~~text
异步
解耦
削峰
暂存
隔离上下游速度差
~~~

例如：

~~~text
平时生产 10,000/s
↓
某一分钟突然 20,000/s
↓
MQ 暂时吸收高峰
↓
高峰过去
↓
Consumer 用剩余处理能力慢慢补回来
~~~

这是 MQ 很擅长的场景。

但如果：

~~~text
长期生产 20,000/s
长期消费 15,000/s
~~~

MQ 只是把暂时处理不了的数据保存起来。

它没有凭空创造缺失的：

~~~text
5,000 条/s
~~~

处理能力。

另外，在 MQ 场景下，比普通 HTTP 的 Response Time 更准确的概念是：

~~~text
消息处理延迟
消费延迟
backlog lag
~~~

## 十三、积压恢复时间为什么不能直接除最大消费速度

第七道训练题：

MQ 已经积压：

~~~text
1,000,000 条
~~~

系统恢复后：

~~~text
正常生产速度：
10,000/s

消费者最大处理能力：
15,000/s
~~~

错误计算：

~~~text
1,000,000 ÷ 15,000
≈ 67 秒
~~~

这相当于假设：

> 清积压期间完全没有新数据进入。

但实际上新的：

~~~text
10,000 条/s
~~~

仍然持续进入。

所以真正可以拿来“还旧账”的能力只有：

~~~text
15,000 - 10,000
= 5,000/s
~~~

恢复时间：

~~~text
1,000,000 ÷ 5,000
= 200 秒
≈ 3 分 20 秒
~~~

最终公式：

~~~text
积压恢复速度
=
最大消费速度 - 当前生产速度
~~~

~~~text
恢复时间
=
当前积压量 ÷ 积压恢复速度
~~~

---

## 十四、积压恢复公式的边界条件

### 消费能力 > 生产速度

存在净恢复能力，旧积压可以逐渐清完。

### 消费能力 = 生产速度

新产生多少，刚好消费多少。

旧积压没有额外能力处理：

~~~text
恢复时间 → 无限
~~~

### 消费能力 < 生产速度

不仅旧积压清不掉，还会继续增加新积压。

此时不能问：

> 多久能恢复？

因为当前状态下：

> **根本不会恢复。**

## 十五、今天 7 道题形成的判断

### 第 1 题：QPS 不变为什么仍然过载

~~~text
并发 ≈ QPS × 耗时
~~~

SQL：

~~~text
50ms → 500ms
~~~

数据库并发需求：

~~~text
25 → 250
~~~

入口虽然仍是 500 QPS，内部资源压力已经发生巨大变化。

### 第 2 题：Tomcat 200 → 500

不能只靠增加 Tomcat 线程解决。

后面的 HikariCP / 数据库能力没有增加，更多线程很可能只是更多等待者。

### 第 3 题：HikariCP 50 → 300

可能有效，但不能直接修改。

必须继续确认：

~~~text
数据库 CPU
数据库 IO
锁竞争
SQL RT
数据库最大安全并发
~~~

核心问题就是：

> **数据库吃不吃得消？**

### 第 4 题：800 QPS 还行，850 QPS 突然崩

容量余量耗尽以后开始排队，排队又继续放大 RT 和并发，所以性能可能非线性恶化。

### 第 5 题：1000 HTTP QPS 为什么可能变成 5000 DB QPS

因为：

~~~text
1 HTTP → 5 SQL
~~~

这就是 Fan-out。

### 第 6 题：MQ 能不能解决 20,000/s → 15,000/s

不能解决长期容量不足。

每秒净积压：

~~~text
5,000
~~~

MQ 只能削峰、异步、解耦和暂存。

### 第 7 题：100 万积压多久恢复

~~~text
净恢复能力
=
15,000 - 10,000
=
5,000/s

恢复时间
=
1,000,000 / 5,000
=
200 秒
~~~

## 十六、今天容易混淆的几个点

### 1. 高并发一定是流量上涨造成的？

错误。

~~~text
QPS 不变
+
RT 上升
~~~

一样可以造成在途并发暴涨。

### 2. 线程池越大，吞吐越高？

错误。

~~~text
线程增加
≠
数据库处理能力增加
~~~

### 3. HikariCP 越大越好？

错误。

连接池扩大只是让更多压力进入数据库。

### 4. 系统 1000 QPS = 数据库 1000 QPS？

错误。

还要计算一次请求产生多少次数据库操作，也就是请求扇出。

### 5. MQ = 限流？

不准确。

MQ 更主要是：

~~~text
削峰
异步
解耦
暂存
~~~

### 6. 有 MQ 就不怕长期生产大于消费？

错误。

~~~text
生产 > 消费
→
持续积压
~~~

### 7. 清积压速度 = 最大消费速度？

错误。

真正用于处理旧积压的是：

~~~text
最大消费速度 - 当前新增生产速度
~~~

## 十七、AI / Codex 在容量分析里应该负责什么

今天这类问题不适合直接让 Codex：

> 接口慢，帮我把线程池和连接池调大。

因为这等于：

~~~text
没有容量模型
↓
直接修改参数
~~~

更合理的方式是先让 AI 只读取证：

~~~text
请只读分析当前项目，不修改任何代码或配置。

梳理：

1. HTTP 入口线程模型；
2. 所有自定义线程池；
3. HikariCP 最大连接数；
4. 某接口完整调用链；
5. 一次请求执行多少次 SQL；
6. 是否同步访问 Pika / IoTDB / 外部 HTTP；
7. 各下游 Timeout；
8. 是否存在 Retry；
9. 是否存在无界队列；
10. 给出潜在容量瓶颈及代码 / 配置证据。

只输出证据和调用关系，不直接修改。
~~~

AI 非常适合：

~~~text
扫描配置
搜索代码
统计请求扇出
找线程池
找连接池
找 Retry
找 Timeout
找无界队列
画调用链
~~~

最终工程判断仍然要回答：

~~~text
真实 QPS 是多少？
P95 / P99 RT 是多少？
哪个资源最接近极限？
数据库是否还有余量？
增加线程会增加吞吐还是增加等待？
增加连接会不会把数据库打满？
系统有没有容量余量？
~~~

是否产生级联放大
~~~

真正需要留下的判断方式：

> **先算需求，再看容量；先找瓶颈，再谈扩容；先判断系统缺的是处理能力还是只是缓冲能力。**

线程池、连接池、MQ 都只是资源控制手段。

它们可以：

~~~text
限制并发
隔离资源
暂存任务
吸收峰值
保护下游
~~~

但不能违反一个基本事实：

> **如果长期进入系统的工作量大于系统真实处理能力，最终一定会以排队、延迟、积压、Timeout 或资源耗尽的形式暴露出来。**

以后再遇到：

~~~text
线程池要不要调大？
连接池要不要调大？
为什么 QPS 没涨还是超时？
加了 MQ 为什么还积压？
积压多久能恢复？
~~~

都应该回到：

~~~text
QPS
耗时
并发
资源容量
请求扇出
生产 / 消费速度
容量余量
~~~

这套统一模型里判断。
