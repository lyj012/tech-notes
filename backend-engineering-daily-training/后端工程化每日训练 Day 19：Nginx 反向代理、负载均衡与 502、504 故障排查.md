# 后端工程化每日训练 Day 19：Nginx 反向代理、负载均衡与 502、504 故障排查

## 一、今天学习的知识点

今天学习的是：

**Nginx 反向代理、负载均衡与 502、504 故障排查**

Nginx 在 Java 后端系统中的常见位置是：

```text
客户端
↓
Nginx
↓
Spring Boot 服务集群
```

它通常承担：

```text
统一入口
反向代理
负载均衡
HTTPS 终止
静态资源分发
请求大小限制
超时控制
真实 IP 透传
基础限流
灰度发布
```

对于 Java 后端开发者，今天真正需要理解的重点不是只记住：

```text
upstream 是后端服务列表
proxy_pass 是转发请求
Round Robin 是轮询
```

而是理解：

```text
为什么线上服务通常不让客户端直接访问 Spring Boot
502 为什么由 Nginx 返回，但根因不一定在 Nginx
为什么一个 API 实例宕机后只有部分请求失败
Nginx 如何判断上游节点暂时不可用
如何沿着 Nginx、容器、网络、端口和应用日志排查故障
为什么长耗时 AI 接口会在 60 秒后返回 504
为什么单纯扩大超时时间不是长任务的最佳设计
如何平滑加入新实例
如何做低权重灰度
如何在错误率上升时快速切断新版本流量
```

一句话理解：

> Nginx 是客户端与后端服务之间的统一流量入口。Java 后端不仅要会写一份能工作的代理配置，还要能够根据 502、504、413 等现象判断故障发生在哪一层，并理解多实例发布、流量切换和快速回滚的基本链路。

## 二、为什么生产环境需要 Nginx

如果客户端直接访问单个 Spring Boot 服务：

```text
Browser
↓
Spring Boot :8080
```

会存在以下问题：

```text
服务地址直接暴露
单实例宕机后整体不可用
难以部署多个实例
HTTPS 配置分散
前端静态资源占用 Java 服务资源
无法统一限制请求大小
无法统一处理超时
无法统一限流
无法方便地做灰度发布
```

加入 Nginx 后，系统可以变成：

```text
Client
↓
Nginx
├── /                → Vue 静态资源
├── /api/*           → Spring Boot API 集群
├── /download/*      → 本地文件或对象存储代理
└── /ws/*            → WebSocket 服务
```

后端服务可以部署多个实例：

```text
Nginx
├── API-1
├── API-2
└── API-3
```

客户端只需要访问一个域名：

```text
https://api.example.com
```

至于请求最终进入哪个实例，由 Nginx 决定。

## 三、正向代理和反向代理的区别

### 1. 正向代理

正向代理代表客户端访问外部服务。

```text
客户端
↓
正向代理
↓
目标网站
```

目标网站看到的直接访问者通常是代理服务器。

常见场景：

```text
企业出口代理
网络访问代理
客户端隐藏自身地址
```

### 2. 反向代理

反向代理代表服务端接收客户端请求。

```text
客户端
↓
Nginx
↓
真实后端服务
```

客户端只知道 Nginx 的地址，不需要知道后端有多少实例，也不需要知道真实端口。

Nginx 对外表现为服务入口，对内负责选择上游节点。

Java 后端项目中的 Nginx 通常属于：

```text
反向代理
```

## 四、Nginx 请求转发的核心链路

典型链路：

```text
客户端发送 HTTP 请求
↓
请求到达 Nginx
↓
Nginx 匹配 server
↓
Nginx 匹配 location
↓
选择 upstream 中的一个后端节点
↓
与后端建立连接
↓
转发请求头和请求体
↓
等待后端响应
↓
将响应返回客户端
```

例如：

```nginx
upstream backend {
    server 192.168.1.10:8080;
    server 192.168.1.11:8080;
}

server {
    listen 80;
    server_name api.example.com;

    location /api/ {
        proxy_pass http://backend;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

关键配置：

```text
upstream
定义一组后端节点

server
定义上游节点地址、端口和部分故障参数

location
匹配请求路径

proxy_pass
将请求转发给指定上游

proxy_set_header
控制转发给后端的请求头
```

## 五、Nginx 在真实业务中的使用场景

### 1. AI 异步任务平台

架构：

```text
Client
↓
Nginx
↓
API-1 / API-2
↓
MySQL / Redis / MQ
↓
Worker
```

Nginx 主要负责：

```text
统一 API 域名
HTTPS
将请求分发给多个 API 实例
限制上传大小
透传客户端信息
处理 SSE 或 WebSocket 连接
```

真正的 AI 长任务不应该长期占用普通 HTTP 请求，而应该由：

```text
API 创建任务
↓
MQ 投递
↓
Worker 执行
↓
前端轮询、SSE 或 WebSocket 获取结果
```

### 2. PDF 工具平台

可以按照路径分流：

```text
/api/*
→ Spring Boot

/download/*
→ Nginx 静态目录或对象存储

/
→ Vue 静态资源
```

示例：

```nginx
server {
    listen 80;

    location / {
        root /usr/share/nginx/html;
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://backend;
    }

    location /download/ {
        alias /data/files/;
    }
}
```

这样可以减少 Java 服务处理静态文件的压力。

### 3. 后台管理系统

前端：

```text
Vue 3
```

后端：

```text
Spring Boot
```

对外统一使用：

```text
https://admin.example.com
```

浏览器访问页面：

```text
/
→ Nginx 返回 Vue 文件
```

前端调用接口：

```text
/api/user/list
→ Nginx 转发到 Spring Boot
```

统一域名还可以减少跨域配置复杂度。

## 六、常见负载均衡策略

## 1. Round Robin：轮询

默认情况下，Nginx 按顺序将请求分配给后端节点。

```text
请求 1 → API-1
请求 2 → API-2
请求 3 → API-1
请求 4 → API-2
```

适合：

```text
后端实例配置相近
请求处理时间差异不大
服务无状态
```

轮询并不保证：

```text
同一个用户永远进入同一个实例
```

因此多实例系统不应依赖单机内存保存登录状态。

---

## 2. Weight：权重

示例：

```nginx
upstream backend {
    server api-1:8080 weight=5;
    server api-2:8080 weight=1;
}
```

大致表示：

```text
API-1 获得更多请求
API-2 获得更少请求
```

适合：

```text
服务器配置不同
新版本低流量灰度
某个节点需要临时降流量
```

权重表示相对流量比例，不保证每一个固定窗口都绝对符合比例。

---

## 3. Least Connections：最少连接

示例：

```nginx
upstream backend {
    least_conn;

    server api-1:8080;
    server api-2:8080;
}
```

Nginx 倾向于将新请求交给当前连接数较少的节点。

适合：

```text
请求耗时差异较大
存在较多长连接
部分接口执行时间较长
```

但连接数少不一定代表：

```text
CPU 最空闲
内存最充足
业务压力最低
```

它仍然只是一个流量分配指标。

---

## 4. IP Hash

示例：

```nginx
upstream backend {
    ip_hash;

    server api-1:8080;
    server api-2:8080;
}
```

根据客户端 IP 将请求较稳定地分配到同一节点。

适合部分需要会话黏性的旧系统。

但它存在问题：

```text
大量用户可能共享同一个出口 IP
节点变化时映射会变化
无法解决单机 Session 的高可用问题
负载可能不均衡
```

因此更推荐：

```text
JWT
或
Redis Session
```

而不是把 IP Hash 当成登录状态设计的根本方案。

---

## 七、多实例下为什么不能依赖单机 Session

假设登录信息保存在 API-1 内存中：

```text
用户登录
↓
API-1 保存 Session
```

下一次请求经过轮询进入 API-2：

```text
用户请求
↓
API-2
↓
本机没有该 Session
↓
被判断为未登录
```

这会导致：

```text
登录状态随机丢失
部分请求正常
部分请求要求重新登录
```

解决方向：

### 方案一：JWT

```text
身份信息由客户端携带
后端实例不依赖本机 Session
```

适合无状态认证，但需要考虑：

```text
Token 过期
刷新机制
撤销机制
权限变化
密钥管理
```

### 方案二：Redis Session

```text
多个后端实例
↓
共同读取 Redis 中的 Session
```

适合需要服务端会话管理的系统。

核心原则：

> 只要服务需要横向扩容，就不应该把关键共享状态只保存在单个实例内存中。

## 八、502 Bad Gateway 的准确含义

用户今天最先给出的判断是：

```text
502 报错
→ 通常就是 Nginx 的问题
→ Nginx 连接不了上游
```

这个判断只对了一半。

更准确的说法是：

> 502 通常由 Nginx 返回，表示 Nginx 没有从上游服务获得有效响应。但根因既可能在 Nginx 配置，也可能在 Spring Boot、容器、端口、网络或上游进程。

常见原因：

```text
Spring Boot 没有启动
Spring Boot 启动后立即退出
Docker 容器已经停止
容器反复重启
Nginx upstream 地址错误
Nginx upstream 端口错误
服务只监听 127.0.0.1
容器端口映射错误
Nginx 与后端不在可通信网络
防火墙或安全组拦截
后端主动关闭连接
后端返回了无效 HTTP 响应
```

因此：

```text
502 是 Nginx 暴露出来的现象
≠
Nginx 本身一定故障
```

## 九、常见 Nginx 错误日志如何理解

### 1. Connection refused

日志可能出现：

```text
connect() failed (111: Connection refused) while connecting to upstream
```

通常表示：

```text
目标 IP 可以到达
但目标端口没有服务正常监听
```

重点检查：

```text
容器是否运行
Spring Boot 是否启动成功
应用监听端口
容器端口
upstream 端口
```

### 2. Connection timed out

日志可能出现：

```text
upstream timed out
```

或连接阶段超时。

可能表示：

```text
网络不通
防火墙拦截
目标地址错误
后端处理太慢
后端线程池阻塞
下游依赖超时
```

需要根据日志中的阶段判断是：

```text
连接上游超时
还是
读取上游响应超时
```

### 3. No live upstreams

日志可能出现：

```text
no live upstreams
```

表示：

```text
当前 upstream 中没有可用节点
```

可能原因：

```text
所有节点都失败
节点被临时标记不可用
配置中节点地址无法解析
```

### 4. Prematurely closed connection

日志可能出现：

```text
upstream prematurely closed connection
```

通常表示：

```text
后端在完整响应返回之前关闭了连接
```

可能原因：

```text
Java 进程崩溃
容器被杀
后端异常退出
响应过程中连接被中断
网关或应用超时
```

### 5. Host not found in upstream

日志可能出现：

```text
host not found in upstream
```

重点检查：

```text
Docker 服务名
DNS
容器网络
upstream 域名拼写
```

## 十、为什么只有部分用户出现 502

假设：

```text
API-1 正常
API-2 宕机
```

Nginx 使用轮询：

```text
请求 1 → API-1 → 200
请求 2 → API-2 → 502
请求 3 → API-1 → 200
请求 4 → API-2 → 502
```

因此表现为：

```text
部分用户正常
部分用户失败
```

更准确地说，不一定是固定的“部分用户”，也可能是：

```text
同一个用户前一次成功
下一次失败
```

因为轮询通常按请求分配，而不是按用户身份固定分配。

如果某个请求被转发给 API-2，就可能失败；转发给 API-1 就正常。

这种现象通常提示：

```text
集群中可能只有部分节点异常
```

而不是：

```text
整个系统全部不可用
```

## 十一、Nginx 如何暂时避开异常节点

示例：

```nginx
upstream backend {
    server api-1:8080 max_fails=3 fail_timeout=30s;
    server api-2:8080 max_fails=3 fail_timeout=30s;
}
```

含义可以基础理解为：

```text
在 fail_timeout 时间窗口内
如果某节点失败达到 max_fails
Nginx 会在一段时间内暂时认为该节点不可用
```

需要注意：

> 开源版 Nginx 常见的 `max_fails` 和 `fail_timeout` 主要属于被动故障判断。

也就是说：

```text
请求已经被转发给异常节点
↓
请求发生连接失败或响应异常
↓
Nginx 记录失败
↓
达到条件后暂时避开节点
```

它不是默认持续主动调用：

```text
/actuator/health
```

提前发现故障。

所以故障刚发生时，仍可能有少量请求进入异常节点并返回 502。

更完整的主动健康检查可能由：

```text
Nginx Plus
第三方模块
云负载均衡器
Kubernetes Readiness Probe
服务注册与发现系统
```

负责。

## 十二、502 的标准排查思路

用户今天最初猜测的顺序是：

```text
先检查网络连通性
再看 Nginx
再看 Spring Boot
```

这个顺序不完全错误，但缺少：

```text
故障范围
Nginx 错误日志
容器状态
具体错误类型
```

更成熟的排查方式如下。

### 第一步：确认故障范围

先判断：

```text
所有请求失败
还是部分请求失败

所有接口失败
还是某个接口失败

持续失败
还是偶发失败

只有新版本失败
还是旧版本也失败

只有一个节点失败
还是所有节点失败
```

如果只有部分请求失败，优先怀疑：

```text
某一个上游实例异常
```

### 第二步：查看 Nginx error.log

```bash
tail -n 200 /var/log/nginx/error.log
```

或：

```bash
tail -f /var/log/nginx/error.log
```

根据错误关键词缩小范围：

```text
connection refused
→ 进程、端口、容器

timed out
→ 网络、性能、线程池、下游依赖

host not found
→ DNS、服务名、容器网络

prematurely closed
→ 后端异常关闭连接
```

### 第三步：检查容器或进程状态

Docker 场景：

```bash
docker ps -a
```

重点观察：

```text
是否 Up
是否 Exited
是否 Restarting
启动时间
端口映射
```

查看日志：

```bash
docker logs --tail 200 api-2
```

或持续观察：

```bash
docker logs -f api-2
```

非 Docker 场景可以检查：

```bash
ps -ef | grep java
ss -lntp
systemctl status 服务名
```

### 第四步：从 Nginx 所在环境测试上游

```bash
curl -v http://api-2:8080/actuator/health
```

或：

```bash
curl -v http://192.168.1.11:8080/actuator/health
```

测试端口：

```bash
nc -vz 192.168.1.11 8080
```

结果判断：

```text
Connection refused
→ 端口没有监听或服务退出

Connection timed out
→ 网络、防火墙、安全组或地址问题

HTTP 500
→ 网络已通，请求已到达后端，应用内部异常

HTTP 200
→ 上游基本可访问，继续检查 Nginx 配置、路径、Host 和请求差异
```

### 第五步：查看 Spring Boot 日志

重点寻找：

```text
应用启动失败
端口冲突
数据库连接失败
Redis 连接失败
配置中心不可用
OutOfMemoryError
线程池耗尽
请求异常堆栈
被 SIGTERM 或 OOM Kill
```

### 第六步：检查 Nginx 配置

先检查语法：

```bash
nginx -t
```

重点检查：

```text
upstream 地址
端口
location 匹配
proxy_pass 路径
Host 请求头
容器服务名
配置是否已经 reload
```

最终链路：

```text
确认故障范围
↓
Nginx error.log
↓
容器或进程状态
↓
从 Nginx 到上游的网络和端口
↓
Spring Boot 日志
↓
Nginx 配置与最近变更
```

实际线上可以并行检查，但思维上必须覆盖完整链路。

## 十三、502 与 500 的区别

### 500 Internal Server Error

通常表示：

```text
请求已经进入 Spring Boot
↓
业务处理过程中发生异常
```

排查重点：

```text
Java 异常堆栈
traceId
SQL
业务参数
下游调用
```

### 502 Bad Gateway

通常表示：

```text
请求到达 Nginx
↓
Nginx 无法从上游获得有效响应
```

排查重点：

```text
上游进程
容器
端口
网络
upstream 配置
后端异常断开
```

基础判断：

```text
500
→ 更偏应用内部处理失败

502
→ 更偏代理到上游的连接或响应链路失败
```

但不能只凭状态码直接确定唯一根因。

## 十四、504 Gateway Timeout 的含义

504 通常表示：

```text
请求到达 Nginx
↓
Nginx 已经尝试访问上游
↓
在规定时间内没有得到需要的响应
↓
Nginx 返回 504
```

常见原因：

```text
后端接口执行时间过长
Java 线程池阻塞
数据库慢 SQL
下游 AI 服务响应慢
第三方接口超时
proxy_read_timeout 太短
负载均衡器超时更短
```

AI 推理需要三分钟，但客户端 60 秒收到 504，首先应检查：

```nginx
proxy_read_timeout
```

例如：

```nginx
location /api/ai/ {
    proxy_pass http://backend;
    proxy_read_timeout 300s;
}
```

## 十五、Nginx 常见超时配置

### 1. proxy_connect_timeout

```nginx
proxy_connect_timeout 10s;
```

表示：

```text
Nginx 与上游建立连接允许等待多久
```

如果后端地址不可达或网络异常，可能在连接阶段超时。

### 2. proxy_send_timeout

```nginx
proxy_send_timeout 300s;
```

表示：

```text
Nginx 向上游发送请求数据时，相邻两次写操作允许的最大间隔
```

上传大请求体或上游读取非常慢时需要关注。

### 3. proxy_read_timeout

```nginx
proxy_read_timeout 300s;
```

表示：

```text
Nginx 从上游读取响应时，相邻两次读操作允许的最大间隔
```

它不是简单的“整个接口总耗时必须小于这个值”。

如果上游长期没有返回任何数据，超过该时间，就可能返回 504。

对于普通同步接口，最常需要关注的是：

```text
proxy_read_timeout
```

### 4. send_timeout

```nginx
send_timeout 300s;
```

表示：

```text
Nginx 向客户端发送响应数据时，相邻两次写操作允许的最大间隔
```

如果客户端接收速度过慢，可能触发。

## 十六、为什么只修改 Nginx 超时可能仍然无效

完整请求链路可能是：

```text
浏览器
↓
前端 Axios
↓
CDN
↓
云负载均衡器
↓
Nginx
↓
Spring Boot
↓
AI SDK
↓
模型服务
```

任何一层都可能配置 60 秒超时。

例如：

```javascript
const request = axios.create({
    timeout: 60000
});
```

即使 Nginx 配置：

```nginx
proxy_read_timeout 300s;
```

前端仍可能在 60 秒主动取消请求。

还需要检查：

```text
浏览器或前端请求超时
CDN 超时
云负载均衡器空闲超时
Nginx 超时
Spring MVC 异步请求超时
Spring Cloud Gateway 超时
HTTP 客户端超时
AI SDK 超时
模型服务自身超时
```

所以正确方法是：

```text
找到究竟是哪一层在 60 秒终止请求
```

而不是无差别把所有超时都改得很大。

## 十七、长耗时 AI 接口为什么更适合异步任务

直接保持三分钟同步连接的问题：

```text
客户端长时间等待
连接中途容易断开
Nginx 长连接数量增加
后端线程可能被长期占用
重试可能重复执行任务
超时后用户不知道任务是否仍在运行
服务重启后状态难以恢复
```

更合理的架构：

```text
客户端提交任务
↓
API 校验参数并创建任务记录
↓
返回 taskId
↓
任务消息进入 MQ
↓
Worker 异步执行
↓
更新任务状态和结果
↓
前端轮询、SSE 或 WebSocket 获取进度
```

创建任务接口：

```http
POST /api/tasks
```

返回：

```json
{
  "taskId": "task_10001",
  "status": "PENDING"
}
```

查询状态：

```http
GET /api/tasks/task_10001
```

返回：

```json
{
  "taskId": "task_10001",
  "status": "RUNNING",
  "progress": 60
}
```

这种设计更容易实现：

```text
失败重试
任务幂等
状态持久化
限流
排队
进度查询
超时补偿
任务取消
结果复用
```

因此：

> 扩大 Nginx 超时可以解决部分同步接口问题，但对 AI 推理、OCR、PDF 转换等分钟级任务，更优方案通常是异步任务化。

## 十八、SSE 和 WebSocket 经过 Nginx 时的注意点

### 1. SSE

SSE 是持续返回数据的长连接。

常见配置：

```nginx
location /api/sse/ {
    proxy_pass http://backend;

    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 3600s;
}
```

需要关注：

```text
代理缓冲
读取超时
上游是否定期发送心跳
客户端断开后的资源释放
```

如果 Nginx 缓冲未关闭，可能出现：

```text
后端已经推送
但前端迟迟收不到
```

### 2. WebSocket

示例：

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    '' close;
}

server {
    location /ws/ {
        proxy_pass http://backend;

        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 3600s;
    }
}
```

需要透传：

```text
Upgrade
Connection
```

否则 WebSocket 协议升级可能失败。

## 十九、上传大文件为什么出现 413

用户上传：

```text
500 MB PDF
```

Nginx 返回：

```text
413 Request Entity Too Large
```

首先检查：

```nginx
client_max_body_size
```

例如：

```nginx
server {
    client_max_body_size 600m;

```

或只针对上传接口：

```nginx
location /api/files/upload {
    client_max_body_size 600m;
```

需要同时检查：

```text
Nginx 限制
Spring Boot multipart 限制
网关限制
对象存储限制
前端上传策略
```

Spring Boot 可能还配置：

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 600MB
      max-request-size: 600MB
```

如果 Nginx 已经在入口拒绝请求，请求甚至不会到达 Spring Boot。

## 二十、真实客户端 IP 为什么会丢失

Spring Boot 直接获取：

```java
request.getRemoteAddr()
```

可能得到：

```text
Nginx 的 IP
容器网关 IP
127.0.0.1
```

因为真正与 Spring Boot 建立 TCP 连接的是 Nginx。

常见配置：

```nginx
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
proxy_set_header Host $host;
```

含义：

```text
X-Real-IP
当前直接客户端地址

X-Forwarded-For
保留经过多个代理时的地址链

X-Forwarded-Proto
原始请求协议，例如 http 或 https

Host
原始访问域名
```

需要注意安全边界：

> `X-Forwarded-For` 可以被客户端伪造。只有来自可信代理的转发头才能被后端当作真实来源使用。

如果系统经过：

```text
CDN
↓
云负载均衡器
↓
Nginx
↓
Spring Boot
```

需要明确：

```text
哪些代理可信
真实 IP 应从地址链的哪个位置读取
```

否则限流、审计和安全日志都可能使用错误 IP。

## 二十一、proxy_pass 路径拼接的常见坑

以下两种配置结果可能不同。

### 配置一

```nginx
location /api/ {
    proxy_pass http://backend;
}
```

请求：

```text
/api/user/list
```

通常转发为：

```text
http://backend/api/user/list
```

### 配置二

```nginx
location /api/ {
    proxy_pass http://backend/;
}
```

请求：

```text
/api/user/list
```

通常可能转发为：

```text
http://backend/user/list
```

也就是：

```text
是否保留 /api/ 前缀
```

可能受到 `proxy_pass` 尾部斜杠影响。

这类问题常表现为：

```text
Nginx 可以连接后端
但接口返回 404
```

此时不是网络问题，而是路径重写问题。

## 二十二、Nginx 日志应该记录什么

访问日志至少应能看到：

```text
请求时间
客户端 IP
Host
请求方法
URI
状态码
响应大小
请求耗时
上游地址
上游状态码
上游响应时间
```

示例思路：

```nginx
log_format main_ext
    '$remote_addr - $request '
    'status=$status '
    'request_time=$request_time '
    'upstream_addr=$upstream_addr '
    'upstream_status=$upstream_status '
    'upstream_response_time=$upstream_response_time';

access_log /var/log/nginx/access.log main_ext;
```

关键字段：

```text
$request_time
客户端请求在 Nginx 侧的总耗时

$upstream_addr
实际选中的后端节点

$upstream_status
上游返回状态

$upstream_response_time
等待上游响应的耗时
```

如果只有 API-2 异常，可以通过：

```text
upstream_addr
```

判断失败请求是否集中进入 API-2。

## 二十四、不停机加入新版本 API

假设旧集群：

```nginx
upstream backend {
    server api-1:8080;
    server api-2:8080;
}
```

新版本实例：

```text
api-3
```

合理流程：

```text
启动 api-3
↓
检查容器状态
↓
检查 Spring Boot 启动日志
↓
调用 /actuator/health
↓
执行基础冒烟测试
↓
加入 Nginx upstream
↓
nginx -t
↓
平滑 reload
↓
观察错误率、延迟和资源
```

健康检查：

```bash
curl -f http://api-3:8080/actuator/health
```

修改 upstream：

```nginx
upstream backend {
    server api-1:8080;
    server api-2:8080;
    server api-3:8080;
}
```

检查配置：

```bash
nginx -t
```

平滑重载：

```bash
nginx -s reload
```

或：

```bash
systemctl reload nginx
```

平滑 reload 的基础行为：

```text
新 Worker 使用新配置接收新连接
旧 Worker 继续处理已有连接
旧请求完成后旧 Worker 退出
```

因此比直接停止 Nginx 更适合线上变更。

## 二十五、如何进行低权重灰度

不要立刻让新版本承担全部流量。

可以先配置：

```nginx
upstream backend {
    server api-1:8080 weight=10;
    server api-2:8080 weight=10;
    server api-3:8080 weight=1;
}
```

观察：

```text
HTTP 5xx 错误率
接口 P95、P99 延迟
CPU
内存
GC
数据库连接数
慢 SQL
业务异常
容器重启次数
日志错误数量
```

确认稳定后逐渐提高：

```nginx
server api-3:8080 weight=5;
```

最终再让新版本承担正常比例流量。

但需要注意：

> 权重灰度只解决流量比例问题，不能自动解决数据库兼容、缓存兼容、消息格式兼容和接口兼容问题。

新旧版本同时运行时，需要考虑：

```text
数据库字段是否兼容
新版本写入的数据旧版本是否能读取
消息体是否向后兼容
Redis 数据结构是否变化
接口响应结构是否影响前端
```

还要看：

## 二十八、回滚为什么可能失败

即使把流量切回旧版本，也不代表一定安全。

可能出现：

```text
新版本已经执行数据库迁移
旧版本无法识别新表结构

新版本写入了新格式数据
旧版本无法解析

新版本发送了新版 MQ 消息
旧消费者无法处理

新版本修改了 Redis 数据结构
旧版本读取失败
```

因此可靠发布需要：

```text
代码向后兼容
数据库变更可兼容
消息协议可兼容
配置版本可追踪
镜像版本明确
回滚步骤提前验证
```

常见数据库策略：

```text
先增加字段
新旧版本都能运行
再发布新代码
最后在确认稳定后清理旧结构
```

而不是：

```text
先删除旧字段
再尝试发布新版本
```

## 三十二、今天练习题的回答复盘

### 问题一：502 通常意味着问题更可能发生在哪里

用户原回答：

```text
502 报错
那么通常就是 Nginx 的问题
Nginx 连接不了上游
```

其中正确部分是：

```text
Nginx 无法正常获得上游响应
```

需要修正的部分是：

```text
因此一定是 Nginx 自身故障
```

正确结论：

```text
502 由 Nginx 返回
↓
表示代理到上游的连接或响应链路异常
↓
根因可能在 Nginx、Spring Boot、容器、端口或网络
```

面试中可以说：

> 502 是网关层暴露出来的上游异常，不应该直接归类为 Nginx 自身故障。我会结合 Nginx error.log 判断是 connection refused、timeout、DNS 还是后端提前断开，再继续检查容器、端口和应用日志。

---

### 问题二：为什么只有 API-2 宕机时只有部分请求报错

用户回答的核心方向是正确的：

```text
Nginx 会轮询
API-2 宕机只影响分配给 API-2 的请求
API-1 仍然可以处理请求
```

需要补充：

```text
同一个用户也可能一会儿成功、一会儿失败
```

因为默认轮询通常按请求分配，而不是固定用户。

还要补充：

```text
Nginx 在被动检测到 API-2 多次失败后
可能暂时避开 API-2
```

所以实际现象可能是：

```text
故障刚发生时
部分请求 502

达到失败条件后
Nginx 暂时不再选择 API-2

过一段时间后
再次尝试该节点
```

### 问题三：按照什么顺序排查

用户最初在以下顺序之间犹豫：

```text
Nginx
网络
Docker
Spring Boot
```

问题不在于某一个顺序绝对错误，而在于缺少：

```text
先确认故障范围
根据错误日志决定下一步
```

正确思路：

```text
确认全部失败还是部分失败
↓
查看 Nginx error.log
↓
检查 Docker 容器和进程
↓
从 Nginx 环境测试上游地址和端口
↓
查看 Spring Boot 日志
↓
检查 Nginx 配置和最近变更
```

关键原则：

> 排障顺序不是机械背诵，而是先拿到最接近故障现场的证据，再沿着请求链路逐层缩小范围。

### 问题五：不停机加入新版本并快速回滚

用户原回答：

## 三十四、面试表达

可以这样回答：

> 在部署 Java 服务时，我会将 Nginx 作为统一入口，负责 HTTPS、反向代理、负载均衡、静态资源分流以及请求大小和代理超时控制。多个 Spring Boot 实例放在 upstream 后面，服务本身尽量保持无状态，登录状态使用 JWT 或 Redis Session，避免轮询到不同实例后丢失会话。

> 如果线上出现部分请求 502，我不会直接判断为 Nginx 自身故障。502 虽然由 Nginx 返回，但根因可能是某个 Spring Boot 实例宕机、Docker 容器退出、端口未监听、upstream 配置错误或网络不通。我会先确认是全部请求还是部分请求失败，再查看 Nginx error.log，根据 connection refused、upstream timed out、host not found 等信息判断方向，然后检查容器状态、从 Nginx 所在环境访问健康接口，最后结合 Spring Boot 日志和最近发布变更定位问题。

> 如果只有 API-2 宕机，而 API-1 正常，默认轮询会导致进入 API-1 的请求成功、进入 API-2 的请求失败，所以表现为部分请求 502。开源 Nginx 常见的 max_fails 和 fail_timeout 属于被动故障判断，通常需要请求先失败，达到条件后才会暂时避开异常节点。

> 对于需要三分钟的 AI 推理接口，我会先检查 proxy_read_timeout，同时检查前端、负载均衡器、Spring Boot 和 AI SDK 的超时配置。但如果任务稳定需要分钟级时间，更合理的方案是异步任务化：提交接口返回 taskId，任务通过 MQ 交给 Worker 执行，客户端通过轮询、SSE 或 WebSocket 获取进度和结果。

> 发布新版本时，我会先启动新实例并完成健康检查，再以较低权重加入 upstream，执行 nginx -t 和平滑 reload，观察 5xx、延迟、资源和业务指标后逐步放量。如果出现异常，先把新实例从 upstream 移除并 reload，快速切断流量，同时保留故障容器和日志用于排查。为了保证回滚有效，还需要确保数据库、Redis 数据结构和 MQ 消息格式能够向后兼容。

## 三十六、今天的最终结论

第一个必须修正的判断是：

```text
502 由 Nginx 返回
=
Nginx 自己一定坏了
```

正确理解：

```text
502 表示 Nginx 没有从上游获得有效响应
根因可能在 Nginx、容器、端口、网络或 Spring Boot
```

第二个必须记住的结论：

```text
部分请求 502
+
集群中部分请求正常
```

优先怀疑：

```text
某一个上游实例异常
```

第三个必须记住的排障链路：

```text
确认故障范围
↓
Nginx error.log
↓
容器和进程状态
↓
网络、端口和健康接口
↓
Spring Boot 日志
↓
Nginx 配置和最近变更
```

第四个必须记住的 504 配置：

```nginx
proxy_read_timeout
```

但不能只检查 Nginx，还要检查完整超时链路。

第五个必须记住的架构判断：

```text
分钟级 AI、OCR、PDF 任务
优先异步任务化
而不是无限扩大同步请求超时
```

第六个必须记住的发布流程：

```text
启动新实例
↓
健康检查
↓
低权重加入 upstream
↓
nginx -t
↓
reload
↓
观察指标
↓
逐步放量
```

第七个必须记住的回滚顺序：

```text
先切断新实例流量
↓
再确认系统恢复
↓
最后保留现场排查
```

今天最核心的一句话是：

> 502、504 不是单纯背状态码，而是用来判断客户端、Nginx、容器、Spring Boot 和下游依赖之间哪一段链路出现了问题；真正的中级后端能力，是能够根据日志和现象缩小故障范围，并完成可控发布、灰度和回滚。

能力等级：

```text
能够解释反向代理、upstream 和轮询
→ Nginx 基础认知

能够完成 Spring Boot 反向代理、静态资源分流和真实 IP 透传
→ 初级部署实践

能够根据日志排查 502、504、413 和单节点故障
→ 初级到中级后端工程能力

能够设计无状态服务、超时链路、灰度发布和平滑回滚
→ 中级服务交付与稳定性能力
```
