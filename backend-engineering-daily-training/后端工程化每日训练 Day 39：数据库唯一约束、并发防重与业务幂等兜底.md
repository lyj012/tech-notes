# 后端工程化每日训练 Day 39：数据库唯一约束、并发防重与业务幂等兜底

## 一、今天学习的知识点

今天学习的是：

**数据库唯一约束（Unique Constraint）、联合唯一索引、并发场景下的防重复写入，以及 UNIQUE 与 Redis、MQ、幂等、事务之间的职责边界。**

一句话理解：

> 对于订单号、支付流水号、消息 ID、用户领取记录等业务上“绝对不能重复”的数据，最终底线应该交给数据库唯一约束，而不能只依赖 Java 代码先查询再插入。

前面已经学习过：

```text
幂等
↓
数据库索引
↓
乐观锁 / 悲观锁
↓
事务隔离
↓
死锁
↓
原子更新
↓
大事务拆分
```

今天继续建立一个非常重要的数据层思维：

```text
Java 判断“没有重复”
≠
数据库最终一定没有重复
```

真正要问的是：

```text
这个业务不变量
能不能直接让数据库强制保证？
```

如果答案是：

```text
这个业务键绝对不能重复
```

那么第一反应应该是：

```text
数据库能不能建立 UNIQUE？
```

## 二、为什么 SELECT 再 INSERT 不能保证并发安全

假设支付回调携带第三方流水号：

```text
trade_no = PAY202608140001
```

代码逻辑：

```text
SELECT 是否存在 trade_no
↓
不存在
↓
INSERT
```

单请求执行时没有明显问题。

但如果多个请求同时进入：

```text
请求 A：SELECT → 不存在
请求 B：SELECT → 不存在
请求 C：SELECT → 不存在
```

然后：

```text
请求 A：INSERT
请求 B：INSERT
请求 C：INSERT
```

如果数据库没有唯一约束，三次 INSERT 都可能成功。

今天练习中已经能够直接判断出原因：

> A、B、C 几乎同时查询，都看到数据还不存在，所以都继续插入，最终形成多条重复记录。

问题的本质不是：

```text
SELECT 写错了
```

而是：

```text
SELECT
和
INSERT
是两个独立操作
```

中间存在：

```text
并发窗口
```

所以：

```text
if (!exists()) {
    insert();
}
```

只能降低普通重复操作的概率，不能作为并发情况下的最终正确性保证。

## 三、数据库 UNIQUE 为什么能够兜底

假设支付流水表：

```text
payment_record

id
order_no
trade_no
amount
status
```

业务要求：

```text
trade_no
```

绝对不能重复。

可以建立：

```sql
CREATE UNIQUE INDEX uk_trade_no
ON payment_record(trade_no);
```

这时多个请求同时执行：

```sql
INSERT INTO payment_record
(trade_no, order_no, amount)
VALUES (?, ?, ?);
```

数据库最终会保证：

```text
第一个合法 INSERT
→ 成功

后续相同 trade_no
→ 唯一键冲突
→ 写入失败
```

因此正确的分层应该是：

```text
Java
→ 负责业务判断、参数校验、友好提示

数据库 UNIQUE
→ 负责最终不变量约束
```

今天要形成的工程原则是：

> **能够由数据层强制保证的不变量，不要只依赖应用层代码约定。**

## 四、什么叫联合唯一约束

今天优惠券练习的业务规则是：

```text
同一个用户
同一种优惠券
只能领取一次
```

表结构：

```text
coupon_receive

id
user_id
coupon_id
receive_time
```

如果只给：

```text
user_id
```

建立 UNIQUE，会变成：

```text
一个用户一生只能领取一张优惠券
```

显然不符合业务。

如果只给：

```text
coupon_id
```

建立 UNIQUE，会变成：

```text
一种优惠券全系统只能被一个用户领取
```

同样错误。

真正不能重复的是：

```text
(user_id, coupon_id)
```

所以应该建立：

```sql
UNIQUE KEY uk_user_coupon (user_id, coupon_id)
```

允许：

```text
1001 + 2001  √
1001 + 2002  √
1002 + 2001  √
```

不允许再次出现：

```text
1001 + 2001  ×
```

今天已经能够正确判断：

> 业务唯一性不是看单个字段，而是看“什么组合才代表同一个业务事实”。

这就是联合唯一约束最核心的设计思路。

## 五、100 个并发 INSERT，最终会发生什么

假设已经建立：

```sql
UNIQUE KEY uk_user_coupon (user_id, coupon_id)
```

100 个请求同时执行：

```sql
INSERT INTO coupon_receive(user_id, coupon_id)
VALUES (1001, 2001);
```

最终应该是：

```text
1 个 INSERT 成功
99 个 INSERT 失败
```

这里要注意一个表达准确性问题。

剩下 99 个不是：

```text
“不符合 WHERE 条件”
```

而是：

```text
Duplicate Key
Unique Constraint Violation
唯一键冲突
```

在 Spring 中常见的异常表现可能是：

```java
DuplicateKeyException
```

所以应用层可以针对真正的唯一键冲突做业务处理，例如：

```text
该优惠券已经领取过
```

但不能把所有数据库异常都统一解释成：

```text
重复领取
```

因为数据库异常还可能是：

```text
数据库连接失败
SQL 语法错误
字段超长
其他唯一键冲突
数据类型错误
```

因此：

> **异常处理必须识别具体失败原因，不能把所有 DataAccessException 都当成 Duplicate Key。**

## 六、UNIQUE 和数据库原子更新的区别

前面 Day 37 学过：

```sql
UPDATE product
SET stock = stock - 1
WHERE id = ?
  AND stock > 0;
```

如果库存已经不足：

```text
affected rows = 0
```

这是：

```text
UPDATE 条件不满足
```

而今天的 UNIQUE 场景：

```sql
INSERT INTO coupon_receive(user_id, coupon_id)
VALUES (1001, 2001);
```

如果 `(1001, 2001)` 已经存在：

```text
INSERT 直接发生唯一键冲突
```

所以两个模型要区分：

```text
原子 UPDATE 条件竞争失败
→ affected rows = 0

UNIQUE 冲突
→ Duplicate Key / Constraint Violation
```

不能把所有并发失败都理解成同一种数据库行为。

## 七、有 UNIQUE 以后，还要不要 Java 先 SELECT

答案不是简单的：

```text
一定要
```

或者：

```text
一定不要
```

应该拆成两个目标。

### 1. 正确性

如果数据库已经存在：

```text
UNIQUE(user_id, coupon_id)
```

那么正确性不应该依赖：

```text
SELECT → 不存在 → INSERT
```

因为并发情况下 SELECT 不能提供最终保证。

### 2. 用户体验

某些普通业务可以提前 SELECT：

```text
发现已经存在
↓
提前返回友好提示
```

减少一次异常写入。

但最终仍然必须接受：

```text
SELECT 后到 INSERT 前
数据可能被其他请求写入
```

所以即使提前 SELECT：

```text
INSERT 时仍然要处理 Duplicate Key
```

可以记成：

```text
SELECT
→ 可以改善体验

UNIQUE
→ 保证最终正确性
```

## 八、高并发不等于一定要加 Redis 分布式锁

今天练习中最需要纠正的一个判断是：

```text
看到并发
↓
下意识想加 Redis 分布式锁
```

例如：

```text
优惠券接口每天只有几千次调用
同一个用户偶尔重复点击
产生 2～5 个并发请求
数据库已经有 UNIQUE(user_id, coupon_id)
```

这种情况下默认应该优先：

```text
UNIQUE 就够了
```

而不是马上引入：

```text
Redis 分布式锁
```

因为 Redis 分布式锁不是免费的。

它会额外引入：

```text
Redis 依赖
锁超时
锁释放
锁续期
误释放风险
网络故障
Redis 故障
更多代码复杂度
更多运维复杂度
```

如果数据库本身已经能够可靠解决正确性问题，而且实际压力很小，再增加一层锁往往属于：

```text
过度设计
```

## 九、“每天有很多重复请求”不等于“瞬时高并发”

今天练习中还纠正了一个容易出现的推导：

假设：

```text
一天 5000 个请求
其中 1000 个请求属于重复点击
```

不能直接推导为：

```text
有 1000 个高并发请求同时冲击数据库
```

因为它们可能分散在全天：

```text
用户 A：同时 3 个
用户 B：同时 2 个
用户 C：同时 4 个
...
```

这和：

```text
1000 个请求在同一秒竞争同一个业务键
```

完全不是一个压力级别。

所以判断系统是否需要额外并发控制时，应该看：

```text
瞬时 QPS
热点 key 的竞争程度
单次业务成本
数据库真实负载
失败率
响应时间
```

而不能只看：

```text
一天总共有多少请求
```

## 十、什么时候 UNIQUE 不够

UNIQUE 能解决：

```text
最终数据不能重复
```

但它不能解决：

```text
系统会不会被瞬时流量打垮
```

例如大促：

```text
同一张优惠券
瞬间 3 万请求
```

领取流程还包括：

```text
查库存
↓
查用户资格
↓
调用会员服务
↓
写多个数据
```

这时虽然数据库最终有：

```sql
UNIQUE(user_id, coupon_id)
```

可以保证：

```text
同一用户不会重复领取
```

但 3 万个请求可能已经执行了大量昂贵操作。

所以问题已经从：

```text
数据重复
```

升级为：

```text
流量保护
资源消耗
削峰
热点库存竞争
```

这时候只靠 UNIQUE 就不够。

## 十一、大促场景为什么不能简单“一把分布式锁”解决

假设给整张优惠券加：

```text
lock:coupon:10001
```

那么：

```text
3 万个用户
↓
全部抢同一把锁
↓
请求被强制串行
```

可能导致：

```text
吞吐量暴跌
大量排队
大量超时
锁本身成为瓶颈
```

如果改成：

```text
lock:user_id:coupon_id
```

3 万个不同用户会对应大量不同的锁。

这时：

```text
大家还是可以同时进入后面的重业务流程
```

它并不能解决：

```text
3 万个不同用户同时冲击下游
```

所以今天要明确：

> **分布式锁解决的是多个节点对同一个资源的互斥访问，不是通用的“高并发解决方案”。**

## 十二、5 万请求抢 1000 张券应该怎么想

场景：

```text
优惠券库存：1000
瞬时请求：50000
```

方案 A：

```text
5 万请求全部查数据库库存
↓
全部进入后续业务
```

方案 B：

```text
Redis 维护库存
↓
原子判断 / 原子扣减
↓
没有库存的快速失败
↓
抢到库存的进入 MQ / 数据库流程
```

今天能够明确判断：

```text
选 B
```

原因不是：

```text
Redis 一定比数据库“高级”
```

而是：

```text
只有 1000 张券
↓
没必要让 5 万个请求全部进入核心数据库流程
```

更合理的链路可能是：

```text
50000 请求
↓
限流 / 基础校验
↓
Redis 原子库存控制
↓
大部分请求快速失败
↓
少量成功请求进入 MQ
↓
消费者异步处理
↓
数据库落库
↓
UNIQUE 最终兜底
```

这里各组件职责不同：

```text
UNIQUE
→ 防止业务数据重复

Redis 原子操作 / Lua
→ 高频库存判断和扣减

限流
→ 控制进入系统的瞬时流量

MQ
→ 削峰，把瞬时压力摊开处理

分布式锁
→ 必须互斥访问同一资源时再考虑
```

## 十三、为什么前面有 Redis 和 MQ，数据库 UNIQUE 仍然不能删

即使已经有：

```text
Redis 预扣库存
+
MQ 异步处理
```

数据库仍然应该保留：

```sql
UNIQUE(user_id, coupon_id)
```

因为整个链路可能出现：

```text
客户端重试
MQ 重复投递
消费者重复消费
网络超时
程序 Bug
任务重试
```

例如：

```text
第一次消息消费
→ 发券成功

同一消息再次投递
→ 消费者又执行一次
```

如果没有最终数据库约束，就可能产生重复业务结果。

所以：

```text
Redis / MQ
→ 提高吞吐、削峰、协调

数据库 UNIQUE
→ 保证最终数据底线
```

二者不是互相替代关系。

## 十四、MQ 重复投递为什么必须做幂等

假设同一条领取消息被投递 3 次：

```text
message_id = MSG001
user_id    = 1001
coupon_id  = 2001
```

消费者不能认为：

```text
MQ 发了 3 次
↓
业务就执行 3 次
```

而应该做到：

```text
同一个业务请求执行一次
和
执行多次
最终结果一致
```

这就是：

```text
幂等
```

一种常见方式是建立消费记录：

```text
message_consume_record

message_id
status
consume_time
```

并建立：

```sql
UNIQUE(message_id)
```

第一次：

```text
MSG001
→ 记录成功
→ 执行业务
```

后续重复消息：

```text
MSG001
→ 唯一键冲突 / 已存在
→ 不重复执行业务
```

## 十五、消息级幂等和业务级唯一约束为什么最好同时存在

只用：

```text
UNIQUE(message_id)
```

只能保证：

```text
同一条消息不会重复处理
```

但如果系统 Bug 产生了：

```text
MSG001 → user 1001 + coupon 2001
MSG002 → user 1001 + coupon 2001
```

两个 message_id 不同，但它们代表的是同一个业务结果。

这时：

```text
message_id UNIQUE
```

挡不住第二条。

而：

```sql
UNIQUE(user_id, coupon_id)
```

还可以继续兜底。

所以更完整的防线是：

```text
消息级幂等
+
业务级唯一约束
```

分别解决：

```text
同一消息重复投递
+
不同消息产生同一业务结果
```

## 十六、Redis 成功但数据库失败是什么问题

假设抢券流程：

```text
Redis 库存：1000 → 999
↓
MQ
↓
数据库 INSERT coupon_receive
↓
数据库故障
↓
INSERT 失败
```

此时：

```text
Redis
→ 已经少了 1 张

数据库
→ 用户没有领取记录
```

这是典型的：

```text
跨组件部分成功
↓
最终一致性问题
```

不能简单地：

```text
数据库一失败
→ 立即把 Redis +1
```

因为数据库可能只是短暂抖动。

如果：

```text
库存补回
↓
消息随后重试成功
```

就可能又产生新的库存不一致。

更合理的思路是：

```text
消费失败
↓
MQ 重试
↓
仍然失败
↓
死信 / 异常任务
↓
后续补偿和对账
```

根据最终业务状态决定：

```text
补写数据库
或者
补偿 Redis 库存
```

而不是看到一次失败就立即反向修改。

## 十七、本地消息表不是所有一致性问题的万能答案

今天练习中另一个需要纠正的思维是：

```text
一看到跨系统不一致
↓
下意识想到本地消息表
```

本地消息表非常有用，但有明确适用边界。

典型场景：

```text
本地数据库业务操作
+
需要可靠发送 MQ
```

例如：

```text
创建订单
+
发送订单创建消息
```

如果直接：

```text
INSERT order
↓
COMMIT
↓
发送 MQ
```

可能发生：

```text
订单已经提交
↓
程序宕机
↓
MQ 没发出去
```

这时可以使用：

```text
同一个本地事务：

INSERT order
+
INSERT local_message
↓
COMMIT
```

然后后台任务扫描：

```text
local_message.status = WAIT
```

持续重试发送 MQ。

所以本地消息表主要解决的是：

> **“本地数据库事务成功”与“外部消息发送”之间的可靠衔接。**

## 十八、如果两个操作都在同一个数据库，先考虑本地事务

场景：

```text
INSERT message_consume_record
+
INSERT coupon_receive
```

如果两个表都在同一个数据库里，最直接的方案不是再加本地消息表，而是：

```java
@Transactional
public void consume(Message msg) {
    insertMessageConsumeRecord(msg.getMessageId());
    insertCouponReceive(msg.getUserId(), msg.getCouponId());
}
```

事务结果：

```text
两步都成功
→ COMMIT
```

或者：

```text
第二步失败
→ ROLLBACK
→ 第一步也一起回滚
```

这样不会出现：

```text
消费记录显示成功
但业务实际上没有完成
```

今天需要建立的判断顺序是：

```text
多个操作发生一致性问题
↓
先问：是不是同一个数据库？
```

如果是：

```text
优先数据库事务
```

如果是：

```text
DB + MQ
Redis + DB
服务 A + 服务 B
```

才进一步考虑：

```text
最终一致性
重试
事务消息
本地消息表
补偿
对账
```

## 十九、@Transactional 里吞异常为什么危险

今天最后延伸到了一个非常常见的 Spring 事务坑。

错误示例：

```java
@Transactional
public void consume() {
    insertMessageRecord();

    try {
        insertCouponReceive();
    } catch (Exception e) {
        log.error("领取失败", e);
    }
}
```

执行过程可能是：

```text
insertMessageRecord
→ 成功

insertCouponReceive
→ 失败

catch
→ 把异常吃掉

方法正常结束
```

Spring 事务代理从外部可能看到：

```text
方法正常返回
```

于是可能提交事务。

最终变成：

```text
message_consume_record
→ MSG001 已消费

coupon_receive
→ 实际没有发券
```

如果 MQ 再次投递：

```text
系统发现 MSG001 已消费
↓
直接跳过
```

用户可能永久拿不到权益。

所以需要记住：

```text
@Transactional
+
catch 后直接吞异常
=
可能破坏预期回滚
```

如果确实需要 catch，通常还要让异常继续向外传播，或者明确标记事务回滚，不能只记录日志后正常 return。

## 二十、今天几个工具到底分别解决什么问题

今天最大的价值不是记住某一个组件，而是建立职责边界。

### 1. 数据库 UNIQUE

解决：

```text
业务数据绝对不能重复
```

例如：

```text
支付流水号
订单号
用户 + 优惠券
message_id
第三方 request_id
```

---

### 2. 数据库原子更新

解决：

```text
判断 + 修改需要原子完成
```

例如：

```sql
UPDATE product
SET stock = stock - 1
WHERE id = ?
  AND stock > 0;
```

---

### 3. Redis 分布式锁

解决：

```text
多个节点确实需要互斥操作同一个资源
```

不是：

```text
只要高并发就加锁
```

---

### 4. Redis 原子操作 / Lua

适合：

```text
热点库存
高频状态判断
快速扣减
```

用于在高流量入口快速过滤大量请求。

---

### 5. 限流

解决：

```text
瞬时流量超过系统承载能力
```

核心目标：

```text
保护系统
```

---

### 6. MQ

解决：

```text
瞬时业务处理不过来
```

通过：

```text
异步
+
削峰
```

把瞬时压力摊开。

---

### 7. 幂等

解决：

```text
同一个请求 / 消息重复执行
最终结果仍然一致
```

---

### 8. 数据库事务

解决：

```text
同一个数据库中的多个操作
需要一起成功或一起失败
```

---

### 9. 本地消息表

典型解决：

```text
本地数据库事务
+
可靠发送 MQ
```

---

### 10. 重试 + 补偿 + 对账

解决：

```text
跨 Redis / MQ / DB 等多个组件后
出现部分成功
```

让系统最终恢复到正确状态。

## 二十一、面试怎么表达

如果面试官问：

**为什么防重复不能只写 SELECT 再 INSERT？**

可以回答：

> `SELECT` 和 `INSERT` 是两个独立操作，并发情况下多个请求可能同时查询到数据不存在，然后同时执行插入，因此应用层的“先查再插”不能作为最终唯一性保证。对于支付流水号、订单号、消息 ID 或联合业务键这类必须唯一的数据，我会在数据库建立 UNIQUE 约束，把唯一性作为最终数据层防线，应用层可以提前查询改善体验，但 INSERT 时仍然需要正确处理唯一键冲突。

如果面试官问：

**同一个用户同一种优惠券只能领一次，索引怎么建？**

可以回答：

> 不能只给 user_id 或 coupon_id 单独加唯一约束，因为业务唯一性是两者组合。我会建立 `(user_id, coupon_id)` 联合唯一索引，使同一个用户可以领取不同优惠券，同一种券也可以被不同用户领取，但同一个用户和同一种券的组合不能重复。

如果面试官问：

**已经有 UNIQUE，还要不要 Redis 分布式锁？**

可以回答：

> 如果只是低到中等并发下防止重复写入，数据库 UNIQUE 已经能够保证最终正确性，我不会因为“有并发”就默认再加分布式锁，否则会增加 Redis 依赖、锁超时、释放和故障处理复杂度。如果出现热点资源竞争、昂贵前置流程或瞬时高流量，我会先分析具体瓶颈，可能使用限流、Redis 原子操作或 MQ 削峰；只有确实需要跨节点互斥访问同一资源时才考虑分布式锁。

如果面试官问：

**MQ 重复消费怎么防止重复发券？**

可以回答：

> 消费者必须做幂等。我可以对 message_id 建唯一约束避免同一消息重复处理，同时在实际领取表上保留 `(user_id, coupon_id)` 业务唯一约束。前者解决消息级重复，后者解决即使出现不同 message_id 但代表同一业务操作时的最终数据兜底。

## 二十二、今天练习中的关键纠正

### 1. “100 个并发，所以要 Redis 锁”不成立

最开始容易形成：

```text
请求多
↓
分布式锁
```

今天需要改成：

```text
先确认问题是什么
```

如果只是：

```text
同一业务键不能重复
```

数据库 UNIQUE 通常已经是更直接、更可靠的底线。

---

### 2. “一天有 1000 个重复请求”不等于“1000 并发”

要区分：

```text
总请求量
```

和：

```text
同一时刻的瞬时并发
```

系统压力主要看后者以及单次请求成本。

---

### 3. 不能自己补充题目里没有的高成本条件

如果题目只说：

```text
简单优惠券领取
偶发 2～5 个重复请求
已有 UNIQUE
```

不能因为想象：

```text
“这个接口应该很重”
```

就直接上分布式锁。

工程判断要基于：

```text
已有事实
真实指标
明确瓶颈
```

而不是假设复杂度。

---

### 4. 高并发真正的问题不一定是“锁”

例如：

```text
5 万请求抢 1000 张券
```

核心问题是：

```text
没有必要让 5 万请求都进入数据库重流程
```

更应该想到：

```text
限流
Redis 原子扣减
MQ 削峰
```

而不是简单：

```text
加一把锁
```

---

### 5. 本地消息表不能一看到不一致就套

如果：

```text
消费记录
+
业务数据
```

都在同一个数据库：

```text
优先本地事务
```

本地消息表更典型的使用位置是：

```text
数据库本地事务
和
MQ 发送
```

之间的可靠衔接。

---

### 6. @Transactional 不是写上注解就一定按预期回滚

如果代码：

```text
catch 异常
↓
只打日志
↓
正常 return
```

就可能让事务边界失去预期效果。

所以需要同时理解：

```text
事务范围
+
异常传播
+
回滚规则
```

不能只记住一个注解名字。

## 二十三、今天的最小记忆模型

### 模型一：业务绝对不能重复

```text
订单号 / 流水号 / 业务唯一键
↓
第一反应
↓
数据库能不能 UNIQUE？
```

---

### 模型二：先查再插的并发窗口

```text
A：SELECT → 不存在
B：SELECT → 不存在
↓
A：INSERT
B：INSERT
```

所以：

```text
Java 判断
≠
最终并发安全
```

---

### 模型三：联合唯一约束

业务：

```text
同一个用户
同一种优惠券
只能一次
```

约束：

```sql
UNIQUE(user_id, coupon_id)
```

不是：

```text
UNIQUE(user_id)
```

也不是：

```text
UNIQUE(coupon_id)
```

---

### 模型四：UNIQUE 与 Redis 锁

```text
防止数据重复
→ UNIQUE

确实需要跨节点互斥
→ 分布式锁
```

不要：

```text
看到并发
→ 默认加锁
```

---

### 模型五：高并发流量保护

```text
流量太大
→ 限流

热点库存
→ Redis 原子操作 / Lua

瞬时处理不过来
→ MQ 削峰

最终数据重复
→ UNIQUE
```

---

### 模型六：MQ 幂等

```text
message_id UNIQUE
→ 防同一消息重复

(user_id, coupon_id) UNIQUE
→ 防业务结果重复
```

---

### 模型七：一致性问题先看边界

```text
同一个数据库
→ 本地事务优先

DB + MQ / Redis + DB / 跨服务
→ 最终一致性、重试、补偿、对账
```

---

### 模型八：事务异常

```text
@Transactional
+
异常正确传播
→ 才能按预期触发整体回滚
```

警惕：

```text
catch 后吞异常
```

---

## 二十四、今天的最终总结

今天真正需要建立的，不只是：

```sql
CREATE UNIQUE INDEX ...
```

而是一套：

**“正确性先落到最可靠的数据层，再按真实压力增加上层机制”的工程判断。**

核心链路是：

```text
业务要求数据绝对不能重复
↓
不要只写 SELECT 再 INSERT
↓
识别真正的业务唯一键
↓
建立 UNIQUE / 联合 UNIQUE
↓
应用层正确处理 Duplicate Key
↓
并发不高时不要过度设计
↓
不要因为“有并发”就默认加 Redis 分布式锁
↓
如果出现真正的大流量
再区分：

数据重复？
→ UNIQUE

热点库存？
→ 原子扣减

瞬时流量太大？
→ 限流

业务处理不过来？
→ MQ 削峰

同一资源必须互斥？
→ 分布式锁
↓
MQ 重复消费继续做幂等
↓
数据库保留业务唯一约束最终兜底
↓
跨组件失败通过重试、补偿、对账恢复最终一致性
```

最终要形成的条件反射：

```text
看到“这个数据绝对不能重复”
↓
先问数据库能不能 UNIQUE
↓
看到“高并发”
↓
先问真正的瓶颈是什么
↓
再选择锁、Redis、限流、MQ 等工具
```

而不是：

```text
并发
↓
加锁
↓
再加缓存
↓
再加 MQ
```

最终原则：

> **正确性机制要尽量简单、可靠、靠近数据底线；性能和流量机制则应该根据真实瓶颈按需增加，不能为了“看起来更安全”无限叠加复杂度。**
