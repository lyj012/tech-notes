## 二、先解释：`putIfAbsent()` 是什么？

### 1. 它解决什么问题？

假设一个 Map 中没有订单 ID `1001`。两个线程几乎同时想登记这个 Key。

普通写法：

```java
if (!map.containsKey("1001")) {
    map.put("1001", true);
}
```

这里的检查和插入是两个独立操作。线程 A 检查完、还没来得及插入时，线程 B 也可能检查到 Key 不存在。两个线程随后都执行插入，并都误以为自己抢到了首次登记资格。

使用：

```java
map.putIfAbsent("1001", true);
```

可以将“Key 不存在才插入”的判断作为一个原子操作完成。对同一个 Map 中的同一个 Key 并发调用时，不会有两个调用都成功完成这次首次插入。

### 2. 两种返回情况

| 调用前的状态 | Map 最终状态 | `putIfAbsent()` 返回值 |
|---|---|---|
| Key 不存在 | 插入新映射 | `null` |
| Key 已存在 | 保留原映射，不覆盖 | 返回原来的值 |

因此，下面的代码只有在本次插入成功时才会进入 `if`：

```java
if (map.putIfAbsent("1001", true) == null) {
    System.out.println("处理订单");
}
```

若 A、B 同时对同一个空 Map 的 Key `1001` 执行上述逻辑，只有成功完成首次插入的那个线程会因为返回 `null` 而进入代码块。究竟 A 还是 B 成功，取决于实际执行顺序，不能预先断定。

**术语纠正：** `putIfAbsent()` 是 Map 的方法，不应简单理解成“整个 Map 只有一把锁”。`ConcurrentHashMap` 的内部并发控制实现会使用相应的并发机制；本日只需掌握公开 API 的原子语义，不需要假定所有操作都由同一把全局锁保护。

## 三、第一题：两个线程竞争同一个 Key

### 题目

初始 Map 为空：

```java
ConcurrentHashMap<String, Boolean> map =
        new ConcurrentHashMap<>();

// 线程 A
if (map.putIfAbsent("1001", true) == null) {
    System.out.println("A 处理订单");
}

// 线程 B
if (map.putIfAbsent("1001", true) == null) {
    System.out.println("B 处理订单");
}
```

### 实际回答与评估

用户先回忆了“检查和插入合并成原子操作”的机制，随后正确判断：

> 不会两个线程都打印。假设 A 先插入，B 后执行时发现 Key 已经存在，就不会进入处理订单的代码块。

**评估：通过。** 能够使用返回值和原子插入机制解释结果。补充边界：这里的“先插入”不代表固定由 A 获胜。

## 四、第二题：迁移到用户注册

### 题目

```java
ConcurrentHashMap<String, String> users =
        new ConcurrentHashMap<>();

// 线程 A
users.putIfAbsent("liu", "用户A");

// 假设 A 插入成功后，线程 B 才执行
users.putIfAbsent("liu", "用户B");
```

### 实际回答与评估

用户正确判断最终仍为 `"liu" -> "用户A"`，因为 B 执行时 Key 已经存在，不会覆盖旧值。

**评估：通过。** 能将机制迁移到不同业务名词。

随后将题目改为 Key 已存在时：

```java
users.put("liu", "旧用户");

String result = users.putIfAbsent("liu", "新用户");
```

用户最初不确定返回值，猜测可能返回错误。经过解释后，能够正确复述：

- Map 中仍然保存 `"旧用户"`；
- `result` 也得到 `"旧用户"`；
- 不会报错，也不会用 `"新用户"` 覆盖旧值。

再换成 `"apple" -> "苹果"` 与待插入的 `"香蕉"` 时，用户独立判断最终仍保存“苹果”。

**评估：经解释后掌握。** 首次对已有 Key 时的返回值不确定，随后在相似场景中完成正确迁移。

## 五、关键纠偏：Map 不等于数据库

这是本次训练最重要的一次概念澄清。

### 1. 代码实际访问什么？

```java
map.putIfAbsent("1001", true);
```

这里的 `map` 是 `ConcurrentHashMap` 对象，因此方法检查和修改的是**当前 Map 中的键值映射**。

它不会自动执行 SQL，不会自动查询数据库，也不知道数据库中是否已经有订单。

例如：

```java
// 操作 Java 内存中的 Map
map.putIfAbsent("1001", true);

// 通过数据库访问层查询订单（示意）
orderMapper.selectById("1001");

// 通过数据库访问层尝试插入订单（示意）
orderMapper.insert(order);
```

三者是不同的操作，不能从第一行推断后两行已经发生。

### 2. Map 中保存的是什么？

在教学示例中，`ConcurrentHashMap<String, Boolean>` 只保存类似：

| Key | Value |
|---|---|
| `1001` | `true` |

它不是完整的订单数据存储。商品、金额、支付状态等业务数据通常由数据库等持久化系统保存。Map 只是 Java 程序可以选择使用的一份内存数据结构，可能用于临时标记、缓存或其他键值信息。

### 3. 两台服务器各有自己的 Map

假设：

- 服务器 A 的 Map 已经登记 `1001`；
- 服务器 B 的 Map 仍然为空；
- 两台服务器都收到同一个订单 ID 的请求。

A 的 Map 与 B 的 Map 是两份独立的内存数据。A 插入 Key 不会自动修改 B 的 Map，因此 B 也可能成功插入同一个 Key。

### 实际回答与评估

用户先判断两个独立 Map 可能都能插入，随后又把 `putIfAbsent()` 的检查误认为查询数据库。经过明确区分“`map.` 方法访问 Map”与“Mapper/SQL 访问数据库”后，用户表示理解了该边界。

**评估：经纠偏后理解。** 这是一次概念边界混淆，不应记作从一开始就独立掌握。

## 六、真实订单业务：为什么还需要数据库唯一约束？

### 1. “先查再插入”存在竞态

假设 A、B 访问同一个数据库，并执行类似逻辑：

```java
if (orderMapper.selectById("1001") == null) {
    orderMapper.insert(order);
}
```

如果两个请求几乎同时执行：

1. A 查询时，订单尚不存在。
2. B 在 A 插入前查询，也发现订单不存在。
3. A 和 B 都尝试插入相同的订单 ID。

两次查询都可能没有错，但“查询”和“插入”并不是一个不可分割的原子操作。不能仅靠查询结果保证并发写入不会重复。

### 2. 唯一约束负责什么？

示意表结构：

```sql
CREATE TABLE orders (
    order_id VARCHAR(64) NOT NULL UNIQUE,
    amount DECIMAL(10, 2)
);
```

在两台服务访问同一个数据库、`order_id` 是同一业务唯一标识的前提下，唯一约束可以阻止相同的非空订单 ID 被重复写入。

A、B 同时尝试插入相同的 `1001` 时，数据库会协调唯一键冲突：一个插入成功，另一个遇到唯一键冲突。哪个请求成功不能提前确定。

### 实际回答与评估

用户能够独立说明：

> 两台服务器的 Map 是独立的，可能都认为订单不存在；但相同订单 ID 的重复数据是不允许的，因此需要数据库唯一约束防止重复插入。

**评估：通过。** 能解释为什么需要数据库层面的最终防重约束。

### 3. 唯一约束触发后，应用怎么处理？

本次继续讨论了两种简化方案：

- 遇到唯一键冲突就向客户端返回内部错误；
- 识别出重复业务请求后，查询已有订单，并根据业务规则返回已有订单结果。

用户选择第二种方案，理由是应向调用方提供明确且合理的业务结果，而不是让调用方盲目重试。

**工程补充：** 第二种通常更符合幂等接口的设计方向，但不能对所有唯一键冲突都一概返回已有订单。应用应区分确实属于同一业务请求的重复提交，还是不同请求错误地争用了相同标识；还要考虑订单状态、调用方权限和返回结果是否允许复用。

## 七、插入标记不代表业务处理成功

### 1. 教学代码

```java
if (map.putIfAbsent("1001", true) == null) {
    processOrder("1001");
}
```

可能出现以下过程：

1. `putIfAbsent()` 成功插入 `"1001" -> true`；
2. 开始执行 `processOrder()`；
3. 订单处理抛出异常；
4. Map 中的映射仍然存在，因为 Java 不会自动把此前的 Map 操作撤销。

如果客户端再次提交同一个订单，`putIfAbsent()` 会发现 Key 已存在并返回旧值，`== null` 条件不成立，因此不会再次进入 `processOrder()`。

### 实际回答与评估

用户独立判断：第二次请求不会执行 `processOrder()`，因为 Map 中仍然有该 Key。

随后在问题引导下，用户也正确指出，单独的 `true` 只能证明 Map 中有这个映射，无法判断订单究竟正在处理中还是已经处理成功；真实业务状态需要有明确的状态管理和可靠的数据来源。

**评估：核心判断通过。** 已理解“登记标记”和“业务成功”不是同一件事。

### 2. 失败后删除标记：只是简化思路，不是通用生产方案

教学中介绍了失败后删除标记、允许后续请求再次尝试的思路：

```java
if (map.putIfAbsent("1001", true) == null) {
    try {
        processOrder("1001");
    } catch (RuntimeException e) {
        map.remove("1001", true);
        throw e;
    }
}
```

这段代码只是帮助理解“标记不会自动回滚”的示意，不应直接当成生产实现。

原因包括：

- 业务处理失败时，数据库写入或外部副作用可能已经部分成功；删除标记后直接重试，可能造成重复操作。
- 只捕获 `RuntimeException` 并不代表所有失败路径都已覆盖。
- 失败、处理中、成功等状态需要有清晰的生命周期与恢复策略。
- `remove(key, value)` 可以原子地比较当前映射并删除，但若另一个任务已删除并重新登记了相同的 Key/Value，旧任务仍可能删除新任务的映射。生产设计可能需要请求所有权标识、版本或持久化状态来避免误删。
- 本地 Map 不能提供跨服务器协调或持久化保证。

**可复用原则：** 先明确业务失败是否意味着可以安全重试，再决定如何清理标记；不能将“删掉 Map 中的 Key”当作业务回滚。

## 八、`remove(key)` 与 `remove(key, value)`

这是本次出现过误判、并在解释后纠正的知识点。

假设 Map 保存：

```java
map.put("1001", "SUCCESS");
```

### 1. 只传 Key

```java
map.remove("1001");
```

删除当前 Key 对应的映射，不要求原来的 Value 等于某个指定值。

### 2. 同时传 Key 和 Value

```java
map.remove("1001", "PROCESSING");
```

当前值是 `"SUCCESS"`，与 `"PROCESSING"` 不匹配，因此不会删除。

而：

```java
map.remove("1001", "SUCCESS");
```

因为 Key 和 Value 都匹配，所以会删除。

### 实际回答与评估

用户最初认为 `remove(key, value)` 也会直接把 Key 删除。经过对比解释后，能够正确复述：

> 虽然 Key 一样，但 Value 不匹配就不会删除；只有 Key 和当前 Value 都匹配，才会删除。

随后在 `"SUCCESS"` 与 `"SUCCESS"` 的同值场景中，用户正确判断会删除。

**评估：纠错后理解，建议以后间隔复测。**

## 九、Map 的内存边界：Java 服务重启后会怎样？

假设服务器 A 的 Map 中曾经登记订单 `1001`，但 Java 服务进程崩溃，随后重新启动并重新创建 Map。

如果没有额外的恢复机制，新创建的 Map 不会自动包含旧进程内存中的映射。因此，再次执行：

```java
map.putIfAbsent("1001", true);
```

在新 Map 中没有这个 Key 的条件下，插入会成功，返回 `null`。

与此同时，数据库中已经提交的订单不会仅因为 Java 服务重启而自动消失。

### 实际回答与评估

用户独立判断：服务进程重启后，原来的 Map 内存数据没有自动恢复，因此新 Map 会认为 Key 不存在并允许插入。

**评估：通过。**

这再次说明：进程内 Map 的生命周期与数据库持久化数据的生命周期不同。不能用本地 Map 作为跨重启、跨服务器的唯一幂等依据。

## 十、最后回忆 Day 96：ThreadLocal 的线程隔离

遵守训练顺序，在 Day 97 新知识训练完成后，最后回忆 Day 96 的一个核心知识点。

### 回忆题

```java
USER.set("1001");

CompletableFuture.runAsync(() -> {
    System.out.println(USER.get());
});
```

题目条件：异步任务由工作线程 B 执行；B 从未设置过 `USER`；没有额外的上下文传播机制。

### 实际回答

用户正确说明：

> `ThreadLocal` 是线程隔离的。A 执行 `USER.set("1001")`，异步任务在 B 中执行，B 读取的是自己线程中的值；B 从未设置过，因此输出 `null`。

**评估：间隔回忆通过。** 能解释线程隔离和不自动跨线程传播的原因。

## 十三、可复用的工程判断模型

以后遇到 `putIfAbsent()` 或类似的幂等代码，按以下顺序检查：

```text
1. 当前调用的对象是什么？
   ↓
   Map、数据库访问层，还是 Redis 等共享存储？
   ↓
2. 原子操作的作用范围是什么？
   ↓
   单个 Map、单个数据库约束，还是跨实例协调？
   ↓
3. Key 已存在时，方法返回什么？是否覆盖？
   ↓
4. 插入标记后，业务是否真的执行成功？
   ↓
5. 失败后，标记的生命周期和重试策略是什么？
   ↓
6. 多台服务器是否访问同一共享数据源？
   ↓
7. 是否有数据库唯一约束等最终防重机制？
   ↓
8. 服务重启、并发冲突、部分成功和重试时，结果是否正确？
   ↓
9. 是否有测试或运行证据验证这些结论？
```

**一句话总结：** `putIfAbsent()` 只能保证当前 Map 中这次检查并插入操作的原子性；它不检查数据库，不共享不同服务器的本地 Map，也不自动保证业务失败后的重试正确性。

### 后续轻量复习方向

下一次遇到本地 Map 防重代码时，使用一个不同的业务例子，检验能否在没有提示的情况下区分：

- 当前 Map 中的标记；
- 数据库中已提交的业务数据；
- 数据库唯一约束；
- 业务执行状态和失败重试。

在能独立说明这些边界后，再继续深入更完整的幂等设计与验收。
