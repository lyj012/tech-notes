# Redis 缓存穿透、缓存击穿、缓存雪崩

## 一、今天的知识点是什么

Redis 缓存系统中常见的三类可靠性问题：

- 缓存穿透（Cache Penetration）
- 缓存击穿（Cache Breakdown）
- 缓存雪崩（Cache Avalanche）

核心目标：避免缓存异常导致数据库承受巨大压力。

---

# 二、AI 平台业务场景

例如任务查询接口：

```http
GET /task/{taskId}
```

正常流程：

```
Client
 ↓
Redis
 ↓
MySQL
```

Redis 未命中时才查询数据库。

如果缓存策略设计不合理，大量请求会绕过缓存直接访问 MySQL。

---

# 三、缓存穿透

## 定义

查询一定不存在的数据。

例如：

```
taskId=-1
taskId=-2
taskId=-999999
```

流程：

```
Redis Miss
 ↓
MySQL查询
 ↓
不存在
```

特点：

> 不存在的数据持续访问数据库。

解决方案：

## 1. 布隆过滤器

请求进入系统后先判断数据是否可能存在。

不存在的数据直接拒绝，避免访问数据库。

## 2. 缓存空值

例如：

```
task:-1 = NULL
TTL = 60秒
```

注意：空值缓存时间不能过长，避免数据恢复后仍返回空结果。

---

# 四、缓存击穿

## 定义

某个热点 Key 过期，大量请求同时访问数据库。

例如：

```
taskId=10001
```

原本：

```
Redis:
task:10001
TTL=30分钟
```

过期后：

```
大量请求
 ↓
Redis Miss
 ↓
MySQL
```

解决方案：

## 1. 分布式锁

只有一个线程查询数据库并重建缓存。

其他线程等待缓存恢复。

## 2. 热点数据永不过期

通过后台刷新保证热点 Key 一直存在。

---

# 五、缓存雪崩

## 定义

大量缓存 Key 在同一时间失效。

例如：

```
10000个缓存
TTL全部30分钟
```

30分钟后：

```
Redis大量Miss
 ↓
MySQL压力暴涨
```

解决方案：

## TTL增加随机值

例如：

```
30分钟 + random(0~5分钟)
```

避免大量 Key 同时过期。

---

# 六、线上故障分析案例

现象：

```
数据库CPU飙升
Redis正常
```

排查发现：

```
taskId=-1
 taskId=-2
 taskId=-999999
```

属于缓存穿透。

同时：

```
taskId=10001
缓存刚好过期
```

属于缓存击穿。

最终数据库压力来源：

```
无效请求穿透缓存
+
热点请求击穿缓存
+
MySQL承受大量查询
```

---

# 七、面试表达

> 在实际系统中，需要区分缓存穿透、缓存击穿和缓存雪崩。对于缓存穿透，可以使用布隆过滤器和空值缓存过滤不存在的数据；对于热点 Key 击穿，可以使用分布式锁或后台刷新机制；对于缓存雪崩，需要通过 TTL 随机化和缓存预热避免大量缓存同时失效。同时需要结合监控指标和日志定位数据库压力来源。

# 八、思考总结

## 问题1

|问题|原因|
|-|-|
|缓存穿透|查询不存在的 taskId|
|缓存击穿|热点 taskId=10001 缓存过期|

## 问题2

Redis正常不代表系统正常。

如果大量请求无法命中缓存，数据库仍然可能成为压力瓶颈。

## 问题3

设计策略：

- 不存在数据：布隆过滤器 + 空值缓存
- 热点数据：分布式锁 + 主动刷新
- 大量缓存：TTL随机化 + 预热

## 问题4

所有缓存统一30分钟可能导致缓存雪崩。
