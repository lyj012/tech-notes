# 后端工程化每日训练 Day 47：API 向后兼容、版本演进与滚动发布复盘

## 一、今天学习什么

今天主要学习：

- API 为什么本质上是一份“契约”
- 什么叫向后兼容（Backward Compatibility）
- 为什么新增字段通常比删除、改名更安全
- `name → username` 应该如何分阶段迁移
- 为什么“前后端一起发版”仍然不能忽略兼容性
- Kubernetes 滚动发布时为什么 V1、V2 Pod 会同时存在
- 新增请求参数什么时候应该给默认值，什么时候应该升 API 版本
- 为什么“只是增加一个枚举值”也可能把旧 Java 客户端搞挂
- 数据库 Schema 的 `Expand → Migrate → Contract` 演进模式
- Kafka 消息为什么也存在版本兼容问题
- 字段名不变、语义变化为什么属于更危险的 Breaking Change
- 公共 API 做重大升级时，如何让 V1、V2 在几周甚至几个月内稳定共存
- Docker、镜像仓库、Jenkins、Kubernetes 各自负责什么

今天最核心的判断：

> 系统升级不是“新代码能运行就结束了”，而是要让旧客户端、旧服务、旧 Pod、旧消息和新版本在迁移窗口内能够同时存在，并且业务仍然稳定。

---

# 二、API 本质上是一份契约

以前容易把接口理解成：

```text
URL + 请求参数 + 返回 JSON
```

但真正的 API 契约还包括：

```text
URL
HTTP Method
请求字段
字段类型
字段是否必填
返回字段
状态码
错误码
枚举值
字段语义
单位
null / 空集合行为
```

例如原接口返回：

```json
{
  "id": 1,
  "name": "Tom"
}
```

旧前端、旧 App、其他 Java 服务可能都已经写了：

```java
user.getName();
```

或者：

```javascript
user.name
```

这时候后端直接把：

```text
name
```

改成：

```text
username
```

即使：

```text
后端编译成功
单元测试成功
新前端也改好了
```

仍然可能造成生产故障。

原因是：

> API 一旦被其他调用方使用，字段本身就已经成为外部依赖的一部分。

---

# 三、什么叫向后兼容

假设线上已经存在：

```text
V1 客户端
```

现在服务端升级成：

```text
V2
```

如果：

```text
V1 客户端完全不修改
仍然能够正常调用 V2 服务端
```

那么可以认为：

```text
V2 对 V1 向后兼容
```

例如原返回：

```json
{
  "id": 1,
  "name": "Tom"
}
```

现在只是增加：

```json
{
  "id": 1,
  "name": "Tom",
  "avatar": "xxx"
}
```

旧客户端仍然只读取：

```text
id
name
```

通常不会关心新增加的：

```text
avatar
```

因此这种修改通常比较安全。

今天需要记住一个非常重要的原则：

> **Prefer Additive Changes：优先新增，而不是直接删除、改名、改类型。**

# 四、为什么删除字段风险明显更大

例如原接口：

```json
{
  "id": 1,
  "name": "Tom"
}
```

如果后端直接删除：

```text
name
```

变成：

```json
{
  "id": 1
}
```

旧客户端仍然可能执行：

```java
user.getName();
```

此时可能出现：

```text
拿到 null
反序列化失败
页面字段不显示
业务逻辑异常
```

这里今天纠正了一个表达：

不是简单说：

```text
“后面的请求还会用 name”
```

更准确的是：

```text
旧前端
旧 App
其他服务
旧 Pod
第三方调用方
```

仍然可能依赖这个字段。

# 五、name → username 为什么不能一次改完

假设产品要求：

```text
name
↓
username
```

错误做法：

```text
今天把 name 删除
今天新增 username
前端也一起改
直接发布
```

这样会要求：

```text
所有调用方必须在同一时刻升级成功
```

现实生产环境很难保证。

更合理的迁移方式：

## 第一阶段：新增新字段，保留旧字段

```json
{
  "id": 1,
  "name": "Tom",
  "username": "Tom"
}
```

此时：

```text
旧调用方 → 继续读取 name
新调用方 → 开始读取 username
```

## 第二阶段：推动调用方迁移

逐个迁移：

```text
Web
Android
iOS
内部 Java 服务
第三方调用方
```

并监控：

```text
还有谁在使用 name？
旧接口还有多少请求？
```

## 第三阶段：废弃旧字段

当所有调用方已经迁移后：

```text
name → deprecated
```

继续保留一段观察窗口。

## 第四阶段：最终删除

确认：

```text
旧字段调用量 = 0
旧版本已经退出
观察期没有问题
```

再真正删除：

```text
name
```

完整流程：

```text
新增
↓
兼容
↓
迁移
↓
观测
↓
废弃
↓
删除
```

# 六、为什么“前端和后端一起发”仍然可能失败

今天回答时想到一个很典型的场景：

```text
20:00 前端开始发布
20:03 后端才发布完成
```

或者反过来。

这几分钟内，就可能出现：

```text
新前端 + 旧后端
```

或者：

```text
旧前端 + 新后端
```

因此所谓：

```text
“前后端今天一起发”
```

并不等于：

```text
“前后端在同一毫秒完成切换”
```

真正安全的迁移窗口里，应该尽量允许：

```text
旧客户端 + 旧服务端
旧客户端 + 新服务端
新客户端 + 旧服务端
新客户端 + 新服务端
```

这些组合至少在迁移期间能够工作。

# 七、Kubernetes 滚动发布为什么天然存在 V1 + V2

今天一开始把它理解成：

```text
“是不是按最坏情况假设 V1、V2 会同时存在”
```

这个理解不准确。

真正原因是：

> Kubernetes 的滚动发布机制本来就会让新旧 Pod 在一段时间内同时存在。

例如原来有 6 个 V1 Pod：

```text
V1 V1 V1 V1 V1 V1
```

开始滚动更新：

```text
V1 V1 V1 V1 V1 V2
```

继续更新：

```text
V1 V1 V1 V2 V2 V2
```

最后才变成：

```text
V2 V2 V2 V2 V2 V2
```

因此发布过程中，负载均衡收到一个请求后：

```text
可能命中 V1
也可能命中 V2
```

这不是异常状态，而是滚动发布的正常过程。

所以必须考虑：

```text
V1 能不能理解 V2 的数据？
V2 能不能兼容 V1 的数据？
数据库是否允许 V1、V2 同时运行？
MQ 消息是否允许新旧消费者同时存在？
```

# 八、新增请求参数：默认值还是新 API 版本

假设旧接口请求：

```json
{
  "productId": 1001
}
```

现在增加：

```text
channel
```

如果后端直接要求：

```text
channel 必填
```

旧客户端仍然发送：

```json
{
  "productId": 1001
}
```

那么就可能直接：

```text
参数校验失败
↓
400 Bad Request
```

这属于破坏向后兼容。

什么时候适合默认值？

如果：

```text
channel 不是业务核心必填
缺失时能够合理兜底
```

可以设计：

```java
String channel = request.getChannel();
if (channel == null) {
    channel = "UNKNOWN";
}
```

什么时候不应该硬塞默认值？

如果：

```text
没有 channel 就无法正确执行业务
channel 会影响核心业务语义
```

那么为了“看起来兼容”而填一个假的默认值，反而可能制造错误数据。

这种情况下更适合：

```text
保留旧 API
+
创建新版本 API
```

可以简单记：

> 能安全兜底，就优先兼容；不能安全兜底，就考虑新版本。

# 九、为什么新增枚举值也可能破坏旧客户端

今天这题一开始误以为：

```text
是不是服务端多加了一个校验
旧客户端没这个字段
所以校验失败
```

这个理解不对。

真正的问题是：

> 旧 Java 客户端可能根本不认识新的枚举值。

原状态：

```text
CREATED
PAID
CANCELLED
```

旧代码：

```java
switch (status) {
    case CREATED:
        break;
    case PAID:
        break;
    case CANCELLED:
        break;
    default:
        throw new RuntimeException();
}
```

新服务端增加：

```text
REFUNDING
```

旧客户端收到：

```text
REFUNDING
```

可能直接：

```text
进入 default
↓
抛异常
↓
业务失败
```

甚至有些 Java JSON 反序列化实现，在把字符串转换成枚举对象时就可能失败。

所以：

```text
“服务端只是增加枚举值”
```

不代表：

```text
“旧客户端一定兼容”
```

更健壮的调用方应该考虑：

```text
UNKNOWN
```

或者对未知枚举值进行容错。

这就是：

```text
Tolerant Reader
宽容读取者
```

思想的一部分。

# 十、数据库 Schema：Expand → Migrate → Contract

假设数据库字段也需要：

```text
name
↓
username
```

不能直接：

```sql
RENAME COLUMN name TO username;
```

因为滚动发布期间还有旧 Pod 在执行：

```sql
SELECT name FROM user;
```

或者：

```sql
INSERT INTO user(name) VALUES (?);
```

如果直接重命名，旧 Pod 会立刻出错。

更安全的模式是：

## 1. Expand

先扩展数据库能力：

```sql
ALTER TABLE user
ADD COLUMN username VARCHAR(100);
```

此时：

```text
name
username
```

同时存在。

旧代码继续使用：

```text
name
```

新代码逐步支持：

```text
username
```

## 2. Migrate

迁移历史数据：

```sql
UPDATE user
SET username = name
WHERE username IS NULL;
```

今天这里还纠正了 SQL 方向。

正确的是：

```text
username = name
```

因为目标是把旧字段 `name` 的数据迁到新字段 `username`。

迁移期间，新代码还可以根据实际情况：

```text
双写 name + username
```

或者兼容读取。

## 3. Contract

等到：

```text
所有旧 Pod 已退出
所有新代码只使用 username
历史数据迁移完成
```

再删除：

```text
name
```

所以：

```text
Expand
↓
Migrate
↓
Contract
```

本质就是：

```text
先扩大兼容能力
↓
完成迁移
↓
最后收缩旧能力
```

# 十一、为什么这种数据库迁移支持滚动发布和回滚

今天最初回答：

```text
“因为一步一步来，更稳定、可追溯”
```

这个方向不算错，但不够具体。

真正的工程原因是：

```text
name 和 username 在迁移窗口内同时存在
```

所以滚动发布期间：

```text
旧 Pod → 还能继续使用 name
新 Pod → 可以使用 username
```

两套代码都能运行。

如果 V2 发布以后发现 Bug，需要：

```text
回滚 V1
```

V1 仍然依赖：

```text
name
```

由于 `name` 还没有被删除，旧版本仍然能够启动和运行。

如果一开始就直接：

```sql
RENAME COLUMN name TO username;
```

那么回滚后的 V1 可能直接：

```text
Unknown column 'name'
```

也就是说：

> Contract 放在最后，不只是为了兼容，也是为了保留回滚能力。

# 十二、Kafka 消息也属于版本契约

假设 Kafka 中已经积压了一批旧格式消息。

旧格式：

```json
{
  "orderId": 10001,
  "amount": 999
}
```

消费者升级后只支持新格式：

```json
{
  "id": 10001,
  "totalAmount": 999
}
```

如果新消费者重新读取旧消息：

```text
读取旧消息
↓
解析 / 处理失败
↓
重试
↓
继续失败
↓
消费进度无法正常推进
↓
消息开始积压
```

今天还纠正了一个理解：

旧 Kafka 消息处理失败后，通常不是：

```text
“退回给生产者”
```

而是消费者侧可能：

```text
重试
阻塞
进入死信处理
或导致消费位点无法继续推进
```

具体行为取决于消费者实现。

Kafka 与 HTTP API 的共同本质是：

> 新版本不能假设旧世界会瞬间消失。

HTTP 中可能还存在：

```text
旧前端
旧 App
旧服务
旧 Pod
```

Kafka 中可能还存在：

```text
旧格式消息
```

所以两者本质上都是：

```text
版本契约兼容问题
```

# 十三、字段名不变但语义变化更加危险

原来：

```text
amount = 元
```

接口：

```json
{
  "amount": 500
}
```

表示：

```text
500 元
```

后来后端决定：

```text
amount = 分
```

字段名不改，类型也不改。

同样：

```json
{
  "amount": 500
}
```

现在却表示：

```text
500 分 = 5 元
```

这种变更非常危险。

因为旧调用方：

```text
解析完全成功
程序也不一定报错
```

但是业务语义已经错了。

例如支付场景可能出现：

```text
原本 500 元
↓
被当成 5 元
```

或者余额、充值、结算金额被错误解释。

这种错误比直接字段不存在更危险，因为它可能：

```text
没有异常
没有报错
业务却已经产生错误金额
```

这属于：

```text
Semantic Breaking Change
语义破坏性变更
```

所以 API 契约不仅包括：

```text
字段名
字段类型
```

还包括：

```text
字段含义
单位
边界条件
```

更合理的方式可以是新增一个语义明确的新字段，例如：

```text
amountCent
```

并让旧字段逐步废弃，而不是偷偷修改旧字段单位。

# 十四、重大公共 API 升级应该怎么做

假设一个公共用户接口被：

```text
Web 前端
Android
iOS
订单服务
支付服务
第三方合作方
```

同时使用。

现在返回结构必须做一次无法避免的重大 Breaking Change。

不能只回答：

```text
“那就加一个 /v2”
```

完整迁移方案应该包含以下过程。

## 1. 保留 V1

先继续维护：

```text
/api/v1/user
```

不能直接破坏已有生产调用方。

## 2. 发布 V2

重大结构变化使用：

```text
/api/v2/user
```

承载新的契约。

## 3. 新旧接口同时存在

迁移窗口可能持续：

```text
几周
甚至几个月
```

这段时间：

```text
V1 正常工作
V2 也正常工作
```

## 4. 逐个推动调用方迁移

例如：

```text
Web → V2
订单服务 → V2
支付服务 → V2
Android 新版本 → V2
iOS 新版本 → V2
第三方合作方 → V2
```

不能假设：

```text
所有调用方今天晚上同时升级
```

特别是：

```text
移动端
第三方合作方
```

往往无法强制瞬间升级。

## 5. 做流量监控

这里的“流量监控”不是只看：

```text
CPU
QPS 总量
```

而是要知道：

```text
谁还在调用 V1？
V1 每天还有多少请求？
哪个 Android / iOS 版本还在使用 V1？
哪个内部服务没有迁移？
第三方迁移了吗？
V1 / V2 错误率分别是多少？
```

如果发现：

```text
V1 每天还有几十万请求
```

说明：

```text
V1 仍然是生产依赖
```

不能删除。

## 6. 废弃通知

正确流程：

```text
标记 deprecated
↓
通知调用方
↓
提供 V2 文档和迁移方案
↓
给出迁移窗口
↓
持续跟踪迁移进度
```

而不是：

```text
今天 deprecated
明天删除
```

## 7. 滚动发布

应用发布时必须允许：

```text
V1 Pod
+
V2 Pod
```

同时存在。

因此：

```text
API
数据库
MQ
缓存结构
```

都应该在迁移窗口内保持兼容。

## 8. 数据库 Schema

数据库遵循：

```text
Expand
↓
Migrate
↓
Contract
```

不能为了 V2 一上线就把 V1 依赖的数据库字段删除。

## 9. 保留回滚能力

V2 发布后如果出现问题：

```text
能够回滚到 V1
```

因此在观察期内：

```text
旧字段不能过早删除
旧数据结构不能过早破坏
```

## 10. 最终清理

只有确认：

```text
V1 调用量 = 0
所有内部服务迁移完成
移动端旧版本低于淘汰阈值
第三方完成迁移
观察期无异常
回滚窗口结束
```

才进入：

```text
删除 V1
删除旧字段
删除兼容代码
删除旧监控
清理旧文档
```

这才是完整的 API 生命周期治理。

# 十五、为什么兼容层不能永久保留

兼容不是：

```text
旧接口永远留着
旧字段永远留着
旧逻辑永远留着
```

如果只新增不清理，几年以后可能出现：

```text
v1
v2
v3
legacy
old
new
new2
```

系统复杂度会持续上升。

所以完整生命周期一定是：

```text
引入
↓
兼容
↓
迁移
↓
观测
↓
废弃
↓
删除
```

兼容的目标是：

> 给新旧版本一个安全重叠窗口，而不是永久背负历史包袱。

# 十六、今天补充厘清：Docker、镜像仓库、Jenkins、Kubernetes

今天最后还把几个以前容易混淆的工程工具重新区分了一遍。

## 1. Docker 不是“存储环境”

一开始的理解接近：

```text
Docker = 发布环境的存储
K8s = 环境管理
```

这个理解不准确。

更准确的是：

```text
Docker
→ 把应用和运行依赖打包成镜像
→ 启动成容器
```

例如 Java 服务：

```text
Java 项目
↓
mvn package
↓
jar
↓
Dockerfile
↓
Docker 镜像
↓
容器运行
```

真正负责保存镜像的通常是：

```text
Docker Hub
Harbor
其他镜像仓库
```

所以可以区分：

```text
Docker 镜像 = 打包好的应用运行模板
镜像仓库     = 保存镜像
容器         = 镜像真正运行起来后的实例
```

## 2. Kubernetes 负责容器统一部署和管理

Kubernetes 更关注：

```text
Pod 调度
副本数量
故障重建
服务发现
负载均衡
扩缩容
滚动发布
```

例如：

```text
order-service:1.0
```

K8s 可以运行：

```text
Pod1 → order-service:1.0
Pod2 → order-service:1.0
Pod3 → order-service:1.0
```

某个 Pod 挂了：

```text
K8s → 重新创建
```

流量增大：

```text
3 Pod → 6 Pod
```

发布 2.0：

```text
逐步把 1.0 Pod 替换成 2.0 Pod
```

## 3. Jenkins 更偏向 CI/CD 自动化流水线

以前手工部署可能需要：

```text
拉代码
↓
mvn package
↓
导出 jar
↓
上传服务器
↓
停止旧服务
↓
启动新服务
```

配置 Jenkins 后，这些步骤可以变成流水线：

```text
代码提交 / 点击构建
↓
拉代码
↓
编译
↓
测试
↓
打包
↓
构建镜像
↓
推送镜像仓库
↓
触发部署
```

所以 Jenkins 和 K8s 不是同一个层面的东西。

可以简单记：

> Jenkins 管“从代码到部署”的自动化流程，K8s 管“部署之后这些容器怎么运行”。

## 4. 公司里它们通常会配合

典型流程：

```text
Git 提交代码
↓
Jenkins
↓
编译 + 测试
↓
Docker 构建镜像
↓
推送 Harbor
↓
更新 Kubernetes 部署
↓
K8s 拉取新镜像
↓
滚动发布新的 Pod
```

因此可以形成一个清晰的职责边界：

```text
Git       → 保存源码
Jenkins   → 自动化 CI/CD 流程
Docker    → 打包并运行容器
Harbor    → 保存镜像
K8s       → 统一部署和管理容器
```

# 十七、今天暴露出来的几个易混点

## 1. “兼容”不能只看新代码能不能运行

真正需要考虑：

```text
旧调用方还能不能运行
新旧版本能不能共存
出现问题还能不能回滚
```

## 2. API 字段迁移和数据库字段迁移不是一回事

API：

```text
name + username 双字段返回
↓
调用方迁移
↓
旧字段废弃
```

数据库：

```text
Expand
↓
Migrate
↓
Contract
```

二者思想相似，但层次不同。

## 3. K8s 新旧版本同时存在不是“最坏假设”

而是：

```text
滚动发布的正常过程
```

## 4. Kafka 消息失败不会自动“退回生产者”

更常见的是：

```text
消费失败
重试
阻塞
积压
```

具体行为由消费者策略决定。

## 5. 新增东西也不一定永远安全

虽然：

```text
新增字段通常更安全
```

但：

```text
新增必填参数
新增严格枚举值
改变字段语义
```

仍然可能是 Breaking Change。

# 十八、今天最终形成的工程判断

今天最重要的不是记住几个 API 规则，而是建立“系统演进”的思维。

以前容易想：

```text
需求改了
↓
代码改完
↓
测试通过
↓
发布
↓
结束
```

现在应该进一步考虑：

```text
谁在调用旧版本？
发布过程中有没有版本组合？
数据库能不能同时支持新旧代码？
MQ 里还有没有旧消息？
移动端能不能强制升级？
第三方什么时候迁移？
发布失败还能不能回滚？
什么时候才能真正删除旧能力？
```

最终可以把今天的核心总结成一句话：

> **可演进系统的关键，不是让所有组件同时升级，而是允许新旧世界在一段时间内安全共存，然后通过迁移、观测、废弃和清理逐步完成切换。**
