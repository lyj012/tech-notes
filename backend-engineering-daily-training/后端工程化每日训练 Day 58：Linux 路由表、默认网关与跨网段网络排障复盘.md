# 后端工程化每日训练 Day 58：Linux 路由表、默认网关与跨网段网络排障复盘

## 一、今天学习什么

今天继续沿着 Linux 网络与监控排障往下学习，核心解决一个真实工作里非常常见的问题：

```text
服务器网卡 UP
IP 配置正常
同网段设备可以访问

但是

跨网段交换机 SNMP Timeout
数据库 Connection timed out
某个网段设备全部采集失败
```

这类问题不一定出在：

```text
Java
SNMP
OID
Community
数据库账号密码
目标设备
```

也可能根本还没有走到应用层，而是卡在：

```text
Linux 路由
默认网关
ACL
防火墙
VPN
中间网络
回程路由
```

今天重点学习：

- IP、子网掩码、默认网关分别解决什么问题
- 同网段为什么通常可以直接通信
- 跨网段为什么必须先查路由
- `ip route` 怎么读
- Linux 为什么优先选择更具体的路由，而不是所有流量都走默认网关
- 路由错误为什么可能表现为 `Connection timed out`
- 为什么 Ping 通默认网关仍然不能证明远端目标可达
- 为什么 SNMP Timeout 不应该一开始就在 OID / Community 里打转
- 多网卡服务器为什么可能选错出口
- Codex 应该查源码里的什么，Linux / 网络环境又必须实际验证什么

今天最重要的主线：

```text
目标 IP
↓
判断目标属于哪个网段
↓
查询路由表
↓
选择最匹配的路由
↓
选择出口网卡
↓
选择下一跳
↓
数据包真正发出去
```

今天最重要的排障原则：

> 先证明数据有没有路能到目标，再讨论目标上的服务是否正常。

## 二、IP、子网掩码、默认网关分别干什么

假设服务器配置：

```text
IP：192.168.10.20
掩码：255.255.255.0
默认网关：192.168.10.1
```

当前阶段可以先这样理解：

```text
IP
=
我是谁

子网掩码
=
哪些 IP 和我是同一个本地网络

默认网关
=
如果目标不在本地网络，而且没有更具体的路由，我默认先把数据交给谁
```

这三个概念不能混成一件事。

服务器知道自己的 IP，并不代表它天然知道任何目标应该从哪里走。

真正决定数据包下一步路径的是：

```text
Linux 路由表
```

---

## 三、同网段为什么通常不走默认网关

服务器：

```text
192.168.10.20/24
```

目标：

```text
192.168.10.50
```

`/24` 当前可以先理解成：

```text
前 24 位表示网络部分
```

所以两台机器都属于：

```text
192.168.10.0/24
```

Linux 会判断：

```text
目标和我在同一个本地网段
↓
不需要先交给默认网关
↓
直接从本地网卡发给目标
```

今天答题时这一点判断是正确的：

```text
192.168.10.20/24
→
192.168.10.50
```

通常不需要先经过：

```text
192.168.10.1
```

可以先记：

```text
同网段
→
通常直接通信
```

---

## 四、跨网段为什么必须先查路由

服务器还是：

```text
192.168.10.20/24
```

现在访问：

```text
10.20.30.40
```

Linux 一看就会发现：

```text
10.20.30.40
不属于
192.168.10.0/24
```

所以它不能按照本地同网段的方式直接发送。

正确过程不是：

```text
发现跨网段
→
无脑走默认网关
```

而是：

```text
发现目标不在本地网段
↓
查询路由表
↓
看看有没有更具体的目标路由
↓
有具体路由就走具体路由
↓
没有更具体的路由才考虑默认路由
```

今天答题时一开始把“跨网段”直接理解成“走默认路由”，这个需要纠正。

真正关键的是：

> 跨网段以后，先查路由表，而不是先认定一定走默认网关。

## 五、`ip route` 到底怎么看

Linux 常用命令：

```bash
ip route
```

例如看到：

```text
default via 192.168.10.1 dev ens33

192.168.10.0/24 dev ens33

10.30.0.0/16 via 192.168.10.254 dev ens33
```

### 第一条

```text
default via 192.168.10.1 dev ens33
```

用自己的话解释就是：

```text
如果没有更具体的路可以走
就从 ens33 出去
把数据交给 192.168.10.1
```

这就是默认路由。

---

### 第二条

```text
192.168.10.0/24 dev ens33
```

意思不是简单的“这是路由表”。

它是路由表中的一条具体规则：

```text
如果目标属于 192.168.10.0/24
就直接从 ens33 这张网卡出去
```

今天答题后已经把这条理解清楚：

```text
目标是 192.168.10.x
→
直接走 ens33
```

---

### 第三条

```text
10.30.0.0/16 via 192.168.10.254 dev ens33
```

意思是：

```text
如果目标属于 10.30.x.x
就从 ens33 出去
先交给 192.168.10.254
```

所以路由表本质上就是：

> 一张“去哪里应该走哪条路”的规则表。

---

## 六、为什么不是所有流量都走默认网关

假设路由表里同时存在：

```text
default via 192.168.10.1

10.30.0.0/16 via 192.168.10.254
```

现在访问：

```text
10.30.5.20
```

Linux 会发现这个目标明确匹配：

```text
10.30.0.0/16
```

于是会优先走：

```text
10.30.0.0/16 via 192.168.10.254
```

而不是：

```text
default via 192.168.10.1
```

当前阶段可以先记一句：

> 有专门的路就走专门的路；没有更具体的路时才走默认路由。

所以默认网关不是：

```text
所有网络请求必须经过的总开关
```

更像是：

```text
没有找到更明确路径时的兜底下一跳
```

---

## 七、为什么路由错误会表现成 Timeout

假设 Java 服务：

```text
192.168.10.20
```

访问 OceanBase / OBProxy：

```text
10.50.1.10:2883
```

Java 发起：

```text
connect()
```

但 Linux 路由不正确。

可能出现：

```text
Java
↓
TCP
↓
Linux 网络栈
↓
查询路由
↓
没有正确路径 / 走错下一跳
↓
请求到不了数据库
↓
一直收不到正常响应
↓
Connection timed out
```

这时候：

```text
数据库用户名
数据库密码
```

不是高优先级排查项。

因为：

```text
网络路径都没有打通
↓
数据库认证可能根本还没开始
```

今天答题时这一点已经判断正确：

> 网络不可达时，没有必要先深挖账号密码。

所以排障时要先区分：

```text
网络可达
↓
协议 / 端口可达
↓
认证
↓
业务
```

不能看到 `Connection timed out` 就直接进入应用配置。

## 八、Ping 默认网关成功为什么仍然可能访问不了目标

假设：

```text
服务器
Ping 192.168.10.1 成功
```

但是：

```text
10.50.1.10
完全访问不了
```

这两个现象并不矛盾。

因为 Ping 通默认网关只能证明：

```text
服务器
→
默认网关
```

这一小段基本正常。

完整路径其实是：

```text
服务器
↓
默认网关
↓
中间网络
↓
目标服务器
```

后面仍然可能出现：

```text
网关没有去目标网段的路由
ACL 阻断
防火墙阻断
VPN 路由改变
中间链路故障
目标服务器不可达
回程路由错误
```

所以今天需要留下一个很实用的判断：

```text
能到默认网关
≠
能到远端目标
```

同样：

```text
网卡 UP
≠
所有网络都正常
```

## 九、去程正常也不代表回程一定正常

网络通信通常是双向的。

例如：

```text
Collector
192.168.10.20
↓
交换机
10.20.1.50
```

请求有可能已经成功到达交换机。

但是设备返回时：

```text
10.20.1.50
↓
中间网络
↓
192.168.10.20
```

如果返回路径配置错误，Collector 仍然收不到响应。

最终看到的还是：

```text
SNMP Timeout
```

所以复杂网络故障不能只问：

```text
请求能不能过去？
```

还要问：

```text
响应能不能回来？
```

也就是：

```text
去程路由
+
回程路由
```

都可能出问题。

## 十、它在监控系统里为什么重要

监控系统本质上不断发生网络通信：

```text
Collector
↓
SNMP GET
↓
交换机 / 路由器 / 防火墙
```

以及：

```text
Agent
↓
Push
↓
监控 Server
```

还有：

```text
Java Server
↓
OceanBase / IoTDB / Pika
```

这些链路最终都依赖：

```text
正确 IP
+
正确路由
+
正确网关 / 下一跳
+
中间网络允许
+
正确回程路径
```

所以：

> 有些“Java 问题”或“SNMP 问题”，根因实际上根本不在 Java 源码和 SNMP 配置里。

这是今天非常重要的工程判断。

## 十一、真实场景：同网段能采，10.30 网段全部 Timeout

假设 Collector：

```text
192.168.10.20
```

可以正常采集：

```text
192.168.10.50
```

但是：

```text
10.30.5.20
SNMP Timeout
```

并且：

```text
OID
Community
SNMP 配置
```

都确认正常。

这时候不应该继续长时间陷在：

```text
OID 是不是错了？
Community 是不是错了？
模板是不是错了？
```

而应该提高这些方向的优先级：

```text
10.30 网段路由
网关 / 下一跳
ACL
防火墙
VPN
中间网络
回程路由
```

先执行：

```bash
ip route
```

看：

```text
有没有 10.30.x.x 对应的路由？
应该走哪张网卡？
下一跳是谁？
```

需要进一步确认单个目标实际匹配哪条路时，还可以结合：

```bash
ip route get 10.30.5.20
```

今天答题时已经抓到关键点：

> 192.168.10.x 能采，只能证明本地这个范围的通信基本正常，不能证明 10.30.x.x 的公共网络路径也正常。

如果是：

```text
192.168.10.x 全部正常
10.30.x.x 全部异常
```

应该优先找：

```text
10.30 网段的共同故障域
```

而不是假设几十台设备同时各自坏掉。

## 十二、如果所有设备突然一起 Timeout 怎么想

假设：

```text
100 台设备
```

突然同时：

```text
SNMP Timeout
```

而 Collector 进程还在。

优先级应该放到公共路径：

```text
Collector 网卡
↓
本机 IP
↓
路由表
↓
默认网关 / 下一跳
↓
上联网络
↓
ACL / 防火墙 / VPN
```

而不是：

```text
100 台设备是不是同时坏了？
```

同样，如果只有一个网段全部异常：

```text
192.168.x.x 正常
10.20.x.x 全部异常
10.30.x.x 正常
```

就应该把范围快速收缩到：

```text
10.20 网段对应的公共路径
```

这就是监控排障里很重要的思维：

> 找共同故障域。

## 十三、多网卡服务器为什么会出现“某个网络完全不通”

Linux 服务器可能同时有：

```text
ens33
192.168.10.20

ens34
10.10.1.20
```

现在访问：

```text
10.20.1.50
```

应用代码通常不能简单决定：

```text
这个包一定从 ens33 走
```

或者：

```text
这个包一定从 ens34 走
```

真正的出口主要由：

```text
Linux 路由表
```

决定。

如果路由配置错误：

```text
本来应该从 ens34 走
↓
却匹配成 ens33
```

就可能出现：

```text
某个网段完全不可达
```

所以以后看到多网卡服务器上的网络问题，需要额外问：

```text
目标到底匹配了哪条路由？
最终选了哪张网卡？
```

## 十四、今天常见错误判断复盘

### 错误 1：网卡 UP，所以网络正常

错误。

```text
ens33 = UP
```

只能说明网卡接口已经启用。

后面还有：

```text
IP
路由
网关
ACL
防火墙
VPN
目标主机
```

---

### 错误 2：Ping 默认网关成功，所以远程网络正常

错误。

只能先证明：

```text
服务器
→
本地网关
```

这一段基本正常。

---

### 错误 3：跨网段就一定直接走默认网关

不准确。

正确逻辑：

```text
跨网段
↓
查路由表
↓
先匹配更具体的路由
↓
没有更具体规则才走默认路由
```

---

### 错误 4：Timeout 就先检查用户名密码

优先级不对。

如果网络路径根本不存在：

```text
认证阶段都可能还没开始
```

---

### 错误 5：Collector 能采一台设备，所以 Collector 网络没问题

错误。

如果它只能采：

```text
192.168.10.50
```

只能证明对应网络路径正常。

不能继续推出：

```text
10.30.5.20
也一定可达
```

---

### 错误 6：只看去程，不看回程

错误。

```text
请求到达目标
```

不等于：

```text
响应一定能正确返回 Collector
```

---

### 错误 7：发现缺路由就直接在生产环境随手加

不应该这么做。

正确顺序应该是：

```text
确认这个目标确实应该由当前服务器访问
↓
确认网络设计里应该走哪个网关 / 哪张网卡
↓
确认当前确实缺少正确路由
↓
再按现场规范修改
↓
重新验证
```

排障的目标是找到根因，不是看到一个现象就立即改生产配置。

## 十五、Collector 访问远程设备失败的分层排查

以后遇到：

> Collector 访问某个远程设备失败。

可以按下面顺序排：

```text
第一层：确认目标

目标 IP 配对了吗？
↓

第二层：确认本机

网卡 UP？
IP 正确？
↓

第三层：判断网段

目标和 Collector 同网段还是跨网段？
↓

第四层：检查 Linux 路由

ip route
ip route get <目标IP>

目标匹配哪条路？
从哪张网卡出去？
下一跳是谁？
↓

第五层：检查下一跳

网关 / 下一跳能到吗？
↓

第六层：中间网络

路由器
ACL
防火墙
VPN
交换网络
↓

第七层：目标设备

设备在线吗？
↓

第八层：协议

SNMP UDP 161？
TCP 端口？
↓

第九层：应用 / SNMP

Agent 是否正常？
Community？
OID？
模板？
↓

第十层：监控链路

失败结果
→
状态判断
→
存储
→
告警
→
后端接口
→
前端
```

这套顺序的核心不是死背十层，而是：

> 不要在网络还没证明可达之前，就直接钻进应用和模板细节。

## 十六、Codex 和 Linux / 网络环境应该怎么分工

今天综合题是：

> Collector 可以采集 192.168.10.x 的交换机，但所有 10.30.x.x 设备全部 SNMP Timeout。哪些问题让 Codex 从源码里找，哪些问题必须去 Linux / 网络环境验证？

### Codex 负责回答“程序是怎么做的”

可以让 Codex 追：

```text
deviceIp
host
target
collector
timeout
socket
snmp
ping
reachability
```

重点确认：

```text
设备 IP 从哪里读取？
↓
Collector 如何拿到目标设备？
↓
SNMP 请求在哪里构造？
↓
请求发向哪个 IP / 端口？
↓
timeout 配置是多少？
↓
有没有网段过滤、黑名单、特殊判断？
↓
失败结果如何处理？
↓
如何判断 offline / unavailable？
↓
结果如何存储、告警并返回前端？
```

也就是说：

> Codex 主要帮忙确认“程序想访问谁、怎么发、失败以后怎么处理”。

---

### Linux / 网络环境负责回答“包到底能不能走”

必须实际验证：

```text
ip route
ip route get <目标IP>

有没有去 10.30.x.x 的路？
走哪张网卡？
下一跳是谁？
网关能不能到？
ACL 有没有拦？
防火墙有没有拦？
VPN 有没有改路由？
回程路径是否正确？
```

因为：

```text
Java / Collector 代码
↓
通常只是把数据交给操作系统网络栈
↓
真正选哪条网络路径
主要由 Linux 路由配置决定
```

今天最后形成了一句很实用的边界：

> Codex 查“程序怎么发”；Linux 查“包到底怎么走”。

## 十七、交给 Codex 的真实调查目标

以后工作里遇到：

> Collector 可以采集 192.168.10.x，但所有 10.30.x.x 设备 SNMP Timeout。

可以直接把完整调查目标交给 Codex，而不是自己机械搜一堆零散关键词：

```text
帮我追踪“为什么 Collector 可以采集 192.168.10.x 的设备，但 10.30.x.x 设备全部 SNMP Timeout”的项目源码链路。

重点定位：

1. 目标设备 IP 从哪里读取和组装。
2. 哪个 Collector / 任务负责 SNMP 采集。
3. SNMP 请求在哪里创建和发送。
4. 实际请求的目标 IP、端口、版本、Community 从哪里来。
5. 是否存在按 IP、网段、设备类型进行过滤或跳过采集的逻辑。
6. timeout、retry 在哪里配置。
7. 请求失败后如何区分 timeout、其他异常和正常返回。
8. 失败次数如何累计，何时判定设备 / 监控项异常。
9. 采集结果如何进入存储、告警和后端接口。
10. 前端哪个页面最终显示 SNMP Timeout / DOWN。
```

## 十八、今天训练问题复盘

### 问题 1：192.168.10.20/24 访问 192.168.10.50

结论：

```text
通常不需要先交给默认网关
```

因为：

```text
两者都属于 192.168.10.0/24
```

所以属于同网段通信。

---

### 问题 2：192.168.10.20/24 访问 10.20.30.40

结论：

```text
目标不在本地网段
↓
先查询路由表
```

今天需要纠正的是：

```text
不是一发现跨网段
就直接认定走默认路由
```

而是：

```text
先看有没有更具体路由
没有才走 default
```

---

### 问题 3：解释两条 `ip route`

```text
default via 192.168.10.1 dev ens33
```

表示：

```text
没有更具体的路时
从 ens33 出去
交给 192.168.10.1
```

而：

```text
192.168.10.0/24 dev ens33
```

表示：

```text
目标属于 192.168.10.x
就直接从 ens33 出去
```

---

### 问题 4：本地网段能采，10.30.5.20 SNMP Timeout

在 OID / Community / SNMP 配置确认正常以后：

```text
优先检查 10.30 网段路由和公共网络路径
```

而不是继续在模板里反复打转。

---

### 问题 5：Java 访问 10.50.1.10:2883 timed out，且没有 default / 目标路由

结论：

```text
当前服务器没有可用的目标网络路径
```

数据库用户名和密码不是高优先级排查项。

---

### 问题 6：Ping 默认网关成功，但 10.50.1.10 不可达

结论：

```text
不矛盾
```

因为 Ping 网关只证明：

```text
服务器
→
网关
```

不能证明：

```text
网关
→
中间网络
→
目标服务器
```

也全部正常。

---

### 问题 7：Codex 和 Linux 怎么分工

今天最终理解：

```text
Codex
→
追采集源码、目标地址、请求构造、超时、失败处理、状态判断、前端链路

Linux / 网络
→
验证路由、出口网卡、下一跳、ACL、防火墙、VPN、去程和回程
```

如果已经证明：

```text
Java / Collector 确实向 10.30.5.20:161 发请求
代码没有禁止采集
Linux 又明确没有正确目标路由
```

那么当前阻塞点已经在网络层。

此时继续深挖 Java 的收益很低。

正确做法是先按照网络设计确认并修复路由问题，再重新验证；如果网络打通后仍然 Timeout，再继续往 SNMP / Java 采集链路排查。

## 十九、今天真正需要记住的内容

不需要死记所有路由命令和网络协议细节，当前阶段先牢牢记住下面几条。

### 1. 同网段通常直接通信

```text
192.168.10.20/24
→
192.168.10.50
```

通常不需要先走默认网关。

---

### 2. 跨网段先查路由表

```text
目标不在本地网段
↓
查 route
```

不是直接默认走网关。

---

### 3. 更具体的路由优先于默认路由

```text
有专门的路
→
走专门的路

没有
→
才走 default
```

---

### 4. `ip route` 是网络排障的核心基础命令之一

需要回答三个问题：

```text
目标匹配哪条路？
从哪张网卡出去？
下一跳是谁？
```

---

### 5. Timeout 不等于账号密码错误

```text
网络路径都没通
↓
认证可能还没发生
```

所以先证明网络可达。

---

### 6. 能 Ping 网关不等于能到远端目标

```text
服务器 → 网关 正常
```

只证明完整链路中的一小段。

---

### 7. 去程和回程都要考虑

```text
请求能过去
≠
响应一定能回来
```

---

### 8. 整个网段一起异常，要找共同故障域

```text
10.30.x.x 全部异常
```

优先想：

```text
路由
网关
ACL
防火墙
VPN
公共链路
```

而不是几十台设备同时坏掉。

---

### 9. Codex 和系统环境要各司其职

```text
Codex
→
程序怎么发、怎么处理

Linux / 网络
→
包到底怎么走
```

---

### 10. 排障的本质是逐层缩小故障域

```text
目标 IP
↓
本机网卡 / IP
↓
同网段还是跨网段
↓
路由
↓
下一跳
↓
中间网络
↓
目标设备
↓
协议 / 端口
↓
SNMP / Java 应用
↓
状态判断
↓
前端
```

今天真正建立的不是“会背一条 `ip route`”，而是开始能够看到 `SNMP Timeout`、`Connection timed out` 时，不再默认只盯着 Java、OID 或账号密码，而是先判断故障到底发生在哪一层。
