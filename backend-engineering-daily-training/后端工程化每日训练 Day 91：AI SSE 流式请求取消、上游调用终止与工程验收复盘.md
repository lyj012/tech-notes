## 二、真实场景：前端停止了，后台一定停止了吗？

假设 Spring Boot 实现一个 AI 聊天接口，服务端调用第三方大模型，并通过 SSE 持续把结果返回浏览器。

~~~text
浏览器
  │
  │ 连接 A：浏览器 ←→ Spring Boot 的 SSE 连接
  ▼
Spring Boot
  │
  │ 连接 B：Spring Boot ←→ 第三方模型 API 的上游请求/响应流
  ▼
第三方 AI 模型服务
~~~

模型正在生成一篇长文章。用户点击「停止生成」：

~~~text
用户点击停止
    ↓
浏览器关闭或取消 SSE 请求（连接 A）
    ↓
页面不再显示新文字
    ↓
连接 B 是否取消？—— 不能仅凭上述现象确定
~~~

本题刻意给定：**只知道前端关闭了 SSE，未观察到后端主动取消上游模型请求。**

关键判断：

- 用户不再接收文字，说明用户侧的接收链路停止；
- Spring Boot 是否收到取消信号、是否把取消传递给上游调用，需要单独验证；
- 第三方服务商是否真的停止生成、费用如何结算，还取决于上游协议、客户端实现及服务商行为。

**客户端连接关闭 ≠ 上游请求必然取消 ≠ 模型侧计算必然立即结束。**

## 三、核心机制：取消需要跨越调用边界

用一个简化模型理解：

~~~text
浏览器发起「停止」
    ↓
前端终止 SSE 接收
    ↓
后端感知取消（需要实现/验证）
    ↓
后端取消仍在进行的上游请求或流订阅（需要实现/验证）
    ↓
上游连接/响应流以取消原因结束（需要观察）
    ↓
模型侧实际停止与 Token 计费（需结合服务商能力、记录与规则核实）
~~~

两个特别容易混淆的地方：

1. **「停止显示」不等于「停止计算」**。即使浏览器没有后续内容，后端和模型仍可能继续工作。
2. **取消上游调用，不一定需要再给模型发送一句「请停止生成」的提示词**。实际方案可以利用 HTTP 请求中止、响应流订阅取消、取消信号传播，或服务商明确支持的取消 API；具体路径应由真实客户端、SDK、框架和 API 能力决定。

还要注意：并不是调用了一个名为 cancel 的方法，就能直接宣称模型内部计算已停止。取消是一个涉及多个参与者、需要观测结果的过程。

## 四、第 1 题：浏览器断开 SSE，模型一定停止吗？

### 题目

用户点击停止 → 浏览器关闭 SSE → Spring Boot 正在调用第三方模型。问：第三方模型一定停止生成吗？为什么？

### 我的回答（按实际口述整理）

> 应该不会停止生成吧。第三方 AI 是另外的接口。我一开始觉得后端还需要发要求让它停止，但又想到，前端点击停止可能只是后端不把后续内容传过来了。

### 评估与纠错

**主结论正确；取消手段出现过混淆，经讲解后建立了连接边界的直觉。**

- 正确：前端 SSE 关闭，不保证模型请求停止。
- 需要纠正：不能把「发送一条停止提示词」当作标准的取消协议。
- 需要记住：浏览器到后端和后端到模型服务商是两个不同的调用边界。

该题可以证明已有基本直觉，但不能证明已掌握 Java 异步流的实际取消传播实现。

## 五、第 2 题：停止显示后，Token 费用可能继续产生吗？

### 题目

用户已停止，SSE 已关闭；Spring Boot 没有取消上游模型请求，第三方模型仍在生成。问：Token 消耗是否还可能继续？

### 我的回答（按实际口述整理）

> 仍然会消耗 Token。因为没有取消第三方模型请求，模型还在往后生成。只是用户看不到，也没有把后续内容传给前端。

### 评估

**独立答对，并能解释因果关系。**

~~~text
用户看不到文字
    ≠
模型不再生成
    ↓
如果上游实际仍在生成
    → 就可能产生额外 Token 消耗及相关资源占用
~~~

边界：**实际计费并不能仅由浏览器显示情况推断**。不同供应商的计量口径和取消结算规则可能不同；输入 Token、已经生成的输出 Token 等，也不能简单认为点击停止后全部免费或全部取消计费。

## 六、第 3 题：Codex 说「前端停止显示」，能直接验收吗？

### 题目

Codex 表示：点击停止后，前端关闭 SSE，页面不再输出文字，功能已完成。问：作为后端工程师能直接验收吗？

### 我的回答（按实际口述整理）

> 不能。点击停止只是前端不显示文字。还要看后端是不是继续生成、是不是继续调用第三方接口，必须搞清楚后端有没有真正停止。

### 评估

**独立答对，具备基础的 AI 方案审查意识。**

不能只把前端视觉表现当作功能验收标准。至少要区分：

| 验收维度 | 要证明什么 | 仅看前端是否足够 |
| --- | --- | --- |
| 用户体验 | 停止后页面不再出现新内容 | 可以观察到一部分 |
| 后端取消行为 | 取消信号被接收并向上游传播 | 不足够 |
| 上游请求结束 | 上游请求/流确实以取消等可辨认原因结束 | 不足够 |
| 费用与资源 | 无效生成是否减少，资源是否释放 | 不足够 |

今天是对一个假设方案的判断，**没有实际打开 Codex 提交或运行自动化验收测试**。

## 七、第 4～5 题：怎样证明上游真的被取消？

### 第 4 题：首次提出验证思路

**问题：** Codex 声称已修复停止生成，如何验证不是只停止前端显示？

**我的首次回答（按实际口述整理）：**

> 直接看第三方 API 调用和 Token 消耗量。点击停止后，观察还会不会继续生成、Token 是否继续消耗。

**评估：方向正确，但单独依靠 Token 统计不够严谨。**

纠错重点：

- 第三方 Token 用量统计可能延迟；
- 停止前已经生成的 Token 可能照常计费；
- 用量较低并不能证明正确发出了取消；
- 同时存在其他请求时，账号级总用量也不一定能准确对应单次操作。

Token 用量是**辅助证据**，不是唯一、直接的取消确认。

### 第 5 题：无法实时查看 Token 用量时看什么？

**问题：** 服务商的 Token 统计数分钟后才更新；只能查看 Spring Boot 日志，如何判断取消？

**我的回答（按实际口述整理）：**

> 看第三方接口调用是不是还在继续，后端是不是还在收到或输出内容。

**评估：能够想到检查上游调用，但缺少明确的取消事件、结束原因和同一请求的关联证据；经提示后补齐思路。**

建议为单次流式请求建立可关联的观察记录，例如：

~~~text
[requestId=101] 上游 AI 请求开始
[requestId=101] 接收到用户/客户端取消信号
[requestId=101] 向上游请求传播取消
[requestId=101] 上游响应流终止，观察到原因=CANCELLED
[requestId=101] 清理本次请求关联资源
~~~

上面是**期望观察的日志设计示意，不是本次真实运行产出的日志**。其中「原因=CANCELLED」必须根据真实客户端或流终止信号判断，不能在调用取消方法后就无条件记录为「取消成功」。

验证时还需要区分以下结果：

- **正常完成**：模型恰好已经生成完；
- **用户取消**：主动取消且取消信号沿链路传播；
- **超时/网络断开/异常**：被动结束，不能误报成用户取消；
- **仅本地不再消费**：尚不能证明上游计算已结束。

此外，「日志里没有新 Token」也可能只是日志不再写入，不能独立证明模型内部已停止。

**情况 B：**

### 评估

**独立答对，完成简单工程证据迁移。**

## 九、今天实际建立的 AI / Codex Review 模型

今天没有审阅真实代码，但已经通过口头场景训练出一条合理的审查路径：

~~~text
Codex 声称「停止生成功能完成」
    ↓
第一问：前端是否真的停止接收、停止渲染？
    ↓
第二问：后端能否感知取消，并传播到对应上游请求？
    ↓
第三问：能否观察上游请求以何种原因终止？
    ↓
第四问：重复、并发、正常完成与主动取消是否能够区分？
    ↓
第五问：是否能用请求级日志/指标和服务商用量信息交叉验证？
    ↓
最后：有证据再验收，不根据 Codex 自述直接放行
~~~

**验收时可以设计的最小测试：**

1. 发起足够长的流式回答，确认正在持续返回内容；
2. 中途点击停止，记录请求 ID 与停止时间；
3. 检查前端停止接收、后端捕获取消事件；
4. 检查对应上游请求的取消传播与终止原因；
5. 重复若干次，避免把「恰好生成完」误判为取消成功；
6. 在服务商支持的前提下，用请求级用量或结算记录进行辅助核验。

这是**后续真实工程可执行的验收设计**，不是本日已经实际执行的测试记录。若真实系统还有异步队列、代理层或后台持久化任务，则还需对那些独立生命周期的任务分别定义取消语义，不能默认 SSE 关闭会取消所有工作。

## 十、最重要的工程边界与 Trade-off

### 1. 用户取消、网络断连、服务端超时不一定相同

这些事件可能都导致响应流结束，但业务含义和日志原因不同。实现应避免把所有连接关闭都当成用户点击停止。

### 2. 取消是协作过程，不是强制保证上游瞬时停止

取消信号能否传播到底层 HTTP 客户端、SDK 是否支持取消、模型服务商是否响应取消，都需要查具体实现和 API 行为。取消与正常完成之间也可能发生竞态。

### 3. 降低 Token 消耗是目标，不是单靠一次日志就能证明的结果

应同时考虑用户体验、无效算力、API 成本、连接/线程资源释放、并发取消安全，以及取消后的可观测性和计费规则。

### 4. 不预设具体 Java 实现

真正把需求交给 Codex 时，应明确目标、现象、风险、约束与验收标准，让能读取真实项目的 Codex 确认使用了什么 Web/SSE 框架、HTTP 客户端和模型 SDK，再决定取消如何实现。不能在没有查看代码时指定必须修改哪个类、使用哪个操作符或哪种异步框架。

## 十二、上一正式训练日 Day 90 回忆：FOR UPDATE 为什么读到 1？

按照 V3.3，今天的新知识理解与工程判断完成后，最后才安排旧知识回忆。

### 题目

条件：MySQL InnoDB，隔离级别为 REPEATABLE READ；无其他事务阻塞；A 自己未修改该行。

~~~sql
-- 初始 status = 0

-- 事务 A
START TRANSACTION;
SELECT status FROM orders WHERE id = 1;
-- 得到 0

-- 事务 B（另一个连接）
START TRANSACTION;
UPDATE orders SET status = 1 WHERE id = 1;
COMMIT;

-- 事务 A 尚未结束
SELECT status FROM orders WHERE id = 1 FOR UPDATE;
-- 问：得到 0 还是 1？为什么？
~~~

### 我的回答（按实际口述整理）

> 读到的是 1。因为后面有 FOR UPDATE。没有 FOR UPDATE 的普通 SELECT，在这个事务里可能仍查到旧数据，涉及 MVCC；加了 FOR UPDATE 就是要查当前的数据，所以是 1。

回答时仍将关键字口述为近似「full update」的读音。

### 评估与纠错

**结果独立答对，并能区分普通快照读和 FOR UPDATE 当前读，回忆通过。**

- 普通非锁定 SELECT 在本题 RR 条件下可以继续依据旧 Read View 读取旧版本；
- SELECT ... FOR UPDATE 属于当前读/锁定读取，在 B 已提交且不受冲突锁阻塞的条件下，读到 1；
- FOR UPDATE **不是执行 UPDATE**，也不是单纯「强制刷新缓存」；
- 锁定读取带有加锁效果，不能为了看到新值而无差别给查询加锁。

需要实事求是：本次回忆**没有单独要求我完整解释 Read View 可见性规则与 Undo 如何重建历史版本**。Day 90 文档里曾记录这部分隔天回忆不稳定，今天不能据此认定那个薄弱点已彻底解决。今天能确认的是**快照读与当前读的结果区别已能独立复述**。

## 十四、今天真正值得保留的判断模型

> **前端停止显示 ≠ 后端停止处理 ≠ 上游模型请求结束 ≠ 计算与计费立即停止。**

工程验收不能停留在「按钮可点击、页面不出字、Codex 说已完成」：

1. **分清边界**：浏览器—后端 SSE 与后端—模型 API 是不同链路；
2. **验证传播**：看取消信号是否传递到对应上游调用；
3. **验证结果**：看请求结束原因及资源清理，而非仅看界面；
4. **交叉核验**：用请求级日志/指标配合 Token 用量和服务商规则；
5. **保留不确定性**：上游取消能证明到哪一层，就只宣称到哪一层。

这条机制还可以迁移到文件导出、长 SQL 查询、异步后台任务等场景：**用户不再等待结果，不表示服务端所有工作都会自动停止。**

**Day 91 的学习价值，不在于背诵 SSE API，而在于学会对 AI 生成的功能提出可验证的取消语义和验收证据。**
