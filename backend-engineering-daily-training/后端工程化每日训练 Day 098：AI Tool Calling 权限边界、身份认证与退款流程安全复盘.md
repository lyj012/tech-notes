## 二、先教学：什么是 Tool Calling？

### 1. 它解决什么问题？

普通大语言模型主要根据输入上下文生成内容，本身不能凭空读取业务数据库中的实时订单，也不能直接执行 Java 服务中的退款方法。

如果希望 AI 助手查询订单、创建任务或申请退款，可以由后端向模型提供可用工具的名称、参数结构和用途。

例如：

~~~json
{
  "name": "getOrderStatus",
  "arguments": {
    "orderId": 1001
  }
}
~~~

模型判断需要查询订单时，会生成结构化的工具调用请求。Java 后端接收请求、识别工具、校验参数，再调用对应的业务服务，并把结果返回给模型。

一个简化的数据流：

~~~text
用户发起请求
    ↓
Java 后端接收用户请求
    ↓
模型根据上下文决定是否提出 Tool Calling
    ↓
模型返回工具名称和参数
    ↓
Java 后端校验工具、身份、权限和业务规则
    ↓
执行允许的业务操作
    ↓
将工具执行结果返回模型
    ↓
模型组织最终答复
~~~

### 2. 模型与后端的职责边界

| 参与方 | 负责什么 | 不应该负责什么 |
| --- | --- | --- |
| AI 模型 | 理解用户意图、提出工具调用请求、组织回答 | 自行认证用户、自行授予权限、绕过业务规则 |
| Java 后端 | 识别工具、验证参数、获取可信身份、执行授权和业务校验 | 无条件相信模型传入的参数 |
| 业务服务 / 数据库 | 执行业务规则、持久化状态、处理并发约束 | 把模型生成的请求直接当成可信业务事实 |

**核心直觉：模型输出的是请求，不是授权凭证。**

即使模型返回了 refundOrder，也不意味着当前用户有权退款，更不意味着订单当前可以退款。

## 三、先建立权限模型：操作权限、资源权限与业务状态

今天的退款场景逐渐引入了三个不同层次的判断。

| 层次 | 核心问题 | 示例 |
| --- | --- | --- |
| 操作权限 | 当前用户有没有退款资格？ | 用户是否具有退款权限 |
| 资源权限 | 当前用户能否操作这笔具体订单？ | 订单是否属于当前用户，或用户是否具有管理员授权 |
| 业务状态 | 这笔订单当前是否允许退款？ | 是否已支付、是否已经退款、是否存在处理中退款 |

这三个判断不能互相替代。

例如：

- 用户 A 有退款权限，不代表他可以退款用户 B 的订单。
- 订单属于用户 A，不代表订单已经退款成功后还能再次退款。
- 用户有权限且订单属于自己，也不代表大额退款可以绕过审批规则。

对于普通用户自助退款，通常要同时验证操作权限、订单归属和订单状态。管理员、客服等跨用户操作角色则应有明确、独立的授权规则，不能简单假设所有角色都只能操作自己的订单。

## 四、真实问答：从工具请求到退款权限边界

以下按当天实际互动整理。保留用户原本的判断、犹豫和纠错过程，不把经解释后才掌握的内容改写成一开始就独立答对。

### 第 1 题：AI 请求退款，后端是否必须执行？

**题目条件：**

- 用户 A 只有订单查询权限，没有退款权限。
- AI 模型返回 refundOrder(orderId=1001)。
- Java 后端已经确认用户 A 没有退款权限。

**我的回答（按口述整理）：**

> 肯定不能退款。用户没有退款权限，就不能因为 AI 模型要求退款而给他退款。AI 模型想退款也不行，退款应该走相应的权限和审批规则。

**评估：核心判断通过。**

用户理解了模型请求和后端执行权限不是一回事。

**补充纠偏：** 退款并不是所有场景都必须人工审批。是否需要人工审批，应由业务规则决定，例如金额阈值、风险等级或特殊订单类型。人工审批不能替代后端权限校验；即使审批通过，也不能绕过身份和资源授权。

### 第 2 题：用户有退款权限，但订单属于别人

**题目条件：**

- 用户 A 拥有退款权限。
- 订单 1001 属于用户 B。
- AI 请求退款订单 1001。
- 后端只检查用户是否具有退款权限。

**我的回答（按口述整理）：**

> 用户 A 怎么能给用户 B 退款？A 只能给自己退款，不能因为自己有退款权限，就去操作 B 的订单。

**评估：通过。**

用户独立识别出仅检查操作权限是不够的，还必须检查具体资源的归属关系。

这里的普通用户自助退款场景应检查：

~~~java
if (!order.getUserId().equals(currentUserId)) {
    throw new AccessDeniedException("无权操作该订单");
}
~~~

这只是资源归属检查的最小示例。实际系统还要考虑管理员、客服等经过明确授权的跨用户操作角色。

### 第 3 题：订单已经退款成功，还能再次退款吗？

**题目条件：**

- 用户 A 拥有退款权限。
- 订单 1001 属于用户 A。
- 订单已经退款成功。
- 后端已经通过用户权限和订单归属检查。

**我的回答（按口述整理）：**

> 得看吧。如果金额合适的话可以退款，大笔金额的话还是要审批。

**评估：未通过首次验证，经纠正后理解。**

这里漏掉了题目最重要的条件：订单已经退款成功。

金额大小和审批规则不能改变已经退款成功的事实。已经退款成功的订单不能再次执行退款，否则可能产生重复资金操作。

需要区分：

- 有权限：用户是否有资格发起退款。
- 有资源权限：用户是否有权操作这笔订单。
- 状态允许：订单当前是否仍处于允许退款的状态。
- 幂等控制：相同退款请求重复到达时，不能重复产生资金副作用。

例如：

~~~text
订单状态：REFUNDED
       ↓
再次收到退款请求
       ↓
后端读取并校验当前订单状态
       ↓
发现已经退款成功
       ↓
拒绝再次执行退款，按业务规则返回已有结果
~~~

**本题的关键结论：** 有权限、有权操作资源，不等于当前可以执行操作。

### 第 4 题：大额退款是否可以绕过审批？

**题目条件：**

- 用户 A 有退款权限。
- 订单 1001 属于用户 A。
- 订单状态为 PAID，尚未退款。
- 退款金额为 8000 元。
- 业务规定超过 5000 元必须人工审批。
- AI 请求执行退款。

**我的回答（按口述整理）：**

> 肯定不能直接退款。八千元超过五千元，必须走人工审批，先显示待审批状态。

**评估：通过。**

用户能根据明确的业务阈值判断不能直接执行退款，而应先创建退款申请。

需要区分退款申请状态与订单状态：

~~~text
退款申请：PENDING_APPROVAL（待审批）
订单状态：PAID（已支付）
~~~

创建待审批申请，不代表退款已经成功，也不应该提前把订单标记成 REFUNDED。

### 第 5 题：审批延迟期间，订单已经退款成功

**题目条件：**

- 用户 A 已提交 8000 元退款申请。
- 退款申请状态为 PENDING_APPROVAL。
- 十分钟后审批人员点击通过。
- 这十分钟内，另一个业务流程已经将订单退款成功。

**我的回答（按口述整理）：**

> 应该不行。审批人员点击通过后，如果后端直接调用退款方法，可能又重复退款。应该单独设计退款流程，退款时还要修改状态，并且加上幂等性。

**评估：核心风险识别通过，关键校验动作经补充后理解。**

用户独立意识到了重复退款和重复点击的风险，也提出了状态管理和幂等控制。

需要进一步明确：审批通过并不代表可以无条件执行退款。审批人员点击通过后，后端必须重新检查订单的最新状态。不能依赖十分钟前创建申请时的旧状态。

同时需要区分两个对象：

| 对象 | 示例状态 | 含义 |
| --- | --- | --- |
| 退款申请 | PENDING_APPROVAL | 正在等待审批 |
| 订单 | REFUNDED | 订单已经退款成功 |

如果另一个业务流程已经将订单退款成功，那么当前审批流程应终止重复退款，按业务规则将申请标记为已处理、失效或冲突，而不是再次调用支付渠道。

**可复用原则：审批通过是一个新的业务执行时点，必须重新校验当前数据，不能把申请创建时的检查结果永久当成有效。**

### 第 6 题：两名审批人员同时点击通过

**题目条件：**

退款申请初始状态为 PENDING_APPROVAL。审批人员 A 和 B 几乎同时点击通过，执行：

~~~sql
UPDATE refund_application
SET status = 'APPROVING'
WHERE id = 1001
  AND status = 'PENDING_APPROVAL';
~~~

假设 A 先成功更新，B 随后执行。

**我的回答（按口述整理）：**

> A 执行完之后，状态已经更新了。B 再执行时就不满足原来的状态条件了，所以 A 会影响一行，B 不会影响。最终由 A 继续执行后面的流程。

**评估：通过。**

在题目给定的执行顺序和数据库条件更新语义下：

| 执行者 | 执行结果 | 影响行数 |
| --- | --- | ---: |
| A | 将 PENDING_APPROVAL 更新为 APPROVING | 1 |
| B | 当前状态已改变，不再满足 WHERE 条件 | 0 |

这利用数据库原子条件更新控制同一退款申请的并发竞争。

**重要边界：** 这条 SQL 只解决同一退款申请的处理资格竞争。它本身不能保证订单没有被其他业务流程退款，也不能单独保证外部支付渠道只退款一次。审批流程取得处理资格后，仍然要检查订单最新状态，并对实际退款执行设置可靠的幂等控制。

另外，A 获胜是题目指定 A 先更新成功的结果；真实并发中谁先成功不能预先确定。

## 五、身份边界：AI 提供的 userId 能不能相信？

### 1. 为什么不能把 userId 交给模型决定？

假设当前登录用户 A 的 ID 是 100，但模型返回：

~~~json
{
  "name": "refundOrder",
  "arguments": {
    "userId": 200,
    "orderId": 1001
  }
}
~~~

如果 Java 后端直接使用模型返回的 userId，就可能拿着错误的用户身份执行后续业务。

模型可能根据对话内容错误提取用户 ID，也可能生成错误参数。具体原因并不重要：**模型输出的工具参数属于不可信输入，不能作为身份认证依据。**

**我的实际反应（按口述整理）：**

> 我很疑惑，用户登录之后不就应该使用登录的 ID 吗？为什么还会误传一个 ID？后端应该根据登录的 ID 获取用户 ID。

**评估：核心方向正确。**

用户主动发现了身份来源问题：当前登录用户是谁，应该由后端认证机制确定，而不是由 AI 参数决定。

### 2. SecurityContext 到底是什么？

这里需要纠正一个术语理解：Spring Security 的 SecurityContext 不是 AI 对话上下文，也不是模型随便提供的一个 ID。

在典型的 Spring Security Servlet 请求处理中，认证流程会验证用户提交的身份凭证，并将已认证的 Authentication 放入 SecurityContext。业务代码可以从可信的认证上下文中取得当前用户身份。

简化流程：

~~~text
用户提交登录凭证
    ↓
后端认证机制验证身份
    ↓
建立已认证的 Authentication
    ↓
保存到当前请求的 SecurityContext
    ↓
业务代码获取已认证用户
    ↓
使用该身份进行权限和资源校验
~~~

示意代码：

~~~java
Authentication authentication =
    SecurityContextHolder.getContext().getAuthentication();

// 项目中 principal 的具体类型由认证实现决定
LoginUser loginUser = (LoginUser) authentication.getPrincipal();

Long currentUserId = loginUser.getId();
~~~

这里的 LoginUser 是示意类型，实际项目需要使用自己的 Principal 类型，并确认 Authentication 已经认证成功。

**准确表述：** 后端应该从经过认证的身份信息中获取当前用户 ID。SecurityContext 是 Spring Security 提供的一种承载认证信息的机制，不是仅凭使用这个类就自动获得安全保证；前提是认证链配置正确，业务代码也没有不安全地伪造或覆盖认证信息。

### 3. 为什么 Tool Calling 不需要让模型传 userId？

普通用户退款工具可以只暴露订单 ID：

~~~json
{
  "name": "refundOrder",
  "arguments": {
    "orderId": 1001
  }
}
~~~

Java 后端自行从当前认证信息中获取用户 ID，再执行授权。

这样可以减少模型参数中不必要的身份字段，避免把模型生成的 userId 当成真实身份。

**我的回答（按口述整理）：**

> 应该直接去拿登录用户的 ID，或者校验传入的 ID 和登录的 ID 是否一致。退款就应该给登录的用户退款，不能相信其他 ID。

**评估：通过。**

比较两个 ID 可以作为额外的参数一致性检查，但不能把 AI 提供的 ID 当作身份来源。即使两个 ID 恰好相同，真正用于后续业务判断的也应该是后端认证上下文中的 currentUserId。

### 4. 关于异步执行的额外注意

Spring Security 的 SecurityContext 在典型 Servlet 配置下默认与线程上下文有关。若后续把 Tool Calling 执行转移到异步线程或线程池，不能想当然地认为认证上下文一定自动传播。

对于异步任务，可以在经过认证的请求边界由后端取得当前用户 ID，再把这个可信值显式传给任务；不能改为使用 AI 传入的 userId。

这部分只记录为后续学习提醒，本日没有专项验证 Spring Security 异步上下文传播机制。

## 六、AI Code Review：审查 Codex 生成的退款代码

### 1. 待审查代码

~~~java
public void executeTool(ToolRequest request) {

    Long userId = request.getUserId();
    Long orderId = request.getOrderId();

    Order order = orderMapper.selectById(orderId);

    if (order != null) {
        refundService.refund(userId, orderId);
    }
}
~~~

### 2. 我的实际回答

**我的回答（按口述整理）：**

> request 得到了 userId 和 orderId，然后根据 orderId 查询订单。现在只是判断 order 不为 null，就直接退款。是不是应该加权限校验？要看这个订单有没有权限退款，不能这么随意退款。

**评估：部分通过。**

用户独立发现了“只检查订单是否存在，就直接退款”的问题，知道还需要权限检查。

但当时没有主动识别出第一行的身份来源风险：

~~~java
Long userId = request.getUserId();
~~~

这里的 userId 来自 ToolRequest，可能是 AI 模型生成的参数，不能作为当前登录用户身份的可信来源。

### 3. 完整的 Review 方向

| 代码问题 | 风险 | 应有的检查 |
| --- | --- | --- |
| userId 来自 request | AI 参数可能冒充其他用户 | 从后端认证上下文取得 currentUserId |
| 只判断 order != null | 订单存在不代表当前用户有权操作 | 检查资源归属或明确的角色授权 |
| 没有退款权限检查 | 无退款权限的用户也可能触发退款 | 检查操作权限 |
| 没有检查订单状态 | 已退款或其他不允许状态可能再次退款 | 校验最新业务状态 |
| 直接调用 refundService | 可能绕过大额退款审批规则 | 根据金额和业务策略决定直接执行或创建审批申请 |
| 没有体现幂等控制 | 重试、重复点击可能重复执行资金操作 | 设计请求幂等键和状态流转，并对外部退款调用做幂等处理 |

### 4. 一个更合理的伪代码结构

以下仅用于表达职责顺序，不是可直接复制到生产环境的完整实现：

~~~java
public RefundResult executeTool(ToolRequest request) {

    // 1. 从后端可信的认证信息获取当前用户
    Long currentUserId = currentUserProvider.requireCurrentUserId();

    // 2. AI 只提供业务参数
    Long orderId = request.getOrderId();

    // 3. 查询订单并确认存在
    Order order = orderMapper.selectById(orderId);
    if (order == null) {
        throw new OrderNotFoundException();
    }

    // 4. 检查当前用户是否有权操作这笔订单
    authorizationService.checkCanRefund(currentUserId, order);

    // 5. 检查订单当前状态是否允许退款
    refundPolicy.checkCanRequestRefund(order);

    // 6. 根据金额、审批规则和幂等策略创建或执行退款流程
    return refundApplicationService.handle(currentUserId, order);
}
~~~

这段伪代码强调的是：

- currentUserId 来自后端认证信息，不来自模型参数。
- 订单存在性、用户操作权限、资源归属和业务状态是不同的检查。
- 退款申请、人工审批和实际退款执行应由业务流程统一管理。
- 不能因为模型请求了退款，就绕过已有业务规则直接调用资金操作。

**本日 Review 结果：** 能发现缺少权限校验，但身份来源风险、状态检查、审批和幂等等问题是在后续教学中逐步补齐的。不能记作一次完整的独立代码审查。

## 七、三个需要特别区分的业务状态与机制

### 1. 退款申请状态不等于订单状态

例如：

| 业务对象 | 状态 | 含义 |
| --- | --- | --- |
| 退款申请 | PENDING_APPROVAL | 等待人工审批 |
| 退款申请 | APPROVING | 已取得审批处理资格，正在处理 |
| 退款申请 | REJECTED | 审批拒绝 |
| 订单 | PAID | 已支付 |
| 订单 | REFUNDING | 退款处理中 |
| 订单 | REFUNDED | 已退款成功 |

实际项目的状态机可以不同，但必须明确每个状态属于哪个业务对象，不能把“退款申请待审批”误认为“订单退款处理中”或“订单已经退款成功”。

### 2. 数据库条件更新不等于完整的资金幂等

~~~sql
UPDATE refund_application
SET status = 'APPROVING'
WHERE id = 1001
  AND status = 'PENDING_APPROVAL';
~~~

它可以帮助控制同一个退款申请只有一个并发请求取得处理资格。

但真实退款还涉及：

- 订单可能已被其他流程退款；
- 业务服务可能在数据库更新后、调用支付渠道前后失败；
- 支付渠道可能已经执行退款，但应用没有收到响应；
- 客户端或模型可能重复发起相同工具调用。

因此，生产系统通常还需要订单状态的原子流转、稳定的退款幂等键、外部支付渠道的幂等能力，以及失败后的查询、补偿或对账机制。

**本日只验证了条件更新的基础推理，没有设计或实测完整资金幂等系统。**

### 3. 认证、授权和业务规则不是一回事

| 概念 | 回答的问题 |
| --- | --- |
| Authentication（认证） | 当前用户是谁？ |
| Authorization（授权） | 当前用户能做什么、能操作哪些资源？ |
| Business validation（业务校验） | 当前业务状态是否允许执行？ |
| Idempotency（幂等） | 相同请求重复到达时，是否会重复产生业务副作用？ |

不能用“用户已经登录”替代授权，也不能用“用户有退款权限”替代订单状态检查。

## 八、最后回忆 Day 97：ConcurrentHashMap.putIfAbsent()

遵守 V3.3 的训练顺序：先完成 Day 98 新知识训练，再回忆上一正式训练日 Day 97。

### 回忆题

~~~java
ConcurrentHashMap<String, String> map =
    new ConcurrentHashMap<>();

map.put("1001", "旧订单");

String result = map.putIfAbsent("1001", "新订单");
~~~

### 我的回答（按口述整理）

用户先回忆了 putIfAbsent() 的核心机制：

> 它把检查和插入合在一起，保证原子性。

随后结合题目判断：

> 前面已经 put 了 1001 旧订单，所以 putIfAbsent 检查时发现 Key 已经存在，不会覆盖。最终 Map 保存的还是旧订单，result 得到的也是旧值。

**评估：通过。**

| 项目 | 正确结果 |
| --- | --- |
| 最终 Map | 1001 -> 旧订单 |
| result | 旧订单 |
| 原因 | Key 已存在，不覆盖原值，并返回原来的 Value |

补充 API 边界：

| 调用前状态 | 调用后 Map | 返回值 |
| --- | --- | --- |
| Key 不存在 | 插入新映射 | null |
| Key 已存在 | 保留原映射 | 返回原来的 Value |

本题中旧订单已经提前插入，没有发生并发竞争。因此，本题直接验证的是 Key 已存在时不覆盖并返回旧值；原子性是该方法在并发调用场景下的重要保证。

**评估边界：** 本次完成的是 Day 97 的一个核心 API 回忆题，不代表重新验证了 Day 97 的所有多实例、数据库唯一约束、条件删除和失败重试知识。

## 十一、可复用的 Tool Calling 安全判断模型

以后审查 AI Agent、Tool Calling 或 AI 生成的工具执行代码，可以按以下顺序检查：

~~~text
1. 模型请求调用了哪个工具？
   ↓
2. 这个工具是否是后端明确注册、允许调用的工具？
   ↓
3. 工具参数是否经过格式、类型和业务范围校验？
   ↓
4. 当前真实登录用户是谁？
   ↓
   从后端认证结果获取，不相信模型提供的 userId
   ↓
5. 当前用户是否具有该操作权限？
   ↓
6. 当前用户是否有权操作指定资源？
   ↓
7. 资源当前状态是否允许执行？
   ↓
8. 是否需要人工审批、二次确认或其他业务流程？
   ↓
9. 并发请求、重复点击、网络重试时是否会重复执行？
   ↓
10. 外部副作用失败或结果不确定时，如何恢复、查询和对账？
   ↓
11. 是否有测试和运行证据证明设计正确？
~~~

**一句话总结：** AI 只负责提出工具调用请求；Java 后端必须以可信认证身份为起点，独立完成工具校验、操作授权、资源归属、业务状态、审批和幂等控制，最后才决定是否执行。
