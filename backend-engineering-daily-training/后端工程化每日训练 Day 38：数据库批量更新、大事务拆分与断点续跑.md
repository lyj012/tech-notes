# 后端工程化每日训练 Day 38：数据库批量更新、大事务拆分与断点续跑

## 一、今天学习的知识点

今天学习的是：

**数据库批量更新与大事务拆分（Batch Processing）、短事务、主键游标推进、Checkpoint 断点续跑、幂等、限速以及生产环境批处理任务的资源保护。**

一句话理解：

> 百万级 UPDATE / DELETE 不应该只考虑“SQL 能不能执行”，更应该考虑事务会有多大、会锁多少数据、失败如何回滚、能不能拆批、能不能断点续跑，以及会不会影响在线业务。

前几天连续学习了：

```text
数据库索引与慢 SQL
↓
乐观锁
↓
悲观锁
↓
事务隔离级别
↓
死锁与锁等待
↓
数据库原子更新
```

今天继续往真实生产环境推进：

```text
一条 SQL 语法完全正确
≠
适合直接在生产环境执行
```

例如：

```sql
UPDATE monitor_data
SET status = 1
WHERE create_time < '2026-01-01';
```

假设它一次命中：

```text
500 万行
```

SQL 本身可能没有任何语法错误，业务条件也可能完全正确，但仍然可能成为一次高风险生产操作。

今天重点解决这些问题：

```text
为什么一次 UPDATE / DELETE 几百万行很危险
为什么大事务不仅是“慢”
为什么拆批可以降低回滚成本
为什么拆批后仍然要考虑锁和数据库资源
为什么不能使用超大 OFFSET 做批处理
last_id / 主键游标是什么
Checkpoint 为什么重要
Checkpoint 和幂等为什么必须一起考虑
为什么批次不是越小越好
为什么数据库 CPU 很高时批处理必须减速
为什么拆批后仍然应该优先在业务低峰执行
一个生产级批处理任务应该具备哪些基本能力
```

## 二、一次修改几百万行，危险在哪里

假设数据库中有：

```text
monitor_data：3000 万条
```

现在需要把 2026 年以前的数据统一修改状态：

```sql
UPDATE monitor_data
SET status = 1
WHERE create_time < '2026-01-01';
```

命中：

```text
500 万条
```

如果一次性执行，数据库可能经历：

```text
扫描符合条件的数据
↓
修改 500 万行
↓
维护相关索引
↓
生成 Undo / Redo
↓
持有大量锁
↓
持续消耗 CPU / IO
↓
最终 COMMIT
```

这时不能只看：

```text
这条 SQL 最终能不能成功
```

还要看：

```text
执行期间数据库是否还能稳定服务在线业务
```

因此大批量数据操作的风险，本质不是单一的“SQL 慢”，而是：

```text
大事务
+
长时间资源占用
+
大范围锁竞争
+
高日志压力
+
高失败回滚成本
+
对在线业务的持续影响
```

---

## 三、大事务为什么不仅仅是执行时间长

今天一个重要认知是：

```text
大事务的问题
≠
只是执行得慢
```

它至少包含下面几类成本。

### 1. 锁持有时间长

如果一个事务修改大量数据：

```text
事务开始
↓
持续修改几百万行
↓
长时间不提交
```

那么事务涉及的锁可能长期存在。

这期间其他业务如果也需要修改相同或相邻数据范围，就可能出现：

```text
锁等待
↓
接口响应变慢
↓
事务堆积
↓
连接占用时间增长
↓
进一步放大数据库压力
```

这里需要注意：

> 普通 SELECT 并不一定会因为大 DELETE / UPDATE 就直接报错或全部阻塞，具体还取决于数据库、隔离级别、MVCC、查询方式和锁类型。

真正应该担心的是：

```text
大事务长时间占用数据库资源
并且提高其他读写操作受到影响的概率
```

---

### 2. Undo / Redo 压力

修改大量数据时，数据库通常还需要维护事务相关日志。

可以理解成：

```text
修改的数据越多
↓
需要记录的事务信息越多
↓
日志、磁盘 IO、恢复成本越高
```

所以：

```text
DELETE 800 万行
```

不是简单地：

```text
把 800 万行瞬间消失
```

背后还会有大量数据库内部工作。

---

### 3. 索引维护成本

如果被修改 / 删除的数据涉及索引：

```text
数据发生变化
↓
索引结构也需要同步维护
```

因此一条看起来很简单的：

```sql
DELETE FROM history_data
WHERE create_time < ?;
```

实际成本可能远高于只看 SQL 文本时的直觉。

---

### 4. 失败回滚成本非常高

这是今天练习中最先抓到的风险。

假设：

```text
需要删除 800 万条
```

事务已经处理到：

```text
799 万条
```

然后发生异常，需要：

```text
ROLLBACK
```

那么数据库不是简单地：

```text
宣布失败
```

而是需要撤销前面已经产生的大量修改。

所以可能出现：

```text
执行本身已经很久
+
回滚继续很久
+
回滚期间仍然持续占用资源
```

因此：

> **大事务失败以后，回滚本身也可能成为一次高成本操作。**

---

## 四、为什么要把一个大事务拆成多个小事务

假设需要处理：

```text
100 万条历史任务
```

不推荐：

```text
BEGIN
↓
处理 100 万条
↓
COMMIT
```

可以拆成：

```text
第 1 批：5000 条
↓
COMMIT

第 2 批：5000 条
↓
COMMIT

第 3 批：5000 条
↓
COMMIT

...
```

这时原来：

```text
100 万条
↓
1 个大事务
```

变成：

```text
5000 条
↓
独立短事务
↓
提交
↓
继续下一批
```

如果总共 100 万条，每批 5000 条：

```text
1000000 ÷ 5000 = 200 批
```

每个批次都可以独立成功或失败。

---

## 五、拆批为什么可以降低风险

今天练习中形成的第一个核心判断是：

假设执行到：

```text
第 100 批成功
第 101 批失败
```

如果每批是独立事务：

```text
前 100 批
→ 已经 COMMIT
→ 不需要回滚

第 101 批
→ 只回滚当前这一小批
```

所以相比：

```text
800 万行一起回滚
```

现在只需要：

```text
回滚 5000 条左右
```

这就是拆批最直观的收益之一：

**降低单次失败回滚成本。**

除此之外还有三个重要收益。

### 1. 锁持有时间更短

```text
处理 5000 条
↓
快速 COMMIT
↓
释放这一批事务相关资源
```

而不是长时间让一个超大事务持续存在。

### 2. 单次资源峰值更可控

每批只处理有限数量数据，可以让：

```text
CPU
IO
Undo / Redo
连接占用
锁范围
```

更容易控制。

### 3. 可以人为控制处理速度

例如：

```text
处理 5000 条
↓
COMMIT
↓
sleep 100ms
↓
继续下一批
```

批处理就不再是：

```text
有多少数据就尽可能快地全部压给数据库
```

而是：

```text
以数据库可承受的速度持续处理
```

这实际上是一种：

**数据库流量整形。**

---

## 六、批处理的目标不是“最快跑完”

今天一个很重要的工程原则是：

> **批处理任务的目标通常不是不计代价地尽快跑完，而是在不影响在线业务的前提下尽可能快地跑完。**

例如：

```text
历史数据清理任务晚 2 小时完成
```

很多时候只是：

```text
后台任务延迟
```

但如果为了让它更快，把数据库 CPU、IO、连接池打满：

```text
在线接口超时
支付失败
用户操作失败
数据库雪崩
```

那就是生产事故。

因此优先级应该是：

```text
在线业务稳定
>
后台批处理吞吐
```

---

## 七、为什么不推荐超大 OFFSET 做批处理

一种很自然的分页方式是：

```sql
SELECT id
FROM history_data
ORDER BY id
LIMIT 5000 OFFSET 5000000;
```

表面看：

```text
反正最终也只拿 5000 条
```

但 OFFSET 越大，数据库的跳过成本通常越高。

可以简单理解成：

```text
找到前 5,005,000 条
↓
跳过前 5,000,000 条
↓
只返回最后 5000 条
```

因此：

```text
OFFSET 5000
→ 成本还比较小

OFFSET 500000
→ 越来越重

OFFSET 5000000
→ 可能需要扫描 / 跳过大量数据
```

所以今天形成一个非常实用的记忆：

> **OFFSET 更像“从头数到这里”，last_id 更像“直接从这里继续”。**

---

## 八、主键游标 / last_id 推进

批处理更常见的方式是记录：

```text
last_id
```

例如当前处理到：

```text
last_id = 3000000
```

下一批查询：

```sql
SELECT id
FROM history_data
WHERE id > 3000000
  AND create_time < ?
ORDER BY id
LIMIT 5000;
```

如果 `id` 是主键或有合适索引，数据库可以从：

```text
id = 3000000 附近
```

继续往后扫描。

处理完这一批之后：

```text
last_id = 本批最后一个 id
```

然后继续：

```sql
WHERE id > last_id
ORDER BY id
LIMIT 5000
```

这种思想也叫：

```text
Keyset Pagination
主键游标分页
基于游标推进的批处理
```

---

## 九、边删除边 OFFSET 还有额外风险

如果一边删除数据，一边继续用固定 OFFSET：

```text
前面的数据被删除
↓
后面的数据位置向前移动
↓
OFFSET 的“第 N 条”含义发生变化
```

这时可能导致：

```text
跳过一部分本来应该处理的数据
```

例如最开始：

```text
第 1～5000 条被删除
```

下一次如果直接：

```text
OFFSET 5000
```

由于前 5000 条已经不存在，原本后面的数据已经整体前移，这种方式就可能跳过一段数据。

所以对于长期批处理任务：

```text
主键游标
+
last_id
```

通常比不断扩大 OFFSET 更稳妥。

## 十、什么是 Checkpoint

今天第一次重点建立：

**Checkpoint（检查点 / 断点）**

假设服务已经处理到：

```text
第 600 批
```

如果服务器突然重启，而程序没有任何进度记录：

```text
服务启动
↓
不知道之前处理到哪里
↓
只能重新扫描 / 重新执行
```

这对于百万级任务非常低效。

更合理的做法是维护任务进度，例如：

```text
task_id
last_id
success_count
fail_count
status
```

示例：

```text
task_id       = 1001
last_id       = 3000000
success_count = 3000000
fail_count    = 0
status        = RUNNING
```

服务重启以后：

```text
读取 task_id = 1001 的 checkpoint
↓
得到 last_id = 3000000
↓
从 id > 3000000 继续
```

而不是：

```text
重新从 id = 1 开始
```

因此 Checkpoint 解决的是：

> **长时间批处理任务的断点续跑问题。**

---

## 十一、Checkpoint 不能单独看，还必须考虑幂等

这是今天最关键的连接点之一。

假设第 601 批执行：

```text
DELETE 5000 条
↓
COMMIT 成功
↓
准备更新 checkpoint
```

但就在：

```text
COMMIT 成功
```

和：

```text
checkpoint 更新成功
```

之间，服务宕机了。

此时数据库真实状态：

```text
第 601 批已经处理成功
```

但 Checkpoint 仍然认为：

```text
只完成到第 600 批
```

服务重启后就可能：

```text
再次尝试处理第 601 批
```

所以：

```text
Checkpoint
只能解决“从哪里继续”
```

还不能自动解决：

```text
某一批会不会重复执行
```

这就重新连接到了 Day 1 的核心能力：

**幂等。**

---

## 十二、为什么 DELETE 相对容易做到幂等

例如：

```sql
DELETE FROM history_data
WHERE id = 100;
```

第一次执行：

```text
删除 1 行
```

第二次再执行：

```text
删除 0 行
```

最终数据库状态都是：

```text
id = 100 的记录不存在
```

所以删除操作很多时候比较容易满足：

```text
执行一次
和
执行多次
最终状态一致
```

但如果业务操作是：

```sql
UPDATE account
SET balance = balance + 100
WHERE id = 1;
```

第一次：

```text
+100
```

第二次：

```text
又 +100
```

最终就变成：

```text
+200
```

这种操作不是天然幂等。

所以批处理不能只说：

```text
我有 checkpoint
```

还要继续问：

```text
如果上一批已经成功，但 checkpoint 还没落库就宕机
重启后重复执行会不会产生错误结果？
```

---

## 十三、批次是不是越小越安全

不是。

假设：

```text
需要处理 800 万条
```

如果每批：

```text
1 条
```

那么意味着：

```text
800 万批
≈
800 万次事务提交
```

事务提交本身也不是免费的。

可能涉及：

```text
事务开启 / 提交
日志处理
刷盘
数据库连接使用
应用和数据库之间的网络往返
```

所以批次太小会导致：

```text
事务数量爆炸
↓
吞吐降低
↓
任务总耗时非常长
↓
数据库长期持续承受后台任务压力
```

因此：

```text
批次太大
→ 事务长、锁多、回滚重

批次太小
→ 提交太频繁、吞吐低、任务时间长
```

真正要做的是：

**在风险与吞吐之间找到平衡。**

---

## 十四、每批到底 1000、5000 还是 10000

没有固定答案。

例如文档中经常会看到：

```text
每批 5000 条
```

这只能作为示例，不能当成生产环境的固定标准答案。

实际应该综合：

```text
单条数据大小
SQL 执行时间
索引情况
数据库 CPU
磁盘 IO
锁等待
连接池压力
在线业务流量
业务高峰 / 低峰
```

然后通过：

```text
压测
+
监控
+
逐步调整
```

确定。

所以如果面试官问：

**为什么不是每批 1000 或 10000？**

应该回答：

> 批次大小没有统一固定值，需要根据单条数据成本、SQL 耗时、数据库资源和线上负载通过测试确定，并结合监控动态调整。

## 十五、数据库 CPU 85% 时不能继续全速跑

今天练习中还有一个非常重要的生产判断。

假设：

```text
数据库 CPU = 85%
批处理还有几百万条没有完成
```

这时不能因为：

```text
任务还没结束
```

就继续：

```text
5000 条
→ COMMIT
→ 立刻下一批
→ COMMIT
→ 立刻下一批
```

因为数据库已经接近高负载，如果继续压入大量后台任务：

```text
CPU 进一步升高
↓
接口延迟增加
↓
数据库连接占用时间增加
↓
请求堆积
↓
在线业务风险扩大
```

更合理的做法包括：

```text
降低批次大小
例如 5000 → 1000

增加批次间隔
例如 sleep 100ms / 500ms / 1s

动态限速
高负载时减速
低负载时恢复

必要时暂停任务
在线业务稳定后再继续
```

如果已经明显影响线上业务：

```text
后台批处理应该让路
```

---

## 十六、什么叫数据库流量整形

原来一个后台任务可能是：

```text
能跑多快就跑多快
```

改造以后：

```text
处理 5000 条
↓
COMMIT
↓
检查数据库负载
↓
必要时 sleep
↓
再处理下一批
```

甚至可以根据指标动态调整：

```text
CPU < 50%
→ 可以适当提高处理速度

CPU 60%～75%
→ 保持

CPU > 80%
→ 降低批次 / 增加间隔

在线业务出现明显延迟
→ 暂停
```

具体阈值需要根据真实系统确定，不能直接照抄。

这种思想本质是：

> **后台任务不能无限制地争夺数据库资源，而应该根据数据库容量进行流量整形。**

---

## 十七、为什么拆批以后仍然优先在低峰期执行

有人可能会认为：

```text
已经每批只处理 5000 条
所以什么时候执行都一样
```

这是错误的。

即使拆批，后台任务仍然需要消耗：

```text
CPU
IO
数据库连接
Undo / Redo
锁资源
Buffer Pool
```

业务高峰期本身就存在：

```text
大量在线请求
```

再叠加批处理：

```text
在线业务
+
后台批处理
↓
共同竞争数据库资源
```

可能造成：

```text
接口延迟
锁等待增加
连接池压力升高
慢 SQL 增多
数据库负载上升
```

所以对于大型：

```text
数据修复
历史清理
迁移
归档
```

通常仍然应该优先：

```text
业务低峰执行
+
拆批
+
限速
+
监控
+
可暂停
```

而不是只做一个：

```text
LIMIT 5000
```

就认为万事大吉。

## 十八、生产级批处理任务应该具备哪些能力

今天最终可以把一个比较完整的批处理任务拆成下面几个能力。

### 1. 拆批

```text
大任务
↓
多个小批次
```

### 2. 短事务

```text
每批独立事务
↓
快速 COMMIT
```

### 3. 主键游标推进

```text
last_id
↓
id > last_id
```

避免：

```text
超大 OFFSET
```

### 4. Checkpoint

记录：

```text
last_id
成功数量
失败数量
任务状态
```

用于：

```text
断点续跑
```

### 5. 幂等

保证：

```text
某一批重复执行
不会产生错误业务结果
```

### 6. 限速

控制：

```text
批次大小
批次间隔
并发度
```

### 7. 可暂停 / 可恢复

当：

```text
数据库负载过高
在线业务异常
```

可以：

```text
暂停任务
```

恢复后：

```text
从 checkpoint 继续
```

### 8. 监控

至少关注：

```text
任务进度
```

## 十九、一个完整批量删除任务怎么设计

场景：

```text
history_data：5000 万条
需要删除：180 天前约 800 万条
```

要求：

```text
不能明显影响在线业务
服务重启后能继续
不能每次从头扫描
某一批失败不能让前面全部回滚
数据库压力高时可以减速
```

可以按下面的骨架设计。

### 第一步：业务低峰启动任务

```text
凌晨 / 流量低峰
↓
启动历史数据清理任务
```

并先检查：

```text
数据库负载是否允许开始
```

---

### 第二步：读取 Checkpoint

第一次执行：

```text
last_id = 0
```

服务重启恢复：

```text
读取已有 last_id
```

---

### 第三步：按主键查询下一批

例如：

```sql
SELECT id
FROM history_data
WHERE id > ?
  AND create_time < ?
ORDER BY id
LIMIT 5000;
```

不要直接依赖：

```text
OFFSET 5000000
```

---

### 第四步：删除当前批次

例如：

```sql
DELETE FROM history_data
WHERE id IN (...);
```

真实实现还需要结合数据库能力、索引和 SQL 方案评估，不能机械照抄 IN 列表。

---

### 第五步：当前批次独立 COMMIT

```text
第 N 批成功
↓
COMMIT
```

如果第 N 批失败：

```text
只回滚第 N 批
```

前面的：

```text
1 ～ N-1 批
```

已经提交，不需要一起回滚。

---

### 第六步：更新 Checkpoint

记录：

```text
last_id
success_count
fail_count
status
```

例如：

```text
last_id = 本批最大 id
```

---

### 第七步：检查数据库负载

关注：

```text
CPU
IO
锁等待
连接池
慢 SQL
在线业务延迟
```

如果负载正常：

```text
继续下一批
```

如果压力偏高：

```text
降低批次
或
增加 sleep
```

如果已经影响线上业务：

```text
暂停任务
```

---

### 第八步：继续循环

```text
读取下一批
↓
处理
↓
COMMIT
↓
更新 checkpoint
↓
限速
↓
下一批
```

---

### 第九步：没有数据后结束

当：

```text
查询不到符合条件的数据
```

则：

```text
status = SUCCESS
```

任务结束。

## 二十、面试怎么表达

如果面试官问：

**线上要 UPDATE / DELETE 几百万条数据，你会怎么做？**

可以回答：

> 对于百万级数据更新或清理，我一般不会直接使用一个大事务一次性处理，因为大事务会长时间持锁，同时增加 Undo、Redo、索引维护、数据库 IO 和失败回滚成本。我会按照主键或游标进行分批处理，每批使用独立短事务，并记录 lastId 或 checkpoint，使任务支持断点续跑。同时保证批处理具备幂等性，避免某一批提交成功但 checkpoint 更新前宕机后重复执行产生错误结果。批次大小不会写死，会根据 SQL 耗时和数据库 CPU、IO、锁等待、连接池以及线上负载通过测试确定，并结合限速、低峰执行和监控避免影响在线业务。

如果面试官问：

**为什么不用 OFFSET 分页？**

可以回答：

> 大 OFFSET 往往需要数据库扫描或跳过大量前置记录，页数越深成本越高，而且边删除边 OFFSET 还可能因为数据位置变化产生跳过风险。长期批处理通常更适合基于主键游标，通过 `id > lastId ORDER BY id LIMIT N` 持续向后推进。

如果面试官问：

**每批到底多少条？**

可以回答：

> 没有固定值。批次太大会形成较长事务并增加锁和回滚成本，批次太小又会产生大量事务提交和网络往返，吞吐很低。应该根据单条数据大小、SQL 耗时、索引、CPU、IO、锁等待以及在线业务负载压测后确定，并可以根据监控动态调整。

如果面试官问：

**服务处理到一半重启怎么办？**

可以回答：

> 我会给批处理任务记录 checkpoint，例如 taskId、lastId、成功数量和任务状态。服务启动后读取 checkpoint，从 lastId 后继续，而不是重新从第一条开始。同时必须考虑某批已经提交但 checkpoint 尚未更新就宕机的情况，所以批处理本身还应该具备幂等能力。

## 二十一、今天练习中的关键纠正

### 1. “别人查询会出现 Bug”不够准确

今天最开始认为：

```text
删除 800 万行期间
别人查询可能出现 Bug
```

这个说法太笼统。

更准确应该说：

```text
大事务会长时间占用数据库资源和持有大量锁
可能影响其他 UPDATE / DELETE
并可能间接拖慢查询和整个数据库
```

普通 SELECT 是否阻塞还要结合：

```text
数据库实现
MVCC
事务隔离级别
查询方式
锁类型
```

具体分析。

---

### 2. 拆批不仅是“失败时回滚得快”

今天已经能够直接想到：

```text
第 101 批失败
↓
只回滚第 101 批
↓
前 100 批不用回滚
```

还需要继续补全：

```text
锁持有时间更短
Undo / Redo 压力更平滑
资源峰值更可控
可以主动限速
```

---

### 3. Checkpoint 的核心是“明确进度”

Checkpoint 不只是：

```text
数据库崩了不用重新执行
```

更准确的是：

```text
明确记录批处理已经推进到哪里
↓
服务重启后从这个位置继续
```

同时必须处理：

```text
业务操作成功
但 checkpoint 还没更新
```

这一故障窗口。

---

### 4. Checkpoint 必须和幂等一起考虑

```text
COMMIT 成功
↓
checkpoint 更新前宕机
↓
重启后可能重复执行上一批
```

所以：

```text
断点续跑
+
幂等
```

应该作为一组能力理解。

---

### 5. OFFSET 越大不是“只是页码更大”

需要形成：

```text
OFFSET
≈
从前面一路数过去再丢掉

last_id
≈
直接从上次位置继续
```

这才是为什么深分页时更倾向主键游标的本质理解。

---

### 6. 批次不是越小越安全

今天已经判断出：

```text
每批 1 条
```

完全不可取。

进一步要明确原因：

```text
事务数量太多
COMMIT 成本太高
网络往返太多
吞吐太低
总任务时间过长
```

所以工程上追求的是平衡，不是无限拆小。

---

### 7. 数据库 CPU 高时后台任务必须让路

今天已经形成：

```text
CPU 85%
↓
不能继续全速跑
```

进一步需要记住处理手段：

```text
减小批次
增加批次间隔
动态限速
必要时暂停
低峰继续
```

核心优先级：

```text
在线业务稳定
>
批处理尽快完成
```

---

## 二十三、今天的最终总结

今天真正需要掌握的不是：

```text
把 DELETE 后面加一个 LIMIT 5000
```

而是建立一整套：

**长期批处理任务的工程化思维。**

核心链路是：

```text
百万级数据任务
↓
不要做一个超大事务
↓
按照主键 / 游标拆批
↓
每批独立短事务
↓
COMMIT
↓
记录 Checkpoint / last_id
↓
服务重启后断点续跑
↓
考虑上一批重复执行
↓
保证幂等
↓
根据数据库负载限速
↓
优先低峰执行
↓
持续监控并支持暂停恢复
```

最终需要形成的条件反射：

```text
看到百万级 UPDATE / DELETE
↓
先问事务大小和生产风险
↓
再问如何拆批
↓
再问如何续跑
↓
再问重复执行是否安全
↓
最后问数据库能承受多快
```

而不是：

```text
这条 SQL 能跑
↓
直接执行
```

最终原则：

> **生产环境的大批量数据处理，优先追求可控、可恢复、可限速、可观测，而不是单次 SQL 看起来最简单或总执行时间最短。**
