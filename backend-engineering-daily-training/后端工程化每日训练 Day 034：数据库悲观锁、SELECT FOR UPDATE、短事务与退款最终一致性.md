# 后端工程化每日训练 Day 34：数据库悲观锁、SELECT FOR UPDATE、短事务与退款最终一致性

## 一、今天学习的知识点

今天学习的是：

**数据库悲观锁（Pessimistic Lock）、`SELECT ... FOR UPDATE`、锁与事务的关系、短事务设计，以及退款场景下如何结合幂等、补偿、状态机和本地消息表保证最终一致性。**

一句话理解：

> 悲观锁的核心不是“让代码更安全”，而是在并发冲突概率较高、业务必须严格串行判断时，先锁住关键数据，让竞争请求等待；但锁必须尽快释放，绝不能把不可控的外部调用长时间放在持锁事务中。

今天重点解决以下问题：

```text
什么是数据库悲观锁
SELECT ... FOR UPDATE 到底锁在哪里
为什么悲观锁必须和事务一起理解
什么时候应该使用悲观锁
为什么不能持锁等待 HTTP / AI / OSS / 支付接口
为什么退款状态要先从 NOT_REFUNDED 改成 REFUNDING
为什么第三方退款成功后不能无脑再次重试退款
本地数据库为什么可能更新失败
幂等、补偿、状态机分别解决什么问题
本地消息表如何把退款任务可靠保存下来
悲观锁和乐观锁怎么选
数据库悲观锁和分布式锁有什么区别
```

## 二、悲观锁到底在解决什么问题

Day 33 学习了乐观锁。

乐观锁的思想是：

```text
大家先正常执行
↓
真正提交更新时
↓
检查 version / 当前状态
↓
冲突了就失败或重新处理
```

这种方式适合：

```text
并发冲突概率不高
```

但有些场景的业务特征不同。

例如库存只剩：

```text
stock = 1
```

请求 A 和请求 B 同时购买。

原始代码可能是：

```text
查询库存
↓
判断 stock > 0
↓
扣库存
↓
生成订单
```

如果 A、B 同时读取：

```text
stock = 1
```

那么两边都可能认为：

```text
还有库存，可以购买
```

悲观锁的思路是：

```text
A：先锁住目标数据
↓
A：完成判断和修改
↓
A：提交事务
↓
释放锁
↓
B：才能继续
```

它的核心假设是：

> **我认为这份数据很可能发生并发冲突，所以在真正修改之前先获得独占处理权。**

## 三、SELECT ... FOR UPDATE 应该加在哪里

今天最开始对下面三个问题都没有形成清晰概念：

```text
锁在哪一步加？
锁住什么？
什么时候提交事务？
```

用退款订单来理解最直接。

订单：

```text
order_id = 1001
status = PAID
refund_status = NOT_REFUNDED
```

比较典型的流程是：

```text
BEGIN
↓
SELECT ... FOR UPDATE
↓
判断 refund_status
↓
NOT_REFUNDED → REFUNDING
↓
COMMIT
```

SQL：

```sql
SELECT *
FROM orders
WHERE id = 1001
FOR UPDATE;
```

在支持行级锁并且查询命中合适索引的情况下，可以先理解为：

```text
锁住订单 1001 对应的记录
```

随后在同一事务中判断：

```text
refund_status == NOT_REFUNDED ?
```

如果允许退款，就快速更新：

```sql
UPDATE orders
SET refund_status = 'REFUNDING'
WHERE id = 1001;
```

然后：

```text
COMMIT
```

事务提交后，数据库锁释放。

所以今天最需要记住的最小模型是：

```text
开启事务
↓
FOR UPDATE 查询并锁住数据
↓
快速判断业务状态
↓
快速修改数据库状态
↓
立即提交事务
↓
释放锁
```

## 四、为什么第二个退款请求会被挡住

假设请求 A 先进入：

```sql
SELECT *
FROM orders
WHERE id = 1001
FOR UPDATE;
```

A 读取到：

```text
refund_status = NOT_REFUNDED
```

此时 A 持有锁。

请求 B 也执行：

```sql
SELECT *
FROM orders
WHERE id = 1001
FOR UPDATE;
```

因为 A 还没有提交事务，所以 B 会发生锁等待。

A 随后执行：

```text
NOT_REFUNDED → REFUNDING
↓
COMMIT
```

事务提交后，B 才能继续。

B 再读取时看到的是：

```text
refund_status = REFUNDING
```

于是业务就知道：

```text
这笔退款已经有人正在处理
不能再次发起退款
```

这里的关键不是简单的“数据库锁住了”，而是：

> **锁保证了“读取当前状态 → 判断 → 修改状态”这一小段关键逻辑不会被另一个事务同时基于旧状态执行。**

## 五、为什么绝对不能持锁等待第三方支付平台 30 秒

一种非常危险的代码结构是：

```text
BEGIN
↓
SELECT ... FOR UPDATE
↓
锁住订单
↓
调用第三方支付退款
↓
等待 10 秒 / 30 秒
↓
UPDATE REFUNDED
↓
COMMIT
```

今天最开始的直觉是：

```text
这样会太慢
```

这个方向没错，但真正的工程问题更加严重：

> **这 10～30 秒里，数据库锁和数据库连接可能一直被占用。**

假设线上出现大量退款请求：

```text
100 个事务
↓
全部拿着数据库连接
↓
全部等待第三方支付平台返回
```

可能进一步形成：

```text
锁长期不释放
↓
其他请求锁等待
↓
事务时间变长
↓
数据库连接长期占用
↓
连接池压力上升
↓
请求堆积
↓
超时增加
↓
严重时连接池耗尽
```

而第三方接口耗时本身不可控：

```text
正常：300 ms
偶发：3 s
异常：30 s
超时：60 s
```

如果把外部调用放在锁事务中，那么数据库事务时长就被第三方系统决定了。

这和 Day 28 学习的事务边界是同一条原则：

> **数据库事务只包住必须保证一致性的本地数据库操作；HTTP、AI、OSS 等不可控外部调用尽量移出事务。**

---

## 六、更合理的退款流程：先进入 REFUNDING，再调用第三方

相比一直持有悲观锁，更合理的流程是：

```text
事务 1
↓
FOR UPDATE 锁订单
↓
确认 NOT_REFUNDED
↓
NOT_REFUNDED → REFUNDING
↓
COMMIT
↓
立即释放数据库锁和连接

然后
↓
调用第三方支付平台退款

最后
↓
事务 2
↓
REFUNDING → REFUNDED
```

今天对这个方案的理解是：

```text
处理更快
响应更快
高并发下系统仍然更容易保持正常运行
```

更准确地说，这个设计真正提升的是：

```text
锁持有时间更短
数据库连接释放更快
竞争请求不会长时间排队
数据库不会因为外部接口慢而被拖住
```

同时：

```text
REFUNDING
```

不只是一个展示状态。

它实际上还表达：

> **这笔退款已经被某个处理流程接管，其他重复请求不能再次启动同一笔退款。**

## 七、为什么第三方退款成功后，本地数据库仍然可能更新失败

一个非常重要的问题是：

```text
支付平台已经退款成功
为什么数据库还会失败？
```

因为：

```text
第三方支付平台
和
本地数据库
```

是两个独立系统。

典型流程：

```text
1. 调用支付平台退款
2. 支付平台返回 SUCCESS
3. Java 准备 UPDATE 本地数据库
4. 数据库更新失败
```

第 4 步可能因为很多原因失败：

```text
数据库连接中断
数据库重启
网络抖动
SQL 超时
锁等待超时
死锁导致事务回滚
程序执行 UPDATE 前抛异常
服务突然宕机
容器被杀
机器断电
数据库约束异常
后续代码异常导致整个事务回滚
```

最典型的异常窗口甚至是：

```text
支付平台：退款成功
↓
Java 服务突然宕机
↓
根本没有机会执行 UPDATE
```

于是形成：

```text
第三方支付平台：SUCCESS

本地数据库：REFUNDING
```

这就是典型的：

```text
跨系统一致性问题
```

以后看到下面这种业务，都应该想到同一类风险：

```text
数据库成功 → MQ 发送失败
数据库成功 → OSS 上传失败
支付成功 → 数据库更新失败
AI 调用成功 → 结果保存失败
```

核心原则是：

> **只要一次业务跨越两个独立系统，就必须考虑“前一个成功、后一个失败”的中间状态。**

---

## 八、为什么不能看到数据库失败就直接重新退款

假设发生：

```text
支付平台退款成功
↓
本地数据库更新 REFUNDED 失败
```

此时不能简单写成：

```text
失败了
↓
重新调用一次退款
```

今天马上判断到的问题是：

> **如果再退一次，就可能多退一笔钱给客户。**

这就是支付场景里非常严重的资金风险。

所以外部退款操作必须设计业务幂等键。

例如：

```text
refund_no = REFUND_1001
```

第一次退款：

```text
订单 1001
退款单号 REFUND_1001
退款金额 100 元
```

如果本地状态没有更新成功，之后也不能重新生成：

```text
REFUND_1002
```

然后再发起一笔新的退款。

更合理的是继续围绕同一个：

```text
refund_no = REFUND_1001
```

查询第三方支付平台：

```text
REFUND_1001 当前到底是什么状态？
```

如果平台返回：

```text
SUCCESS
```

说明真实业务事实已经是：

```text
钱已经退了
```

此时系统需要做的是：

```text
补写本地 REFUNDED
```

而不是再次退款。

## 九、幂等、补偿、状态机分别解决什么问题

今天这个退款案例，可以把前面学过的几个知识点真正串起来。

### 1. 幂等

幂等解决：

```text
同一个退款任务执行多次
会不会真的退多次钱？
```

通过唯一：

```text
refund_no
```

确保同一笔退款业务具有稳定业务身份。

目标是：

```text
重复执行 ≠ 重复产生资金结果
```

---

### 2. 状态机

退款状态不能随便修改。

可以设计：

```text
NOT_REFUNDED
↓
REFUNDING
↓
REFUNDED
```

失败场景：

```text
REFUNDING
↓
REFUND_FAILED
```

状态机解决的是：

> **明确当前业务处于哪个阶段，以及哪些状态转换是允许的。**

例如：

```text
REFUNDED
```

通常不能再次回到：

```text
NOT_REFUNDED
```

也不能因为某次重复请求就重新发起退款。

---

### 3. 补偿机制

补偿解决：

```text
中间某一步失败后
系统以后怎么继续把事情做完？
```

例如：

```text
本地状态 = REFUNDING
↓
补偿任务扫描到异常任务
↓
根据 refund_no 查询支付平台
↓
发现退款实际上 SUCCESS
↓
补写本地 REFUNDED
```

所以：

```text
幂等
→ 防止重复产生业务副作用

状态机
→ 控制合法状态流转

补偿
→ 修复中间失败
```

三者解决的问题不同，但在支付系统中经常一起使用。

## 十、本地消息表为什么适合这个场景

今天最后想到：

> **这个退款流程可以使用本地消息表。**

这个方向非常关键。

一种典型设计是：

```text
用户请求退款
↓
开启本地数据库事务
↓
订单：NOT_REFUNDED → REFUNDING
↓
插入 refund_task / local_message
↓
status = PENDING
refund_no = REFUND_1001
↓
COMMIT
```

其中：

```text
订单进入 REFUNDING
+
本地退款任务写入成功
```

应该放在同一个数据库事务里。

这样可以避免：

```text
订单已经 REFUNDING
↓
但真正负责退款的任务根本没有保存下来
```

事务提交后，再由 Worker 异步处理：

```text
扫描 PENDING 退款任务
↓
调用支付平台
refund_no = REFUND_1001
↓
支付成功
↓
更新订单 REFUNDED
↓
更新任务 SUCCESS
```

如果发生：

```text
支付平台退款成功
↓
数据库更新失败
```

本地任务不会被正常标记完成。

后续补偿任务仍然可以发现：

```text
PENDING / PROCESSING / RETRY
```

然后根据同一个：

```text
refund_no = REFUND_1001
```

去查询第三方真实状态。

如果确认：

```text
SUCCESS
```

则：

```text
补写订单 REFUNDED
↓
退款任务 SUCCESS
```

所以本地消息表可以理解为：

> **先把“将来必须完成的事情”与当前数据库业务状态一起可靠保存下来，然后再异步执行外部操作。**

---

## 十一、本地消息表不能单独解决所有问题

不能因为有了本地消息表，就认为退款系统已经安全。

本地消息表主要解决：

```text
任务不能丢
```

但它本身不能完全解决：

```text
重复退款
```

也不能自动知道：

```text
第三方到底成功还是失败
```

所以完整组合应该是：

```text
本地消息表
→ 可靠保存待执行任务

唯一 refund_no / 幂等
→ 防止重复退款

NOT_REFUNDED / REFUNDING / REFUNDED / FAILED
→ 状态机控制业务流转

定时扫描 / 重试 / 主动查询第三方
→ 补偿异常

最终
→ 本地状态和支付平台真实状态重新一致
```

## 十二、悲观锁常见坑

### 1. FOR UPDATE 后调用外部服务

错误：

```text
BEGIN
↓
FOR UPDATE
↓
调用支付平台 / AI / HTTP / OSS
↓
等待几十秒
↓
COMMIT
```

风险：

```text
锁长期持有
数据库连接长期占用
锁等待增加
吞吐下降
连接池压力增加
```

原则：

> **锁内逻辑必须尽可能短。**

---

### 2. 认为 FOR UPDATE 永远只锁一行

锁范围与：

```text
数据库实现
事务隔离级别
查询条件
索引使用情况
```

都有关系。

例如：

```sql
SELECT *
FROM orders
WHERE id = ?
FOR UPDATE;
```

命中主键通常更容易控制锁范围。

而大范围条件、缺少合适索引的查询，可能造成比预期更大的锁影响。

---

### 3. 到处使用悲观锁

悲观锁的代价是：

```text
并发请求
↓
变成等待和串行
```

例如：

```text
100 个请求竞争同一条记录
↓
1 个执行
99 个等待
```

所以悲观锁不是“更安全的默认方案”。

它适合的是：

```text
冲突概率高
+
业务必须严格串行判断
+
临界区足够短
```

---

### 4. 多个事务加锁顺序不一致

事务 A：

```text
锁订单 1
↓
锁订单 2
```

事务 B：

```text
锁订单 2
↓
锁订单 1
```

可能形成：

```text
A 等 B
B 等 A
```

最终导致：

```text
死锁
```

工程上应该：

```text
统一加锁顺序
保持事务短小
减少一次事务锁定资源数量
```

---

## 十三、悲观锁、乐观锁和分布式锁不要混在一起

### 乐观锁

核心思路：

```text
先正常执行
↓
提交时检查冲突
```

典型：

```text
version
状态条件 UPDATE
CAS
```

适合：

```text
冲突概率低
不希望大量请求提前阻塞
```

---

### 数据库悲观锁

核心思路：

```text
先锁住数据库数据
↓
再判断和修改
```

典型：

```sql
SELECT ... FOR UPDATE
```

适合：

```text
冲突概率较高
必须严格串行判断
关键数据库操作很短
```

---

### 分布式锁

Day 06 学习的分布式锁主要解决：

```text
多个应用实例
对同一个业务资源
谁拥有执行权
```

常见实现可能是：

```text
Redis
ZooKeeper
数据库等
```

所以：

```text
数据库悲观锁
→ 重点保护数据库事务里的数据并发

分布式锁
→ 重点协调多个进程 / 服务实例的业务执行权
```

两者使用层级并不完全相同。

---

## 十四、悲观锁和乐观锁怎么选

可以先按下面的判断方式理解。

### 冲突概率低

例如：

```text
后台偶尔多人编辑
普通业务状态偶发并发更新
```

优先考虑：

```text
乐观锁
version
条件 UPDATE
```

因为：

```text
没必要让所有请求先排队
```

---

### 冲突概率高，而且必须严格串行

例如：

```text
资金状态判断
有限资源竞争
部分库存扣减
关键业务状态抢占
```

可以考虑：

```text
悲观锁
SELECT ... FOR UPDATE
```

但必须满足：

```text
事务非常短
锁范围可控
索引合理
没有外部慢调用
```

---

### 高并发热点资源

例如：

```text
秒杀
大量 Worker 抢同一个任务
超高频热点库存
```

不能机械地说：

```text
冲突多
↓
全部 FOR UPDATE
```

因为数据库可能直接变成系统瓶颈。

还需要根据业务考虑：

```text
数据库原子 UPDATE
Redis
MQ 串行化
任务分片
削峰
更合理的数据模型
```

---

## 十五、今天退款案例的完整工程流程

把今天所有知识串起来，可以得到：

```text
用户请求退款
↓
开启短事务
↓
FOR UPDATE / 原子条件 UPDATE
↓
确认 NOT_REFUNDED
↓
生成唯一 refund_no
↓
NOT_REFUNDED → REFUNDING
↓
写入本地退款任务 PENDING
↓
COMMIT
↓
释放数据库锁和连接
↓
Worker 调用第三方支付平台
↓
使用同一个 refund_no
↓
第三方退款成功
↓
本地 REFUNDING → REFUNDED
↓
退款任务 SUCCESS
```

如果中途发生异常：

```text
支付平台可能已经成功
↓
本地仍然 REFUNDING
↓
补偿任务扫描未完成任务
↓
使用同一个 refund_no 查询第三方
↓
确认真实退款状态
↓
补写 REFUNDED / FAILED
↓
最终恢复一致
```

这个流程体现的是：

```text
悲观锁
→ 保护短暂的关键状态判断

短事务
→ 避免数据库被外部调用拖住

REFUNDING 状态
→ 防止第二个请求再次启动退款

幂等 refund_no
→ 防止重复退款

本地消息表
→ 保证退款任务不会丢

补偿机制
→ 处理跨系统中间失败

状态机
→ 控制退款业务合法流转
```

## 十六、面试怎么表达

可以这样回答：

> 在库存扣减、资金状态变更这类并发冲突概率较高，而且业务要求严格串行判断的场景中，我会考虑数据库悲观锁，例如在事务内使用 `SELECT ... FOR UPDATE` 锁定目标记录，完成状态判断和本地状态变更后立即提交事务。使用时重点控制事务长度，避免在持锁期间调用 HTTP、AI、OSS 或支付平台等外部服务，否则会导致锁和数据库连接长期占用，引发锁等待、连接池压力和请求堆积。

退款场景可以继续补充：

> 对于退款，我不会一直持有数据库锁等待第三方支付平台返回，而是先在短事务中把 `NOT_REFUNDED` 原子地推进到 `REFUNDING`，同时保存唯一退款单号和待处理任务，然后释放数据库事务再调用支付平台。如果外部退款成功但本地更新失败，就通过相同的 `refund_no` 做幂等查询和补偿，结合状态机、本地消息表保证最终一致性，避免重复退款。

## 十七、今天真正需要记住的结论

### 1. 悲观锁不是“锁得越多越安全”

真正原则是：

```text
只锁关键数据
只锁关键时间窗口
尽快提交
尽快释放
```

### 2. FOR UPDATE 必须和事务一起理解

```text
BEGIN
↓
FOR UPDATE
↓
判断 + 更新
↓
COMMIT
```

没有事务边界，就无法真正理解悲观锁的生命周期。

### 3. 外部调用不能拖住数据库锁

```text
HTTP
AI
OSS
MQ
支付平台
```

都属于耗时不可控的外部系统。

### 4. 跨系统业务一定要考虑“前一步成功、后一步失败”

所以支付系统不能只依赖：

```text
调用成功
↓
UPDATE 成功
```

而必须有：

```text
幂等
状态机
补偿
任务持久化
最终一致性
```

### 5. 本地消息表的核心价值

> **先可靠记录“这件事必须完成”，再异步执行外部动作。**

这也是今天从悲观锁继续延伸到支付最终一致性后，最重要的一条工程化连接。
