# 后端工程化每日训练 Day 33：数据库乐观锁、并发更新冲突与状态覆盖控制

## 一、今天学习的知识点

今天学习的是：

**数据库乐观锁（Optimistic Lock）、Lost Update（更新丢失）、版本号控制、条件更新，以及并发修改下的状态覆盖与冲突处理。**

一句话理解：

> 乐观锁不是为了让更新一定成功，而是为了防止一个基于旧数据做出的更新，在并发情况下悄悄覆盖掉别人已经提交的新数据。

今天重点解决以下问题：

```text
什么是 Lost Update（更新丢失）
为什么“最后执行的 UPDATE”不一定代表正确业务结果
version 字段到底解决什么问题
affected rows = 0 为什么是乐观锁的核心信号
乐观锁冲突以后为什么不能直接强制覆盖
什么时候应该想到乐观锁
状态条件更新和 version 有什么关系
乐观锁和幂等有什么区别
为什么不直接“加锁，不让别人动”
乐观锁、悲观锁、分布式锁分别适合什么场景
为什么高频乐观锁冲突可能说明消费架构本身有问题
AI 异步任务里如何避免 SUCCESS / FAILED 互相覆盖
```

---

## 二、先理解真正的问题：Lost Update

假设数据库中有一条广告计划：

```text
budget = 1000
version = 5
```

管理员 A 和管理员 B 几乎同时读取：

```text
A：budget = 1000
B：budget = 1000
```

随后：

```text
A 修改为 1200
B 修改为 1500
```

如果直接执行普通 UPDATE：

```sql
UPDATE ad_plan
SET budget = ?
WHERE id = ?;
```

可能出现：

```text
A 更新成功 → budget = 1200
B 更新成功 → budget = 1500
```

最终数据库：

```text
budget = 1500
```

表面看只是“B 最后提交，所以 B 赢了”。

真正的问题是：

> **B 做出修改决定时，看到的还是 A 修改之前的旧数据。**

也就是说：

```text
B 的业务判断基于旧数据
↓
B 提交时数据库已经发生变化
↓
B 仍然无条件 UPDATE
↓
A 的新结果被静默覆盖
```

这就是典型的：

**Lost Update（更新丢失）。**

危险之处不是最终值一定错误，而是：

```text
系统完全不知道发生过并发冲突
```

---

## 三、乐观锁的核心：提交时验证“我拿的数据还是不是最新的”

最常见方式是在表中增加：

```text
version
```

例如：

```text
id = 1001
status = RUNNING
version = 5
```

读取以后，更新时不只是：

```sql
UPDATE task
SET status = 'SUCCESS'
WHERE id = 1001;
```

而是：

```sql
UPDATE task
SET status = 'SUCCESS',
    version = version + 1
WHERE id = 1001
  AND version = 5;
```

这条 SQL 实际表达的是：

> 只有当这条数据仍然是我当初读取到的第 5 版时，才允许我更新。

---

## 四、为什么 affected rows 是乐观锁真正的核心

### 情况一：没有其他请求修改

数据库仍然是：

```text
version = 5
```

更新条件匹配：

```text
WHERE id = 1001 AND version = 5
```

结果：

```text
affected rows = 1
version = 6
```

说明：

```text
更新成功
```

---

### 情况二：别人已经先修改

假设 Worker A 已经执行成功：

```text
status = SUCCESS
version = 6
```

Worker B 还拿着旧数据：

```text
version = 5
```

然后 B 执行：

```sql
UPDATE task
SET status = 'FAILED',
    version = version + 1
WHERE id = 1001
  AND version = 5;
```

数据库已经没有：

```text
id = 1001 AND version = 5
```

所以结果不是一定抛 SQL 异常，而通常是：

```text
affected rows = 0
```

这就是乐观锁告诉应用：

> **你做出当前更新决策时依赖的数据已经过期。**

Java 端因此必须检查：

```java
int rows = taskMapper.update(...);

if (rows == 0) {
    throw new ConcurrentModificationException();
}
```

如果代码完全不检查更新行数，那么即使 SQL 加了条件，也没有完整处理并发冲突。

---

## 五、什么时候应该想到乐观锁

以后看到下面这种代码结构，要产生警觉：

```java
Task task = taskMapper.selectById(id);

// 中间做业务判断、调用其他逻辑、等待用户提交等

task.setStatus("SUCCESS");
taskMapper.updateById(task);
```

它存在一个非常关键的时间窗口：

```text
SELECT
↓
一段时间
↓
UPDATE
```

这段时间里可能发生：

```text
其他线程修改
其他 HTTP 请求修改
其他 Worker 修改
其他管理员修改
其他服务实例修改
```

因此应该问：

> **如果我 SELECT 以后，别人已经修改了这条数据，我现在还能不能基于旧数据继续覆盖？**

如果答案是：

```text
不能接受
```

就应该考虑：

```text
version 乐观锁
状态条件更新
CAS 思路
```

所以乐观锁最应该和一句话绑定：

> **防止旧数据覆盖新数据。**

---

## 六、典型场景一：后台多人编辑

例如后台商品配置：

```text
price = 100
stock = 50
version = 5
```

管理员 A 和 B 同时打开编辑页面。

A 修改价格：

```text
price = 120
```

A 提交后：

```text
price = 120
stock = 50
version = 6
```

但 B 打开的还是旧页面：

```text
price = 100
stock = 50
version = 5
```

B 只想修改库存：

```text
stock = 40
```

如果前端把整条旧对象提交回来：

```sql
UPDATE product
SET price = 100,
    stock = 40
WHERE id = 1;
```

那么 A 刚改成的：

```text
price = 120
```

会重新被覆盖成：

```text
price = 100
```

使用 version：

```sql
UPDATE product
SET price = 100,
    stock = 40,
    version = version + 1
WHERE id = 1
  AND version = 5;
```

因为数据库现在已经是：

```text
version = 6
```

所以 B：

```text
UPDATE 0 rows
```

系统就可以提示：

```text
数据已经被其他人修改，请刷新后重新编辑
```

这个场景非常适合乐观锁，因为管理员同时修改同一条记录通常不是高频事件，没有必要长期锁住数据库记录。

---

## 七、典型场景二：AI 异步任务状态冲突

今天的核心练习：

```text
id = 1001
status = RUNNING
version = 5
```

因为消息重复等原因：

```text
Worker A
Worker B
```

同时读取任务。

随后：

```text
Worker A：AI 调用成功 → 准备 SUCCESS
Worker B：AI 调用超时 → 准备 FAILED
```

如果没有乐观锁：

```text
A：RUNNING → SUCCESS
B：RUNNING → FAILED
```

执行顺序可能是：

```text
A 写 SUCCESS
↓
B 再写 FAILED
↓
最终 FAILED
```

今天首先判断到的问题是：

> **A 的更新被 B 覆盖了。**

这个判断正确。

更准确地说：

```text
B 得出 FAILED 的业务判断时
看到的是之前的 RUNNING

但 B 真正提交时
任务已经被 A 修改成 SUCCESS
```

因此：

> **数据库执行顺序不等于业务事实优先级。**

不能简单认为：

```text
B 最后执行
所以 FAILED 就一定正确
```

---

## 八、Worker B 冲突以后为什么不能强制改成 FAILED

假设 A 先更新：

```sql
UPDATE task
SET status = 'SUCCESS',
    version = version + 1
WHERE id = 1001
  AND version = 5;
```

结果：

```text
status = SUCCESS
version = 6
```

然后 B 使用旧版本：

```sql
UPDATE task
SET status = 'FAILED',
    version = version + 1
WHERE id = 1001
  AND version = 5;
```

结果：

```text
affected rows = 0
```

今天的判断是：

```text
发生了乐观锁并发冲突
不能强制覆盖
应该重新查询最新状态再核对
```

这个方向正确。

异步 Worker 场景下通常不是“弹提示框”，而是：

```text
UPDATE 0 rows
↓
重新读取任务
↓
发现 status = SUCCESS
↓
确认之前的 RUNNING 已经过期
↓
放弃 FAILED 更新 / 记录冲突 / 按状态机处理
```

因为：

> **UPDATE 0 rows 不是在告诉 Worker“再执行一次就行”，而是在告诉它“你做决策所依据的数据已经不是最新状态”。**

---

## 九、不一定必须使用 version：状态条件更新也是一种乐观并发控制

对于状态机业务，有时可以直接把当前状态放进 WHERE。

例如订单：

```text
UNPAID → PAID
```

更新：

```sql
UPDATE orders
SET status = 'PAID'
WHERE id = 100
  AND status = 'UNPAID';
```

如果另一个线程已经：

```text
UNPAID → CANCELLED
```

那么数据库当前状态：

```text
CANCELLED
```

支付线程再执行：

```text
WHERE status = 'UNPAID'
```

就会：

```text
UPDATE 0 rows
```

这和 version 的核心思想是一致的：

```text
只有数据仍符合我做出决策时的前提
才允许更新
```

对于状态机场景，经常可以写成：

```sql
UPDATE task
SET status = 'SUCCESS'
WHERE id = ?
  AND status = 'RUNNING';
```

而对于后台编辑、多字段更新等场景，version 往往更加通用。

## 十、乐观锁和幂等不是一回事

这两个概念很容易混在一起。

### 幂等解决

```text
同一个请求重复执行怎么办？
```

例如：

```text
支付回调重复 5 次
```

目标是：

```text
不能重复记账 5 次
```

---

### 乐观锁解决

```text
多个并发修改互相覆盖怎么办？
```

例如：

```text
Worker A 写 SUCCESS
Worker B 写 FAILED
```

目标是：

```text
旧状态不能静默覆盖新状态
```

所以：

```text
幂等 ≠ 乐观锁
```

但实际异步任务里经常同时需要：

```text
MQ 重复消息
↓
幂等控制

多个 Worker 同时修改
↓
乐观锁 / 状态条件更新
```

它们解决的是不同维度的问题。

---

## 十一、为什么不直接“加并发锁，我改的时候别人都不许动”

今天提出了一个非常自然的问题：

> 我改的时候你不许动，不就一了百了吗？

这个思路对应的是：

```text
悲观锁 / 排他锁 / 分布式锁
```

本质是：

> 在操作之前先获得独占权，其他竞争者必须等待。

技术上当然可以，但不能所有场景都这么做。

---

### 1. 锁会降低并发能力

例如：

```text
A 获取锁
↓
A 修改
↓
A 提交
↓
A 释放锁
↓
B 才能继续
```

这期间：

```text
B、C、D
```

都必须等待。

如果冲突本来非常少，那么大量请求实际上是在为一个极少发生的问题付出排队成本。

乐观锁的思想则是：

```text
大多数时候不会冲突
↓
大家正常执行
↓
真正提交时再判断是否发生冲突
```

---

### 2. 后台编辑页面不适合长期持锁

例如管理员：

```text
10:00 打开编辑页面
10:05 才点击保存
```

中间 5 分钟用户可能在：

```text
思考
修改表单
接电话
离开电脑
```

如果从打开页面开始就锁数据库记录：

```text
锁 5 分钟
```

其他人都不能正常操作这条数据，代价很高。

使用乐观锁：

```text
10:00 读取 version = 5
↓
用户慢慢修改
↓
10:05 提交
↓
WHERE version = 5
```

如果期间有人已经修改：

```text
UPDATE 0 rows
```

再提示冲突即可。

---

### 3. Java synchronized 只能锁当前 JVM

假设服务部署：

```text
Server A
Server B
Server C
```

在 A 上使用：

```java
synchronized (...) {
    update();
}
```

只能约束：

```text
Server A 这个 JVM 内的线程
```

如果请求落到：

```text
Server B
```

它根本不知道 A 的 JVM 锁存在。

分布式系统中如果真的需要全局互斥，通常要考虑：

```text
数据库悲观锁
Redis 分布式锁
ZooKeeper 等协调机制
```

复杂度、故障处理和资源成本都会更高。

---

### 4. 数据库悲观锁会带来锁等待和资源占用

例如：

```sql
SELECT *
FROM account
WHERE id = 1
FOR UPDATE;
```

如果事务拿锁以后迟迟不提交：

```text
事务 A 长时间持锁
↓
事务 B 等待
事务 C 等待
事务 D 等待
```

可能进一步导致：

```text
锁等待增加
死锁概率增加
事务时间变长
连接长期被占用
连接池压力增加
请求超时
```

这与前面学习的：

```text
事务边界
接口超时
数据库连接池
```

是直接相连的。

因此：

> **“锁住别人”不是没有代价，只是把冲突处理从提交阶段提前到了等待阶段。**

---

## 十二、乐观锁和悲观锁怎么选

可以先用一个非常实用的判断方式。

### 冲突概率低

例如：

```text
两个运营人员偶尔同时编辑一条配置
异步任务偶尔重复消费
普通业务数据偶尔发生并发更新
```

优先考虑：

```text
乐观锁
version
状态条件更新
```

理由：

```text
大部分请求不会冲突
没必要让所有请求提前排队
```

---

### 冲突概率非常高

例如：

```text
大量请求争抢同一个资源
秒杀库存
抢优惠券
同一个热点账户高频更新
```

如果所有请求都：

```text
读旧数据
↓
尝试乐观锁
↓
失败
↓
重试
↓
再次冲突
```

可能造成大量无效数据库操作。

这时要根据业务考虑：

```text
数据库原子 UPDATE
Redis 原子操作
悲观锁
队列串行化
分布式锁
削峰
```

注意：

> 高冲突不等于一定要用分布式锁。

例如库存扣减往往更适合直接使用数据库原子条件更新：

```sql
UPDATE sku
SET stock = stock - 1
WHERE id = ?
  AND stock > 0;
```

具体方案要根据：

```text
冲突频率
吞吐量要求
一致性要求
数据库压力
是否跨服务
失败处理方式
```

共同决定。

## 十三、高频乐观锁冲突为什么可能是架构问题

今天第 4 个思考题：

如果线上每天大量出现：

```text
Worker A 冲突
Worker B 冲突
Worker C 冲突
...
```

今天的判断是：

> 不应该只增加重试次数，而应该怀疑是不是同一个任务被多个 Worker 高频并发处理，检查整个任务消费架构。

这个判断是核心。

大量冲突可能说明：

```text
MQ 重复投递过于频繁
ACK 机制设计不合理
消息处理完成但 ACK 失败，导致重新投递
Worker 领取任务没有原子抢占
定时扫描任务和 MQ 消费同时处理同一任务
幂等控制不足
任务状态机约束不足
同一个业务事件被重复创建
```

如果只是简单增加：

```text
retry = 3
↓
retry = 10
```

可能形成：

```text
冲突
↓
立即重试
↓
再次争抢同一条记录
↓
再次冲突
↓
数据库 QPS 上升
↓
CPU / 连接池压力增加
```

所以：

> **乐观锁冲突是结果，也可以成为系统架构异常的观测信号。**

## 十四、今天四个思考题的回答与修正

### 问题一：没有乐观锁时会发生什么

回答：

> A 的更新会被 B 覆盖。

正确。

完整理解：

```text
A：RUNNING → SUCCESS
B：RUNNING → FAILED

A 先写 SUCCESS
B 后写 FAILED
↓
最终 FAILED
```

真正的问题是：

```text
B 的 FAILED 是基于旧 RUNNING 做出的判断
```

因此属于：

```text
Lost Update / 状态覆盖
```

---

### 问题二：A 已把 version 改成 6，B 再使用 version = 5 会怎样

回答：

```text
UPDATE 0 rows
```

正确。

因为：

```text
WHERE id = 1001 AND version = 5
```

已经匹配不到数据库中的：

```text
version = 6
```

需要重点记住：

> 乐观锁冲突通常不是 SQL 报错，而是 UPDATE 影响 0 行。

---

### 问题三：B 冲突以后应该怎么办

回答思路：

```text
不能强制改 FAILED
应该重新查询最新状态
再核对业务冲突
```

核心正确。

异步 Worker 中更准确的是：

```text
重新读取任务
↓
根据最新状态决定
放弃 / 重试 / 补偿 / 记录冲突
```

而不是无条件：

```text
强制覆盖
```

因为强制覆盖等于绕过刚刚建立的并发保护。

---

### 问题四：线上大量冲突怎么办

回答：

> 大概率需要检查设计架构，而不是单纯增加重试次数。可能是一个任务被多个 Worker 高频并发处理；重试过多只会浪费资源。

这个判断正确。

排查方向：

```text
消息是否重复投递
ACK 是否异常
是否有多个消费入口
任务是否原子领取
幂等是否完整
状态机是否合法
是否存在定时任务 + MQ 双重处理
```

---

## 十五、实现时的几个常见坑

### 1. UPDATE 0 rows 后直接无限重试

错误思路：

```text
失败
↓
立即重试
↓
冲突
↓
继续重试
```

高冲突下可能放大数据库压力。

应该根据业务做：

```text
重新读取
有限重试
随机退避
直接放弃
进入补偿
告知用户冲突
```

---

### 2. 只判断异常，不检查 affected rows

例如：

```java
mapper.update(...);
// 没抛异常就认为成功
```

这是错误的。

乐观锁真正需要判断：

```text
rows == 1 → 更新成功
rows == 0 → 前提已经变化 / 发生冲突
```

---

### 3. 所有表都机械增加 version

乐观锁是解决并发修改问题的工具，不是数据库表的固定模板。

如果业务允许覆盖，或者直接使用原子 SQL 已经能解决问题：

```text
没有必要为了“看起来规范”增加 version
```

---

### 4. 把乐观锁当成分布式锁

乐观锁不会：

```text
阻止别人执行
```

它只是：

```text
提交时发现别人已经修改
```

因此不能把：

```text
乐观锁
悲观锁
分布式锁
```

混成同一个概念。

---

### 5. 乐观锁冲突后绕开 version 强制 UPDATE

例如：

```text
第一次 UPDATE 0 rows
↓
第二次直接 WHERE id = ? 强制覆盖
```

这相当于把并发控制完全绕开。

除非业务明确规定某一操作拥有更高优先级，否则不能这样处理。

---

## 十六、面试时怎么表达

可以这样回答：

> 乐观锁主要用于存在“读取数据—业务处理—再更新”时间窗口，并且不能接受旧数据覆盖新数据的场景。例如后台多人编辑配置、订单状态流转、异步 Worker 并发更新任务状态等。常见实现是在表里增加 version 字段，读取时拿到 version，更新时把 version 放进 WHERE，同时 version + 1。如果 affected rows 为 0，就说明数据在这段时间已经被其他请求修改，需要重新读取最新状态，再根据业务决定有限重试、放弃、补偿或者提示冲突。
>
> 乐观锁和悲观锁的区别是，悲观锁先阻止其他请求修改，乐观锁允许并发执行，只在提交时检查冲突。低冲突场景使用乐观锁通常并发能力更高；如果大量请求持续争抢同一个热点资源，乐观锁会产生大量失败和重试，这时应该考虑数据库原子操作、Redis 原子操作、队列串行化、悲观锁或者分布式锁等方案，而不是无限增加重试次数。

如果结合 AI 异步任务，可以继续补充：

> 比如同一条 RUNNING 任务因为消息重复被两个 Worker 同时处理，一个准备写 SUCCESS，一个准备写 FAILED。如果没有并发控制，后执行的 Worker 可能直接覆盖前面的结果。通过 version 或 `WHERE status = 'RUNNING'` 做条件更新，可以让第二个更新返回 0 行，然后重新读取最新状态，避免旧业务判断覆盖已经完成的最终状态。

## 十七、把乐观锁和之前的知识串起来

### 状态机

状态机解决：

```text
哪些状态允许转换到哪些状态
```

例如：

```text
RUNNING → SUCCESS
RUNNING → FAILED
SUCCESS 不能重新回到 RUNNING
```

乐观锁解决：

```text
多个并发执行者同时修改时
如何避免旧状态覆盖新状态
```

两者经常组合：

```sql
UPDATE task
SET status = 'SUCCESS',
    version = version + 1
WHERE id = ?
  AND status = 'RUNNING'
  AND version = ?;
```

---

### 幂等

幂等解决：

```text
重复请求不要重复产生业务副作用
```

乐观锁解决：

```text
并发修改不要互相静默覆盖
```

异步系统中通常两者都需要。

---

### MQ ACK / 重试

如果 ACK 失败：

```text
消息可能重新投递
↓
多个 Worker 可能再次处理同一任务
```

所以：

```text
ACK / 重试机制
+
幂等
+
状态机
+
乐观并发控制
```

需要放在同一条任务可靠性链路中理解。

---

### 分布式锁

分布式锁是：

```text
先抢到锁
↓
只有持锁者允许执行
```

乐观锁是：

```text
大家可以执行
↓
提交时检查数据是否变化
```

因此选择关键不是：

```text
哪个技术更高级
```

而是：

```text
冲突概率有多高
是否必须串行
等待成本有多高
数据库压力有多大
失败能否重试
业务是否允许冲突后重新计算
```

---

## 十八、今天最终建立的核心认知

### 1. 乐观锁最核心的问题是“旧数据覆盖新数据”

以后看到：

```text
SELECT
↓
业务处理
↓
UPDATE
```

就要考虑中间的数据变化窗口。

### 2. version 只是实现手段，不是乐观锁本身

核心是：

```text
提交时验证业务前提是否仍然成立
```

所以也可以使用：

```text
WHERE status = 'RUNNING'
```

这类条件更新。

### 3. affected rows = 0 是非常重要的业务信号

它可能表示：

```text
数据已经被别人修改
状态已经变化
业务前提已经失效
```

不能只把它当成“更新失败，再来一次”。

### 4. 乐观锁不是幂等

```text
幂等 → 重复执行
乐观锁 → 并发覆盖
```

两者解决的问题不同。

### 5. 悲观锁不是免费的

它会带来：

```text
等待
锁竞争
事务变长
死锁风险
连接池压力
吞吐下降
```

所以低冲突场景没有必要让所有请求提前排队。

### 6. 高频乐观锁冲突不是只靠增加重试解决

如果同一任务持续被多个 Worker 并发处理：

```text
应该检查消息、ACK、任务领取、幂等和状态机设计
```

而不是只扩大重试次数。

### 7. 数据库执行顺序不等于业务正确性

```text
最后一个 UPDATE
```

不代表：

```text
最后一个业务结论一定正确
```

必须判断这个更新是否仍然基于有效的数据和合法状态。

---

## 十九、能力定位

数据库乐观锁并不是只会写：

```sql
WHERE version = ?
```

真正有工程价值的是能够识别：

```text
读取和更新之间是否存在时间窗口
并发请求是否可能基于旧数据决策
状态覆盖是否能被业务接受
什么时候用 version
什么时候直接使用状态条件更新
什么时候应该使用原子 SQL
什么时候乐观锁冲突已经暴露架构问题
什么时候需要悲观锁、队列或分布式锁
```

掌握这些以后，乐观锁才从一个数据库字段升级为：

> **并发业务中的数据一致性与状态竞争控制能力。**
