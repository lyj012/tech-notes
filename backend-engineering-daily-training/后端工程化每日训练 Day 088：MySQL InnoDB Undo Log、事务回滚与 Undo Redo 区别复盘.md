# 后端工程化每日训练 Day 88：MySQL InnoDB Undo Log、事务回滚与 Undo Redo 区别复盘

## 一、今天学习什么

承接 Day 86 的 **InnoDB Buffer Pool** 和 Day 87 的 **Redo Log**，今天只学习一个核心机制：

> **MySQL InnoDB 中，事务已经执行 UPDATE，为什么在执行 ROLLBACK 后，还能撤销修改并恢复事务开始前的数据状态？**

今天的新概念是 **Undo Log（撤销日志）**。本次目标只有三个：

1. 理解 Undo Log 为什么存在，以及它如何帮助事务回滚；
2. 判断同一事务内多次 UPDATE、修改多条记录后的完整回滚结果；
3. 区分 Undo Log 的撤销作用与 Redo Log 的重做作用。

本次沿用熟悉的 Java 支付、账户余额与转账场景。今天**没有**展开 MVCC、Binlog、Undo Log 真实记录格式、复杂崩溃恢复流程，也没有执行 MySQL 实机实验。

按照 V3.2，先用具体 SQL 建立直觉；答不出时降低难度、做同构巩固；当基础机制和简单迁移已经通过，就结束主要训练，不为凑题数继续追问。

## 二、真实问题：UPDATE 成功后，为什么 ROLLBACK 还能恢复原值？

假设 Java 后端的支付系统使用 InnoDB 存储账户余额：

~~~text
账户 id = 1001
原始 balance = 100
~~~

数据库开启一个事务：

~~~sql
START TRANSACTION;

UPDATE account
SET balance = 50
WHERE id = 1001;
~~~

UPDATE 执行成功，在当前事务内查询可以看到余额为 50 元。随后业务校验失败：

~~~sql
ROLLBACK;
~~~

回滚完成后，余额应恢复为 **100 元**，而不是停留在 50 元。

注意这里有两层不同含义：

- **SQL 已经执行成功**：在事务内确实发生了修改；
- **事务尚未提交，随后执行了 ROLLBACK**：这次事务里的修改要被撤销。

这就需要 InnoDB 在修改数据时保留足够的信息，才能在事务决定回滚时找回修改前的状态。

---

## 三、核心机制：Undo Log 为撤销修改提供所需信息

今天使用的简化理解模型：

~~~text
原始余额：100
    ↓
开始事务
    ↓
执行 UPDATE：100 → 50
    ↓
InnoDB 保留用于撤销本次修改的 Undo 信息
    ↓
业务校验失败
    ↓
执行 ROLLBACK
    ↓
InnoDB 利用 Undo 信息撤销事务修改
    ↓
余额恢复为：100
~~~

**这个图只用于说明逻辑关系，不是 InnoDB 生成 Undo、修改页面等内部操作的严格执行时序。**

可以先把 Undo Log 理解为：

> **InnoDB 为了能够撤销事务内的修改，记录恢复所需的 Undo 信息；事务回滚时利用这些信息撤销相关修改。**

它不应被简单理解为“数据库只存一份旧值”，真实 Undo 记录格式要复杂得多；今天不学习这些内部细节。

还要建立一个边界：**Undo Log 为 InnoDB 数据库事务回滚提供支持，不会自动撤销外部系统已经完成的操作**。例如数据库事务回滚，不代表第三方支付接口已经发生的扣款也会自动撤销。

## 四、第 1 题：单条 UPDATE 回滚后余额是多少？

### 题目

~~~sql
-- 初始 balance = 100
START TRANSACTION;

UPDATE account
SET balance = 50
WHERE id = 1001;

-- 后续业务校验失败
ROLLBACK;
~~~

问题：回滚后余额是 100 还是 50？为什么？

### 我的回答（按当时口述整理）

> 肯定是一百块。因为有专门用于回滚的日志，叫 Undo Log。回滚之后就恢复为修改之前的数字。

### 评估

**正确。**

已经能独立判断余额回到 100，并主动说出 Undo Log 的主要用途。这里体现的是对单次修改回滚结果的理解。

但只答对这一题，还不能证明已经理解“一个事务里连续改多次”时的回滚范围，所以继续做简单迁移。

## 五、第 2 题：同一事务连续 UPDATE 两次，会回到哪个值？

### 原题

账户最初有 100 元：

~~~sql
START TRANSACTION;

UPDATE account
SET balance = 80
WHERE id = 1001;

UPDATE account
SET balance = 60
WHERE id = 1001;

ROLLBACK;
~~~

问题：最终余额是 100、80，还是 60？

### 我的第一次回答（按当时口述整理）

> 第一次改成 80，第二次改成 60，两条 UPDATE 都成功。最后回滚到底是多少？我不知道，你教教我。

### 评估与纠错

**第一次没有独立答出；不能记为首次通过。**

这里需要建立的不是“只撤销最后一条 UPDATE”，而是：

> **ROLLBACK 对当前事务执行完整回滚时，会撤销该事务中尚未提交的修改，而不是只撤销最后一次修改。**

可以用一个简化的逆向撤销过程理解：

~~~text
初始余额 100
    ↓
第一次 UPDATE：100 → 80
    ↓
第二次 UPDATE：80 → 60
    ↓
ROLLBACK
    ↓
撤销第二次修改：60 → 80
    ↓
撤销第一次修改：80 → 100
    ↓
最终余额 100
~~~

这不是要求记住 Undo Log 的真实内部记录和回滚算法，而是用直觉理解完整事务回滚的结果。

### 同构巩固题

随后换一组数字：

~~~sql
-- 初始 balance = 200
START TRANSACTION;

UPDATE account SET balance = 170 WHERE id = 1001;
UPDATE account SET balance = 150 WHERE id = 1001;

ROLLBACK;
~~~

### 我的巩固回答（按当时口述整理）

> 最终是 200 块钱。因为只要还在同一个事务里，没有提交，执行回滚就会把这个事务里尚未提交的修改全部回滚。

### 评估

**巩固题正确，通过同构迁移。**

这道题的真实学习过程是：

~~~text
首次：100 → 80 → 60 → ROLLBACK
    ↓
不能独立判断，主动提出疑问
    ↓
解释“完整事务回滚”的范围
    ↓
巩固：200 → 170 → 150 → ROLLBACK
    ↓
独立判断恢复为 200
~~~

不能因为后面的巩固题做对，就抹掉第一次不会的事实；同时也不能因为第一次不会，就忽视纠错后已经建立的理解。

## 六、第 3 题：同一事务修改两条不同记录

### 题目

模拟 Java 支付系统的两账户转账场景：

~~~text
账户 A：初始余额 100 元，id = 1
账户 B：初始余额  50 元，id = 2

目标：A 给 B 转账 20 元
~~~

~~~sql
START TRANSACTION;

-- A 扣 20 元
UPDATE account
SET balance = 80
WHERE id = 1;

-- B 加 20 元
UPDATE account
SET balance = 70
WHERE id = 2;

-- 后续业务校验失败
ROLLBACK;
~~~

两条 UPDATE 都执行成功，但最终回滚。问：A、B 分别剩多少钱？

### 我的回答（按当时口述整理）

> A 恢复到 100，B 恢复到 50。虽然 UPDATE 的是不同 ID，但还是在同一个事务下面，所以都会恢复之前的初始余额。

### 评估

**正确，完成对不同记录的简单迁移。**

最有价值的部分不只是说出两个数字，而是能说明：

- 回滚范围**不由记录 ID 是否相同决定**；
- 它取决于相关修改是否属于**同一个数据库事务**；
- 完整 ROLLBACK 会撤销这个事务中尚未提交的相关修改。

这里的转账只用于说明同一个 InnoDB 事务包含多条修改，并不等于已经训练了真实支付清结算、第三方接口一致性或并发余额扣减设计。

## 七、第 4 题：Undo Log 与 Redo Log 的区别

### 题目

**场景 A：事务失败，需要撤销。**

~~~text
UPDATE 执行成功
    ↓
业务校验失败
    ↓
ROLLBACK
    ↓
恢复修改前的数据
~~~

**场景 B：事务已成功提交，但数据页尚未写回。**

~~~text
UPDATE 执行成功
    ↓
COMMIT 成功，Redo Log 已可靠持久化
    ↓
数据页尚未写回数据文件
    ↓
服务器突然断电
    ↓
InnoDB 重启并恢复需要重做的修改
~~~

问：A、B 分别主要依靠哪种日志？为什么？

### 我的回答（按当时口述整理）

> A 毫无疑问是 Undo Log。因为事务执行了 UPDATE，但业务失败，需要回滚成修改之前的样子。B 是提交成功之后服务器宕机，Redo Log 已持久化，所以恢复时依靠 Redo Log。

### 评估

**正确。** 已能从具体故障场景判断两类日志的主要用途：

| 日志 | 今天掌握的核心作用 | 对应场景 |
| --- | --- | --- |
| **Undo Log** | 为撤销事务修改提供信息 | 未提交事务需要 ROLLBACK |
| **Redo Log** | 为重做必要的页面修改提供信息 | 满足持久化前提下，恢复已提交但数据页尚未写回的修改 |

必须保留边界：不能把两种日志机械说成“Undo 只属于 ROLLBACK、Redo 只属于 COMMIT”；真实 InnoDB 的日志与恢复机制存在更复杂的配合，但今天没有展开。

## 八、今天实际需要保留的纠错与边界

### 1. 没有 COMMIT，不代表数据库会立即自动 ROLLBACK

在第 4 题解释时，我说了类似：

> “只要没提交，那么它就会回滚。”

这个说法容易产生误解。

准确判断：

- **事务还没提交**：它仍可能处于进行中的状态；
- **执行 ROLLBACK**：明确要求数据库撤销当前事务的修改；
- **事务被中止**：例如连接断开等情况，也可能由数据库进行回滚；
- **COMMIT 成功之后**：不能指望后来单独执行 ROLLBACK 就撤销此前已经提交的事务。

所以不能写成“只要没提交就自动回滚”，今天能够证明的是：**在题目明确执行 ROLLBACK 的前提下，能判断完整回滚的结果。**

### 2. Undo Log 撤销数据库事务，不会自动撤销所有业务副作用

假设业务同时修改了数据库记录，并向第三方支付平台发起支付：

~~~text
InnoDB 事务内修改 account
    ↓
事务外或跨系统调用第三方支付
    ↓
第三方支付操作已经完成
    ↓
数据库事务 ROLLBACK
~~~

**数据库回滚不能自动让第三方已经完成的支付操作撤销。**

这与 Day 79 学过的 Spring 事务边界相呼应。但今天只是再次确认边界，并未设计或验证跨系统补偿、支付一致性方案。

### 3. 别把教学模型当成真实 Undo Log 结构

“100 → 80 → 60，再逆向撤销回 100”是帮助理解回滚结果的简化模型。

不能据此宣称已经掌握：

- Undo Log 的真实记录格式；
- Undo 页或撤销记录链的内部实现；
- Undo 与 MVCC 的关系；
- 崩溃恢复时的 Undo、Redo 配合；
- 大事务回滚的资源成本和性能影响。

这些都没有在今天专项训练。

## 十二、昨日核心知识回忆：Day 87 Redo Log

按照 V3.2，先完成今日 Undo Log 的理解和问答，最后才回忆上一训练日的唯一核心知识点。

### 题目

Java 订单系统执行：

~~~sql
UPDATE orders
SET status = 'PAID'
WHERE id = 1001;

COMMIT;
~~~

给定条件：

~~~text
COMMIT 已成功返回
Redo Log 已可靠持久化
修改后的数据页还没写回数据文件
服务器突然断电
~~~

同事认为：

> “磁盘数据页还没改成功，因此 Java 必须再执行一次 UPDATE，订单才能恢复为 PAID。”

问：是否同意？为什么？

### 我的回答（按当时口述整理）

> 肯定不同意。Redo Log 已经持久化，没有必要画蛇添足让 Java 再执行 UPDATE。数据库可以根据 Redo Log 恢复这次修改。

但我还说：

> “磁盘会根据 Redo Log 来重新写入一次。”

### 评估与纠错

**核心判断正确；恢复执行主体的表述再次出现偏差。**

准确说法是：

~~~text
服务器重启
    ↓
MySQL / InnoDB 执行崩溃恢复
    ↓
读取并应用需要重做的 Redo Log 记录
    ↓
使相关页面恢复到正确状态
    ↓
恢复产生的脏页可以在之后写回数据文件
~~~

应该记住：

- **恢复逻辑由 InnoDB 执行**，不是“磁盘自己根据日志恢复”；
- **日志持久化和完整数据页写回不是同一回事**；
- **InnoDB 利用日志恢复修改，不等于让 Java 重新执行原业务 UPDATE**；
- 判断成立依赖本题已给定的持久化和正常恢复前提。

这一点在 Day 87 已经纠正过，Day 88 回忆时又出现类似口误，应作为**后续需要再次巩固的薄弱点**，不能标记为完全稳定掌握。

**昨日回忆结论：Redo Log 的核心作用能够准确回忆；InnoDB 与磁盘的角色区分仍需要巩固。**

## 十三、今天真正建立的判断模型

连续三个训练日的知识可以这样串起来：

~~~text
Day 86：Buffer Pool
    ↓
数据页可以在内存中缓存、修改
    ↓
解决：为什么不必每次查询都从磁盘重新读取页？

Day 87：Redo Log
    ↓
修改后的数据页不一定在事务提交时立即写回数据文件
    ↓
解决：满足持久化前提时，已提交修改如何应对异常断电？

Day 88：Undo Log
    ↓
事务已经修改数据，但最终需要撤销
    ↓
解决：ROLLBACK 如何撤销同一事务内尚未提交的修改？
~~~

本次最终保留五个结论：

1. **UPDATE 成功执行，不等于整个事务已经 COMMIT。**
2. **Undo Log 保存撤销事务修改所需的信息，让 ROLLBACK 可以撤销当前事务的修改。**
3. **同一事务内多次 UPDATE 或修改多条记录，完整回滚时都要撤销属于该事务的尚未提交修改。**
4. **Undo 侧重撤销，Redo 侧重重做；二者作用不同，实际底层关系比今天的简化模型更复杂。**
5. **数据库事务的回滚不等于所有外部业务操作都被撤销；理解日志机制之前，还要确认实际事务边界。**

> **Day 86 学会“数据为什么能够按页缓存在内存”；Day 87 学会“已提交修改为什么能在满足条件时通过日志恢复”；Day 88 学会“未提交修改为什么能被数据库事务完整撤销”。**
