## 二、真实问题：同一个事务，为什么两种 SELECT 看到的结果不同？

模拟监控系统的设备状态表：

~~~sql
CREATE TABLE monitor_host (
    id BIGINT PRIMARY KEY,
    status INT
) ENGINE=InnoDB;
~~~

~~~text
id = 1001
status = 0    -- 离线
status = 1    -- 在线
~~~

**本次场景前提：** InnoDB；事务隔离级别为 `REPEATABLE READ`（可重复读）；`id = 1001` 已存在；无其他并发事务继续修改或阻塞此行；事务 A 自己未修改该行；所有 SQL 都按下述时序执行，事务 A 始终保持开启。

事务 A 第一次普通读取：

~~~sql
START TRANSACTION;

SELECT status
FROM monitor_host
WHERE id = 1001;
-- 0
~~~

事务 B 修改并成功提交：

~~~sql
START TRANSACTION;

UPDATE monitor_host
SET status = 1
WHERE id = 1001;

COMMIT;
~~~

此时最新已提交的 `status` 是 `1`，但 A 在原事务里使用不同方式读取，结果可能不同：

~~~sql
-- 普通一致性读取：本题中仍为 0
SELECT status
FROM monitor_host
WHERE id = 1001;

-- 锁定读取：本题中为 1
SELECT status
FROM monitor_host
WHERE id = 1001
FOR UPDATE;
~~~

这里不是 SQL 查询结果被简单缓存，也不是 B 更新失败，而是两类读取遵循了不同的版本可见性与加锁规则。

## 三、今天补上的核心机制：快照读与当前读

### 1. 快照读（Snapshot Read）

在本次 InnoDB `REPEATABLE READ` 场景中，普通非锁定 `SELECT` 使用一致性读取：

- A 第一次普通一致性读取建立 Read View；
- 后续普通一致性读取通常继续沿用这份 Read View；
- B 后来提交的新版本不符合 A 原来视图的可见性要求；
- InnoDB 可借助 Undo 信息重建符合视图的历史版本，因此 A 仍可以读到 `0`。

**Read View 决定“哪个版本可见”，不等于缓存某条 SELECT 的查询结果。**

### 2. 当前读（Current Read）

`SELECT ... FOR UPDATE` 是锁定读取。它与普通快照读不同：

- 不沿用普通快照读的旧 Read View 来决定本次读取结果；
- 需要读取并锁定适用的当前记录版本；
- 在本题 B 已提交且没有其他事务阻塞的条件下，读取 `1`；
- 此次锁定读取本身**不会把 A 先前的 Read View 更新成新的视图**；
- 在显式事务中，其取得的锁可能保持到事务提交或回滚，而不只是 SQL 语句执行期间。

用一句话区分：

> **快照读：按 Read View 的可见性规则读取相应版本。当前读：读取适用的当前记录版本，并执行相应加锁。**

“当前读一定立即读到全数据库最新值”是过度简化：遇到其他事务尚未释放的冲突锁时，可能需要等待或最终报错；实际读取结果也受事务自己修改、查询条件和并发时序影响。

## 四、第 1 题：A 的 SELECT ... FOR UPDATE 读到 0 还是 1？

### 题目

~~~text
初始：status = 0

事务 A：
    普通 SELECT → 0
    不提交

事务 B：
    UPDATE status = 1
    COMMIT 成功

事务 A：
    SELECT ... FOR UPDATE
    → 0 还是 1？
~~~

### 我的回答（按当时口述整理）

> 如果是普通 SELECT，我认为还是读 0。但是后面加了 FOR UPDATE，我觉得它应该查到最新的数据，所以我认为是 1。

回答时曾将 `FOR UPDATE` 口述成类似“Full Update”，但没有影响场景判断。

### 评估

**读取结果独立答对；原因有正确直觉，锁定读取的机制还需补充。**

在题目给定前提下，A 最后读取 `1`，因为这次是**当前读**，而不是沿用旧 Read View 的快照读。

同时纠正两个容易混淆的表达：

- SQL 关键字是 **`FOR UPDATE`**，不是 `FULL UPDATE`；
- `FOR UPDATE` 并非“强制刷新缓存”，它的关键特征是**锁定读取**，适用于需要锁住相关记录以配合后续业务操作的场景。

## 五、第 2 题：当前读以后再普通 SELECT，还能读到 0 吗？

### 题目

延续前面的时序，A 在 B 提交后，先执行锁定读取，再执行普通查询：

~~~sql
-- 第一次：锁定读取
SELECT status
FROM monitor_host
WHERE id = 1001
FOR UPDATE;

-- 第二次：普通一致性读取
SELECT status
FROM monitor_host
WHERE id = 1001;
~~~

A 在更早时已经通过普通 SELECT 建立了读到 `0` 的 Read View，且自己没有修改这条记录。

问：这两次各读到多少？为什么？

### 我的回答（按当时口述整理）

> 上面有 FOR UPDATE 的，状态是 1。下面没有 FOR UPDATE 的，是 0。我认为当前读不会让原来的东西发生变化，因为这次查询的条件只对当前语句起作用，不会影响后面的查询。

### 评估与纠错

**两次结果独立答对；“当前读不更新原 Read View”的直觉正确，但“查询的影响只在本条 SQL 内”不准确。**

正确结果：

| 执行顺序 | SQL 类型 | 本题读取结果 | 原因 |
| --- | --- | --- | --- |
| A 最初普通 SELECT | 快照读 | `0` | 建立较早的 Read View |
| B UPDATE 后 COMMIT | 写入提交 | 最新提交值变成 `1` | B 修改成功 |
| A 的 `SELECT ... FOR UPDATE` | 当前读 / 锁定读 | `1` | 读取当前记录并加锁 |
| A 随后的普通 SELECT | 快照读 | `0` | A 仍沿用先前的 Read View |

关键区分：

~~~text
当前读可以看见 B 已提交的新版本
                 ≠
当前读会更新 A 原来的 Read View
                 ≠
当前读的加锁效果只持续一条 SQL
~~~

当前读虽然通常不会刷新之前的 Read View，但 `FOR UPDATE` 加的锁可以在事务内持续存在。**“读取结果”和“锁的生命周期”是两个不同的问题。**

本题只讨论 A 自身没有修改这条记录的情况。如果 A 后续自行 `UPDATE`，普通一致性读取也需要考虑事务“看见自己修改”的规则，不能机械套用“普通 SELECT 永远是 0”。

## 六、第 3 题：另一个事务 UPDATE，为什么需要等待？

### 题目

事务 A：

~~~sql
START TRANSACTION;

SELECT status
FROM monitor_host
WHERE id = 1001
FOR UPDATE;
-- 读到 1
-- A 没有 COMMIT，也没有 ROLLBACK
~~~

另一个事务 C 执行：

~~~sql
UPDATE monitor_host
SET status = 0
WHERE id = 1001;
~~~

问题：C 能立即完成更新，还是必须等待？

### 我的回答（按当时口述整理）

> 应该必须等待。因为 A 的 FOR UPDATE 按照刚才讲的会加锁。除非 A 提交或者回滚，否则另一个事务现在更新不了。

### 评估

**正确。已能将“锁定读取”迁移到另一事务写入同一行的场景。**

在本题以主键精确命中已存在记录的前提下，可简化理解为：

~~~text
事务 A：
    SELECT ... FOR UPDATE
    → 读取 status = 1
    → 持有与更新该行冲突的排他锁
    → 事务保持开启
                 ↓
事务 C：
    UPDATE 同一行
    → 需要取得冲突的锁
    → 暂时不能完成，进入等待
                 ↓
事务 A：
    COMMIT 或 ROLLBACK
    → 释放持有的锁
                 ↓
事务 C：
    如果仍可继续执行，取得锁后完成更新
~~~

必须区分：

- **等待**：C 暂时拿不到需要的锁，不等于 UPDATE 已经失败；
- **成功**：A 及时结束、C 获得所需锁后，才可能继续完成；
- **失败**：实际系统中也可能遇到锁等待超时、死锁或其他错误。

锁的范围受索引、谓词、隔离级别等因素影响；本题仅考察 **主键等值匹配一条已存在的记录**，不把这次表现推广为所有 `FOR UPDATE` 查询都只锁一行。

## 八、今天最重要的两处校准

### 1. `FOR UPDATE` 不是简单地“查询最新值”

最初用“多了 `FOR UPDATE`，所以查最新的”建立了正确直觉。

但在工程中必须补上：

> **它属于锁定读取，既涉及当前记录版本，也涉及可能持续到事务结束的锁。**

不能把 `FOR UPDATE` 当成没有副作用的“读最新值开关”。

### 2. 当前读不会刷新旧 Read View，但会影响后续并发

第二题说“这次查询的条件只对当前语句起作用”，在“没有更新原 Read View”这一点上方向正确；但不能据此推导出“其他事务不会受到影响”。

~~~text
SELECT ... FOR UPDATE
    ├── 读取结果：本题中看到最新已提交的 1
    ├── 原 Read View：未因此刷新
    └── 加锁效果：A 不提交时，其他事务修改同行可能阻塞
~~~

这是本日需要长期保留的工程判断：**快照可见性与写锁生命周期不能混为一谈。**

## 九、与 Java / Spring Boot 工程实践的关系

将本题迁移到监控平台设备状态、库存或订单状态更新：

~~~text
Java 请求 A 开启数据库事务
    ↓
普通 SELECT 查到设备状态 0
    ↓
另一个请求 B 更新为 1 并提交
    ↓
A 再次普通 SELECT 仍查到 0
    ↓
A 使用 SELECT ... FOR UPDATE
    ↓
本题条件下查到当前值 1，并锁住该行
    ↓
其他请求尝试 UPDATE 同行
    ↓
可能因等待 A 释放锁而阻塞
~~~

实际排查时应确认：

1. 真正的事务边界是什么，`@Transactional` 是否生效，是否同一数据库连接和事务；
2. 数据库隔离级别是什么，之前是否已经建立 Read View；
3. SQL 是普通一致性读取，还是 `SELECT ... FOR UPDATE` 之类的锁定读取；
4. 对应事务是否一直未提交/回滚，是否导致其他请求锁等待。

**不能仅因看到旧值就断言 Redis/MySQL 缓存故障，也不能为获得新值而随意给所有 SELECT 加 `FOR UPDATE`。** 后者会引入竞争、等待以及更长的锁持有时间。

这是一项从课堂场景推导出的工程提醒，**并非本次已经排查了真实生产故障**。

### 补充讲解（讲解后的知识，不等于已独立验证）

- **MVCC**：多版本并发控制，让不同事务按可见性规则读取数据版本；
- **Read View**：在本题 RR 场景中，A 第一次普通一致性读取创建的视图，供后续一致性读取继续使用；B 后来提交的新版本对 A 原视图不可见；
- **Undo Log**：除帮助事务撤销修改，还提供重建符合读视图的历史记录版本所需的信息；
- **结果**：B 最新提交值是 `1`，但 A 沿用原视图仍可查到 `0`。

~~~text
A 首次普通 SELECT
    → 建立 Read View，读到 0
    ↓
B UPDATE 并 COMMIT
    → 最新提交版本为 1
    ↓
A 后续普通 SELECT
    → 沿用旧 Read View
    → 新版本对该视图不可见
    → 借助历史版本信息读到 0
~~~

上述是便于记忆的**概念模型**，不是完整的 InnoDB 内核执行时序。

本次补讲后直接结束，没有再做新题验证，因此准确结论是：**复习时不能独立解释，已重新讲解，是否重新掌握尚待下一次检查。**

## 十四、今天真正建立的判断模型

~~~text
MySQL InnoDB / REPEATABLE READ
              ↓
事务 A 普通 SELECT
    → 快照读：依据 Read View 选可见版本
              ↓
事务 B UPDATE 并 COMMIT
    → 最新提交版本从 0 变成 1
              ↓
事务 A 再普通 SELECT
    → 沿用原 Read View：本题仍读 0
              ↓
事务 A SELECT ... FOR UPDATE
    → 当前读：本题读 1
    → 对适用记录加锁
              ↓
事务 A 不结束，另一个事务想 UPDATE 同行
    → 可能被锁阻塞
              ↓
事务 A COMMIT / ROLLBACK
    → 释放锁，等待者才有机会继续
~~~

这是用于本次具体并发条件的简化判断图，**不应机械推广到所有查询、所有隔离级别或所有锁范围**。

今天保留五个结论：

1. **普通快照读按 Read View 看符合可见性规则的版本；FOR UPDATE 属于当前读/锁定读取。**
2. **在本题条件下，B 已提交后，A 的普通 SELECT 仍可读到 0，而 FOR UPDATE 读到 1。**
3. **一次 FOR UPDATE 不会自动刷新 A 早先的一致性读取视图，后续普通 SELECT 在本题仍可读到 0。**
4. **FOR UPDATE 的锁效果可以跨 SQL 持续到事务结束，另一个事务更新同行可能需要等待。**
5. **今日当前读主线通过，但昨日 MVCC / Read View / Undo 的机制回忆未通过，下一次应先验证这一薄弱点。**
