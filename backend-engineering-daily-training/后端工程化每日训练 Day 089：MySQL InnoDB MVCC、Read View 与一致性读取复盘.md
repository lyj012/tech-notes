## 二、真实问题：事务 B 提交了，事务 A 为什么还是读到旧值？

模拟监控平台的设备状态表：

~~~sql
CREATE TABLE monitor_host (
    id BIGINT PRIMARY KEY,
    status INT
);
~~~

初始记录：

~~~text
id = 1001
status = 0
~~~

**前提：** MySQL InnoDB，隔离级别为 `REPEATABLE READ`；事务 A 使用普通非锁定 SELECT；事务 A 没有自行修改这条记录，也没有进行锁定读取。

### 事务 A：先开始并读取旧状态

~~~sql
START TRANSACTION;

SELECT status
FROM monitor_host
WHERE id = 1001;
-- 结果：0
~~~

事务 A 保持开启，不提交、不回滚。

### 事务 B：更新并提交

~~~sql
START TRANSACTION;

UPDATE monitor_host
SET status = 1
WHERE id = 1001;

COMMIT;
~~~

事务 B 已提交成功，此时最新提交的设备状态是 `1`。

### 事务 A：在原事务中再次普通查询

~~~sql
SELECT status
FROM monitor_host
WHERE id = 1001;
-- 在本题条件下，结果仍为：0
~~~

这不是事务 B 更新失败，更不是“数据库一定有缓存错误”。

**核心区别：最新提交版本，不一定等于每个尚未结束的事务当前可见的版本。**

## 三、核心机制：MVCC、Read View 与 Undo Log 的分工

MVCC 的完整名称是 **Multi-Version Concurrency Control（多版本并发控制）**。

今天采用的简化理解：

- **MVCC**：通过多版本及可见性规则，让不同事务能够读取符合各自规则的数据版本；
- **Read View**：用来判断哪些事务产生的数据版本对当前一致性读取可见；
- **Undo Log**：除支持事务回滚外，还为重建历史记录版本提供所需信息。

本题里，事务 A 在 `REPEATABLE READ` 下首次进行普通一致性读取时，建立可见性视图。后续普通一致性读取沿用这个视图。事务 B 后来提交的新版本不符合事务 A 这个视图的可见性要求，因此 A 仍可通过旧版本信息读取到 `0`。

~~~text
初始记录：status = 0
      ↓
事务 A 首次普通 SELECT → 读到 0
      ↓
事务 A 建立用于一致性读取的 Read View
      ↓
事务 B UPDATE：0 → 1，并 COMMIT 成功
      ↓
最新提交的状态：1
      │
      ├── 事务 A：沿用之前的 Read View
      │            读取旧版本 → 0
      │
      └── 新事务 C：提交后首次普通一致性读取
                   看到已提交的新版本 → 1
~~~

**注意：这是概念图，不是 InnoDB 内部执行、生成 Undo 和创建视图的严格时序。** Read View 不是把每条 SELECT 的查询结果简单缓存起来；Undo Log 也不是必须直接保存一整份可供查询的旧记录。

今天需要建立的核心判断是：

> **MVCC 解决的是事务读取哪个版本的问题；事务 B 提交成功与事务 A 仍然读取旧版本，可以同时成立。**

## 四、第 1 题：事务 A 第二次读到 0 还是 1？

### 题目

事务 A 第一次普通 SELECT 读到 `status = 0`，但没有结束。

事务 B 将同一条记录更新为 `status = 1` 并提交。

事务 A 再次执行普通查询：

~~~sql
SELECT status
FROM monitor_host
WHERE id = 1001;
~~~

问题：A 第二次得到 `0` 还是 `1`？为什么？

### 我的回答（按实际口述整理）

> 肯定查询的是 0。因为 MVCC 多版本并发控制。事务 A 在同一个事务里之前查到的是 0，继续查还是 0。

### 评估

**结果正确；原因说明不够完整。**

当时能独立判断第二次仍为 `0`，并说出 MVCC 这个机制名称。但“因为 MVCC”主要是在复述概念，还没有说清楚：

- 事务 A 为什么能够维持原来的数据可见性；
- 事务 B 提交后，新旧版本为什么可以同时供不同事务读取；
- Undo Log 在其中扮演什么角色。

所以第 1 题应记录为：**结果独立答对，机制解释需要补足**，不能直接记为完整掌握 MVCC 原理。

## 五、第 1 题后的补充讲解：为什么不是直接读取最新值？

针对第一次回答，补充了以下关系：

~~~text
A 首次普通一致性读取
    ↓
建立 Read View
    ↓
B 更新并提交 status = 1
    ↓
A 仍沿用原来的 Read View
    ↓
B 的新版本对 A 的这次一致性读取不可见
    ↓
InnoDB 可利用 Undo 信息构造符合视图的旧版本
    ↓
A 再次读到 status = 0
~~~

需要区分三个容易混在一起的概念：

| 概念 | 本次要求理解的作用 | 不应误解为 |
| --- | --- | --- |
| MVCC | 让事务按可见性规则读取对应版本 | “只要开启事务，所有查询永远不变” |
| Read View | 判断数据版本对一致性读取是否可见 | 缓存每条 SQL 的查询结果 |
| Undo Log | 支持事务撤销和历史版本重建 | 只有 ROLLBACK 才用得到的日志 |

另一个重要条件：在本题常规 `START TRANSACTION` 场景下，`REPEATABLE READ` 的 Read View 通常在**第一次一致性读取**时建立，而不是简单地把“执行 START TRANSACTION 的时刻”当成所有情况下的快照时刻。

这部分是**讲解后补足的认识**，不是第 1 题中已经独立完整答出的内容。

## 六、第 2 题：新的事务 C 为什么读到 1？

### 题目

已知：

~~~text
事务 A：第一次普通查询读到 status = 0，至今没有结束
事务 B：已将 status 修改为 1，且 COMMIT 成功
事务 A：第二次普通查询仍读到 0
~~~

此时，一个**全新的事务 C** 在 B 提交之后开始，并进行首次普通查询：

~~~sql
START TRANSACTION;

SELECT status
FROM monitor_host
WHERE id = 1001;
~~~

问题：C 得到 `0` 还是 `1`？为什么同一条记录在 A 和 C 中结果不同？

### 我的回答（按实际口述整理）

> 肯定是 1。A 要保证同一个事务里查询数据的一致性，之前读的是 0，所以再次查询还是 0。新的事务 C 应该读取最新的数据，所以它查到状态 1。

解释过程中，我还把 `Undo Log` 口述成了类似 “under lock” 的发音，术语不够准确。

### 评估与补充

**简单迁移正确。**

在上一题的解释之后，这次能够独立完成以下判断：

1. A 仍在原事务里，普通一致性读取保持之前的可见性，所以得到 `0`；
2. C 是新事务，且在 B 提交之后才进行第一次普通一致性读取，因此可以看到 B 已提交的 `1`；
3. 两个事务读取同一条记录，结果不同并不矛盾。

但“新事务一定读最新数据”仍需限定条件。更准确的说法是：

> **事务 C 读取符合自身 Read View 可见性规则的版本；本题中 B 已经在 C 首次普通读取前提交，因此 C 看到的是 1。**

术语也要改正：这里是 **Undo Log（撤销日志）**，不是锁。Undo 的作用是提供历史版本重建所需的信息，不能把“Undo”误解为“对旧数据加一把锁”。

本题可以记为：**经前一题讲解后，能够将机制迁移到新事务 C 的场景**；但还不能据此认为已经熟悉 Read View 的底层判定算法。

## 七、本次真正掌握的版本读取判断表

假设没有其他事务继续修改记录，且使用前文相同的普通一致性读取条件：

| 事务 | 查询时机与视图条件 | 查询结果 | 原因 |
| --- | --- | --- | --- |
| A 第一次查询 | B 更新提交之前，A 首次一致性读取 | `0` | 当时可见的是原值 |
| B 的修改 | UPDATE 后 COMMIT 成功 | 最新提交值为 `1` | 修改已提交 |
| A 第二次查询 | 仍在原事务，沿用此前 Read View | `0` | 新版本对原视图不可见 |
| C 第一次查询 | B 提交之后，新事务首次一致性读取 | `1` | B 的提交对 C 的新视图可见 |

不能从上表推导出“所有 SQL 在 REPEATABLE READ 下一定永远返回同一个值”。这里的表只对应**普通非锁定 SELECT、事务 A 不自行修改这条记录**的题目。

## 八、今天必须保留的边界与容易误判之处

### 1. 事务 A 读到旧值，不代表事务 B 提交失败

错误推断：

> “B 已经提交了，A 还查到 0，所以 B 的 UPDATE 一定失败了。”

这在本题中不成立。B 可以成功提交 `1`，同时 A 的一致性读取仍看到 `0`。

处理线上类似现象时，应先确认隔离级别、事务是否仍在持续、读取方式和操作先后，再判断是否真有异常。

### 2. REPEATABLE READ 不代表任何读取都只能见到旧值

今天使用的是普通非锁定 `SELECT`，属于一致性读取的讨论范围。

`SELECT ... FOR UPDATE`、`UPDATE` 等涉及当前读或锁定行为的路径与普通一致性读取不同。事务自身修改过记录时，也不能简单套用“A 只能看到首次读取时的旧值”。

**这些差异今天没有出题验证，后续再学。**

### 3. Read View 不是 SQL 结果缓存

如果把 A 两次结果都是 `0` 简化为“第一次查到了 0，数据库就把 SELECT 的答案缓存下来”，会误导后续排查。

本题的关键不是简单复用查询结果，而是**根据版本可见性规则读取符合视图的记录版本**。

### 4. Undo Log 不只是用来 ROLLBACK

Day 88 主要学习 Undo Log 对事务回滚的支持；Day 89 新增一个关联：

~~~text
Undo Log
    ├── 支持撤销事务内的修改（Day 88）
    └── 支持重建一致性读取需要的历史版本（Day 89）
~~~

但不能因此说已经掌握 Undo 版本链、清理机制、记录格式或 InnoDB 内核实现。

## 十二、昨日核心知识回忆：Day 88 Undo Log

按照 V3.2，完成今天 MVCC 的两道问题后，最后只回忆一个 Day 88 核心知识点。

### 题目

原始账户余额为 `100`：

~~~sql
START TRANSACTION;

UPDATE account
SET balance = 50
WHERE id = 1001;

ROLLBACK;
~~~

问题：

1. `ROLLBACK` 后余额是多少？
2. 为什么数据库能撤销之前的 `UPDATE`？
3. Undo Log 在这里有什么作用？

### 我的回答（按实际口述整理）

> 回滚后当然是 100。Undo Log 会记录更新之前恢复所需要的数据。只要还没提交，在同一个事务里面，无论更新多少次，完整回滚后都恢复到事务开始之前的状态。

### 评估与必要纠正

**核心判断正确，昨日回忆通过。**

已经能够回忆：

- 最终余额是 `100`，不是 `50`；
- Undo Log 保存撤销修改所需的信息；
- 一个尚未提交的事务中多次 UPDATE，若执行完整的 `ROLLBACK`，会撤销该事务内的相关修改。

用简化模型表示：

~~~text
初始 100
   ↓
第一次 UPDATE → 80
   ↓
第二次 UPDATE → 50
   ↓
ROLLBACK
   ↓
撤销第二次修改 → 80
   ↓
撤销第一次修改 → 100
~~~

需要补足的边界：

1. Undo Log 不一定保存完整的一份旧记录，而是记录撤销所需的信息；
2. **必须区分“尚未提交”和“已经执行 ROLLBACK”**：没提交本身不等于已经回滚；
3. 已经成功 `COMMIT` 的事务，不能再依赖普通 `ROLLBACK` 撤销之前已提交的修改；
4. “恢复到事务开始之前”是本题只涉及这笔未提交事务修改时的简化说法，不能无条件推广到所有复杂并发和保存点场景。

**昨日回忆结果：Undo Log 的回滚用途记忆通过；对 Undo Log 还有 MVCC 历史版本用途的认识在 Day 89 得到补充。**

## 十四、今天真正建立的判断模型

将最近四天连起来：

~~~text
Buffer Pool：数据页为什么能缓存在内存里
      ↓
Redo Log：已提交修改怎样在满足条件时支持崩溃恢复
      ↓
Undo Log：未提交事务的修改怎样被撤销
      ↓
MVCC：为什么不同事务可能读取到不同版本
      ↓
Read View + Undo 历史版本：
决定普通一致性读取该看哪个版本、如何获取旧版本
~~~

遇到两个事务查询同一行却出现不同结果时，先检查：

~~~text
是不是同一条记录？
    ↓
数据库是 InnoDB 吗？隔离级别是什么？
    ↓
两个事务何时开始？何时首次一致性读取？
    ↓
写事务何时提交？
    ↓
查询是普通 SELECT 还是锁定读取？
    ↓
读取者是否自行修改过这条记录？
    ↓
再判断版本可见性，而不是直接认定数据更新失败
~~~

今天最后保留五个结论：

1. **事务 B 提交成功，并不意味着之前已建立一致性读取视图的事务 A 必须立刻看到新值。**
2. **在本题的 InnoDB REPEATABLE READ 普通一致性读取条件下，A 第二次仍可读到 0。**
3. **在 B 提交后才首次读取的新事务 C，可以读到已经提交的 1。**
4. **Read View 判断可见性，Undo Log 支持历史版本重建；Undo 同时还有事务回滚用途。**
