# 后端工程化每日训练 Day 30：灰度发布、流量控制与快速回滚

## 一、今天学习的知识点

今天学习的是：

**灰度发布（Canary Release）、流量控制、灰度监控、数据库兼容性设计，以及线上异常时的快速回滚。**

一句话理解：

> 灰度发布不是简单地“先部署几台新机器”，而是在新版本正式全量上线之前，只让一小部分真实流量进入新版本，通过技术指标和业务指标验证稳定性；一旦出现异常，立即停止扩大流量，并把请求快速切回稳定旧版本，把故障影响范围控制在最小。

今天重点解决以下问题：

```text
为什么新版本不能直接 100% 全量切换
灰度发布的核心为什么是流量控制而不是部署
按用户、按请求、按实例灰度分别有什么区别
技术指标正常为什么不代表业务正常
灰度阶段应该监控哪些技术指标和业务指标
数据库新增字段时为什么必须考虑新旧版本并存
什么是数据库的向前兼容、向后兼容
为什么回滚前必须提前准备数据库兼容方案
灰度过程中发现内存泄漏时应该先修 Bug 还是先恢复服务
如何把 v2 流量快速切回 v1
为什么线上故障处理通常遵循“止损 → 定位 → 修复”
```

---

## 二、为什么不能直接 100% 全量发布

假设 AI 平台当前运行的是：

```text
模型 A
```

现在准备上线新的模型调用逻辑：

```text
模型 B
```

如果直接执行：

```text
100% 用户
↓
模型 B
```

那么新版本中任何没有在测试环境暴露的问题，都会立即影响全部线上用户。

可能出现：

```text
模型调用失败
响应时间明显增加
超时率升高
Token 成本暴涨
输出质量下降
内存泄漏
线程池被占满
数据库连接异常
计费 / 支付链路受到新版本代码影响
```

如果 100% 用户已经全部切换：

```text
新版本故障
↓
全部用户同时受影响
↓
故障范围最大
↓
线上事故处理压力最大
```

所以灰度发布解决的核心问题是：

> **在真实流量下验证新版本，同时把未知风险的故障半径限制在一个可控范围内。**

例如：

```text
1%
↓
5%
↓
20%
↓
50%
↓
100%
```

如果在 5% 阶段已经发现明显异常：

```text
立即停止扩大流量
↓
把新版本流量降到 0%
↓
旧版本恢复 100%
```

此时受到主要影响的只是少量灰度流量，而不是全部用户。

---

## 三、灰度发布的核心不是部署，而是流量控制

灰度发布经常会同时存在两个版本：

```text
v1：稳定旧版本
v2：待验证新版本
```

真正需要控制的是：

```text
哪些请求进入 v1
哪些请求进入 v2
```

也就是：

> **流量路由。**

典型流程：

```text
部署 v2
↓
只分配少量流量
↓
观察监控
↓
指标正常
↓
逐步扩大流量
↓
最终 100% 切换
```

异常流程：

```text
部署 v2
↓
少量流量进入
↓
发现异常
↓
停止扩容
↓
流量切回 v1
↓
下线 / 隔离 v2
↓
再定位问题
```

## 四、常见灰度方式

### 1. 按用户灰度

例如：

```text
userId
↓
Hash
↓
命中灰度比例
↓
进入 v2
```

假设灰度比例为 5%。

可以通过稳定 Hash 规则，让同一个用户始终进入同一个版本。

优点：

```text
同一用户体验稳定
不会一次进入 v1、一次进入 v2
适合需要会话一致性或业务体验对比的场景
```

这类方式也适合：

```text
内部员工
测试租户
指定客户
白名单用户
付费套餐用户
```

先进行定向灰度。

---

### 2. 按请求比例灰度

例如：

```text
100 个请求
↓
95 个进入 v1
5 个进入 v2
```

优点：

```text
实现简单
容易控制整体比例
```

缺点：

```text
同一个用户可能这次访问 v1
下一次访问 v2
```

如果服务依赖本地 Session、本地缓存或版本间行为差异较大，容易出现体验不一致。

---

### 3. 按实例灰度

例如：

```text
v1：9 个实例
v2：1 个实例
```

在实例规格、负载和路由条件接近时，可以近似形成一部分流量进入新版本。

但需要注意：

> 单纯把 Kubernetes Pod 做成 9:1，并不天然等于精确的 90%:10% 加权流量。

实际生产环境如果需要更精确的比例控制，通常还会结合：

```text
Nginx
Ingress
API Gateway
Service Mesh
负载均衡器的权重能力
```

进行路由。

---

## 五、灰度阶段应该监控什么

今天一个需要强化的认识是：

> **灰度不能只看“服务有没有挂”，而要同时看技术指标和业务指标。**

### 1. 技术指标

#### 接口层

```text
QPS
请求成功率
错误率
P50 / P95 / P99 RT
超时率
5xx 数量
```

#### JVM / 系统资源

```text
CPU
内存
Heap 使用率
GC 次数与 GC Pause
线程数
线程池 active / queue / reject
```

#### 数据库

```text
连接池 active
idle
pending
连接获取超时
慢 SQL
锁等待
数据库错误率
```

#### AI 调用

```text
模型调用成功率
平均响应时间
P95 / P99 响应时间
超时率
重试次数
Token 消耗
单次请求成本
```

---

### 2. 业务指标

AI 平台还应该观察：

```text
AI 任务成功率
任务完成率
失败任务数量
用户有效结果率
模型输出质量
用户反馈
```

涉及付费业务时，还需要观察：

```text
支付成功率
订单成功率
回调成功率
退款率
付费转化率
```

今天一个非常重要的结论是：

```text
HTTP 200
AI 调用成功
CPU 正常
```

并不能说明新版本一定正常。

例如模型 B：

```text
技术调用全部成功
↓
但是输出质量严重下降
```

从技术监控看：

```text
没有异常
```

从业务角度看：

```text
已经失败
```

所以：

> **技术指标正常，不代表业务正常。灰度发布必须同时验证系统稳定性和业务结果。**

## 六、为什么数据库变更会让回滚变复杂

应用版本通常可以快速回滚：

```text
v2 → v1
```

但数据库不是一个可以随便一起回滚的组件。

例如旧表：

```sql
CREATE TABLE user (
    id BIGINT PRIMARY KEY,
    name VARCHAR(64)
);
```

新版本增加字段：

```sql
ALTER TABLE user
ADD COLUMN status INT NOT NULL;
```

如果 `status` 没有默认值，而旧版本仍然执行：

```sql
INSERT INTO user(id, name)
VALUES (1, 'liu');
```

旧版本不知道 `status` 字段的存在，插入就可能失败。

于是出现：

```text
v2 上线
↓
数据库结构改变
↓
v2 出问题
↓
应用回滚到 v1
↓
v1 已经无法兼容新数据库结构
↓
回滚失败
```

所以灰度期间必须考虑：

> **新旧两个应用版本需要在一段时间内同时兼容当前数据库结构。**

## 七、数据库兼容性怎么设计

如果只是新增字段，更安全的方式通常是先进行兼容性扩展。

例如：

```sql
ALTER TABLE user
ADD COLUMN status INT DEFAULT 0;
```

那么旧版本仍然可以：

```sql
INSERT INTO user(id, name)
VALUES (1, 'liu');
```

数据库自动补：

```text
status = 0
```

于是：

```text
v1 不认识 status
↓
仍然可以正常运行

v2 认识 status
↓
可以开始使用新字段
```

更完整的思路通常是：

```text
先扩展数据库结构
↓
保证旧代码仍兼容
↓
发布支持新结构的新版本
↓
灰度验证
↓
全部实例升级完成
↓
确认旧逻辑已经不再使用
↓
最后再清理废弃字段 / 旧逻辑
```

这类方式常被概括为：

> **Expand → Migrate → Contract**

即：

```text
先扩展
再迁移
最后收缩
```

而不是：

```text
改数据库
+
改代码
+
全量上线
+
希望一次成功
```

## 八、Session 为什么会影响灰度

假设系统使用本地 Session：

```text
用户第一次请求
↓
v2
↓
Session 保存在 v2 本机
```

第二次请求：

```text
用户第二次请求
↓
v1
↓
v1 本机没有刚才的 Session
```

用户可能表现为：

```text
登录状态丢失
权限异常
重复登录
```

因此多实例和灰度环境更适合使用：

```text
Redis Session
JWT
集中式会话存储
```

或者通过稳定路由保证同一个用户在灰度期间进入固定版本。

## 九、发现新版本内存泄漏时应该怎么处理

假设当前灰度流量：

```text
v1：95%
v2：5%
```

监控发现：

```text
v2 内存持续上涨
Full GC 越来越频繁
内存始终无法回落
↓
疑似内存泄漏
```

这时线上第一目标不是：

```text
马上 SSH 上去研究代码
马上现场修 Bug
```

而应该优先：

> **恢复稳定服务，缩小用户影响。**

处理流程：

```text
发现 v2 异常
↓
立即停止扩大灰度
↓
把 v2 权重降到 0
↓
所有新请求重新进入 v1
↓
等待 / 处理 v2 中已有请求
↓
隔离或下线 v2
↓
确认 v1 指标恢复正常
↓
再排查 v2 内存泄漏
```

流量从：

```text
v1：95%
v2：5%
```

切回：

```text
v1：100%
v2：0%
```

这样新的用户请求不再继续进入故障版本。

## 十、为什么线上故障要先止损，再定位

如果新版本已经明显影响用户：

错误处理方式：

```text
发现 Bug
↓
开发开始现场分析
↓
分析 20 分钟
↓
线上仍然不断有用户进入故障版本
```

更合理：

```text
确认新版本异常
↓
停止灰度
↓
流量切回稳定版本
↓
确认服务恢复
↓
保留日志 / Metrics / Trace / Heap Dump 等证据
↓
离线定位
↓
修复
↓
重新测试
↓
再次灰度
```

核心原则：

```text
止损
↓
恢复服务
↓
保留现场
↓
定位问题
↓
修复问题
↓
重新灰度
```

也可以简单记成：

> **止损 > 定位 > 修复。**

这里不是说 Bug 不重要，而是线上故障期间：

> 用户正在持续受到影响时，恢复服务的优先级通常高于现场长时间调试。

---

## 十一、快速回滚必须提前准备什么

真正可靠的回滚不能等事故发生以后再想。

发布前至少应该明确：

```text
旧版本镜像 / JAR 是否仍然可用
旧版本配置是否仍然保留
流量权重如何快速调整
数据库是否兼容旧版本
是否存在无法回滚的数据迁移
新版本是否启动了不可逆任务
回滚脚本是否已经准备
谁有执行回滚的权限
回滚后看哪些指标确认恢复
```

因此成熟的发布流程不是只有：

```text
发布方案
```

而应该同时存在：

```text
发布方案
+
验证方案
+
回滚方案
```

## 十二、Nginx / Kubernetes 中如何理解灰度

### Nginx 概念示例

逻辑上希望达到：

```text
95% → v1
5%  → v2
```

实际可以通过：

```text
upstream 权重
Hash 路由
Cookie
Header
用户标识
```

控制。

重点不是记某一段 Nginx 配置，而是理解：

```text
请求进入网关
↓
根据灰度规则选择版本
↓
路由到 v1 或 v2
```

---

### Kubernetes 概念示例

可能同时存在：

```text
Deployment v1
Deployment v2
```

然后通过：

```text
Ingress / Gateway / Service Mesh
```

做：

```text
v1：95%
v2：5%
```

也可以先只部署少量 v2 实例进行初步验证。

重点仍然是：

> **版本并存 + 可控路由 + 可观测 + 可回滚。**

## 十三、一个完整的 AI 模型灰度流程

假设 AI 平台从模型 A 切换到模型 B。

### 阶段一：部署但不接真实流量

```text
部署 v2
↓
健康检查
↓
内部测试
↓
确认实例可以正常运行
```

### 阶段二：内部用户 / 白名单

```text
内部员工
测试账号
指定租户
↓
模型 B
```

重点验证：

```text
功能正确性
Prompt 是否正常
结果格式是否兼容
模型输出质量
```

### 阶段三：1% ~ 5% 真实流量

观察：

```text
错误率
P95 / P99 RT
AI 超时率
CPU
内存
GC
线程池
数据库连接池
Token 消耗
任务成功率
业务成功率
```

### 阶段四：逐步扩大

```text
5%
↓
20%
↓
50%
↓
100%
```

每一个阶段都应该满足预先定义的发布条件。

例如：

```text
错误率没有显著升高
P95 没有明显恶化
内存没有持续增长
业务成功率正常
成本在预算范围内
```

### 阶段五：发现异常

```text
停止扩大流量
↓
v2 → 0%
↓
v1 → 100%
↓
确认稳定
↓
分析原因
↓
修复后重新灰度
```

## 十四、今天思考题的回答与修正

### 问题一：为什么不建议直接让 100% 用户切换到模型 B

原回答核心思路：

```text
模型 B 可能存在问题
如果一次性全部切换
重要业务出现 Bug
所有用户都会受到影响
```

这个方向正确。

补充完整以后：

> 新版本在测试环境中无法覆盖全部真实流量和真实数据场景。如果直接让 100% 用户切换到模型 B，一旦出现功能 Bug、性能下降、模型质量下降、Token 成本上涨、内存泄漏或其他稳定性问题，故障会立即影响全部用户。灰度发布通过先放少量真实流量，把未知风险的故障半径限制住，同时保留快速回滚能力。

---

### 问题二：灰度阶段应该监控哪些指标

原回答：

```text
支付模块
能让公司盈利的关键模块
AI 模型调用
支付等重要业务
数据库一致性
```

业务风险意识是对的，但监控指标需要进一步工程化。

更完整应该分为：

#### 技术指标

```text
QPS
错误率
P95 / P99 RT
超时率
CPU
内存
GC
线程池
数据库连接池
慢 SQL
AI 调用成功率
AI 调用耗时
Token 消耗
```

#### 业务指标

```text
任务成功率
有效结果率
支付成功率
订单成功率
付费转化率
退款率
用户反馈
```

核心结论：

> **技术指标和业务指标必须一起看。**

---

### 问题三：数据库新增一列，旧版本仍然运行，需要满足什么要求

原回答：

```text
新增一列以后
依旧不能影响旧代码运行
```

这个核心判断正确。

工程化表达是：

> 数据库结构变更必须保证灰度期间的新旧版本兼容。新增字段时，不能让旧版本因为不知道新字段而无法插入、更新或查询；删除字段、修改字段语义等破坏性变更则更需要拆成多个阶段执行。

例如：

```text
先新增可空字段 / 合理默认值
↓
旧版本继续正常运行
↓
新版本开始读取 / 写入新字段
↓
全部切换完成
↓
确认旧代码不再使用
↓
最后清理旧结构
```

---

### 问题四：灰度发现新版本内存泄漏，如何快速回滚

今天这一题最开始没有思路。

正确处理链路：

```text
发现 v2 内存持续上涨
↓
立即停止扩大灰度
↓
将 v2 流量权重调整为 0
↓
将 v1 恢复为 100%
↓
处理 v2 已经进入的请求
↓
隔离 / 下线 v2 实例
↓
确认错误率、RT、内存等指标恢复
↓
保存日志、Metrics、Heap Dump 等故障现场
↓
定位内存泄漏
↓
修复并测试
↓
重新灰度
```

需要真正记住的是：

> **线上已经出现明显故障时，优先恢复稳定服务，而不是让用户继续承担故障流量的同时现场长时间修 Bug。**

## 十五、面试表达

可以这样表达：

> 新版本上线时，我不会直接把 100% 流量全部切过去，而会采用灰度发布，让新旧版本并存，通过用户、租户或流量权重把少量请求路由到新版本。灰度期间不仅看 CPU、内存、错误率、P95/P99、数据库连接池等技术指标，也会看任务成功率、支付成功率、AI 输出质量和 Token 成本等业务指标。
>
> 如果灰度过程中发现内存泄漏、错误率明显升高等问题，我会先停止扩大灰度，把新版本流量降到 0，将请求快速切回稳定旧版本，确认线上恢复后再保留日志、Metrics、Heap Dump 等现场进行定位。数据库变更会提前采用兼容性设计，保证灰度期间 v1、v2 能同时运行，避免应用代码虽然能回滚，但旧版本已经无法兼容数据库结构。

## 十六、今天的核心结论

```text
灰度发布的核心不是“部署新版本”
而是“控制新版本接收多少真实流量”
```

```text
100% 全量发布
→ 故障半径最大

小流量灰度
→ 先用真实流量暴露问题
→ 控制故障半径
```

```text
灰度不能只看 CPU、内存、错误率
还必须看业务成功率、模型质量、支付结果、成本等业务指标
```

```text
HTTP 200
≠
业务一定正确
```

```text
数据库升级不能只考虑新版本能不能运行
还要考虑旧版本能不能在回滚后继续运行
```

```text
发布之前必须同时准备：
发布方案 + 监控方案 + 回滚方案
```

```text
灰度异常：
停止扩大
↓
切断新版本流量
↓
恢复稳定版本
↓
确认服务恢复
↓
再定位和修复
```

今天最重要的线上稳定性认识是：

> **发布不是“把新代码部署成功”就结束了。真正成熟的发布能力，是能够控制流量、观察真实效果、限制故障半径，并在异常发生后快速恢复到一个已知稳定状态。**
