# 后端工程化每日训练 Day 35：数据库事务隔离级别、脏读、不可重复读与幻读

## 一、今天学习的知识点

今天学习的是：

**数据库事务隔离级别（Transaction Isolation Level）、脏读、不可重复读、幻读、MVCC，以及事务隔离和具体业务并发控制之间的区别。**

一句话理解：

> 事务隔离级别解决的是“多个事务同时执行时，一个事务到底能看到另一个事务的哪些数据”；它主要控制数据可见性，并不等于自动解决库存超卖、重复退款、状态覆盖等所有业务并发问题。

今天重点解决以下问题：

```text
什么是脏读
什么是不可重复读
什么是幻读
三个并发现象怎么快速区分
READ UNCOMMITTED 是什么
READ COMMITTED 能解决什么
REPEATABLE READ 为什么叫可重复读
SERIALIZABLE 为什么隔离最强
隔离级别和 MVCC / 锁是什么关系
@Transactional 为什么不等于并发安全
REPEATABLE READ 为什么不能自动解决库存超卖
库存扣减为什么优先考虑原子 UPDATE
为什么不能一害怕超卖就同时上悲观锁和分布式锁
```

## 二、先理解事务隔离到底在解决什么

假设订单当前状态：

```text
status = PAID
```

事务 A：

```text
BEGIN
↓
SELECT status
↓
PAID
```

此时事务 B：

```text
BEGIN
↓
UPDATE orders
SET status = 'REFUNDED'
↓
COMMIT
```

然后事务 A 再查询：

```text
SELECT status
```

事务 A 第二次到底应该看到：

```text
PAID
```

还是：

```text
REFUNDED
```

这不是单纯的 SQL 对错问题。

它取决于：

```text
事务隔离级别
+
数据库自身的实现机制
```

所以事务隔离最核心的问题其实是：

> **当多个事务并发执行时，每个事务允许看到什么版本的数据。**

---

## 三、三个最容易混淆的并发现象

今天一开始最大的混淆点，就是把：

```text
脏读
不可重复读
幻读
```

混在了一起。

最终用下面三个判断标准把它们区分开。

---

### 1. 脏读：读到了别人还没有提交的数据

初始余额：

```text
balance = 1000
```

事务 B：

```text
1000 → 500

但是：
还没有 COMMIT
```

事务 A 此时竟然读取到：

```text
balance = 500
```

随后事务 B：

```text
ROLLBACK
```

最终数据库实际上仍然是：

```text
balance = 1000
```

说明事务 A 刚才读取到的：

```text
500
```

是一份最终根本没有生效的数据。

这就是：

**脏读（Dirty Read）。**

判断关键词：

> **未提交。**

只要看到：

```text
A 读到了 B 尚未 COMMIT 的修改
```

优先想到：

```text
脏读
```

---

### 2. 不可重复读：同一行数据前后两次读取结果不同

订单初始状态：

```text
id = 1
status = PAID
```

事务 A 第一次查询：

```text
id = 1
status = PAID
```

事务 B 修改同一行：

```sql
UPDATE orders
SET status = 'REFUNDED'
WHERE id = 1;

COMMIT;
```

事务 A 第二次查询同一个：

```text
id = 1
```

结果变成：

```text
status = REFUNDED
```

这里事务 B 已经：

```text
COMMIT
```

所以这不是脏读。

真正的问题是：

```text
同一个事务
同一行数据
第一次：PAID
第二次：REFUNDED
```

也就是同样的数据重复读取，却得到了不同结果。

这就是：

**不可重复读（Non-repeatable Read）。**

判断关键词：

> **同一行，值变了。**

---

### 3. 幻读：同一个查询条件前后查出的记录集合发生变化

事务 A 第一次查询：

```sql
SELECT *
FROM orders
WHERE status = 'PAID';
```

结果：

```text
100 行
```

事务 B 新增一条：

```text
status = PAID
```

然后：

```text
COMMIT
```

事务 A 再执行完全相同的条件查询：

```sql
SELECT *
FROM orders
WHERE status = 'PAID';
```

这次变成：

```text
101 行
```

重点不是某一行：

```text
PAID → REFUNDED
```

而是：

```text
符合条件的记录集合发生了变化
100 行 → 101 行
```

像突然“冒出来”一条数据。

这就是：

**幻读（Phantom Read）。**

判断关键词：

> **同一条件，记录集合变了。**

在最简单的学习模型里，可以先记成：

```text
行数多了 / 少了
```

但严格来说，幻读关注的是：

```text
符合查询条件的记录集合发生变化
```

而不只是 COUNT 数字本身。

---

## 四、三个并发现象如何快速判断

今天最终形成的最小判断模型：

```text
有没有读到别人“未提交”的数据？
        ↓
       有
        ↓
      脏读

否则
        ↓
是不是同一行数据前后值发生变化？
        ↓
       是
        ↓
   不可重复读

否则
        ↓
是不是同一查询条件下记录集合发生变化？
        ↓
       是
        ↓
      幻读
```

最容易记忆的版本：

```text
脏读
= 读到未提交

不可重复读
= 同一行，值变了

幻读
= 同一条件，记录集合变了
```

## 五、四个事务隔离级别

SQL 标准定义了四个典型事务隔离级别：

| 隔离级别 | 中文 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- | --- |
| READ UNCOMMITTED | 读未提交 | 可能 | 可能 | 可能 |
| READ COMMITTED | 读已提交 | 防止 | 可能 | 可能 |
| REPEATABLE READ | 可重复读 | 防止 | 防止 | SQL 标准模型下仍可能 |
| SERIALIZABLE | 串行化 | 防止 | 防止 | 防止 |

可以先建立这条主线：

```text
READ UNCOMMITTED
        ↓
READ COMMITTED
        ↓
REPEATABLE READ
        ↓
SERIALIZABLE

隔离能力越来越强
```

学习阶段可以粗略记成：

```text
READ UNCOMMITTED
→ 三种问题都可能

READ COMMITTED
→ 先防脏读

REPEATABLE READ
→ 再防不可重复读

SERIALIZABLE
→ 再防幻读
```

但工程上不能机械理解为：

```text
隔离级别越高
=
一定越好
```

因为更强的隔离通常意味着数据库需要付出更多并发控制成本。

---

## 六、READ COMMITTED 为什么会出现不可重复读

`READ COMMITTED` 的核心规则可以先理解为：

> **只能读取已经提交的数据。**

例如事务 B：

```text
PAID → REFUNDED

还没 COMMIT
```

事务 A 不能读取到这份未提交的新数据。

所以：

```text
READ COMMITTED
→ 可以防止脏读
```

但是如果事务 B 已经：

```text
COMMIT
```

事务 A 后续再次查询时，就可能看到事务 B 新提交的数据。

于是：

```text
A 第一次：PAID

B：修改成 REFUNDED
B：COMMIT

A 第二次：REFUNDED
```

这就是：

```text
不可重复读
```

所以：

> **READ COMMITTED 防止的是“读到未提交数据”，但不保证一个事务内多次读取始终看到同一个历史版本。**

---

## 七、REPEATABLE READ 为什么叫“可重复读”

如果业务希望：

```text
事务 A 第一次读取：PAID

事务 B：
PAID → REFUNDED
COMMIT

事务 A 再次普通读取：
仍然保持原来的读取视图
```

那么就需要比 `READ COMMITTED` 更强的隔离语义。

`REPEATABLE READ` 的目标就是：

> **在同一个事务内，对同一份数据进行重复读取时，保持一致的读取结果。**

因此可以先记住：

```text
READ COMMITTED
→ 防脏读

REPEATABLE READ
→ 在此基础上进一步防不可重复读
```

这也是今天练习中最终稳定掌握的区别。

---

## 八、SERIALIZABLE 为什么隔离最强

`SERIALIZABLE` 可以先粗略理解为：

```text
让并发事务的执行效果尽可能接近串行执行
```

也就是：

```text
事务 A
↓
事务 B
↓
事务 C
```

而不是所有事务都毫无约束地同时操作同一批数据。

它能够提供非常强的隔离能力，但代价可能是：

```text
等待增加
锁竞争增加
吞吐下降
事务冲突增加
```

所以工程上不能因为：

```text
SERIALIZABLE 最安全
```

就把所有接口统一设置成：

```text
SERIALIZABLE
```

正确思路仍然是：

> **根据业务一致性要求选择隔离级别，而不是无脑拉满。**

---

## 九、MySQL InnoDB 下的 REPEATABLE READ 要特别注意

上面的四级隔离表，是学习 SQL 标准时常用的简化模型。

但实际使用 MySQL InnoDB 时，不能机械地说：

```text
REPEATABLE READ 一定会发生幻读
```

MySQL InnoDB 还会结合：

```text
MVCC
Next-Key Lock
Record Lock
Gap Lock
```

等机制处理并发读取和范围修改。

因此 InnoDB 的 `REPEATABLE READ` 对幻读的处理，比最简单的 SQL 标准表更加复杂。

当前阶段先掌握：

```text
SQL 标准模型
↓
RU / RC / RR / SERIALIZABLE
```

后续再单独学习：

```text
InnoDB MVCC
Read View
快照读
当前读
Next-Key Lock
Gap Lock
```

避免现在一次塞入过多实现细节。

## 十、事务隔离、MVCC 和锁到底是什么关系

今天最重要的一条关系是：

```text
事务
↓
隔离级别规定“应该看到什么”
↓
MVCC / 锁等机制负责底层实现
```

可以这样理解：

### 隔离级别

解决：

```text
事务之间的数据可见性规则是什么？
```

例如：

```text
能不能看到未提交数据？
同一事务重复查询是否应该保持一致？
```

---

### MVCC

MVCC：

```text
Multi-Version Concurrency Control
多版本并发控制
```

可以先粗略理解为：

```text
数据库保留数据版本信息
↓
事务根据自己的可见性规则
↓
读取适合自己的版本
```

这样很多普通读操作不需要简单粗暴地和写操作互相堵死。

所以：

```text
事务隔离
≠
所有事务排队执行
```

---

### 锁

数据库锁则负责处理很多：

```text
写写冲突
当前读
范围锁定
行级互斥
```

等场景。

所以最小区分是：

```text
隔离级别
→ 规定规则

MVCC / 锁
→ 实现规则的重要机制
```

---

## 十一、@Transactional 为什么不等于并发安全

Spring 中：

```java
@Transactional
public void process() {
    // ...
}
```

主要是在建立：

```text
事务边界
```

也就是：

```text
哪些数据库操作属于同一个事务
什么时候提交
什么时候回滚
```

但它不意味着：

```text
只要加了 @Transactional
↓
所有并发问题都会自动消失
```

事务内部仍然需要面对：

```text
事务隔离级别
并发更新
乐观锁冲突
悲观锁等待
死锁
超时
长事务
```

所以：

> **事务是原子性和一致性处理的基础设施，但不是所有业务并发问题的万能答案。**

---

## 十二、为什么 REPEATABLE READ 不能自动解决库存超卖

这是今天从“事务隔离”进一步走到“业务并发控制”的关键点。

假设库存：

```text
stock = 1
```

两个请求同时：

```text
请求 A：查询 stock = 1
请求 B：查询 stock = 1
```

如果代码写成：

```java
int stock = selectStock();

if (stock > 0) {
    updateStock(stock - 1);
}
```

那么：

```text
查询
↓
Java 判断
↓
UPDATE
```

被拆成多个步骤。

两个线程都可能基于：

```text
stock = 1
```

做出：

```text
还有库存，可以下单
```

的业务判断。

即使最终数据库库存没有变成负数，仍然可能发生：

```text
库存只有 1
但业务上成功卖出 2 件
```

这就是：

**超卖。**

因此今天形成的关键认识是：

> **隔离级别主要解决“我看到什么”，而库存超卖属于“多个请求同时修改时，业务结果是否正确”的问题。**

两者不是同一层次。

## 十三、简单库存扣减为什么优先使用原子 UPDATE

相比：

```text
先查询库存
↓
Java 判断库存
↓
再 UPDATE
```

更适合的方式往往是直接：

```sql
UPDATE product
SET stock = stock - 1
WHERE id = ?
  AND stock > 0;
```

把：

```text
检查 stock > 0
+
stock - 1
```

压进一条数据库语句中完成。

假设：

```text
stock = 1
```

两个线程同时竞争。

可以先粗略理解为：

```text
请求 A：
UPDATE
↓
stock 1 → 0
↓
affected rows = 1
↓
成功
```

随后另一个请求执行时：

```text
stock = 0
```

条件：

```sql
stock > 0
```

已经不满足。

所以：

```text
affected rows = 0
```

业务可以把它解释为：

```text
库存不足 / 抢购失败
```

如果业务前面已经确认商品一定存在，那么：

```text
affected rows = 0
```

通常就可以直接按照库存不足处理。

如果没有提前确认商品存在，则还需要区分：

```text
商品不存在
```

和：

```text
商品存在但库存已经为 0
```

## 十四、为什么不能为了“绝对安全”同时叠悲观锁和分布式锁

今天在库存问题上最开始的直觉是：

```text
我害怕超卖
↓
先使用悲观锁
↓
再加一个分布式锁
```

这个思路的问题是：

> **锁不是叠得越多越安全。**

额外的锁会带来额外成本：

```text
等待时间增加
吞吐下降
代码复杂度上升
故障点增加
Redis 依赖增加
锁超时问题
锁续期问题
误释放问题
死锁 / 锁竞争风险增加
```

对于简单的单数据库库存扣减：

```sql
UPDATE product
SET stock = stock - 1
WHERE id = ?
  AND stock > 0;
```

数据库本身已经是所有应用实例共同访问的数据一致性控制点。

例如：

```text
应用实例 A ─┐
应用实例 B ─┼→ MySQL
应用实例 C ─┘
```

三个实例最终都要竞争数据库里的同一行库存。

因此不能因为：

```text
系统有多个 Java 实例
```

就自动推导出：

```text
必须 Redis 分布式锁
```

正确的工程判断顺序应该是：

```text
能不能用一条原子 SQL 解决？
        ↓
       能
        ↓
优先原子 UPDATE

解决不了
        ↓
是否需要数据库事务内的行级互斥？
        ↓
乐观锁 / 悲观锁

仍然存在真正的跨进程、跨节点业务互斥需求？
        ↓
再考虑分布式锁
```

## 十五、悲观锁和分布式锁分别什么时候更合理

### 悲观锁

如果业务必须：

```text
先锁住一条数据库记录
↓
读取当前状态
↓
完成一小段严格串行的判断和修改
↓
提交事务
```

可以考虑：

```sql
SELECT ... FOR UPDATE
```

例如 Day 34 的退款状态：

```text
NOT_REFUNDED
↓
REFUNDING
```

这种数据库行级状态转换，就可能使用悲观锁保护关键区间。

---

### 分布式锁

分布式锁更适合解决：

```text
多个应用实例
↓
对某个业务资源
↓
要求同一时刻只能有一个执行者
```

例如：

```text
服务器 A
服务器 B
服务器 C

都可能执行同一个定时任务
```

如果业务要求：

```text
整个集群同一时刻只能执行一次
```

这时 Redis / ZooKeeper 等分布式锁方案才更符合问题本身。

核心不是：

```text
只要多实例就加分布式锁
```

而是：

> **是否真的存在跨进程、跨节点的全局互斥需求。**

---

## 十六、事务为什么仍然应该尽可能短

今天的事务隔离和 Day 34 的悲观锁最终又回到同一条工程原则：

> **数据库事务应该尽可能短。**

危险示例：

```text
BEGIN
↓
查询数据库
↓
调用 AI 30 秒
↓
调用 HTTP 接口
↓
再次查询数据库
↓
UPDATE
↓
COMMIT
```

长事务可能带来：

```text
数据库连接长期占用
锁持有时间变长
锁等待增加
死锁风险增加
MVCC 历史版本保留时间增加
数据库资源回收压力上升
```

所以不要把：

```text
事务范围越大
=
越安全
```

当作原则。

更合理的是：

```text
只把必须保证原子性的本地数据库操作放进事务
```

而把：

```text
AI 调用
HTTP 调用
OSS 上传
第三方支付
长时间计算
```

等不可控操作尽量移出数据库长事务。

## 十七、Spring 中如何指定隔离级别

Spring 可以显式指定：

```java
@Transactional(
    isolation = Isolation.READ_COMMITTED
)
public void process() {
    // 数据库操作
}
```

也可以指定：

```java
@Transactional(
    isolation = Isolation.REPEATABLE_READ
)
public void process() {
    // 数据库操作
}
```

但实际项目中不要看到：

```java
@Transactional
```

就顺手修改隔离级别。

更合理的原则是：

```text
优先使用数据库和项目已经确定的默认隔离策略
↓
确认具体业务确实有特殊一致性要求
↓
再针对性调整
```

因为修改隔离级别不是普通代码风格调整，而是在修改：

```text
事务并发语义
```

## 十八、今天形成的核心知识关系

今天最重要的不是背四个单词，而是把下面这条链路串起来：

```text
事务
↓
隔离级别控制事务之间的数据可见性
↓
MVCC / 锁是数据库实现隔离规则的重要机制
↓
乐观锁 / 悲观锁 / 原子 UPDATE
处理具体业务并发修改问题
↓
真正存在跨节点全局互斥需求时
再考虑分布式锁
```

再压缩成一句：

> **隔离级别主要管“看见什么”，并发控制方案主要管“同时修改时怎么保证业务结果正确”。**

## 十九、今天的易错点复盘

### 易错点 1：把脏读和不可重复读混为一谈

今天最开始看到：

```text
第一次 PAID
第二次 REFUNDED
```

第一反应多次回答成：

```text
脏读
```

但判断脏读最重要的条件不是：

```text
数据变了
```

而是：

```text
读到了别人未提交的数据
```

只要对方已经：

```text
COMMIT
```

就不能再叫脏读。

---

### 易错点 2：把不可重复读和幻读混为一谈

最终区分：

```text
不可重复读
→ 同一行，值变了

幻读
→ 同一查询条件，记录集合变了
```

---

### 易错点 3：认为隔离级别可以解决所有业务并发问题

错误理解：

```text
用了 REPEATABLE READ
↓
库存并发就一定安全
```

实际：

```text
事务隔离
解决数据可见性

库存超卖
需要额外考虑更新方式和业务并发控制
```

---

### 易错点 4：害怕超卖就叠加更多锁

错误直觉：

```text
悲观锁
+
分布式锁
=
更安全
```

实际上如果原子 SQL 已经能解决核心竞争问题，继续叠锁只会增加复杂度和故障面。

工程目标不是：

```text
锁最多
```

而是：

> **用最低必要复杂度满足业务一致性要求。**

## 二十、面试怎么表达

如果面试官问：

### 事务隔离级别是什么？

可以回答：

> 数据库事务隔离级别主要解决多个事务并发执行时的数据可见性问题。SQL 标准定义了 READ UNCOMMITTED、READ COMMITTED、REPEATABLE READ 和 SERIALIZABLE 四个级别，隔离能力逐渐增强。常见并发现象包括脏读、不可重复读和幻读。实际数据库通常会结合 MVCC 和锁实现这些隔离语义，我会根据业务一致性要求选择隔离策略，而不是无脑使用最高隔离级别。

---

如果继续问：

### 脏读、不可重复读和幻读有什么区别？

可以回答：

> 脏读是读到了其他事务尚未提交的数据；不可重复读是同一事务重复读取同一行时值发生变化；幻读是同一事务用相同查询条件重复查询时，符合条件的记录集合发生变化。

---

如果继续问：

### 事务隔离和锁是什么关系？

可以回答：

> 隔离级别定义事务之间的数据可见性规则，而 MVCC 和锁是数据库实现这些隔离规则的重要机制。隔离级别解决的是“能看到什么”，乐观锁、悲观锁和原子 UPDATE 则更多是在解决具体业务中的并发修改冲突。

---

如果继续问：

### 如何避免库存超卖？

可以回答：

> 如果只是单库里的简单库存扣减，我不会第一反应上分布式锁，而是优先使用类似 `UPDATE product SET stock = stock - 1 WHERE id = ? AND stock > 0` 的原子条件更新，并检查 affected rows。只有业务流程无法通过原子更新完成，或者确实需要数据库行级互斥、跨节点全局互斥时，才进一步考虑悲观锁、乐观锁或分布式锁。

## 二十一、今天真正需要记住的内容

第一组：三个并发现象。

```text
脏读
= 读到了未提交数据

不可重复读
= 同一行，前后值变了

幻读
= 同一条件，前后记录集合变了
```

第二组：四个隔离级别。

```text
READ UNCOMMITTED
↓
READ COMMITTED
↓
REPEATABLE READ
↓
SERIALIZABLE
```

简化理解：

```text
RU
→ 三种问题都可能

RC
→ 防脏读

RR
→ 再防不可重复读

SERIALIZABLE
→ 隔离最强
```

第三组：不要混淆问题层次。

```text
隔离级别
→ 数据可见性

MVCC / 数据库锁
→ 底层实现机制

原子 UPDATE / 乐观锁 / 悲观锁
→ 业务并发修改控制

分布式锁
→ 真正需要跨节点全局互斥时再考虑
```

第四组：工程原则。

> **数据库事务尽可能短；能用简单、可靠的数据库原子操作解决的问题，不要为了“感觉更安全”盲目叠加更多锁。**

## 二十二、能力复盘

今天已经能够稳定判断：

```text
读取未提交数据
→ 脏读

同一行前后值变化
→ 不可重复读

同一查询条件记录集合变化
→ 幻读
```

并且已经理解：

```text
READ COMMITTED
和
REPEATABLE READ
```

的核心差异之一，是后者进一步提供可重复读语义。

同时从事务隔离进一步延伸到了真实库存并发场景：

```text
不能因为害怕超卖就无脑叠锁
```

而应该先判断：

```text
原子 UPDATE 是否已经足够
```

今天真正完成的能力升级不是多记了四个数据库术语，而是开始建立：

> **先识别并发问题属于“数据可见性”还是“业务修改冲突”，再选择对应机制。**
