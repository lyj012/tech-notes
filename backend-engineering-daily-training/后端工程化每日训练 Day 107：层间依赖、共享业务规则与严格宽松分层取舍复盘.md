## 二、今天学习什么：层间依赖与职责边界

### 1. 一个最小三层架构

~~~text
HTTP 请求
    ↓
Controller（表现层：接入、参数处理、响应转换）
    ↓
Service（业务逻辑层：统一执行业务规则）
    ↓
Mapper / Repository（数据访问层：封装数据访问）
    ↓
Database
~~~

分层架构的重点不在代码放进几个目录，也不在是否存在名为 ServiceImpl 的类，而在：

1. **职责清晰**：什么规则由哪个模块负责？
2. **依赖受控**：上层是否越过既定边界，直接依赖不应暴露的实现细节？
3. **变化隔离**：业务规则或数据访问变化时，修改范围是否可控？
4. **多入口一致**：同一规则能否被多个入口复用，避免一处已更新、一处遗漏？

本轮核心质量属性是**可修改性（Modifiability）**。可修改性不意味着“代码最少”，而是让需求变更的影响范围、修改成本和风险更可控。

### 2. 正常运行不代表架构合理

假设订单系统原本在 Service 检查库存：

~~~text
Controller → OrderService（库存校验）→ Mapper
~~~

有人为了减少一次方法调用，把判断移到 Controller：

~~~text
Controller（库存校验）→ Mapper
~~~

代码可能仍然运行，但 Controller 开始承担业务判断，并直接依赖数据访问细节；当同一规则需要由其他接口、定时任务或消息消费者使用时，易出现复制、遗漏和不一致。

这里的“风险”不是说所有 Controller → Repository 调用在所有架构中都必然违法，而是指：**若项目约定业务规则由业务层统一承担，该跨层调用就可能破坏既定职责和依赖约束。**

### 3. 业务规则统一与多个入口

~~~text
普通用户创建订单 Controller ─┐
                            ├──→ OrderService（库存和商品状态规则）
管理员创建订单 Controller ───┘              ↓
                                        Repository
~~~

假设两个入口确实需要遵守同一项“库存充足、商品允许销售”规则，把公共部分集中在受控位置，通常有利于减少重复修改和漏改。

边界：管理员和普通用户也可能有不同业务权限、商品可见范围或操作规则；不能因为“复用”而错误地强制它们完全一致。共同规则共享，差异规则显式建模。

## 三、真实互动记录：从职责理解到独立迁移

本节按本轮聊天的实际先后顺序整理。用户回答保留原意与关键措辞；语音输入中的非正式表达仅做最小规范化。纠正前后的表现分开记录，不把讲解者给出的答案当成用户首次独立掌握。

### 1. 第一题：Controller 绕开 Service 检查库存有什么风险？

**题目：** 某订单系统原由业务层检查库存，开发人员为了减少一次方法调用，让表现层直接查询库存表并决定是否允许创建订单。问主要架构风险及原因。

**用户回答（整理）：**

> Controller 是接收用户请求的。虽然可以运行，但是可能绕过业务层代码；从设计角度看，职责分类不清晰，可修改性太糟糕。

**评估：正确，基础理解通过。**

用户能够独立把“可运行”和“架构合理”区分开，也能指出业务规则被绕过与职责混杂的关系。

**补充：** 架构问题不只是某个方法调用“多了一层”或“少了一层”，而是业务规则是否被统一执行、依赖是否遵守约定。单凭一次普通 Java 方法调用，不能直接推断有明显性能收益。

### 2. 第二题：两个 Controller 各写库存判断，新规则如何变更？

**题目：** 普通用户创建订单与管理员创建订单都各自在 Controller 检查库存。后来要求同时检查商品是否下架。应该继续各自实现还是统一到 Service？为什么？

**用户回答（整理）：**

> 如果已经把检查逻辑放在接口这一层，检查逻辑也要同时加到这两个控制层，不然很有可能没有调用这个逻辑。

**评估：识别到漏改风险，但没有正面完成“如何改进设计”的选择。**

这段回答说明用户理解了现有设计的维护代价：两个入口需要分别改，可能漏掉一个。但是题目要求提出未来更合理的架构时，还缺少明确的“抽取共享业务规则”结论。

**关键纠正：** 对确实共享的库存与商品状态规则，应由 Service 或 Service 使用的业务组件集中维护，两个 Controller 通过统一入口调用。规则只改一处，才可能同时覆盖所有受约束入口。

### 3. 第三题：换成密码安全规则，能否独立迁移？

**题目：** 用户修改密码、管理员重置密码两个 Controller 都需要检查新密码是否符合某项共同安全规则。以后安全规则可能经常变化，应放在哪里，为什么？

**用户回答（整理）：**

> 服务层，方便多个接口调用，不用到处加代码。

**评估：独立迁移通过。**

用户从上一题的“多个地方都要修改”推进到“把共同规则集中到可复用位置”，能够解释其可修改性收益。

**边界：** 规则可以由 Service 协调、复用专门的密码策略组件完成；不意味着每一种安全判断都必须直接堆进一个 Service 类，也不意味着管理员重置与用户改密必然遵守完全相同的全部规则。

### 4. 第四题：宽松分层一定错误吗？

**题目：** 商品查询只返回名称和价格，不涉及额外业务规则。开发人员主张 Controller 直接调用 Mapper，跳过一层纯转发 Service。这种做法一定错误吗？为什么？

**用户回答（整理）：**

> 不一定。简单查询的确可以这样子，这叫宽松分层，可以简化代码；但以后加代码时，可能不知道在哪里加，也可能漏掉逻辑调用。现在代码由 AI 来写，写代码已经不算负担，因此宽松分层就不推荐了。

**评估：架构取舍主体正确，但最后的结论需要纠正。**

**正确部分：**
- 知道宽松分层并非绝对错误。
- 能描述减少空转发代码或无价值抽象的收益。
- 能描述未来业务规则分散、职责边界不清、遗漏调用等风险。
- 能尝试依据维护成本提出技术选择。

**需要纠正的推理：**

> “AI 能写代码 → 写代码没有负担 → 宽松分层不推荐。”

这一推论不成立。AI 可能减少部分重复代码的编写成本，但无法消除审查、测试、理解、维护、联调和架构治理成本。严格分层也可能产生不必要的抽象；宽松分层若有清晰规则与适用场景，仍可能合理。

更严谨的表达：

> 在常规业务系统中，可以默认采取清晰的 Controller → Service → Repository 职责边界；若 Service 只有无价值的转发，且业务规则、接口复用、依赖约束均得到控制，可以评估允许特定跨层调用。最终应以真实需求、维护成本、团队约定和验证证据决定，而不是以“AI 写代码快”为单一依据。

**本题结论：基础架构权衡通过，但取舍依据仍需加强。**

## 四、核心机制：严格分层、宽松分层与质量属性取舍

### 1. 严格分层（Strict / Closed Layering）

~~~text
Controller
    ↓
Service
    ↓
Repository
~~~

严格分层通常要求上层通过相邻下层访问功能，减少随意跨越既定边界。

**适用价值：**
- 更容易约束接入层与业务层的职责；
- 便于收敛需要统一执行的业务规则；
- 当内部实现变化时，减少向上层扩散的机会。

**可能代价：**
- 某些简单查询路径出现只做转发的样板方法；
- 增加接口、对象转换和测试维护的工作；
- 如果层次过多或设计不当，也会形成复杂度。

### 2. 宽松分层（Relaxed / Open Layering）

~~~text
Controller ─────────────────→ Repository
    │                              ↑
    └──────────→ Service ───────────┘
~~~

允许部分上层在明确约束下跨越中间层访问更低层，可能简化极简单的路径。

**不能忽视的约束：**
- 哪些调用允许跨层？
- 以后新增的业务校验在哪里统一执行？
- 是否有多个业务入口必须遵守相同规则？
- 是否无意暴露了数据访问细节？
- 代码评审、测试与架构规则能否维持一致性？

### 3. 不要夸大“少一次方法调用”的性能收益

在常见单进程 Spring Boot 应用中，一次普通 Java 方法转发与跨服务器网络调用不是同一个量级。只有看到可验证的瓶颈证据，才可以主张“移除该层显著改善性能”。

可合理讨论的主要收益，通常是**减少没有业务价值的样板代码和无效抽象**；能否提升性能，仍需具体测量。

## 五、Day 106 间隔回忆：HttpServletRequest 与业务层耦合

按照训练规则，在本日新知识、基础迁移和架构取舍完成后，才进行上一正式训练日回忆。

### 1. 回忆题

假设业务层接口为：

~~~java
public void createOrder(HttpServletRequest request) {
    // 创建订单
}
~~~

HTTP Controller、MQ 消费者和定时任务都需要使用同一套创建订单业务逻辑。

**问题：为什么让 Service 直接接收 HttpServletRequest，会降低复用性？**

### 2. 用户回答（整理）

> 不应该在方法里面放这个 HTTP 参数；它只适合对接 HTTP，无法自然对接 MQ 消费者。这样只能再去服务层新增代码，很繁琐，耦合高。应该换成普通参数，服务类写好 HTTP 和 MQ 的代码。

**评估：主要机制理解正确；最后一句体现接入职责归属仍有混淆。**

已独立说明：
- HttpServletRequest 是 HTTP 接入模型，不是通用业务模型；
- MQ 消费者并没有天然的 HttpServletRequest；
- 业务层依赖它会造成复用受限、耦合增加；
- 应改为传入与传输协议无关的业务参数。

**纠正点：** “服务类写好 HTTP 和 MQ 的代码”不合理。HTTP 解析和消息解析属于各自接入适配器；Service 不应该为了支持不同入口而混入两种协议处理代码。

### 3. 更合适的结构

~~~text
HTTP Controller ──解析 HTTP、认证、参数转换──┐
                                           │
MQ Consumer ─────解析消息、可信性校验───────┼──→ CreateOrderCommand
                                           │            ↓
Scheduled Job ───构造任务所需业务参数───────┘       OrderService
                                                        ↓
                                                   Repository
~~~

~~~java
public record CreateOrderCommand(
    Long userId,
    Long productId,
    int quantity
) {}

public class OrderService {
    public void createOrder(CreateOrderCommand command) {
        // 统一业务校验、库存与订单规则
    }
}
~~~

上面的代码仅演示**降低接入协议耦合**。生产系统中的身份来源、消息可靠性、授权、幂等、事务和并发库存处理仍需另外设计；不能因为参数叫 userId 就信任任意外部输入。

### 4. 间隔回忆结果

**核心因果链通过，接入层与业务层分工经纠正。** 本轮没有再进行一次独立复测，因此不能把这一纠正点记为“已经二次验证通过”；后续在 MQ 或定时任务场景中可以低成本复查。

## 七、可复用的架构分析方法

在新的软考题目或真实业务需求中，按以下顺序判断：

~~~text
观察业务需求变化
       ↓
识别哪些入口需要遵守相同规则
       ↓
确定规则应由哪个受控业务组件统一承担
       ↓
检查有没有上层绕过规则或依赖过多实现细节
       ↓
比较严格分层与受控的跨层调用
       ↓
列出可修改性、复杂度、测试和性能等收益与成本
       ↓
说明适用前提、风险边界与验证办法
~~~

**答题模板：**

> 在给定的业务约束下，方案 A 的主要收益是……；代价是……。方案 B 能改善……，但可能增加……。由于系统存在……（多个入口共享规则、未来规则变化等），优先采用……，并通过……（回归测试、接口行为一致性验证、性能测试、依赖约束检查等）验证设计是否满足要求。

这个模板只能帮助组织答案，不能替代实际阅读题干、识别关键约束和给出可核实的论证。

### 本日关键结论

- **程序运行正确 ≠ 架构职责划分合理。**
- **共享业务规则应集中在受控位置，避免每个入口复制一遍。**
- **严格分层与宽松分层都不是绝对正确或绝对错误。**
- **AI 能降低部分编写成本，但不能消除架构、测试、维护与治理成本。**
- **HTTP/MQ/定时任务适配处理应留在各自入口，业务层接收普通业务命令对象。**
