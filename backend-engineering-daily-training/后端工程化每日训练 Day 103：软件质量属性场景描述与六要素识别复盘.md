## 二、今天学习什么

**唯一核心主题：软件质量属性场景（Quality Attribute Scenario）。**

质量属性场景是一种结构化描述质量需求的方式。它不只说系统“应该很快”“应该稳定”或“应该安全”，而是明确：

- 谁或什么触发了事件？
- 具体发生了什么？
- 事件发生时系统处于什么环境？
- 系统中的哪个部分受到刺激？
- 系统应该做出什么响应？
- 用什么指标判断响应是否合格？

例如，模糊要求：

> 系统应该具有良好的性能。

改写成更具体的场景：

> 促销高峰期间，当 5000 个用户并发向订单服务提交创建订单请求时，订单创建接口的 P95 响应时间不得超过 300ms。

第二种描述更适合架构分析和测试，因为它明确了负载条件、受影响对象、系统行为和可验证指标。

质量属性场景不是一种新的质量属性，也不是某种架构模式。它是**描述质量属性需求的一种结构化方法**。

## 三、先教学：质量属性场景的六个组成部分

这是 Day 103 的核心知识点。

一个完整的质量属性场景包含六个部分：

| 组成部分 | 英文 | 要回答的问题 | 直观理解 |
|---|---|---|---|
| 刺激源 | Stimulus Source | 谁或什么产生了刺激？ | 谁发起 |
| 刺激 | Stimulus | 具体发生了什么事件或条件？ | 发生什么 |
| 环境 | Environment | 事件发生时处于什么条件下？ | 当时什么环境 |
| 制品 | Artifact | 系统中的哪个部分受到刺激？ | 影响了哪个系统对象 |
| 响应 | Response | 系统应该采取什么行动？ | 系统怎么处理 |
| 响应度量 | Response Measure | 如何衡量系统响应是否达标？ | 处理得怎么样 |

可以用这条顺序帮助记忆：

**谁发起 → 发生什么 → 什么环境 → 哪个对象受影响 → 系统怎么响应 → 响应是否达标。**

### 1. 刺激源（Stimulus Source）

刺激源是产生刺激的实体或参与者。

常见来源：

- 人：用户、管理员、开发人员。
- 外部系统：支付平台、物流平台、第三方 API。
- 内部系统或组件：监控程序、定时任务、其他服务。
- 硬件或设备：传感器、服务器硬件等。

例如：

用户向订单服务提交创建订单请求：

- 用户是刺激源。
- 创建订单请求是刺激。

**判断重点：刺激源回答“谁或什么产生了事件”，不是事件本身。**

### 2. 刺激（Stimulus）

刺激是系统需要处理的具体事件或条件。

例如：

- 用户提交创建订单请求。
- 数据库主节点发生故障。
- 外部支付平台不可用。
- 用户尝试访问没有权限的订单。
- 开发人员提出修改某个模块的请求。

刺激描述的是到达系统、需要系统考虑和处理的事件或条件。

### 3. 环境（Environment）

环境描述刺激发生时系统所处的运行条件。

常见环境：

- 正常运行期间。
- 促销高峰期间。
- 5000 个用户并发访问。
- 系统处于降级状态。
- 某个节点已经发生故障。
- 系统启动或维护期间。

例如：

> 促销高峰期间，5000 个用户同时访问订单服务。

在今天采用的场景拆分中：

- 促销高峰、5000 用户并发：环境。
- 用户实际提交创建订单请求：刺激。

不要把“系统在什么条件下运行”和“具体发生了什么事件”混为一谈。

### 4. 制品（Artifact）

制品指受到刺激的系统对象，可以是整个系统，也可以是某个具体组件、服务、模块或资源。

例如：

- 订单创建接口。
- 订单查询接口。
- 支付服务。
- 数据库服务。
- 消息队列。
- 整个电商系统。

**判断重点：制品回答“系统中的哪个部分受到刺激”，不是“发生了什么故障现象”。**

例如：

- 支付请求连续超时：故障表现。
- 支付服务 / 支付模块：受到刺激的系统对象，即制品。

### 5. 响应（Response）

响应是系统收到刺激后采取的活动或行为。

例如：

- 处理订单并返回结果。
- 切换到备用数据库节点。
- 启用备用支付通道。
- 拒绝未授权请求。
- 记录故障并触发告警。
- 将请求放入队列，等待后续处理。

响应描述系统做了什么，而不是做得是否足够好。

### 6. 响应度量（Response Measure）

响应度量是评价系统响应是否满足质量要求的可验证指标或约束。

例如：

- P95 响应时间不超过 300ms。
- 故障恢复时间不超过 30 秒。
- 错误率低于 0.1%。
- 99.95% 的月度可用性。
- 修改一个模块不超过 2 人日。

响应度量必须尽可能明确，能够通过测试、监控或评估进行验证。

**响应与响应度量的区别：**

- 响应：启用备用支付通道。
- 响应度量：在 10 秒内恢复支付服务。

前者描述动作，后者描述动作需要达到的结果标准。

## 四、互动训练记录：从六要素识别到完整场景拆解

以下按本日实际互动顺序整理。用户回答经过口述整理，保留最初判断、理解偏差、纠错过程和最终掌握边界。

### 1. 促销高峰和 5000 并发属于什么？

**题目：**

一个电商系统在促销高峰期间，5000 个用户同时访问订单服务。

这里的“促销高峰期间，5000 个用户同时访问”属于质量属性场景六要素中的哪一个？

**用户最初回答（整理）：**

> 六个部分是：是谁、发生了什么、在什么样的环境下、影响了什么、怎么处理、最后的结果是什么。促销高峰期间，5000 个用户同时访问，应该是发生了什么事情，属于刺激。

**评估：初次判断错误，但能够回忆六要素的整体结构。**

**纠正：**

在本题的场景拆分中，“促销高峰期间，5000 个用户并发访问”描述的是刺激发生时系统所处的负载环境，因此属于：

**环境（Environment）。**

需要区分：

- 促销高峰、5000 用户并发：环境。
- 用户实际提交创建订单请求：刺激。

用户最初把“发生什么”和“在什么条件下发生”混淆了。

### 2. 用户发送创建订单请求属于什么？

**题目：**

促销高峰期间，用户向订单服务发送创建订单请求。

“用户发送创建订单请求”属于六要素中的哪一个？为什么？

**用户实际回答（整理）：**

> 用户发送订单请求应该属于刺激。刺激源就是用户，刺激就是提交某种操作的请求。用户发送创建订单请求，就是用户做了什么。

**评估：通过。**

用户能够正确区分：

- 用户：刺激源。
- 创建订单请求：刺激。

这是对上一题“环境与刺激”混淆的第一次有效修正。

### 3. 订单创建接口属于什么？

**题目：**

促销高峰期间，5000 个用户同时向订单服务发送创建订单请求。系统需要处理的对象是订单创建接口。

订单创建接口属于六要素中的哪一个？为什么？

**用户实际回答（整理）：**

> 一共有刺激源、刺激、环境、制品、响应、响应度量。订单创建接口应该是制品。

**评估：通过。**

订单创建接口是受到请求刺激、需要处理请求的系统对象，因此属于制品（Artifact）。

### 4. 完成订单创建并返回结果属于什么？

**题目：**

订单创建接口收到请求后，系统执行订单创建逻辑，完成订单创建，并向用户返回处理结果。

这里的行为属于哪一个组成部分？

**用户实际回答（整理）：**

> 创建订单、返回结果，就是响应。因为 Response 就是系统收到请求之后进行响应。

**评估：通过。**

用户能够理解响应描述的是系统收到刺激后采取的行动。

### 5. P95 不超过 300ms 属于什么？

**题目：**

需求规定：

> 促销高峰期间，5000 个用户并发创建订单，订单接口的 P95 响应时间不得超过 300ms。

P95 响应时间不得超过 300ms 属于六要素中的哪一个？

**用户实际回答（整理）：**

> 系统做得怎么样，是否达到要求，处理得怎么样，就是响应度量。

**评估：通过。**

用户能够正确区分：

- 完成订单创建并返回结果：响应。
- P95 不超过 300ms：响应度量。

### 6. 数据库主节点突然宕机属于什么？

**题目：**

订单系统运行期间，数据库主节点突然宕机，系统自动切换到备用节点，并在规定时间内恢复订单服务。

“数据库主节点突然宕机”属于六要素中的哪一个？

**用户实际回答（整理）：**

> 谁发生了什么，在什么样的环境下。数据库主节点突然宕机，应该是发生了什么，属于刺激。

**评估：通过。**

用户能够将数据库主节点宕机识别为刺激（Stimulus）。

### 7. “订单系统运行期间”属于什么？

**题目：**

在上述场景中，“订单系统运行期间”属于六要素中的哪一个？

**用户实际回答（整理）：**

> 谁发生了什么，在什么样的环境下。订单系统运行期间，毫无疑问是第三个，在什么样的环境下，就是环境。

**评估：通过。**

用户能够将：

- 数据库主节点突然宕机：刺激。
- 订单系统运行期间：环境。

正确区分。

### 8. 刺激源和刺激有什么区别？

**题目：**

假设数据库主节点因为硬件故障而宕机。

这里的“硬件故障”和“数据库主节点宕机”应该如何理解？哪个是刺激源，哪个是刺激？

**用户最初回答（整理）：**

> 刺激源就是是谁，刺激就是发生了什么。硬件故障应该是刺激源，数据库主节点宕机应该是刺激。

**评估：方向接近，但刺激源的定义需要纠正。**

**纠正：**

刺激源是产生刺激的实体，不是故障原因或故障事件本身。

在本题采用的拆分方式中：

| 内容 | 对应含义 |
|---|---|
| 发生故障的物理硬件组件 | 刺激源 |
| 硬件发生故障 | 刺激 |
| 数据库主节点因此不可用 | 故障表现或后续影响 |

需要特别注意：刺激源、刺激和故障表现之间可能存在因果链。必须先明确系统边界和场景描述，才能准确拆分。

如果题目直接将“数据库主节点宕机”定义为刺激，那么就不能机械地把它拆成其他含义；应进一步明确产生该宕机事件的实体或系统来源。

**核心纠正：**

- 刺激源：谁或什么产生事件。
- 刺激：具体发生的事件。
- 故障表现：事件发生后观察到的结果。

用户经过纠正后，理解了刺激源与刺激的基本区别，但还需要通过不同场景再次验证。

### 9. 完整场景拆解：第三方支付平台发生故障

**题目：**

某电商系统运行期间，外部支付平台突然发生故障，导致支付请求连续超时。系统自动启用备用支付通道，并在 10 秒内恢复支付服务。

请将这个场景拆解成六个组成部分。

> 受到什么样的影响？支付请求连续超时，我一开始认为这是制品。  
> 怎么处理？启用备用支付通道，就是响应。  
> 最终结果？10 秒内恢复支付服务，就是响应度量。

**评估：整体结构已经建立，但制品识别错误。**

用户能够正确识别：

- 刺激源：外部支付平台。
- 刺激：外部支付平台发生故障。
- 环境：电商系统运行期间。
- 响应：启用备用支付通道。
- 响应度量：10 秒内恢复支付服务。

**关键纠正：**

用户把“支付请求连续超时”当成制品。

实际上：

- 支付请求连续超时：故障表现。
- 支付服务 / 支付模块：受到刺激影响的系统对象，即制品。

完整答案：

| 六要素 | 对应内容 |
|---|---|
| 刺激源 | 外部支付平台 |
| 刺激 | 外部支付平台发生故障 |
| 环境 | 电商系统正常运行期间 |
| 制品 | 支付服务 / 支付模块 |
| 响应 | 自动启用备用支付通道 |
| 响应度量 | 10 秒内恢复支付服务 |

### 10. 订单查询接口属于什么？

**题目：**

一个订单系统的数据库发生故障，导致订单查询接口无法正常工作。

“订单查询接口”属于六要素中的哪一个？为什么？

**用户实际回答（整理）：**

## 五、完整场景对照与常见混淆

### 1. 性能场景

> 促销高峰期间，当 5000 个用户并发向订单服务提交创建订单请求时，订单创建接口的 P95 响应时间不得超过 300ms。

| 六要素 | 对应内容 |
|---|---|
| 刺激源 | 外部用户 |
| 刺激 | 用户提交创建订单请求 |
| 环境 | 促销高峰、5000 用户并发 |
| 制品 | 订单创建接口 |
| 响应 | 系统处理订单并返回结果 |
| 响应度量 | P95 响应时间不超过 300ms |

### 2. 可用性场景

> 订单系统运行期间，数据库主节点发生故障，系统自动切换到备用节点，并在规定时间内恢复订单服务。

| 六要素 | 对应内容 |
|---|---|
| 刺激源 | 发生故障的硬件或基础设施来源（根据场景边界确定） |
| 刺激 | 数据库主节点发生故障或变得不可用 |
| 环境 | 订单系统运行期间 |
| 制品 | 数据库服务及受影响的订单服务组件 |
| 响应 | 自动切换到备用节点 |
| 响应度量 | 在约定时间内恢复订单服务 |

**注意：** 刺激源的填写必须根据题目实际描述和系统边界确定，不能仅凭“硬件故障”四个字机械判断。若题目没有提供刺激来源，不应擅自补造事实。

### 3. 支付服务故障场景

| 六要素 | 对应内容 |
|---|---|
| 刺激源 | 外部支付平台 |
| 刺激 | 外部支付平台发生故障 |
| 环境 | 电商系统正常运行期间 |
| 制品 | 支付服务 / 支付模块 |
| 响应 | 启用备用支付通道 |
| 响应度量 | 10 秒内恢复支付服务 |

### 4. 六要素最容易混淆的四组关系

| 容易混淆的概念 | 正确区分 |
|---|---|
| 刺激源 vs 刺激 | 谁产生事件 vs 具体发生什么 |
| 刺激 vs 环境 | 事件本身 vs 事件发生时的运行条件 |
| 制品 vs 故障现象 | 受到刺激的系统对象 vs 发生后观察到的现象 |
| 响应 vs 响应度量 | 系统采取的行动 vs 行动需要达到的可验证指标 |

### 5. 本日形成的判断口诀

- 问“谁或什么产生事件”——刺激源。
- 问“发生了什么”——刺激。
- 问“当时处于什么条件”——环境。
- 问“系统哪个部分受到刺激”——制品。
- 问“系统采取什么行动”——响应。
- 问“如何判断响应达标”——响应度量。

## 七、最后回忆 Day 102：可靠性与可用性的区别

按照训练顺序，完成 Day 103 新知识后，最后回忆 Day 102。

### 1. 回忆场景

某订单系统每天都会发生多次故障，但每次故障都能在几秒内自动恢复。由于恢复速度很快，系统月度可用性仍然达到 99.99%。

问题：

这个系统目前更值得关注的是可靠性问题，还是可用性问题？为什么？

### 2. 用户实际回答（整理）

> 可靠性是把代码层面的问题解决掉，让它不再发生故障，这个叫可靠性。而题目说每天都会发生故障，但是能够在几秒内自动恢复，这个叫可用性。

**评估：核心判断通过，定义范围需要补充。**

用户能够识别：

- 频繁发生故障：暴露可靠性问题。
- 故障后快速恢复：有助于维持较高可用性。

### 3. 补充纠正

用户最初把可靠性理解为“在代码层面修复问题”，这个范围过窄。

可靠性建设不仅包括修复代码缺陷，还可能涉及：

- 消除架构设计缺陷。
- 减少数据损坏和不一致。
- 降低硬件故障的影响。
- 做好异常处理与故障隔离。
- 防止级联故障。
- 减少重复故障发生。

因此：

- **可靠性（Reliability）：** 关注系统在规定条件和时间内持续、正确运行的能力。
- **可用性（Availability）：** 关注系统需要时能否正常提供服务。

**本题结论：** 频繁发生故障说明可靠性值得重点关注；快速恢复能够减少累计不可用时间，帮助维持较高可用性。高可用性指标本身不能证明系统没有可靠性问题。

**评估：Day 102 间隔回忆通过，可靠性定义的适用范围得到补充。**
