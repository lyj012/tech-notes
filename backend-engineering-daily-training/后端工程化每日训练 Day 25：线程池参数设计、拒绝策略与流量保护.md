# 后端工程化每日训练 Day 25：线程池参数设计、拒绝策略与流量保护

## 一、今天学习的知识点

今天学习的是：

**线程池（Thread Pool）与线程池参数设计**

一句话理解：

> 线程池不是为了“尽可能多地创建线程”，而是为了复用线程、限制本机并发、建立任务缓冲和过载保护边界，防止突发任务耗尽 CPU、内存、数据库连接池或第三方接口容量。

今天重点理解以下问题：

```text
ThreadPoolExecutor 接收任务时到底按什么顺序处理
核心线程数、最大线程数和队列容量应该如何设计
线程池满了以后应该拒绝、排队还是降级
为什么最大线程数不能盲目扩大到 500
线程池如何与 Kafka、限流、熔断和监控配合
```

---

## 二、为什么后端系统需要线程池

如果每收到一个异步任务就直接创建线程：

```java
new Thread(task).start();
```

当线上瞬间到达 5000 个任务时，应用可能同时创建数千个线程。

线程并不是免费的资源。每个线程都会带来：

```text
线程栈内存
线程对象和上下文数据
操作系统调度成本
CPU 上下文切换
GC 压力
数据库和 HTTP 连接竞争
```

最终可能形成以下故障链路：

```text
大量任务到达
↓
不断创建新线程
↓
线程栈和堆内存持续增加
↓
CPU 大量时间用于上下文切换
↓
真正业务处理速度下降
↓
数据库连接池和下游接口被大量并发请求打满
↓
请求超时、重试增加
↓
流量进一步放大
↓
服务 OOM、假死或崩溃
```

线程池的核心价值是：

```text
复用固定数量的线程
限制本机同时执行的任务数
通过有界队列吸收短暂突发流量
在容量耗尽时明确拒绝或降级
提供可监控的并发边界
```

因此线程池不是单纯的性能工具，而是后端系统的资源隔离和过载保护工具。

## 三、ThreadPoolExecutor 接收任务的真实顺序

`ThreadPoolExecutor` 的核心参数包括：

```text
corePoolSize       核心线程数
maximumPoolSize    最大线程数
keepAliveTime      非核心线程空闲存活时间
workQueue          任务队列
threadFactory      线程创建工厂
handler            拒绝策略
```

一个新任务进入线程池后，处理顺序是：

```text
当前线程数 < corePoolSize
↓ 是
创建核心线程执行任务

↓ 否
尝试把任务放入 workQueue

↓ 队列已满
当前线程数 < maximumPoolSize
↓ 是
创建非核心线程执行任务

↓ 否
触发拒绝策略
```

可以简化为：

```text
先补核心线程
↓
核心线程满后先入队
↓
队列满后再扩容到最大线程数
↓
最大线程数和队列都满后拒绝
```

这里最容易理解错误的地方是：

> 达到 `maximumPoolSize` 且有界队列已经满后，线程池不会继续创建线程，而是立即执行拒绝策略。

例如：

```text
corePoolSize = 10
maximumPoolSize = 20
queueCapacity = 100
```

当系统中存在：

```text
20 个线程全部忙碌
100 个任务正在队列等待
```

第 121 个尚未被接纳的任务进入时，就会触发拒绝策略，而不是继续创建第 21 个线程。

## 四、真实业务里怎么使用线程池

### 1. AI 异步任务执行平台

假设 Kafka 中积压了大量 AI 任务：

```text
文本生成
图片生成
OCR
Embedding
文档解析
```

Kafka Consumer 不应该无限制地把消息并发调用到第三方模型。

更合理的执行链路是：

```text
入口参数校验和限流
↓
任务记录持久化到数据库
↓
任务消息进入 Kafka
↓
Worker 消费消息
↓
提交到本地有界线程池
↓
受控并发调用模型或执行计算
↓
更新任务状态和结果
```

本地线程池负责限制单个 Worker 实例的实际执行并发。

例如第三方模型只允许每个账号同时执行 10 个任务，那么即使 Kafka 中有 10 万条消息，本地线程池也不应该启动 500 个线程同时请求模型。

否则可能出现：

```text
第三方返回 429
请求大量超时
Token 或调用成本失控
HTTP 连接池耗尽
任务重试进一步放大流量
```

### 2. PDF 转换和 OCR

PDF 渲染、压缩、图片转换通常偏 CPU 密集型。

如果服务器只有 8 核 CPU，却同时运行 100 个转换线程：

```text
任务并不会快 12 倍
反而会发生大量上下文切换
CPU 持续 100%
接口和健康检查无法及时响应
整台机器出现假死
```

这类任务的并发数通常应接近 CPU 核数，并根据内存占用和实际压测结果调整。

### 3. 广告投放平台

广告投放可能同时调用：

```text
账户接口
计划接口
单元接口
关键词接口
素材上传接口
```

可以对可并行的远程调用使用独立 IO 线程池，提高整体吞吐。

但必须同时考虑：

```text
第三方 QPS 限制
Token 池容量
HTTP 连接池大小
接口平均耗时
失败重试策略
```

线程池并发不能高于整个下游链路真正能承受的容量。

### 4. 支付、通知和低优先级任务隔离

支付回调、AI 推理、报表统计和日志写入不能共用同一个线程池。

否则可能发生：

```text
大量 AI 任务占满线程池
↓
支付回调无法及时执行
↓
订单状态更新延迟
↓
用户重复支付或投诉
```

更合理的做法是根据业务重要性和资源类型拆分：

```text
支付回调线程池
AI 调用线程池
PDF 转换线程池
通知线程池
报表和低优先级任务线程池
```

这种设计叫做资源隔离。

## 五、线程数应该如何设计

线程数没有一个适用于所有系统的固定答案。

应该综合以下因素：

```text
任务是 CPU 密集型还是 IO 密集型
单个任务平均耗时
CPU 核数和内存
数据库连接池容量
HTTP 连接池容量
第三方服务并发和 QPS 限制
任务允许等待多久
失败后的补偿能力
```

### 1. CPU 密集型任务

例如：

```text
PDF 渲染
图片压缩
数据加密
复杂计算
```

这类任务主要消耗 CPU。

线程数通常不应远高于 CPU 核数，可以从以下范围开始压测：

```text
CPU 核数
或
CPU 核数 + 1
```

例如 8 核服务器可以从 8～9 个工作线程开始验证，而不是直接配置 100 个线程。

### 2. IO 密集型任务

例如：

```text
调用 AI 模型 API
访问对象存储
调用第三方广告接口
查询远程服务
```

线程大部分时间可能在等待网络，因此线程数可以高于 CPU 核数。

但不能只看 CPU，还必须受以下资源约束：

```text
数据库最大连接数
HTTP 连接池最大连接数
第三方允许并发数
机器内存
下游限流阈值
```

假设：

```text
线程池最大线程数 = 100
HTTP 连接池最大连接数 = 20
```

那么大量线程只会阻塞等待连接，并不会真正带来 100 路并发。

### 3. 参数设计必须通过压测验证

合理流程应该是：

```text
估算初始参数
↓
使用接近真实业务的任务压测
↓
观察吞吐、延迟、CPU、内存和下游压力
↓
调整线程数和队列容量
↓
建立线上监控和告警
```

不能只依赖公式，也不能把开发环境参数直接复制到生产环境。

## 六、为什么最大线程数不能直接改成 500

当线程池已经满载时，直接把 `maximumPoolSize` 从 20 改成 500，看起来可以接收更多任务，但通常只是把压力从线程池转移到其他资源。

可能产生以下风险。

### 1. 线程栈内存增加

每个线程都需要栈空间。

大量线程可能导致：

```text
本地内存耗尽
无法创建新线程
OutOfMemoryError: unable to create native thread
```

### 2. CPU 上下文切换增加

当可运行线程远多于 CPU 核数时，操作系统需要不断切换线程。

表现可能是：

```text
CPU 使用率很高
但业务吞吐没有提高
接口响应时间反而变长
```

### 3. 数据库连接池被打满

500 个线程同时执行数据库操作，而连接池只有 30 个连接：

```text
30 个线程获得连接
470 个线程等待连接
```

大量线程仍然占用内存和调度资源，最终可能拖垮服务。

### 4. 下游服务被压垮

如果 500 个线程同时调用 AI、OCR 或广告接口：

```text
下游限流
大量 429 或 5xx
调用超时
重试流量增加
触发级联故障
```

### 5. 故障恢复更困难

大线程池和大队列可以暂时隐藏容量不足，但会积累大量尚未完成的任务。

当服务发布、重启或崩溃时：

```text
内存队列任务丢失
任务完成时间无法预测
停机和回滚时间变长
```

所以更准确的原则是：

> 线程池参数不是越大越好，而是要让任务处理能力与 CPU、连接池、下游容量和业务时效保持匹配。

## 七、任务队列为什么必须有界

如果使用无界队列：

```java
new LinkedBlockingQueue<>()
```

当生产速度长期高于消费速度时，任务会不断堆积在 JVM 内存中。

故障链路可能是：

```text
任务持续进入
↓
队列不断增长
↓
任务对象占用大量堆内存
↓
Full GC 频繁
↓
响应时间增加
↓
最终 OOM
```

有界队列的价值是：

```text
明确系统最多允许暂存多少任务
在容量耗尽前产生监控信号
让上游感知系统已经过载
防止任务无限堆积到内存
```

但是队列也不能盲目设置得非常大。

例如队列容量为 100 万：

```text
看起来很少触发拒绝
但用户任务可能排队几个小时
发布重启时大量任务丢失
系统问题被长期隐藏
```

队列容量应该结合任务平均处理时间和允许等待时间设计。

例如：

```text
实际处理能力 = 20 个任务/秒
允许最多排队 10 秒
```

可以先估算：

```text
队列容量 ≈ 20 × 10 = 200
```

然后通过压测和线上指标继续调整。

## 八、拒绝策略应该如何选择

当以下条件同时成立时：

```text
线程数已经达到 maximumPoolSize
有界队列已经满
```

线程池必须执行拒绝策略。

JDK 提供四种常见策略。

### 1. AbortPolicy

```text
直接抛出 RejectedExecutionException
```

优点：

```text
失败明确
不会静默丢失任务
便于上层进入重试、降级或返回错误
```

对于重要业务，通常比静默丢弃更安全。

### 2. CallerRunsPolicy

```text
由提交任务的线程同步执行任务
```

它可以让上游提交速度被迫下降，形成一定的反压。

但需要注意：

```text
如果提交线程是 Tomcat 工作线程
它会被长任务占用
接口延迟会明显增加
甚至拖慢整个入口服务
```

如果提交线程是 Kafka Consumer 线程，长时间执行任务还可能导致：

```text
无法及时 poll
触发 Consumer Group Rebalance
消息重复消费
```

因此不能看到“CallerRunsPolicy 不丢任务”就无条件使用。

### 3. DiscardPolicy

```text
静默丢弃新任务
```

风险很高，因为调用方可能误以为任务已经提交成功。

仅适合真正允许丢失的低价值任务，例如部分非关键统计或采样日志，并且仍应记录丢弃指标。

### 4. DiscardOldestPolicy

```text
丢弃队列中等待最久的任务
再尝试提交新任务
```

这并不意味着它适合所有“新任务优先”的场景。

如果旧任务代表支付、订单或已承诺给用户的 AI 任务，直接丢弃会破坏业务可靠性。

### 5. 重要任务更适合自定义拒绝处理

对于 AI 异步任务、文件转换和广告发布，可以设计自定义策略：

```text
记录 taskId、线程池名称和拒绝原因
↓
更新任务状态为 WAITING_RETRY 或 REJECTED
↓
写入持久化补偿表或重新投递 MQ
↓
增加拒绝计数监控
↓
必要时触发告警
```

关键原则是：

> 拒绝不等于无声丢弃。重要任务必须留下可追踪、可恢复的状态。

## 九、哪些任务应该拒绝，哪些任务可以排队

线程池是否接纳任务，不应该只根据“队列还有没有空间”判断。

### 1. 应在进入执行链路前直接拒绝的任务

```text
参数非法
身份或权限校验失败
任务已经过期
相同业务任务已经存在
用户配额已经耗尽
付费额度不足
文件类型、大小或内容不符合要求
当前系统处于维护或熔断状态
```

这些任务即使有空闲线程也不应该执行。

### 2. 可以进入持久化队列等待的任务

```text
业务合法
允许延迟完成
已经生成稳定 taskId
任务状态可追踪
系统具备幂等和补偿能力
```

例如：

```text
PDF 转换
OCR
AI 内容生成
广告素材批量生成
报表统计
```

它们通常更适合先持久化，再进入 Kafka 或 RabbitMQ 等可靠队列，而不是只进入 JVM 内存队列。

### 3. 需要优先保证的任务

可以按照以下维度进行隔离或调度：

```text
付费用户与免费用户
实时任务与离线任务
支付和订单任务与普通任务
人工重试任务与批量后台任务
高优先级任务与低优先级任务
```

但优先级设计必须避免低优先级任务长期饥饿。

## 十、线程池与 Kafka、限流、熔断如何配合

线程池只能限制一个 JVM 实例中的本地执行并发，不能单独解决整个系统的流量问题。

更完整的保护链路是：

```text
客户端请求
↓
入口参数、权限、配额和重复校验
↓
Nginx / Gateway 限流
↓
创建任务记录并持久化
↓
发送 Kafka 消息进行削峰
↓
Worker Consumer 拉取消息
↓
本地线程池限制实际执行并发
↓
调用数据库、AI、OCR 或第三方服务
↓
设置超时、熔断和降级
↓
更新任务状态和结果
↓
失败重试、死信队列或补偿任务
```

各组件职责不同：

| 组件 | 主要职责 |
| --- | --- |
| 入口限流 | 防止过量请求进入系统 |
| 参数和配额校验 | 拒绝本就不应该执行的任务 |
| 数据库任务表 | 保存可靠任务状态，支持查询和补偿 |
| Kafka | 跨服务持久化排队和削峰 |
| Worker 本地线程池 | 控制单实例实际执行并发 |
| 超时 | 限制一次下游调用占用资源的最长时间 |
| 熔断和降级 | 下游异常时阻止故障扩散 |
| 幂等和状态机 | 防止重复执行和非法状态流转 |
| 监控告警 | 发现队列、线程池和下游正在恶化 |

一个常见错误是：

```text
请求进入
↓
直接提交本地线程池
↓
线程池满了再发送 Kafka
```

这种设计可能导致：

```text
任务是否持久化不清晰
同一任务在本地和 Kafka 中重复存在
接口成功但任务实际丢失
重启后内存队列无法恢复
```

对于需要可靠执行的异步任务，更合理的是：

> 先完成业务校验和任务持久化，再通过 MQ 削峰，Worker 消费后使用本地线程池控制执行并发。

## 十一、线程池需要监控哪些指标

线程池参数不能配置后就不再关注。

至少应该监控：

```text
当前线程数 poolSize
活跃线程数 activeCount
核心线程数 corePoolSize
最大线程数 maximumPoolSize
队列当前长度 queueSize
队列剩余容量 remainingCapacity
已完成任务数 completedTaskCount
任务总数 taskCount
拒绝次数 rejectedCount
单个任务执行耗时
任务排队等待时间
```

重点告警场景：

```text
activeCount 长期接近 maximumPoolSize
队列长度持续上涨
队列剩余容量接近 0
拒绝次数持续增加
任务等待时间超过业务 SLA
任务执行耗时突然上升
```

这些指标需要与以下指标一起观察：

```text
Kafka Lag
数据库连接池活跃连接数
HTTP 连接池等待数
第三方接口耗时和错误率
CPU、内存和 GC
任务成功率和超时率
```

例如：

```text
线程池已满
CPU 只有 20%
HTTP 连接池等待数很高
```

更可能说明瓶颈在 HTTP 连接或下游，而不是 CPU。

如果：

```text
线程池已满
CPU 长期 100%
上下文切换明显增加
```

则更可能是 CPU 密集任务并发过高。

## 十二、常见坑

### 1. 使用 Executors 快捷方法但不了解默认参数

例如：

```java
Executors.newFixedThreadPool(20);
```

其内部通常使用无界队列，流量高峰时任务可能无限堆积。

再例如：

```java
Executors.newCachedThreadPool();
```

最大线程数非常大，可能在高峰期创建大量线程。

生产系统通常更适合显式使用 `ThreadPoolExecutor`，明确所有边界。

### 2. 多种业务共用一个公共线程池

AI 慢任务、支付任务、日志任务和后台统计共用线程池，容易互相拖垮。

应按业务重要性、耗时和资源类型进行隔离。

### 3. 只扩大最大线程数，不检查下游容量

线程数增加并不代表吞吐一定增加，可能只会让数据库、Redis、HTTP 连接池或第三方服务更快崩溃。

### 4. 队列容量过大

大队列会掩盖消费能力不足，使用户等待时间不可控，并增加重启时任务丢失风险。

### 5. 静默丢弃重要任务

使用 `DiscardPolicy` 后没有业务状态、日志、监控和补偿，属于严重可靠性问题。

### 6. 在线程池任务中吞掉异常

任务抛异常后如果没有统一捕获和记录，可能表现为任务“神秘消失”。

至少需要记录：

```text
线程池名称
任务类型
taskId / orderId
traceId
异常类型和堆栈
执行开始时间和耗时
```

### 7. 忽略线程池关闭

应用优雅停机时应停止接收新任务，并等待正在执行的任务完成或持久化恢复状态。

否则发布和重启可能导致：

```text
任务执行到一半被中断
数据库状态长期停留 RUNNING
消息 offset 已提交但业务未完成
```

## 十三、最小必要代码示例

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    10,
    20,
    60,
    TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(100),
    runnable -> {
        Thread thread = new Thread(runnable);
        thread.setName("ai-worker-" + thread.getId());
        thread.setUncaughtExceptionHandler((t, e) ->
            log.error("threadPoolTaskFailed thread={}", t.getName(), e)
        );
        return thread;
    },
    new ThreadPoolExecutor.AbortPolicy()
);
```

这个示例表达了几个核心原则：

```text
核心线程数明确
最大线程数明确
使用有界队列
线程具有可识别名称
拒绝行为明确
```

真实项目中还应增加：

```text
统一线程池配置管理
任务包装和 TraceId 透传
拒绝次数指标
队列长度指标
优雅关闭
业务补偿处理
```

不能直接复制参数到生产环境，参数必须根据服务器资源、任务类型和压测结果确定。

## 十四、面试怎么表达

可以这样表达：

> 在类似的 AI 异步任务或文件处理系统中，我不会直接创建线程，也不会使用无界队列，而是通过 ThreadPoolExecutor 明确设置核心线程数、最大线程数、有界队列和拒绝策略。本地线程池主要负责控制单个 Worker 实例的实际执行并发，Kafka 负责跨服务的持久化排队和削峰。参数设计时我会同时考虑任务属于 CPU 密集型还是 IO 密集型，以及数据库连接池、HTTP 连接池和第三方接口的容量，而不是单纯把线程数调大。线程池满载时，重要任务不能静默丢弃，需要记录任务状态并进入重试、补偿或重新投递流程。同时会监控活跃线程数、队列长度、拒绝次数和任务等待时间，避免容量问题直到用户投诉才被发现。

如果面试官继续追问为什么不能把最大线程数直接扩大到 500，可以回答：

> 线程数过大可能增加线程栈内存和上下文切换，同时把数据库连接池、HTTP 连接池和第三方接口打满。最终可能出现 CPU 很高但吞吐没有提升，或者大量线程阻塞等待下游资源。因此线程池容量必须与整个调用链的最小瓶颈匹配，并通过压测和监控调整。

## 十五、线上故障练习

假设 AI Worker 的线程池配置为：

```text
corePoolSize = 10
maximumPoolSize = 20
queueCapacity = 100
rejectedExecutionHandler = AbortPolicy
```

某天短时间到达 5000 个 AI 任务，监控显示：

```text
20 个线程全部忙碌
队列长度达到 100
拒绝次数持续增加
Kafka Lag 也在上涨
第三方模型平均耗时从 4 秒升高到 15 秒
```

排查时应该依次思考：

1. 任务是否已经持久化，拒绝后会不会永久丢失？
2. 第三方模型变慢是否才是线程池饱和的根本原因？
3. HTTP 连接池、账号配额和第三方 QPS 是否已经达到上限？
4. 能否临时降低 Kafka 消费速率，避免 Worker 持续拉取但无法执行？
5. 是否需要触发熔断、切换备用模型或将任务保持在排队状态？
6. 哪些无效、重复、过期或超额任务应在入口直接拒绝？
7. 是否可以增加 Worker 实例，以及 Kafka Partition 数是否支持继续扩容？
8. 扩容后数据库、Redis 和第三方接口是否仍能承受新增并发？

不能直接采取：

```text
maximumPoolSize 改成 500
queueCapacity 改成 100000
```

因为这很可能只会隐藏问题并扩大故障范围。

## 十六、今天的核心结论

今天最重要的结论是：

1. **线程池的核心价值是控制资源，而不是无限提高并发。**
2. **ThreadPoolExecutor 的顺序是：核心线程 → 队列 → 非核心线程 → 拒绝策略。**
3. **达到最大线程数且有界队列已满后，不会继续创建线程，而是触发拒绝策略。**
4. **最大线程数不能脱离 CPU、内存、数据库连接池、HTTP 连接池和下游容量设计。**
5. **重要任务不能依赖 JVM 无界队列，也不能在拒绝时静默丢弃。**
6. **线程池、Kafka、限流、超时、熔断、幂等、状态机和监控共同组成完整的流量保护和可靠执行体系。**
7. **可靠链路通常是：入口校验与限流 → 任务持久化 → Kafka 削峰 → Worker 消费 → 本地线程池控制并发 → 下游超时、熔断与降级。**

## 能力等级

**中级偏高级后端能力。**

真正掌握线程池，不是记住几个构造参数，而是能够根据业务任务、机器资源和下游容量设计并发边界，并在队列满载、下游变慢和流量突发时保证任务可追踪、系统不崩溃、故障不扩散。
