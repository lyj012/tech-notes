# 后端工程化每日训练 Day 25：线程池参数设计、拒绝策略与流量保护

## 一、今天学习的知识点

今天学习的是：

**线程池（Thread Pool）、线程池参数设计，以及线程池与 Kafka、限流、熔断之间的协同保护。**

一句话理解：

> 线程池不是为了尽可能多地创建线程，而是为了复用线程、限制单个 JVM 的执行并发，并在系统过载时建立明确的资源边界。

今天重点解决以下问题：

```text
ThreadPoolExecutor 接收任务时到底按什么顺序处理
为什么达到最大线程数后不会继续创建线程
为什么不能把最大线程数直接扩大到 500
哪些任务应该直接拒绝，哪些任务适合进入 Kafka 等待
如何组合限流、Kafka、线程池、熔断和降级保护 AI 平台
```

## 二、线程池解决什么问题

如果每收到一个异步任务就直接创建一个线程：

```java
new Thread(() -> {
    // 执行业务任务
}).start();
```

当系统瞬间收到 5000 个任务时，应用可能尝试创建数千个线程。

线程并不是免费的资源。每个线程都会消耗：

```text
线程栈内存
线程对象和运行时数据
操作系统调度资源
CPU 上下文切换时间
数据库连接和 HTTP 连接
```

大量线程可能形成以下故障链路：

```text
大量任务同时进入
↓
应用不断创建线程
↓
线程栈和内存占用持续增加
↓
CPU 大量时间消耗在线程调度和上下文切换
↓
真正用于执行业务的时间减少
↓
数据库连接池、HTTP 连接池和第三方接口被打满
↓
请求超时和失败增加
↓
客户端或系统自动重试
↓
流量进一步放大
↓
服务 OOM、假死或崩溃
```

线程池的核心价值是：

```text
复用线程
限制并发
控制资源消耗
吸收短暂流量波动
在系统过载时明确拒绝或降级
提供可监控的容量边界
```

所以线程池不仅是性能工具，也是资源隔离和过载保护工具。

## 三、ThreadPoolExecutor 的核心参数

Java 后端通常通过 `ThreadPoolExecutor` 显式配置线程池。

```java
ExecutorService executor = new ThreadPoolExecutor(
    10,
    20,
    60,
    TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(100),
    new ThreadPoolExecutor.AbortPolicy()
);
```

核心参数包括：

```text
corePoolSize       核心线程数
maximumPoolSize    最大线程数
keepAliveTime      非核心线程空闲存活时间
workQueue          任务等待队列
threadFactory      线程工厂
handler            拒绝策略
```

### 1. corePoolSize：核心线程数

核心线程用于处理系统的常态流量。

例如：

```text
corePoolSize = 10
```

表示线程池最多先创建 10 个核心线程执行任务。

需要注意：

> 核心线程数不是“始终有 10 个空闲线程”，而是线程池处理常态任务时的基础并发规模。

### 2. maximumPoolSize：最大线程数

当核心线程已经创建、任务队列也已经满时，线程池才会继续创建非核心线程，直到达到最大线程数。

例如：

```text
maximumPoolSize = 20
```

表示整个线程池最多同时存在 20 个工作线程。

### 3. workQueue：任务队列

当线程数已经达到核心线程数后，新任务通常会先进入队列等待。

例如：

```java
new ArrayBlockingQueue<>(100)
```

表示最多允许 100 个任务在 JVM 内存中等待执行。

### 4. keepAliveTime：非核心线程存活时间

流量高峰过去后，超出核心线程数的非核心线程不会永久保留。

例如：

```text
60 秒没有新任务
↓
空闲的非核心线程被回收
```

### 5. RejectedExecutionHandler：拒绝策略

当以下条件同时成立时：

```text
线程数已经达到 maximumPoolSize
任务队列已经满
```

线程池无法再接纳任务，必须执行拒绝策略。

## 四、ThreadPoolExecutor 接收任务的真实顺序

线程池接收一个新任务时，大致按照以下顺序处理：

```text
当前线程数 < corePoolSize？
↓ 是
创建核心线程执行任务

↓ 否
尝试将任务放入 workQueue

↓ 队列已满
当前线程数 < maximumPoolSize？
↓ 是
创建非核心线程执行任务

↓ 否
执行拒绝策略
```

可以简化为：

```text
先补核心线程
↓
核心线程达到上限后先入队
↓
队列满后再扩容到最大线程数
↓
最大线程数和队列都满后拒绝
```

这里最容易出现的错误理解是：

```text
核心线程都忙
↓
立即创建非核心线程
```

实际并不是这样。

对于普通有界队列，核心线程达到上限后，新任务通常先进入队列；只有队列满了，线程池才会继续创建非核心线程。

## 五、5000 个 AI 任务为什么大量提交失败

假设 Worker 的线程池配置为：

```text
corePoolSize = 10
maximumPoolSize = 20
queueCapacity = 100
```

监控显示：

```text
20 个线程全部忙碌
100 个任务正在队列等待
大量任务提交失败
```

### 1. 为什么没有继续创建更多线程

因为线程池已经达到明确配置的最大容量：

```text
当前线程数 = maximumPoolSize = 20
任务队列长度 = queueCapacity = 100
```

此时新任务到达后：

```text
不能继续放入队列
也不能创建第 21 个线程
↓
触发拒绝策略
```

线程池不会根据任务数量无限创建线程。

这正是线程池存在的意义：

> 给并发和资源消耗设置硬边界，避免任务洪峰直接拖垮整个 JVM 和下游系统。

### 2. 线程池最多只接纳 120 个任务吗

不能简单地这样理解。

在某一个瞬间，线程池最多可能存在：

```text
20 个正在执行的任务
+
100 个正在排队的任务
=
120 个已被线程池接纳但尚未全部完成的任务
```

但只要工作线程不断完成任务，队列就会继续释放空间，后续任务仍然可以被接纳。

问题不是系统永远只能处理 120 个任务，而是：

> 在某个时刻，线程池允许同时执行和暂存的任务数量是有上限的。

## 六、为什么不能把最大线程数直接改成 500

把 `maximumPoolSize` 从 20 改成 500，看起来可以减少拒绝，但通常只是把压力从线程池转移到其他资源。

### 1. 线程栈和本地内存消耗

每个线程都需要线程栈和本地资源。

线程数量过多可能导致：

```text
本地内存持续增加
无法继续创建线程
OutOfMemoryError: unable to create native thread
服务崩溃
```

### 2. CPU 上下文切换增加

当可运行线程远多于 CPU 核数时，操作系统会频繁切换线程。

表现可能是：

```text
CPU 使用率很高
但大量 CPU 时间消耗在线程调度
真正业务吞吐量没有提高
任务平均耗时反而增加
```

因此更准确的说法不是“线程越多，CPU 使用率一定下降”，而是：

> CPU 可能依然很高，但有效业务吞吐量可能下降。

### 3. 数据库连接池耗尽

假设：

```text
线程池最大线程数 = 500
数据库连接池最大连接数 = 30
```

那么可能出现：

```text
30 个线程获得数据库连接
470 个线程等待连接
```

这些等待线程仍然占用内存和调度资源，却没有产生有效吞吐。

### 4. HTTP 连接池耗尽

如果 AI 调用使用的 HTTP 连接池只有 50 个连接：

```text
500 个工作线程
↓
只有 50 个线程真正获得连接
↓
其余线程阻塞等待连接
```

增加线程数并不能突破 HTTP 连接池和下游服务的容量上限。

### 5. 第三方 AI 服务被压垮

500 个线程同时调用模型服务，可能导致：

```text
第三方返回 429
大量调用超时
账号并发额度耗尽
调用费用瞬间增加
失败重试进一步放大流量
```

### 6. 故障影响范围扩大

线程数过大后，某个下游服务变慢时，会有更多线程被长期占用。

```text
第三方 AI 服务响应变慢
↓
大量线程等待返回
↓
线程、连接和内存长期被占用
↓
Worker 无法处理其他正常任务
↓
局部故障扩散
```

所以线程池参数设计必须同时受以下资源约束：

```text
CPU 核数
机器内存
数据库连接池
HTTP 连接池
第三方并发额度
第三方 QPS
任务平均耗时
任务允许等待时间
```

## 七、哪些任务应该立即拒绝

不是所有任务都应该进入 Kafka。

以下任务应该在入口阶段直接拒绝：

```text
参数不合法的任务
用户没有权限的任务
用户额度已经耗尽的任务
不支持的模型或任务类型
已经取消或过期的任务
命中幂等记录的重复任务
明显恶意或异常频率的请求
系统过载时的低优先级任务
```

### 1. 重复任务为什么应该直接拦截

假设用户因为网络超时重复点击提交按钮：

```text
同一个业务任务被提交 10 次
```

如果这 10 个任务全部进入 Kafka：

```text
浪费消息队列容量
浪费 Worker 执行能力
重复调用第三方模型
增加调用费用
可能重复写入业务结果
```

因此应在入口使用：

```text
requestId
业务幂等键
数据库唯一索引
Redis 幂等记录
```

直接识别重复请求，并返回已有任务编号或已有执行结果。

### 2. 免费用户是否应该全部拒绝

不能简单地按照“免费用户全部拒绝，付费用户全部接收”设计。

更合理的策略是：

```text
付费用户：更高限额、更高优先级、更短排队时间
免费用户：较低限额、普通优先级、高峰期允许限流
```

这样既能保护付费用户的 SLA，也不会完全失去免费用户体验。

## 八、哪些任务适合进入 Kafka 等待

适合进入 Kafka 的任务通常具有以下特点：

```text
已经通过参数、权限、额度和幂等校验
允许异步执行
允许等待几秒、几分钟甚至更长时间
暂时无法执行，但后续执行仍然有业务价值
失败后可以重试或补偿
任务状态可以持久化和查询
```

典型任务包括：

```text
AI 文本生成
AI 图片生成
OCR 识别
PDF 转换
Embedding 生成
批量广告素材处理
报表生成
```

Kafka 的作用不是提高单个任务的执行速度，而是：

> 将任务接收速度与 Worker 实际处理速度解耦，通过持久化消息承接突发流量。

假设：

```text
1 秒内进入 5000 个任务
Worker 每秒只能处理 20 个任务
```

没有 Kafka 时，大量任务会直接压在线程池和 JVM 内存中。

使用 Kafka 后：

```text
5000 个合法任务先进入 Kafka
↓
Worker 按照自身容量逐步消费
↓
任务不会全部同时进入本地线程池
```

## 九、拒绝策略应该如何选择

JDK 提供四种常见拒绝策略。

### 1. AbortPolicy

```text
直接抛出 RejectedExecutionException
```

优点：

```text
失败明确
不会静默丢任务
上游可以感知系统过载
便于监控拒绝次数
```

适合：

```text
不能静默丢失的核心业务
需要由上游重试、排队或降级的任务
```

### 2. CallerRunsPolicy

```text
由提交任务的调用线程自己执行任务
```

它可以形成一定的反压，因为提交线程被任务占用后，提交速度会下降。

但是它并不适合所有业务。

如果提交线程是 Tomcat 请求线程，而 AI 任务需要执行几十秒：

```text
Tomcat 请求线程被长期占用
↓
接口吞吐下降
↓
其他请求也可能排队
```

如果提交线程是 Kafka Consumer 线程：

```text
Consumer 线程长时间执行任务
↓
无法及时 poll
↓
可能超过 max.poll.interval.ms
↓
触发 Consumer Group Rebalance
```

所以 `CallerRunsPolicy` 必须结合提交线程的身份和任务耗时判断，不能机械使用。

### 3. DiscardPolicy

```text
直接丢弃新任务，不抛异常
```

风险非常高。

如果任务没有其他持久化记录：

```text
任务看起来提交成功
实际已经被静默丢失
```

只适合允许丢失、价值很低且有独立监控的任务，例如部分非核心统计或采样任务。

### 4. DiscardOldestPolicy

```text
丢弃队列中最旧的任务
再尝试提交当前任务
```

这不一定符合业务优先级。

最旧的任务可能已经等待最久，反而更应该被处理。

在核心业务中通常不应直接使用，除非业务明确允许“新任务优先、旧任务过期”。

### 5. 生产环境中的选择原则

对于 AI 异步任务：

```text
不能静默丢失
不能在 Kafka Consumer 线程里执行几十秒任务
不能让 JVM 队列无限增长
```

更合理的做法通常是：

```text
线程池满载时停止继续分发
暂停对应 Kafka Partition 的消费
已拉取但未完成的任务不提前提交 offset
线程池恢复容量后再恢复消费
同时记录线程池拒绝和暂停消费指标
```

## 十、AI 平台的完整流量保护链路

一套较完整的 AI 异步任务保护方案可以设计为：

```text
客户端提交任务
↓
API 网关或业务接口限流
↓
参数、权限、额度和幂等校验
↓
任务记录持久化
↓
发送任务消息到 Kafka
↓
Worker 按容量消费
↓
本地有界线程池控制实际并发
↓
调用第三方 AI 服务
↓
超时、熔断和降级
↓
更新任务状态和执行结果
```

这几个组件各自解决的问题不同。

### 1. 限流：控制入口速度

限流应该尽量在系统前面执行。

可以按照以下维度限流：

```text
用户
租户
IP
API Key
模型类型
付费等级
第三方供应商
```

例如：

```text
免费用户：每分钟最多提交 5 个任务
付费用户：每分钟最多提交 100 个任务
整个平台：每秒最多接收 500 个任务
```

超过限制时返回：

```text
HTTP 429 Too Many Requests
```

限流的目标是：

> 防止无效或过量请求继续进入数据库、Kafka 和 Worker。

### 2. 校验和幂等：拒绝无效任务

任务进入 Kafka 前应该完成：

```text
参数校验
权限校验
用户额度校验
模型可用性校验
幂等校验
```

无效任务越早拒绝，系统成本越低。

### 3. 任务持久化：确保状态可追踪

合法任务应先建立任务记录，例如：

```text
QUEUED
```

后续状态可以设计为：

```text
QUEUED
RUNNING
SUCCEEDED
FAILED
CANCELLED
```

如果数据库写入成功但 Kafka 发送失败，会产生数据不一致问题。

生产环境可以通过以下方式处理：

```text
本地消息表
Outbox Pattern
事务消息
定时补偿扫描
```

确保任务记录最终能够进入消息队列。

### 4. Kafka：承接突发任务

Kafka 负责保存大量待处理任务，使系统不需要在突发流量到达时立即执行全部任务。

可以根据任务类型或业务优先级拆分：

```text
ai-task-paid
ai-task-free
ai-task-text
ai-task-image
ai-task-ocr
```

拆分后可以配置不同的：

```text
分区数
Consumer Group
Worker 数量
并发配额
重试策略
```

这样可以避免低优先级任务完全挤占高优先级任务资源。

### 5. 线程池：限制单个 Worker 的执行并发

Kafka 中可以积压十万条消息，但单个 Worker 不应该一次把十万条消息全部拉到 JVM 队列。

线程池负责控制：

```text
单个实例同时执行多少任务
本地最多暂存多少任务
实例过载时如何反压
```

核心原则是：

> Kafka 是持久化的大缓冲区，本地线程池队列只应该是容量较小的临时缓冲区。

### 6. 熔断：阻止持续调用异常下游

调用第三方 AI 服务时，应统计：

```text
连接超时
读取超时
5xx
网络异常
慢调用率
失败率
```

当某个供应商持续失败或响应过慢时：

```text
熔断器从 Closed 进入 Open
↓
暂时停止真实调用
↓
快速执行降级逻辑
```

这样可以防止大量线程继续阻塞在异常下游上。

### 7. 降级：在下游异常时保住核心能力

AI 平台可以根据业务情况选择：

```text
切换备用模型
切换备用供应商
降低最大输出 Token
减少生成图片数量
将任务继续保留为排队状态
提示任务延迟处理中
暂时拒绝新的低优先级任务
```

降级不是简单返回 500，而是用较低成本的方案保住部分业务能力。

### 8. 重试和死信队列

失败任务不能无限重试。

可以设计为：

```text
第一次失败
↓
延迟 30 秒重试

第二次失败
↓
延迟 5 分钟重试

第三次失败
↓
进入死信队列
```

只有临时错误适合重试，例如：

```text
网络超时
第三方临时 5xx
短时间限流
```

以下错误通常不应重试：

```text
参数错误
用户无权限
额度不足
不支持的模型
永久业务失败
```

## 十一、Kafka Consumer 与线程池如何形成反压

一个常见错误是：

```text
Kafka 一次拉取大量消息
↓
全部提交到本地线程池
↓
线程池队列迅速塞满
↓
任务被拒绝或堆积在 JVM 内存
```

更合理的策略是根据本地执行容量控制消费速度。

### 1. 线程池接近满载时暂停消费

例如监控到：

```text
activeCount 接近 maximumPoolSize
queueSize 接近 queueCapacity
```

Worker 可以暂停对应 Partition：

```text
consumer.pause(partitions)
```

当线程池恢复容量后：

```text
consumer.resume(partitions)
```

需要注意：

> 暂停业务消息分发后，Consumer 仍应按照 Kafka 客户端要求保持正常 poll，避免因长时间不 poll 触发 Rebalance。

### 2. 不要提前提交 offset

如果消息刚被拉取，还没有真正执行完成，就提前提交 offset：

```text
消息已提交 offset
↓
线程池任务执行失败或服务崩溃
↓
Kafka 认为消息已经消费
↓
任务可能永久丢失
```

因此应在业务任务成功完成后，再安全推进对应 Partition 的 offset。

如果采用多线程处理，还需要处理：

```text
同一 Partition 内任务完成顺序不同
不能越过尚未完成的较小 offset 提交
Rebalance 时如何等待或回收正在执行的任务
```

这部分需要与 Day 14 的 Rebalance、Day 15 的顺序消费和幂等设计结合理解。

## 十二、线程数应该如何估算

线程数没有一个适用于所有系统的固定答案。

### 1. CPU 密集型任务

例如：

```text
PDF 渲染
图片压缩
加密计算
复杂数据计算
```

这类任务主要消耗 CPU。

初始线程数可以从以下范围开始压测：

```text
CPU 核数
或
CPU 核数 + 1
```

例如 8 核服务器可以先从 8～9 个线程开始测试，而不是直接配置 100 个线程。

### 2. IO 密集型任务

例如：

```text
调用大模型 API
调用对象存储
访问广告平台接口
访问远程微服务
```

线程大部分时间可能处于网络等待，因此线程数可以高于 CPU 核数。

但必须同时受以下容量限制：

```text
HTTP 连接池大小
数据库连接池大小
第三方允许并发数
第三方 QPS
机器内存
单任务平均耗时
```

### 3. 通过压测验证

合理流程是：

```text
根据任务类型和资源容量估算初始值
↓
使用接近真实业务的任务压测
↓
观察吞吐量、P95/P99 延迟、CPU、内存和连接池
↓
调整核心线程、最大线程和队列容量
↓
上线后继续根据监控调整
```

参数设计不能只背公式，也不能把开发环境配置直接复制到生产环境。

---

## 十三、不同任务为什么要使用独立线程池

如果一个线程池同时处理：

```text
AI 推理
支付回调
PDF 转换
通知发送
日志或报表任务
```

大量慢 AI 任务可能占满整个线程池：

```text
AI 任务持续占用线程
↓
支付回调无法及时处理
↓
订单状态更新延迟
↓
用户重复支付或投诉
```

更合理的做法是按资源和业务重要性隔离：

```text
AI 调用线程池
PDF 计算线程池
支付回调线程池
通知线程池
低优先级统计线程池
```

每个线程池可以配置不同的：

```text
核心线程数
最大线程数
队列容量
拒绝策略
超时时间
监控告警阈值
```

资源隔离的本质是：

> 一个慢任务或低优先级任务出现故障时，不应该占用其他核心业务的全部执行资源。

## 十四、线程池异常处理

线程池任务内部抛出异常时，不能让任务静默失败。

例如使用 `execute()` 时，未捕获异常可能由线程的 `UncaughtExceptionHandler` 处理；使用 `submit()` 时，异常会被封装在 `Future` 中，如果从不调用 `get()`，异常可能长期无人感知。

因此需要：

```text
任务内部统一 try-catch 并记录业务上下文
配置线程名称，便于日志检索
设置 UncaughtExceptionHandler
检查 Future 或 CompletableFuture 的异常
记录 taskId、requestId、traceId
失败后更新任务状态
```

示例：

```java
executor.execute(() -> {
    try {
        aiTaskService.execute(taskId);
    } catch (Exception e) {
        log.error("AI task execution failed, taskId={}", taskId, e);
        aiTaskService.markFailed(taskId, e.getMessage());
    }
});
```

线程名称也应具有业务含义：

```text
ai-worker-1
pdf-worker-1
payment-callback-1
```

而不是全部使用难以定位的默认线程名。

## 十五、线程池需要监控哪些指标

至少需要监控：

```text
corePoolSize
maximumPoolSize
poolSize
activeCount
queueSize
queueRemainingCapacity
completedTaskCount
taskCount
rejectedTaskCount
任务平均执行时间
任务 P95/P99 执行时间
```

同时还要关联观察：

```text
Kafka Lag
数据库连接池活跃连接数
HTTP 连接池等待数
第三方接口耗时和错误率
熔断器状态
任务成功率
任务排队时间
单任务调用成本
```

典型告警条件可以包括：

```text
线程池活跃线程持续接近最大线程数
队列使用率持续超过 80%
拒绝次数大于 0
Kafka Lag 持续增长
任务平均等待时间超过 SLA
第三方接口 P99 持续升高
```

不能只看到线程池满了就扩大线程数。

正确排查顺序应该是：

```text
入口流量是否异常
任务生产速度是否持续高于消费速度
单任务执行时间是否变长
下游服务是否变慢
数据库或 HTTP 连接池是否耗尽
线程池参数是否与真实容量匹配
是否需要扩容 Worker
```

## 十六、最小代码示例

```java
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.ThreadFactory;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;

public final class AiWorkerExecutors {

    private AiWorkerExecutors() {
    }

    public static ExecutorService createAiExecutor() {
        AtomicInteger sequence = new AtomicInteger(1);

        ThreadFactory threadFactory = task -> {
            Thread thread = new Thread(task);
            thread.setName("ai-worker-" + sequence.getAndIncrement());
            thread.setUncaughtExceptionHandler((t, e) ->
                System.err.println("Uncaught exception in " + t.getName() + ": " + e.getMessage())
            );
            return thread;
        };

        return new ThreadPoolExecutor(
            10,
            20,
            60,
            TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(100),
            threadFactory,
            new ThreadPoolExecutor.AbortPolicy()
        );
    }
}
```

这里使用 `AbortPolicy`，目的是让过载明确暴露，由上层决定：

```text
暂停 Kafka 消费
不提交 offset
记录拒绝指标
稍后重新分发
```

而不是静默丢弃任务。

实际项目中还应通过配置中心管理参数，并接入 Micrometer、Prometheus 和 Grafana 监控。

## 十七、面试表达

可以这样回答：

> 在线程池设计中，我不会直接通过 Executors 使用默认的无界队列或无限线程配置，而是使用 ThreadPoolExecutor 显式设置核心线程数、最大线程数、有界队列和拒绝策略。线程池达到最大线程数且队列已满后，不会继续创建线程，而是触发拒绝策略，因为线程池本身就是系统的资源保护边界。对于 AI 异步任务，我会先在入口进行限流、权限、额度和幂等校验，合法任务持久化后进入 Kafka 削峰，Worker 再通过有界线程池限制单实例执行并发。线程池接近满载时降低或暂停 Kafka 消费，避免任务继续堆积到 JVM。调用第三方模型时配置超时、熔断和降级，并监控 Kafka Lag、线程池活跃数、队列长度、拒绝次数和第三方错误率。

更简洁的表达是：

> Kafka 负责承接大量待处理任务，线程池负责控制单个 Worker 的实际执行并发，限流负责控制入口速度，熔断负责阻止持续调用异常下游。

## 十八、今天练习题复盘

### 问题一：为什么线程池没有继续创建更多线程

因为：

```text
maximumPoolSize 已经达到 20
队列容量 100 已经用完
```

线程池已经达到配置的资源上限，因此后续任务触发拒绝策略。

### 问题二：最大线程数直接改成 500 有什么风险

风险包括：

```text
线程栈和本地内存增加
CPU 上下文切换增加
有效业务吞吐下降
数据库连接池耗尽
HTTP 连接池耗尽
第三方 AI 服务过载
调用费用失控
大量任务同时超时
Worker 服务崩溃
```

### 问题三：哪些任务拒绝，哪些进入消息队列

立即拒绝：

```text
参数非法
没有权限
额度耗尽
重复提交
任务已取消或过期
不支持的任务类型
高峰期超限的低优先级任务
```

进入 Kafka：

```text
已经通过校验的合法异步任务
允许等待的任务
后续执行仍然有价值的任务
可以重试和补偿的任务
高优先级或付费用户任务
```

### 问题四：完整保护方案

```text
入口限流
↓
参数、权限、额度和幂等校验
↓
任务持久化
↓
Kafka 削峰
↓
Worker 按容量消费
↓
本地有界线程池控制并发
↓
下游调用超时、熔断和降级
↓
延迟重试与死信队列
↓
监控、告警和容量扩缩容
```

## 十九、今天最重要的结论

### 结论一

> 线程池的核心价值不是创建更多线程，而是限制并发和控制资源消耗。

### 结论二

> `ThreadPoolExecutor` 通常是先补核心线程，再进入队列，队列满后才扩容到最大线程数。

### 结论三

> 最大线程数和队列都满后必须拒绝，不能为了不拒绝而无限扩大线程和队列。

### 结论四

> Kafka 是持久化的大缓冲区，本地线程池队列只应该承担有限的临时缓冲。

### 结论五

> Kafka 负责削峰，线程池负责控制单机执行并发，限流负责保护入口，熔断和降级负责保护异常下游。

### 结论六

> 线程池参数必须结合 CPU、内存、连接池、第三方限额、任务耗时和业务 SLA，通过压测和监控持续调整。

## 二十、能力等级

**中级偏高级 Java 后端工程能力。**

真正的线程池能力不是会写一个 `ThreadPoolExecutor` 构造函数，而是能够回答：

```text
为什么这样设置线程数
队列容量对应多长等待时间
拒绝以后任务会不会丢失
如何对 Kafka Consumer 形成反压
线程池是否会压垮数据库和下游接口
如何通过监控判断应该限流、扩容还是优化任务耗时
```

当线程池能够与 Kafka、限流、熔断、降级、幂等、重试和监控组合起来时，才属于真正的后端工程化设计。
