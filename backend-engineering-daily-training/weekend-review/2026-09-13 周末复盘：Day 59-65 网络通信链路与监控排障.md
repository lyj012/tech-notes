## 三、VLAN：基本掌握

### 1. 当前能够正确理解

VLAN 的核心作用：

> 在二层网络中进行逻辑隔离，把交换网络划分成多个相互隔离的广播域。

不能只理解为“把一台物理交换机切成几块”。

因为：

- 一个 VLAN 可以跨多台交换机；
- Trunk 可以承载多个 VLAN；
- VLAN 的核心是逻辑上的二层隔离，而不是物理设备切割。

### 2. 场景推理

```text
Collector：192.168.1.20/24，VLAN 10
Device：   192.168.1.50/24，VLAN 20
```

虽然两个 IP 从掩码计算看属于同一个网段，但主机会认为目标是本地邻居，因此会直接发送 ARP Request。

由于 VLAN 10 和 VLAN 20 属于不同二层广播域：

```text
Collector
 ↓
ARP Request
 ↓
只在 VLAN 10 内广播
 ↓
VLAN 20 中的目标设备收不到
 ↓
无法获得目标 MAC
 ↓
后续通信无法继续
 ↓
最终常表现为 Timeout
```

### 3. 本次判断

**状态：已掌握。**

已经能够通过 VLAN 隔离机制主动推出 ARP 无响应和 Timeout，而不是只背结论。

## 四、ARP、路由与邻居表：基本掌握，但术语需要稳定

### 1. 同网段通信

```text
192.168.1.20/24 → 192.168.1.50/24
```

Linux 判断目标在本地网段后：

```text
查邻居表
 ↓
没有目标 MAC
 ↓
ARP Request
 ↓
目标返回 ARP Reply
 ↓
得到目标 IP → MAC 映射
 ↓
发送真正的数据帧
```

结论：

> 同网段：ARP 目标设备。

### 2. 跨网段通信

```text
192.168.1.20/24 → 192.168.2.50/24
```

Linux 先查路由表，发现目标不属于本地网段，于是选择下一跳网关。

此时 ARP 的不是远端目标，而是网关：

```text
目标 IP：仍然是 192.168.2.50
目标 MAC：当前下一跳网关的 MAC
```

结论：

> 不同网段：ARP 下一跳网关。

### 3. `ip neigh` 的意义

Linux：

```bash
ip neigh
```

核心看的是：

```text
IP → MAC
```

例如：

```text
192.168.1.50 dev eth0 FAILED
```

表示 Linux 对这个邻居的解析失败。

在典型 IPv4 场景下，可以理解为：

```text
尝试 ARP
 ↓
没有成功获得目标 MAC
 ↓
邻居状态 FAILED
```

### 4. 默认网关 FAILED 为什么影响更大

如果普通同网段设备：

```text
192.168.1.50 → FAILED
```

通常优先怀疑该目标或通往该目标的二层链路。

如果默认网关：

```text
192.168.1.1 → FAILED
```

那么所有需要经过这个网关的跨网段流量都可能失败。

因此：

> 大量设备同时异常时，要优先寻找共同故障点，而不是假设几十台设备同时坏掉。

### 5. 本次判断

**状态：基本掌握。**

已经能推导：

```text
查路由
 ↓
决定下一跳
 ↓
ARP 下一跳
 ↓
获得 MAC
```

但“路由成功”和“ARP 成功”偶尔仍会混在一起，需要继续强化。

## 五、交换机 MAC 地址表：本周最明显的易混点

### 1. 交换机如何学习

假设：

```text
AA → port 1
BB → port 2
```

交换机第一次收到：

```text
源 MAC = AA
目标 MAC = BB
从 port 1 进入
```

交换机首先：

```text
学习源 MAC
AA → port 1
```

然后查询目标 MAC `BB`。

如果 MAC 地址表中没有 BB：

> 在同一个 VLAN 内进行未知单播泛洪。

之后 B 回包，从 port 2 进入：

```text
BB → port 2
```

交换机以后再次收到发往 BB 的帧，就可以直接单播转发到 port 2。

### 2. 本次暴露出的错误

第一次回忆时把：

```text
目标 MAC 未知
```

错误理解成：

```text
交换机发送 ARP Request
```

这是两个不同机制。

#### ARP Request

由主机发起，解决：

```text
已知 IP
不知道 MAC
↓
IP → MAC
```

#### 未知单播泛洪

由交换机执行，解决：

```text
已经知道目标 MAC
但 MAC 地址表不知道这个 MAC 在哪个端口
↓
同 VLAN 内泛洪
```

### 3. 最关键口诀

```text
交换机：学源，查目
```

也就是：

> 学习源 MAC，查询目标 MAC。

### 4. 本次判断

**状态：易忘 / 基本掌握但不稳定。**

本次经过立即重测后已经能够回答：

```text
第一步：学习源 MAC
第二步：目标 MAC 未知 → 未知单播泛洪
```

但下周必须再次抽查。

## 六、必须彻底分开的两个表

这是本次复盘中最明确的混淆点之一。

### Linux 邻居表

```text
IP → MAC
```

查看命令：

```bash
ip neigh
```

例如：

```text
192.168.1.50 → AA:BB:CC:DD:EE:FF
```

### 交换机 MAC 地址表

```text
MAC → Port
```

例如：

```text
AA:BB:CC:DD:EE:FF → GigabitEthernet1/0/3
```

### 一条完整关系

```text
IP
 ↓  ARP / 邻居表
MAC
 ↓  交换机 MAC 地址表
Port
```

也就是：

> Linux 解决“这个 IP 对应哪个 MAC”；交换机解决“这个 MAC 应该从哪个端口转发”。

## 七、TCP、Ping 与端口排障：掌握较稳

### 1. Ping 通不代表服务端口正常

```bash
ping 192.168.1.50
```

成功主要说明：

> 当前主机与目标 IP 之间的 ICMP 通信基本可达。

不能证明：

```text
8082 一定监听
Java 应用一定启动成功
JMX 一定可用
业务接口一定可用
```

### 2. `Connection refused`

例如：

```bash
telnet 192.168.1.50 8082
```

返回：

```text
Connection refused
```

更典型的含义是：

> 目标主机能够到达，但目标 TCP 端口没有正常接受这个连接。

常见原因：

- 8082 没有进程监听；
- Java 应用启动失败；
- 实际监听的是其他端口；
- 监听地址不符合预期；
- 某些防火墙策略直接 REJECT。

不能简单理解成“Nginx 拒绝了请求”。

### 3. Java 进程存在 ≠ 8082 服务可用

```bash
ps -ef | grep java
```

只能证明存在 Java 进程。

还需要继续确认：

```bash
ss -lntp | grep 8082
```

可能出现：

- Java 仍在启动；
- Java 启动过程失败；
- 端口配置发生变化；
- 进程还存在，但监听已经异常；
- 应用内部初始化失败。

因此：

```text
Java 进程存在
≠
8082 正常监听
≠
监控采集一定正常
```

### 4. 本次判断

**状态：已掌握。**

已经能够从“进程、端口、网络、应用”几个不同层次区分服务状态。

## 八、TIME_WAIT 与 CLOSE_WAIT：CLOSE_WAIT 掌握，TIME_WAIT 易忘

### 1. TIME_WAIT

本次闭卷时已经无法稳定解释 TIME_WAIT。

正确理解：

> TCP 主动关闭连接的一方，在连接关闭过程基本完成后，内核仍保留该连接状态一段时间。

主要意义包括：

- 处理网络中可能残留的旧报文；
- 必要时能够重新发送最后的 ACK；
- 避免旧连接报文污染后续同四元组连接。

因此：

```text
TIME_WAIT = 20000
```

**不能直接判定服务器故障。**

高并发短连接场景下，大量 TIME_WAIT 可能是正常现象。

需要结合：

- 是否出现本地端口耗尽；
- 是否无法建立新连接；
- 是否存在异常的短连接设计；
- 系统资源是否出现实际瓶颈。

### 2. CLOSE_WAIT

如果：

```text
CLOSE_WAIT：50 → 5000
并且长期不下降
```

说明对端已经发起关闭，但本机应用没有及时完成关闭。

优先检查应用代码中的资源释放：

```text
Socket
HTTP Response
InputStream
数据库连接
其他网络资源
```

重点确认是否正确执行 close。

### 3. 本次判断

```text
TIME_WAIT：易忘，需要复习
CLOSE_WAIT：已掌握
```

## 九、DNS：核心概念已掌握

DNS 的核心作用：

```text
域名 → IP
```

例如：

```text
device.company.com
 ↓
DNS
 ↓
192.168.1.50
```

DNS 位于真正访问目标服务之前。

如果 DNS 解析失败：

```text
拿不到目标 IP
 ↓
后续 TCP / UDP 通信无法正常开始
```

如果 DNS 解析到了错误 IP，不能简单认为“三次握手一定失败”。

可能出现：

```text
错误 IP 不可达
→ Timeout

错误 IP 可达但端口没有监听
→ Connection refused

错误 IP 上刚好存在服务
→ TCP 甚至可能成功，但连接到了错误机器
```

SNMP 同理：解析错误可能导致 Timeout，也可能访问到错误设备。

### 本次判断

**状态：已掌握核心作用，但需要保持故障结果的多分支思维。**
