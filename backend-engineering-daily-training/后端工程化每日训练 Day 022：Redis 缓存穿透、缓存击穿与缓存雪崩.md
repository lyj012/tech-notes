# 后端工程化每日训练 Day 22：Redis 缓存穿透、缓存击穿与缓存雪崩

## 一、今天学习的知识点

今天学习的是：

**Redis 缓存穿透、缓存击穿与缓存雪崩**

一句话理解：

> Redis 本身没有宕机，不代表缓存体系就是安全的。只要缓存策略设计不合理，大量请求仍然可能绕过 Redis，直接压向 MySQL，最终导致数据库连接池耗尽、接口超时甚至整个系统不可用。

在典型的 Java 后端系统中，缓存查询链路通常是：

```text
Client
↓
Spring Boot
↓
Redis
↓
MySQL
```

正常情况下：

```text
Redis 命中
↓
直接返回结果
↓
减少 MySQL 查询
```

Redis 未命中时：

```text
Redis Miss
↓
查询 MySQL
↓
将结果写回 Redis
↓
返回结果
```

缓存体系真正需要解决的问题，不只是：

```text
Redis 会不会宕机
```

还包括：

```text
不存在的数据是否会反复查询数据库
热点 Key 过期时是否会产生瞬时高并发
大量 Key 是否会在同一时间失效
缓存重建过程是否会放大数据库压力
Redis 恢复后是否会被第一波流量再次打垮
```

今天必须区分三个概念：

```text
缓存穿透：查询数据库中不存在的数据
缓存击穿：一个热点 Key 失效
缓存雪崩：大量 Key 同时失效，或缓存层整体不可用
```

记忆方式：

```text
穿透：不存在
击穿：单个热点
雪崩：大面积失效
```

## 二、缓存为什么能够保护数据库

假设 AI 异步任务平台提供任务状态查询接口：

```http
GET /task/{taskId}
```

例如：

```http
GET /task/10001
```

任务数据存储在 MySQL：

```text
t_task
```

Redis 中使用：

```text
task:10001
```

作为缓存 Key。

正常查询流程：

```text
请求 taskId=10001
↓
查询 Redis task:10001
↓
命中缓存
↓
直接返回任务状态
```

假设接口每秒有 5000 次查询：

```text
Redis 命中率 99%
```

那么真正进入 MySQL 的请求可能只有：

```text
5000 × 1% = 50 次/秒
```

如果缓存策略失效，5000 次请求全部进入 MySQL：

```text
MySQL QPS 突然增加
↓
CPU 上升
↓
磁盘 I/O 增加
↓
连接池活跃连接接近上限
↓
SQL 排队
↓
接口超时
↓
线程池堆积
↓
服务整体不可用
```

因此缓存的核心价值不是单纯让接口更快，而是：

> 将高频读流量挡在数据库之前，控制数据库实际承担的请求规模。

## 三、缓存穿透是什么

### 1. 定义

缓存穿透是指：

> 请求查询的数据在 Redis 中不存在，在数据库中也不存在，导致每次请求都会绕过缓存并访问数据库。

例如攻击者持续请求：

```text
taskId=-1
taskId=-2
taskId=-999999
```

数据库中根本不存在这些任务。

第一次请求：

```text
查询 Redis
↓
Miss
↓
查询 MySQL
↓
不存在
↓
返回空
```

第二次请求同样的 taskId：

```text
查询 Redis
↓
仍然 Miss
↓
再次查询 MySQL
↓
仍然不存在
```

因为系统通常只缓存真实数据，没有缓存“不存在”这个结果，所以无效请求会不断进入数据库。

### 2. 为什么叫“穿透”

请求没有被缓存层拦住，而是直接穿过 Redis，到达数据库：

```text
无效请求
↓
Redis 无数据
↓
MySQL 无数据
↓
每次都重复查询
```

### 3. 常见来源

缓存穿透不一定都是恶意攻击，也可能来自正常业务缺陷：

```text
前端传入非法 ID
接口参数校验缺失
客户端重复请求已删除的数据
任务删除后缓存未正确处理
爬虫随机遍历 ID
攻击者构造大量不存在的 Key
上下游数据同步延迟
```

### 4. AI 平台场景

AI 异步任务平台中可能出现：

```text
GET /task/-1
GET /task/0
GET /task/999999999999
```

如果每次都执行：

```sql
SELECT *
FROM t_task
WHERE id = ?;
```

即使 SQL 使用主键索引，海量无效查询仍然会消耗：

```text
数据库连接
CPU
网络往返
线程资源
连接池等待时间
```

“查询很快”不等于“可以无限查询”。

## 四、缓存穿透的解决方案

### 1. 接口参数校验

最先做的不是直接上复杂组件，而是在请求入口过滤明显非法参数。

例如：

```java
@GetMapping("/task/{taskId}")
public TaskVO getTask(@PathVariable Long taskId) {
    if (taskId == null || taskId <= 0) {
        throw new IllegalArgumentException("taskId must be greater than 0");
    }

    return taskService.getTask(taskId);
}
```

可以直接拦截：

```text
taskId=-1
taskId=-2
taskId=0
```

但参数合法不代表数据一定存在。

例如：

```text
taskId=999999999
```

格式合法，但数据库中可能不存在，所以还需要其他措施。

### 2. 缓存空值

数据库查询结果为空时，将“空结果”也写入 Redis。

例如：

```text
task:999999999 = __NULL__
TTL = 60 秒
```

后续相同请求：

```text
查询 Redis
↓
命中空值标记
↓
直接返回不存在
↓
不再访问 MySQL
```

Java 示例：

```java
private static final String NULL_VALUE = "__NULL__";
private static final Duration NULL_TTL = Duration.ofSeconds(60);
private static final Duration TASK_TTL = Duration.ofMinutes(30);

public TaskVO getTask(Long taskId) {
    String key = "task:" + taskId;
    String cachedValue = stringRedisTemplate.opsForValue().get(key);

    if (NULL_VALUE.equals(cachedValue)) {
        return null;
    }

    if (cachedValue != null) {
        return objectMapper.readValue(cachedValue, TaskVO.class);
    }

    Task task = taskMapper.selectById(taskId);

    if (task == null) {
        stringRedisTemplate.opsForValue().set(key, NULL_VALUE, NULL_TTL);
        return null;
    }

    TaskVO result = convert(task);
    stringRedisTemplate.opsForValue().set(
            key,
            objectMapper.writeValueAsString(result),
            TASK_TTL
    );

    return result;
}
```

空值 TTL 应该短于正常数据 TTL，例如：

```text
正常数据：30 分钟
空值数据：30～120 秒
```

### 3. 为什么空值 TTL 不能太长

假设：

```text
taskId=10001 当前不存在
```

系统缓存：

```text
task:10001 = __NULL__
TTL = 24 小时
```

一分钟后，任务 10001 创建成功。

此时：

```text
MySQL 中已经存在任务
Redis 中仍然是空值
```

用户继续查询时仍然会得到：

```text
任务不存在
```

这会造成短期数据不一致。

因此空值缓存应该：

```text
TTL 较短
任务创建成功后主动删除对应空值 Key
避免使用与正常数据相同的长 TTL
```

### 4. 布隆过滤器

布隆过滤器用于快速判断：

```text
某个数据是否可能存在
```

请求流程：

```text
请求 taskId
↓
查询 Bloom Filter
↓
明确不存在
↓
直接返回
```

如果布隆过滤器判断“可能存在”：

```text
继续查询 Redis
↓
必要时查询 MySQL
```

布隆过滤器有两个重要特性：

```text
判断不存在：可以认为一定不存在
判断存在：只表示可能存在
```

它可能出现：

```text
假阳性
```

即：

```text
布隆过滤器认为可能存在
但数据库实际上不存在
```

但不会出现：

```text
本来存在，却被判断为一定不存在
```

前提是布隆过滤器数据维护正确。

### 5. 布隆过滤器的工程问题

使用布隆过滤器不能只会调用 API，还需要考虑：

```text
系统启动时如何初始化
新增任务时如何同步写入
数据库已有数据如何批量加载
过滤器失效后如何重建
多实例如何共享过滤器
误判率如何选择
数据删除如何处理
```

普通布隆过滤器通常不支持安全删除。

因此在任务删除后，Bloom Filter 可能仍然认为该 ID“可能存在”。

这不会导致错误返回，只是可能继续访问 Redis 或数据库。

### 6. 限流与风控

缓存空值和布隆过滤器不能替代限流。

攻击者可以不断生成不同的随机 ID：

```text
100000001
100000002
100000003
```

即使每个空值都缓存，仍可能造成：

```text
Redis 中出现大量垃圾 Key
内存被占用
数据库承受第一次查询
```

因此还可以结合：

```text
IP 限流
用户级限流
接口级限流
网关黑名单
异常请求比例监控
验证码或鉴权
```

合理组合通常是：

```text
参数校验
+
布隆过滤器
+
短 TTL 空值缓存
+
限流与风控
```

## 五、缓存击穿是什么

### 1. 定义

缓存击穿是指：

> 一个访问量很高的热点 Key 刚好过期，大量并发请求同时发现缓存未命中，并一起访问数据库。

关键词是：

```text
一个热点 Key
```

例如：

```text
task:10001
```

这是一个热门 AI 任务，很多用户或前端页面持续轮询它的状态。

缓存原来存在：

```text
task:10001 = RUNNING
TTL = 30 分钟
```

缓存刚好在 10:30:00 过期。

同一时刻有 10000 个请求进入：

```text
10000 个请求
↓
全部查询 Redis
↓
全部 Miss
↓
全部查询 MySQL
```

数据库可能在极短时间内收到大量相同 SQL：

```sql
SELECT *
FROM t_task
WHERE id = 10001;
```

### 2. 击穿为什么危险

缓存击穿不是持续很久的大面积故障，而是瞬间流量集中到一个数据点：

```text
热点 Key 过期
↓
请求同时回源
↓
数据库瞬时 QPS 暴涨
↓
连接池快速占满
```

即使 MySQL 最终能处理完，其他正常业务也可能被拖慢。

### 3. 常见热点 Key

```text
首页配置
系统配置
热门商品
秒杀商品库存
热门 PDF 文件信息
热门文章
活动页面
排行榜
AI 热门任务状态
广告平台公共账户配置
```

如果团队不知道哪些 Key 是热点，就无法提前保护。

---

## 六、缓存击穿的解决方案

### 1. 互斥锁或分布式锁

缓存 Miss 后，不允许所有请求同时查询数据库。

流程：

```text
请求 A 查询 Redis：Miss
↓
请求 A 获取锁成功
↓
请求 A 查询 MySQL
↓
请求 A 重建缓存
↓
请求 A 释放锁
```

其他请求：

```text
请求 B、C、D 查询 Redis：Miss
↓
获取锁失败
↓
等待或稍后重试
↓
再次查询 Redis
↓
命中新缓存
```

最终数据库只承担一次或极少量查询。

### 2. 双重检查

获取锁后必须再次检查缓存。

原因是：

```text
请求 A 获取锁并重建缓存
↓
请求 A 释放锁
↓
请求 B 获取锁
```

如果请求 B 不再次检查 Redis，就会重复查询数据库。

正确流程：

```text
第一次查缓存
↓
缓存 Miss
↓
获取锁
↓
第二次查缓存
↓
仍然 Miss 才查询数据库
```

### 3. Redisson 示例

```java
public TaskVO getHotTask(Long taskId) {
    String cacheKey = "task:" + taskId;
    String lockKey = "lock:task:" + taskId;

    TaskVO cachedTask = getTaskFromCache(cacheKey);
    if (cachedTask != null) {
        return cachedTask;
    }

    RLock lock = redissonClient.getLock(lockKey);
    boolean locked = false;

    try {
        locked = lock.tryLock(200, 10, TimeUnit.MILLISECONDS);

        if (!locked) {
            throw new ServiceBusyException("系统繁忙，请稍后重试");
        }

        // 双重检查，避免重复回源
        cachedTask = getTaskFromCache(cacheKey);
        if (cachedTask != null) {
            return cachedTask;
        }

        Task task = taskMapper.selectById(taskId);
        if (task == null) {
            cacheNullValue(cacheKey);
            return null;
        }

        TaskVO result = convert(task);
        cacheTask(cacheKey, result);
        return result;
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new ServiceBusyException("请求被中断", e);
    } finally {
        if (locked && lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
}
```

这里只是最小示意，生产环境还需要考虑：

```text
锁等待时间
锁租约时间
业务执行超时
线程中断
锁释放安全
缓存序列化异常
数据库查询失败
降级返回
```

### 4. 不要让所有 Key 都加锁

错误做法：

```text
所有缓存 Miss
↓
统一获取同一把全局锁
```

结果可能变成：

```text
Redis 没有崩
MySQL 没有崩
所有线程堵在锁上
```

应该使用：

```text
每个业务 Key 一把锁
```

例如：

```text
lock:task:10001
lock:task:10002
```

不同任务可以并行重建缓存。

### 5. 热点数据逻辑过期

另一种方案是不让热点 Key 物理过期，而是在缓存值中保存逻辑过期时间。

例如：

```json
{
  "expireAt": "2026-07-30T22:00:00",
  "data": {
    "taskId": 10001,
    "status": "RUNNING"
  }
}
```

读取时：

```text
数据未逻辑过期
↓
直接返回
```

如果已经逻辑过期：

```text
仍然返回旧值
↓
尝试获取锁
↓
后台线程刷新缓存
```

优点：

```text
热点请求不会直接打到数据库
接口延迟更稳定
```

代价：

```text
可能短时间返回旧数据
实现复杂度更高
需要后台刷新和异常处理
```

这是一种：

```text
用短期一致性换高可用性
```

的方案。

### 6. 热点 Key 永不过期并主动刷新

对于极少数核心热点数据，可以不设置物理 TTL：

```text
首页配置
系统开关
公共字典
热门活动信息
```

通过：

```text
配置变更后主动更新
定时任务刷新
消息通知刷新
后台异步刷新
```

维护缓存。

但“永不过期”不代表永远不更新。

需要解决：

```text
数据更新时如何同步
刷新失败如何重试
旧数据最长允许存在多久
缓存和数据库不一致如何发现
```

## 七、缓存雪崩是什么

### 1. 定义

缓存雪崩通常指：

> 大量缓存 Key 在同一时间失效，或者 Redis 缓存层整体不可用，导致大量请求同时进入数据库。

关键词是：

```text
大量 Key
大面积失效
```

### 2. 大量 Key 同时过期

假设系统在启动时批量加载 10000 个缓存：

```text
TTL 全部设置为 30 分钟
```

写入时间接近：

```text
10:00:00
```

那么它们可能在：

```text
10:30:00
```

附近集中失效。

结果：

```text
大量 Redis Miss
↓
大量请求回源 MySQL
↓
数据库 CPU 和连接池同时升高
↓
数据库响应变慢
↓
更多请求堆积
↓
故障进一步放大
```

### 3. Redis 整体不可用

另一种雪崩来源是：

```text
Redis 实例宕机
Redis 网络中断
Redis 集群故障
连接池耗尽
Redis 请求大量超时
错误发布清空缓存
```

此时不是部分 Key 过期，而是整个缓存层无法正常提供服务。

### 4. 为什么叫“雪崩”

故障通常会级联放大：

```text
缓存失效
↓
数据库压力增加
↓
数据库响应变慢
↓
应用线程等待
↓
线程池耗尽
↓
接口超时
↓
客户端重试
↓
请求量进一步增加
↓
系统全面不可用
```

这不是单点慢查询，而是一条完整的故障链。

---

## 八、缓存雪崩的解决方案

### 1. TTL 增加随机值

不要让同一类缓存使用完全相同的固定 TTL。

错误做法：

```text
所有 Key TTL = 30 分钟
```

合理做法：

```text
基础 TTL + 随机 TTL
```

例如：

```java
long baseTtlMinutes = 30;
long randomMinutes = ThreadLocalRandom.current().nextLong(0, 6);
Duration ttl = Duration.ofMinutes(baseTtlMinutes + randomMinutes);
```

最终可能变成：

```text
30 分钟
31 分钟
33 分钟
35 分钟
```

将过期时间分散到不同时间点。

### 2. 缓存预热

在以下场景前主动加载热点缓存：

```text
应用上线
大促活动开始
Redis 故障恢复
数据库恢复
版本切换
流量切换
```

预热流程：

```text
读取热点数据列表
↓
分批查询数据库
↓
写入 Redis
↓
验证缓存数量和命中率
↓
逐步放量
```

不能在 Redis 刚恢复后立即把全部流量放进系统，否则：

```text
Redis 虽然恢复
但缓存仍然为空
↓
第一波请求全部访问数据库
```

### 3. 分批加载和分批失效

批量缓存不能在一个循环中全部使用相同 TTL。

应该：

```text
分批写入
TTL 随机化
按业务优先级加载
热点数据优先预热
```

### 4. 限流、降级和熔断

雪崩发生时，不能无限制把请求转发给数据库。

可以使用：

```text
接口限流
用户级限流
数据库并发保护
快速失败
返回旧缓存
返回默认值
关闭非核心功能
熔断部分查询
```

例如任务状态查询属于高频接口，可以在数据库压力过高时：

```text
返回最后一次缓存状态
提示稍后刷新
限制轮询频率
```

而不是让每个前端页面每秒访问数据库。

### 5. Redis 高可用

针对 Redis 整体故障，需要考虑：

```text
主从复制
Sentinel
Redis Cluster
故障转移
连接超时
客户端重试上限
连接池配置
跨机房容灾
```

但高可用组件不能代替合理缓存设计。

Redis Cluster 正常运行时，仍然可能因为统一 TTL 发生雪崩。

### 6. 多级缓存

部分场景可以使用：

```text
本地缓存 Caffeine
+
分布式缓存 Redis
+
数据库 MySQL
```

查询链路：

```text
本地缓存
↓ Miss
Redis
↓ Miss
MySQL
```

Redis 短暂异常时，本地缓存可以承担一部分热点读流量。

但多级缓存会增加：

```text
一致性复杂度
更新复杂度
失效通知成本
内存占用
排障难度
```

只有真正的热点读场景才值得使用。

## 九、穿透、击穿和雪崩的核心区别

| 问题 | 核心特征 | 典型原因 | 影响范围 | 主要方案 |
|---|---|---|---|---|
| 缓存穿透 | 查询不存在的数据 | 非法 ID、随机 ID、删除数据 | 大量无效请求持续访问数据库 | 参数校验、空值缓存、布隆过滤器、限流 |
| 缓存击穿 | 一个热点 Key 失效 | 热点 Key 到期 | 某个热点数据的并发请求瞬间回源 | 分布式锁、逻辑过期、后台刷新、热点永不过期 |
| 缓存雪崩 | 大量 Key 同时失效或缓存层整体故障 | 统一 TTL、Redis 宕机、批量清空 | 大面积请求同时回源 | TTL 随机化、预热、限流降级、Redis 高可用 |

可以继续记忆：

```text
穿透看“数据是否存在”
击穿看“是否是单个热点 Key”
雪崩看“是否大面积同时失效”
```

## 十、Cache Aside 模式下的数据一致性

今天讨论的查询通常基于 Cache Aside 模式：

### 1. 读取流程

```text
先查缓存
↓
缓存不存在再查数据库
↓
将数据库结果写入缓存
```

### 2. 更新流程

常见做法是：

```text
先更新数据库
↓
再删除缓存
```

而不是：

```text
先更新数据库
↓
再直接更新缓存
```

原因是直接更新缓存容易出现：

```text
并发写入顺序错误
缓存值被旧请求覆盖
复杂对象重建成本高
部分字段遗漏
```

对于任务状态：

```text
RUNNING
↓
SUCCESS
```

数据库更新成功后删除：

```text
task:10001
```

下一次查询重新从数据库加载最新状态。

### 3. 删除缓存失败

如果数据库更新成功，但删除 Redis 失败：

```text
MySQL = SUCCESS
Redis = RUNNING
```

系统会短时间返回旧状态。

可以结合：

```text
重试
消息队列
延迟双删
Canal 订阅 Binlog
缓存一致性任务
```

但需要根据业务一致性要求选择，不应为了一个普通查询接口直接堆叠所有复杂方案。

## 十一、分布式锁防击穿的常见坑

### 1. 锁范围过大

错误：

```text
所有任务共用 lock:task
```

结果：

```text
taskId=10001 重建缓存
会阻塞 taskId=10002 的查询
```

正确：

```text
lock:task:10001
lock:task:10002
```

### 2. 没有双重检查

获取锁后直接查数据库，会导致多个等待线程依次重复回源。

### 3. 锁没有超时时间

线程异常退出后，锁可能长期不释放。

### 4. 锁过期时间小于业务执行时间

请求 A 的锁提前过期，请求 B 又获取到锁，最终仍然并发查询数据库。

### 5. 释放了其他线程的锁

必须确认锁由当前线程持有后再释放。

### 6. 无限等待锁

大量线程一直阻塞，会耗尽 Web 容器线程池。

应该设置：

```text
最大等待时间
快速失败策略
降级结果
重试上限
```

### 7. 缓存重建失败没有处理

数据库异常、序列化异常、Redis 写入失败时，需要确保：

```text
锁最终释放
异常能够记录
不会无限重试
不会形成请求风暴
```

## 十二、缓存空值的常见坑

### 1. 空值缓存时间过长

新数据创建后仍然返回不存在。

### 2. 空值和 Redis 真正的 null 无法区分

需要使用明确占位符，例如：

```text
__NULL__
```

或者使用统一缓存对象：

```json
{
  "exists": false,
  "data": null
}
```

### 3. 随机 ID 产生大量空值 Key

攻击者持续请求不同 ID，可能污染 Redis。

需要配合：

```text
限流
布隆过滤器
短 TTL
最大 Key 数监控
```

### 4. 创建数据后没有删除空值 Key

新增任务成功后，应主动删除：

```text
task:{taskId}
```

避免继续命中旧的空值缓存。

---

## 十三、TTL 设计的常见坑

### 1. 所有缓存统一 30 分钟

容易造成集中失效。

### 2. TTL 完全随机，没有业务边界

随机值不能无限扩大，否则可能导致数据长期不更新。

### 3. 热点和普通数据使用同一策略

热点数据应该单独识别和保护。

### 4. 缓存永不过期但没有更新机制

最终会长期返回旧数据。

### 5. 只设置 TTL，不监控命中率

TTL 是否合理，需要根据：

```text
缓存命中率
数据库 QPS
数据更新频率
缓存内存占用
业务可接受的旧数据时间
```

持续调整。

## 十四、真实故障案例分析

题目场景：

```http
GET /task/{taskId}
```

数据库 CPU 突然飙升。

Redis：

```text
实例正常
CPU 正常
内存正常
网络正常
```

排查发现大量请求：

```text
taskId=-1
taskId=-2
taskId=-999999
```

同时热门任务：

```text
taskId=10001
```

缓存刚好过期。

### 1. 第一类问题：缓存穿透

```text
taskId=-1
taskId=-2
taskId=-999999
```

这些数据在数据库中不存在。

每次请求都会执行：

```text
Redis Miss
↓
MySQL 查询
↓
返回不存在
```

属于缓存穿透。

### 2. 第二类问题：缓存击穿

```text
taskId=10001
```

属于真实存在的热点任务，但缓存刚好失效。

大量并发请求同时回源数据库，属于缓存击穿。

### 3. 数据库为什么突然暴涨

数据库同时承受两部分流量：

```text
不存在 taskId 的无效查询
+
热点 taskId=10001 的并发查询
```

完整链路：

```text
无效请求造成缓存穿透
↓
持续访问 MySQL

热点 Key 过期造成缓存击穿
↓
瞬间大量访问 MySQL

两类流量叠加
↓
MySQL CPU、QPS 和连接数同时上升
```

### 4. Redis 为什么看起来正常

因为问题不是 Redis 宕机，而是：

```text
Redis 中没有对应数据
```

Redis 仍然可以正常快速返回：

```text
Key 不存在
```

每个 Miss 对 Redis 本身的压力可能不大，但应用随后会访问 MySQL。

因此：

```text
Redis 运行正常
!=
缓存命中率正常
!=
数据库受到保护
```

需要重点查看：

```text
缓存命中率
keyspace_hits
keyspace_misses
数据库 QPS
数据库 CPU
HikariCP 活跃连接数
接口请求量
异常 taskId 数量
```

## 十八、面试中怎么表达

可以这样表达：

> 缓存穿透、击穿和雪崩的区别主要在于数据是否存在以及失效范围。缓存穿透是查询数据库中不存在的数据，Redis 和数据库都查不到，请求会反复访问数据库；缓存击穿是单个热点 Key 过期后，大量并发请求同时回源；缓存雪崩是大量 Key 集中过期或者 Redis 整体不可用，导致大面积流量进入数据库。

> 对于缓存穿透，我会先做参数校验，再根据业务使用短 TTL 空值缓存或布隆过滤器，并结合接口限流，防止攻击者通过大量随机 ID 污染缓存和数据库。布隆过滤器只能判断一定不存在或可能存在，还需要处理初始化、增量同步和假阳性问题。

> 对于热点 Key 击穿，我会使用按业务 Key 维度的分布式锁，并在获取锁后再次检查缓存，确保只有一个线程回源数据库。对一致性要求允许的热点数据，也可以采用逻辑过期和后台异步刷新，避免请求等待缓存重建。

> 对于缓存雪崩，我会给 TTL 增加随机值，避免大量 Key 集中过期，并在上线、Redis 恢复或流量切换前预热热点缓存。同时对数据库设置限流和降级保护，避免缓存故障直接演变成数据库故障。

> 排查时不能只看 Redis 是否存活，还要观察缓存命中率、Redis Miss、数据库 QPS、数据库连接池、接口请求量和热点 Key 回源次数。Redis 正常但命中率下降时，数据库仍然可能被压垮。

## 十九、今天思考题的完整回答

### 问题一：哪些属于缓存穿透，哪些属于缓存击穿

```text
taskId=-1
taskId=-2
taskId=-999999
```

这些任务在数据库中不存在，属于：

```text
缓存穿透
```

```text
taskId=10001
```

这是一个真实存在的热门任务，但缓存刚好过期，大量请求同时访问，属于：

```text
缓存击穿
```

### 问题二：为什么数据库压力暴涨，而 Redis 看起来正常

原因不是 Redis 故障，而是大量请求没有命中有效缓存。

数据库同时承担：

```text
不存在数据造成的持续无效查询
+
热点 Key 过期造成的瞬时并发查询
```

Redis 可以正常返回 Miss，所以自身 CPU、内存和连接状态可能都正常。

但应用收到 Miss 后继续访问 MySQL，最终导致数据库压力暴涨。

完整结论：

> Redis 正常只代表缓存服务能够响应，不代表缓存命中率正常，也不代表数据库没有承受回源压力。

### 问题三：应该采用哪些缓存策略

针对缓存穿透：

```text
校验 taskId 必须大于 0
缓存不存在的数据，使用较短 TTL
使用布隆过滤器过滤明确不存在的 ID
对异常请求进行限流和风控
```

针对缓存击穿：

```text
按 taskId 使用分布式锁
获取锁后再次检查缓存
由一个线程查询数据库并重建缓存
热点 Key 使用逻辑过期或后台主动刷新
```

### 问题四：所有缓存 TTL 都设置为 30 分钟会发生什么

未来可能发生：

```text
缓存雪崩
```

如果大量 Key 在接近的时间写入，并统一设置 30 分钟，它们会在接近的时间集中失效。

大量请求会同时回源数据库，可能导致：

```text
数据库 CPU 飙升
连接池耗尽
SQL 排队
接口超时
系统不可用
```

应该使用：

```text
基础 TTL + 随机值
```

并结合：

```text
缓存预热
限流降级
热点 Key 保护
Redis 高可用
```

## 二十一、今天的最终结论

第一个必须记住的区别：

```text
缓存穿透：数据库中不存在的数据
缓存击穿：单个热点 Key 过期
缓存雪崩：大量 Key 同时失效或缓存层整体不可用
```

第二个必须记住的结论：

```text
Redis 正常
!=
缓存命中率正常
!=
数据库安全
```

第三个必须记住的穿透治理组合：

```text
参数校验
+
短 TTL 空值缓存
+
布隆过滤器
+
限流风控
```

第四个必须记住的击穿治理原则：

```text
按业务 Key 加锁
获取锁后双重检查
只允许少量请求回源
避免所有线程无限等待
```

第五个必须记住的雪崩治理原则：

```text
TTL 随机化
缓存预热
Redis 高可用
数据库限流和降级
```

第六个必须记住的排查链路：

```text
数据库 CPU 上升
↓
检查数据库 QPS 和连接池
↓
检查缓存命中率和 Redis Miss
↓
检查是否存在非法 ID
↓
检查是否存在热点 Key 过期
↓
检查是否大量 Key 集中失效
↓
根据原因分别处理
```

今天最核心的一句话是：

> 缓存可靠性的目标不是保证所有请求都能访问数据库，而是在缓存未命中或发生故障时控制回源规模，避免 Redis 的局部问题演变成 MySQL 和整个系统的连锁故障。
