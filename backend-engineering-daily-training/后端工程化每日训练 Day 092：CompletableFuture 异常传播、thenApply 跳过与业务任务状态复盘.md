## 二、真实场景：AI 文档解析与保存

假设开发一个 AI 文档处理服务，用户上传 PDF，后台需要先解析文本，再把解析结果保存。

同步代码可以写成：

~~~java
String result = parseDocument();
saveResult(result);
~~~

它表达的顺序是：解析文档，拿到结果，再保存。

如果希望把解析任务异步安排到其他线程执行，可以用 CompletableFuture 表达依赖关系：

~~~java
CompletableFuture<String> future =
    CompletableFuture.supplyAsync(() -> {
        return parseDocument();
    }).thenApply(result -> {
        saveResult(result);
        return result;
    });
~~~

简化执行图：

~~~text
发起异步解析
    ↓
supplyAsync：执行解析任务
    ↓ 正常完成并产出结果
thenApply：接收解析结果并继续处理
    ↓
保存解析结果
~~~

两个方法的基础分工：

| 方法 | 本次需要掌握的含义 |
| --- | --- |
| supplyAsync | 安排一个会产生结果的异步任务，返回表示未来结果的 CompletableFuture |
| thenApply | 依赖上一个阶段**正常完成**所产生的结果，执行转换或后续处理 |

两个容易误解的边界：

- supplyAsync 不等于“所有后续代码一定执行”；失败时要考虑异常完成；
- thenApply 不保证专门开一个新线程执行。它关注的是**正常结果的依赖处理**，不是线程切换保证。

## 三、训练实际从哪里开始：先补概念，不直接考异常

当天自动训练内容已经给出了“parseDocument 抛异常、thenApply 不执行”的解释，但用户明确反馈：

> 我连它教我的概念是什么都没看懂，你直接问我这段代码，我都看不懂。

因此先暂停提问，从“同步解析 → 保存”和“异步解析 → 正常完成后继续保存”两种流程解释 CompletableFuture，再分别介绍 supplyAsync 与 thenApply。

这个调整很关键：**看到一段代码不等于已经理解相关 API，先建立能读懂代码的直觉，才能判断异常路径。**

### 第 1 题：两个方法分别负责什么？

题目：

~~~java
CompletableFuture.supplyAsync(() -> {
    return "解析成功";
}).thenApply(result -> {
    System.out.println(result);
    return result;
});
~~~

问：没有异常时，supplyAsync 和 thenApply 分别做什么？

**我的回答（按当天口述整理）：**

> 第一个把会产生结果的任务安排成异步执行。第二个是在前面的任务完成、产生结果之后，对这个结果进行加工。

**评估：独立回答正确。** 用户可以用自己的语言说明前后依赖关系。讲解中补充了 thenApply 不保证必定另起线程，但本日没有专门验证不同线程调度方式。

## 四、核心机制：异常完成会让 thenApply 的处理函数被跳过

示例：

~~~java
CompletableFuture<String> future =
    CompletableFuture.<String>supplyAsync(() -> {
        throw new RuntimeException("PDF解析失败");
    }).thenApply(result -> {
        System.out.println("保存结果");
        return result;
    });
~~~

上游解析阶段抛出异常，所对应的 CompletableFuture 异常完成。依赖上游**正常结果**的 thenApply 处理函数不会被调用，依赖阶段也会异常完成（传递失败）。

~~~text
开始解析 PDF
    ↓
parseDocument / supplyAsync 阶段抛异常
    ↓
上游 CompletableFuture 异常完成
    ↓
thenApply 的处理函数不执行
    ↓
依赖阶段异常完成
~~~

需要准确区分：

- **正确**：此处的保存逻辑不会执行，因为它只在 thenApply 处理函数里；
- **不准确**：“整个 Java 程序直接停止了”。实际上，是相关异步阶段异常完成，其他线程和任务并不因此必然停止；
- **不能直接推断**：一定在当前调用处同步抛出同一个异常。异常通常由 CompletableFuture 持有，并可在后续等待结果或错误处理时被观察到；具体表现取决于调用方式。

### 第 2 题：解析失败，还会保存吗？

**题目：** supplyAsync 阶段抛出 RuntimeException，后面的 thenApply 还会执行吗？为什么？

**我的回答（按口述整理）：**

> 不会。解析任务已经失败并抛异常了。必须先解析成功、拿到结果，后面的 thenApply 才能继续做处理。

**评估：独立判断正确，因果关系也能说明。**

**必要纠正：** 用户用“直接停了”描述失败路径。这里更精确的说法是“依赖正常完成的处理函数跳过，CompletableFuture 异常完成”，而不是整个程序停止。

## 五、失败模式：Java 计算状态不等于数据库业务状态

假设提交 AI 文档任务时，数据库存储：

~~~text
task_id = 1001
status = PROCESSING
~~~

异步解析出现异常，但业务代码**没有编写任何失败状态更新逻辑**。

这是两个独立层面：

| 层面 | 当前状态 | 为什么 |
| --- | --- | --- |
| Java CompletableFuture | 异常完成 | 解析任务抛出了异常 |
| 数据库任务记录 | PROCESSING | 没有代码主动执行并成功提交状态变更 |

**CompletableFuture 不会自动理解或更新业务数据库中的 FAILED 字段。**

### 第 3 题：数据库会自动变 FAILED 吗？

**题目：** PDF 解析失败、CompletableFuture 异常完成；没有任何失败状态更新逻辑，数据库会自动由 PROCESSING 变 FAILED 吗？

**我的首次回答（按口述整理）：**

> 应该会吧？我记得这是 CompletableFuture 的特性。但为什么会，我回答不了。

**评估：首次判断错误。** 这是当天真正暴露的知识缺口：混淆了“Java 异步计算结果”与“数据库业务状态”。

**纠错：** CompletableFuture 是 Java 异步编程工具，知道任务异常结束，但不会代替业务代码发 SQL 更新。业务系统必须明确处理失败，并完成数据库变更。

### 同构纠错题：为什么仍是 PROCESSING？

给定：

~~~text
数据库 task 1001 = PROCESSING
Java 解析失败并异常完成
没有执行任何数据库 UPDATE
~~~

**我的再次回答（按口述整理）：**

> 因为 Java 代码里没有写对应处理逻辑，没有执行更新。要处理解析失败，调用相应逻辑去更新数据库，数据库的状态才会改变。

**评估：经讲解、同构练习后正确。**

注意不能把“第一次就掌握了业务状态边界”写进记录。真实过程是：**首次误判 → 纠正概念边界 → 再次能独立说出原因。**

还需要一个工程边界：即使编写了失败状态更新，更新也可能因数据库异常、事务回滚等原因失败；**写了更新代码 ≠ 数据库状态必然成功落库**。这一点今天只做概念提示，未专门出题或验证。

## 六、AI / Codex Review：把 FAILED 写进 thenApply 能修复吗？

教学用原始代码：

~~~java
CompletableFuture.supplyAsync(() -> {
    return parseDocument();
}).thenApply(result -> {
    saveResult(result);
    updateTaskStatus("SUCCESS");
    return result;
});
~~~

现象：解析失败后，数据库记录一直是 PROCESSING。

假设 Codex 提议：

> 在 thenApply 里面再加一行 updateTaskStatus("FAILED")，这样解析失败也能更新数据库。

### 第 4 题：接受这个方案吗？

**我的回答（按口述整理）：**

> 不可以。前面的 supplyAsync 解析失败了，thenApply 必须等到正常解析成功、拿到结果才会执行。前面失败，后面根本不会往下走，因此放在 thenApply 里的 FAILED 更新也不会执行。

**评估：独立判断正确，并且说明了导致修复无效的机制。**

正确的工程判断是：

~~~text
Codex 提议在 thenApply 内补 FAILED
    ↓
先判断：失败路径下 thenApply 处理函数会被调用吗？
    ↓
不会
    ↓
这个 FAILED 更新仍不可达
    ↓
拒绝该修复思路
    ↓
要求在真正可达的异常处理路径中落实状态转换
~~~

本次只审核**假设的错误方案**。没有实际读取 Codex 生成的补丁，也没有据此证明任何线上故障已经修复。

## 七、失败处理的下一步方向（本日不展开新机制）

Java 提供 exceptionally、handle、whenComplete 等处理完成/异常结果的 API。它们的语义并不相同，不能仅凭名字混用。

当天讲解中出现过一个简化示例：

~~~java
CompletableFuture.supplyAsync(() -> {
    return parseDocument();
}).exceptionally(ex -> {
    updateTaskStatus("FAILED");
    return null;
});
~~~

它只用于表达：**失败分支里必须明确执行业务状态更新**，并非可直接复制用于生产的完整方案。

特别注意：

1. exceptionally 返回的值可能将异常转换为正常结果（这里返回 null）。如果后续继续链接处理正常结果的阶段，可能产生新的问题；
2. saveResult、SUCCESS 更新或 FAILED 更新本身也可能失败；
3. 生产级系统还需要根据真实事务边界、任务状态机、日志与重试语义设计，不能仅靠插入一行代码就认定修复完成；
4. 应通过成功路径、解析失败路径、数据库更新失败路径的测试和持久化状态核验后再验收。

**这些属于后续应补的工程边界，不计入当天用户已经通过的测试。**

## 九、上一正式训练日 Day 91 回忆：前端停止 SSE，模型为何还运行？

这道回忆题**安排在 Day 92 主线完成之后**，符合 V3.3 的顺序。

**题目：** 用户点击“停止生成”，前端关闭 SSE，页面不再显示新文字，但后端仍继续调用 AI 模型并消耗 Token。为什么会这样？

**我的回答（按口述整理）：**

> 点击停止生成只是前端不显示了，不代表后端停止了。只要后端还在执行，AI 模型就可能仍在运行。想让它停止，必须让后端也停止相应调用。

**评估：独立回答正确，Day 91 的核心边界回忆通过。**

本次补充的边界：

~~~text
前端停止接收 SSE
    ≠
后端任务一定停止
    ≠
上游模型调用一定取消
    ≠
服务商内部计算立即停止
~~~

后端传递取消请求也不必然保证模型立即停止，取决于客户端、上游接口和服务商行为。本次没有再次考察取消事件日志、结束原因或 Token 计费验证方法，因此不能认为 Day 91 的所有验收细节均已在今天复习通过。

## 十一、今天真正值得保留的工程判断模型

> **上游 CompletableFuture 异常完成 → 依赖正常结果的 thenApply 处理函数不会执行 → 业务数据库不会自动变更 → 要在真实可达的失败处理路径中明确维护任务状态，并验证更新确实成功。**

遇到“任务一直 PROCESSING”时，可以先按以下顺序判断：

~~~text
异步任务是否已经结束？
    ↓
正常完成，还是异常完成？
    ↓
后续代码是否只挂在 thenApply 等正常结果处理阶段？
    ↓
异常处理路径是否可达？
    ↓
是否有明确的 FAILED 状态更新？
    ↓
数据库更新是否实际成功？
    ↓
最后再评估日志、重试、超时、补偿和状态机边界
~~~

与 Day 91 的共同点是：**界面或框架层观察到一种状态，不代表其他参与者的业务状态自动同步变化。**

- Day 91：前端 SSE 停止，不代表后端和上游模型自动停止；
- Day 92：Java 异步计算异常结束，不代表数据库任务状态自动变 FAILED。

**后续建议复习点：** 给出一个新的订单/文件处理异步链，让用户独立区分“异常完成、异常恢复、业务状态持久化”三件事；在基础稳定后，再专门学习 exceptionally 与 handle 等错误处理 API 的区别。
