## 二、今天学习什么：软件架构风格与分层架构

### 1. 软件架构风格是什么？

软件架构风格可以理解为：对系统的组成部分、职责分工、交互方式和依赖约束的常见组织方案。

关注点不是某一个 Java 类的注解，而是：
- 系统由哪些部分组成？
- 各部分承担什么职责？
- 允许哪些依赖和交互？
- 这种组织方式解决什么问题？
- 为此付出什么成本，又会影响哪些质量属性？

常见风格还包括事件驱动、微服务等，本日只学习分层架构风格的入门部分。

### 2. 分层架构（Layered Architecture）

一个常见的 Java Web 订单系统可以按职责分成：

~~~text
HTTP 请求
    ↓
Controller：接收请求、参数校验与响应转换
    ↓
Service：组织和执行业务规则
    ↓
Repository / Mapper：数据访问
    ↓
Database：数据持久化
~~~

分层的核心是**职责分离、隔离变化、控制层间依赖**，而不只是“避免 Controller 文件太长”。

例如：
- HTTP 参数格式改变，尽可能局限在接入层。
- 订单业务规则改变，尽可能集中在业务层。
- 数据库查询实现改变，尽可能集中在数据访问层。
- 同样的业务规则可以供 HTTP、MQ、定时任务等不同入口复用。

**注意术语边界：**
1. Service 是业务层职责，不等同于必须编写接口加 ServiceImpl 实现类。ServiceImpl 是常见命名习惯之一。
2. Mapper / Repository 是数据访问抽象；数据库是基础设施，不代表所有架构文献都将其视为同一逻辑层。
3. 逻辑“分层”（layer）不一定意味着部署到不同服务器上的物理“分级/层级”（tier）；多台机器、网络通信所产生的延迟不能直接套用到同进程中的普通 Java 方法调用上。

### 3. 分层架构主要改善什么？

本日重点联系**可修改性（Modifiability）**：当需求变化时，希望修改范围可控，避免牵连大量与变化无关的模块。

分层通常有利于：
- 降低接入方式与业务逻辑之间的耦合。
- 保持相同业务规则的统一实现。
- 降低重复代码和规则不一致风险。
- 提高组件测试与复用的便利性。

但它不会自动带来高性能、高可用或低复杂度。真正效果仍取决于依赖关系、实现质量和业务约束。

## 三、场景一：形式上分层，但 Service 仍然依赖 HTTP

### 1. 初始场景

创建订单原有链路：

~~~text
Controller → Service → Mapper → Database
~~~

如果把 SQL、校验、扣减库存、创建订单全部写在 Controller 中，就可能导致接入逻辑与业务逻辑混杂、业务规则复用困难。

用户一开始就能识别常规的 Controller、Service、Mapper 职责，但最初解释偏向“这是 Java 基础、逻辑多就放 Service”，还没有完整描述架构上的原因。

### 2. 关键反例：Service 接收 HttpServletRequest

~~~java
@Service
public class OrderServiceImpl {

    public void createOrder(HttpServletRequest request) {
        String userId = request.getHeader("X-User-Id");

        // 校验订单
        // 扣减库存
        // 创建订单
    }
}
~~~

现在需要新增 MQ 消费者和定时任务，都要复用创建订单的业务逻辑。

问题不在于 ServiceImpl 这个类名，而在于业务接口要求调用方提供 HTTP 请求对象：

~~~text
HTTP Controller → HttpServletRequest → OrderService   （自然适配）
MQ Consumer     → 消息对象               → OrderService   （不自然）
定时任务        → 任务参数               → OrderService   （不自然）
~~~

Service 对接入方式形成了不必要的依赖。增加入口时，可能需要修改接口、编写适配代码，或者重复实现业务逻辑。

### 3. 改进示例：接入层转换为业务参数

~~~java
public record CreateOrderCommand(Long userId, Long productId, int quantity) {}

@Service
public class OrderService {

    public void createOrder(CreateOrderCommand command) {
        // 订单业务校验
        // 扣减库存
        // 创建订单
    }
}
~~~

~~~text
HTTP Controller ──┐
                  ├──转换为 CreateOrderCommand──→ OrderService
MQ Consumer ──────┤                               ↓
定时任务 ─────────┘                          Repository
                                                  ↓
                                              Database
~~~

设计意图：
- HTTP、MQ、定时任务负责各自接入数据的解析与转换。
- Service 接收业务所需的参数，不强依赖某一种传输协议。
- 同一套订单业务规则可以被不同入口调用。

安全边界：上例仅用于说明参数解耦。不能因为 HTTP 请求头或 MQ 消息包含 userId 就直接信任；用户身份需要可信认证或消息可信性校验，订单业务也要根据入口设计必要的权限、幂等与事务控制。

## 四、场景二：分层带来的质量属性收益与代价

### 1. 可修改性和性能的权衡

课堂中的假设：一个订单查询接口因增加过多调用层、数据对象转换，响应时间从 100ms 上升到 300ms。

首先要识别：
- **性能（Performance）**：响应时间、吞吐量、资源消耗等；本题已知响应时间增加。
- **可用性（Availability）**：服务能否持续满足其可用要求、故障发生后能否恢复等；本题没有直接给出服务中断证据。

因此，这个例子主要表现为**性能受到损害**，不是直接证明可用性下降。

不能仅凭响应时间从 100ms 变 300ms 就认定吞吐量一定下降，也不能直接断言数据库压力增加。需要结合瓶颈归因、负载、CPU、连接池、调用链等证据判断。

### 2. 性能与可用性的区分练习

| 情况 | 已知现象 | 主要质量属性 |
|---|---|---|
| A | 订单查询正常返回，但从 200ms 变为 2 秒 | **性能** |
| B | 数据库主节点故障，订单查询连续 10 分钟不可服务 | **可用性** |

用户第一次误把变慢判定为可用性下降；经解释后，能够在新的 A/B 场景中准确区分。此处应记录为**纠正后通过**，而不是“首次即掌握”。

### 3. 与 Day 105 的关联

| 设计概念 | 典型做法 | 主要关注 |
|---|---|---|
| 架构风格 | 分层架构 | 系统如何组织、如何控制依赖 |
| 架构策略 | 冗余、故障检测与故障恢复 | 应对可用性需求 |
| 架构策略 | 缓存与减少重复访问 | 应对性能需求 |
| 架构权衡 | 规范分层 vs. 额外处理开销 | 可修改性、性能、复杂度之间的取舍 |

“分层改善可修改性”只是一种有条件的收益，不等于“层数越多越好”。架构设计需要依据明确场景、实际成本和可验证结果进行权衡。

## 五、场景三：严格分层、宽松分层与业务规则统一

### 1. 两种分层方式

**严格分层（Strict / Closed Layering）**：上层通常通过紧邻的下一层访问所需功能，不随意跳过中间层。

~~~text
Controller
    ↓
Service
    ↓
Repository
~~~

**宽松分层（Relaxed / Open Layering）**：按既定边界，允许某些上层在特定情况下跨过中间层访问更下层。

~~~text
Controller ─────────────→ Repository
    │                         ↑
    └────────→ Service ───────┘
~~~

重要区别：严格或宽松描述的是**依赖与调用约束**，不是“前者一定先进、后者一定错误”。对同进程的一个空转发方法，不应夸大所谓跨层调用带来的网络性能改善。

### 2. 为什么有人希望 Controller 直接访问 Repository？

假设 Service 只有一行纯转发：

~~~java
public Product getById(Long id) {
    return productMapper.selectById(id);
}
~~~

短期收益可能是：减少样板代码、避免没有实际价值的抽象、简化非常简单的查询路径。

但如果未来新增“下架商品不能对用户展示”这一规则，问题就出现了：
- 业务规则应该由谁统一维护？
- 多个接入入口是否需要遵守相同规则？
- 直接访问 Repository 会不会绕过校验？
- 规则修改是否必须同时修改多个 Controller？

因此，**跨层调用可以经过评估后使用，但要明确将来如何保证业务约束不被绕过**。对于常规 Spring Boot 业务系统，可以把 Controller → Service → Repository 作为实用默认，但不是所有项目必须遵守的绝对法则。

### 3. 多入口的规则一致性

有两个商品查询入口：

~~~text
AdminController → ProductMapper
UserController  → ProductMapper
~~~

新增统一规则：所有这类查询都要过滤下架商品。

如果两个 Controller 各自实现，可能出现：一个入口改了，另一个漏改，造成行为不一致。

若采用共享业务服务：

~~~text
AdminController ─┐
                 ├──→ ProductService → ProductMapper
UserController ──┘
~~~

相同规则只在受控的公共位置实现和修改。也可以根据系统采用公共查询组件、领域服务或仓储查询约束等方式统一，并不是“任何规则都必须塞入 Service”。

进一步把场景扩展为 10 个 Controller，共用“下架商品不能返回”的同一规则。用户明确指出：共享 Service 可以“改一个方法，十个 Controller 全部生效”，而各处复制逻辑需要逐个修改且容易遗漏。

前提：这 10 个接口的规则确实相同；如果管理员和普通用户存在不同的可见性要求，就应显式建模差异，而不是简单强制复用一个错误规则。

## 六、真实互动训练记录：原始判断、纠错与迁移

本节按本次对话的实际顺序整理。引文为口述整理，并非逐字录音稿；训练中的示例代码和数值都是教学假设。保留错误判断和纠正过程，不把“提示后回答正确”写成“首次独立回答正确”。

### 1. 第一题：Controller 为什么不应承担全部订单业务？

**题目：** Controller 直接写 SQL、扣减库存和创建订单，不经过 Service，会有什么问题？

**用户初始回答（整理）：**

> Controller 是定义路径、放接口的地方；业务逻辑应该写在 ServiceImpl。不同业务逻辑放不同类。可我从一开始学 Java 就是这样学的，为什么这样设计，我说不太清楚。

**评估：基本职责认识正确；设计理由不完整。**

**补充：** 分层的本质是控制依赖、隔离变化、复用业务规则，并非仅仅是让 Controller 代码短一点。Service 层也不等价于必须有 ServiceImpl 类。

### 2. 第二题：已经分层的 Service 为什么仍可能设计不合理？

**题目：** OrderService.createOrder(HttpServletRequest request) 要复用于 HTTP、MQ 和定时任务，有什么问题？

**用户初始回答（整理）：**

> 我看不出来。

**评估：未通过，存在对层间依赖的知识缺口。**

**纠正过程：** 明确解释 HttpServletRequest 是 HTTP 接入对象；MQ 接收消息、定时任务接收任务参数，没有天然的 HTTP 请求对象。业务层依赖 HTTP 类型，使复用受限。

**教学改进：** 改为普通业务命令对象 CreateOrderCommand，由不同入口负责转换。

### 3. 第三题：哪种参数形式更利于多入口复用？

**题目：** A：Service 接收 HttpServletRequest；B：Service 接收 CreateOrderCommand。哪种更便于 HTTP、MQ、定时任务复用？

**用户实际回答（整理）：**

> 肯定是 B。A 只方便 HTTP 接口，MQ 消费者接收的不是 HTTP 请求。参数被限制住了，耦合太高。应该用普通业务参数，让不同入口都能调用。

**评估：通过。**

用户在纠正后能够解释“接入协议依赖 → 复用受限 → 降低耦合”的因果关系。

### 4. 第四题：分层处理开销使响应时间从 100ms 变为 300ms，损害什么？

**用户初始回答（整理）：**

> 我认为是可用性。因为 Response Time 延长了三倍，体验可能下降；高并发时会不会有问题、数据库吃不吃得消，都值得怀疑。

**评估：主要质量属性判断错误，但具备提出性能风险假设的意识。**

**纠正：** 已知直接证据是响应时间增加，因此主要是性能退化。可用性通常关注能否正常提供服务及恢复情况。数据库负载、吞吐量下降等在题目中都未被证实，不可从响应时间增长直接推断。

### 5. 第五题：性能和可用性的新场景对比

**题目：** A：查询从 200ms 变 2 秒但仍返回；B：数据库宕机导致查询服务中断 10 分钟。分别是什么？

**用户实际回答（整理）：**

> A 是性能，B 是可用性。A 关注请求时间、吞吐量；B 是系统能不能正常提供服务，故障能不能恢复。

**评估：纠正后通过。**

本次可以确认能区分这两种典型场景，但不能由此认定已经掌握复杂质量属性冲突分析。

### 6. 第六题：严格分层还是宽松分层？

**题目：** 简单只读商品查询，Service 只有一行调用 Repository；Controller 能否在特定条件下直接调用 Repository？

**用户初始回答（整理）：**

> 我直觉觉得可以在特定条件下允许，代码要灵活。但这属于我的业务盲区；以前只写 Controller、Service、Mapper，没见过绕过中间层。具体收益和代价我说不出来。

**评估：直觉选择合理，尚不能独立分析收益与代价。**

**补充解释：**
- 可能收益：少写无价值的转发代码、降低简单路径的样板成本。
- 可能代价：跨层耦合、业务规则分散、未来修改影响范围扩大。
- 结论：不应机械宣称严格分层永远更好，具体取决于场景。

### 7. 第七题：多个 Controller 直接访问 Mapper，新增统一下架规则怎么办？

**用户实际回答（整理）：**

> 后续新增业务规则要写哪里？总不能都写到 Controller。没有业务逻辑层，以后加功能不方便，代码不好维护。

**评估：指出了业务规则缺少统一位置的风险，但还没有明确说出“重复规则和接口行为不一致”的问题。**

**纠正：** 如果多个入口各自加入规则，就可能出现漏改、重复、行为不一致。统一业务规则的价值不仅是“代码应该写哪儿”，更是“一个规则变动不能让多个入口出现不同结果”。

### 8. 第八题：10 个 Controller 共用规则，为什么共享 Service 更好？

**题目：** 10 个查询接口都必须过滤下架商品。A：分别在 10 个 Controller 写规则；B：共享 Service 统一处理。为什么 B 更容易维护？

**用户实际回答（整理）：**

> 肯定 B。为什么要写十遍？放在一个共享方法里，修改一个方法，十个 Controller 都生效。A 要逐个改，还可能改不完。

**评估：通过。**

用户能够独立解释“统一规则 → 单点修改 → 减少遗漏与不一致 → 提高可修改性”的因果链。

## 七、Day 105 间隔回忆：Redis TTL 与缓存一致性

本次按训练约定，在 Day 106 新知识完成后再回忆 Day 105，不提前打断新知识。

### 1. 回忆场景

原商品价格 50 元，MySQL 已经更新为 100 元，Redis 仍保存旧价格 50 元。开发者认为“把 TTL 设为 10 秒，就能保证每次查询都返回数据库最新价格”。

**用户实际回答（整理）：**

> 不可以。TTL 只是让缓存失效，不能每次都读到最新数据。即使设为 10 秒，数据库更新以后，缓存没过期时用户还是可能读到旧价格。可以删除缓存后重新查，关键业务必要时不走 Redis、读权威数据库。只是让我准确说 TTL 与一致性的关系，我一时组织不出来。

**评估：通过。**

用户能够通过价格变化推导旧值命中问题，理解 TTL 不能保证实时一致；困难主要是术语总结表达，而非缺少机制理解。

### 2. 精炼结论

**TTL 控制缓存条目的存活时间，可以影响旧数据的存活窗口，但不能保证缓存和数据库实时一致。**

在没有其他刷新行为、且到期后通过数据库回源的简化场景中，用户可能在缓存到期前读到旧价格。

需要进一步注意：
- 删除缓存是一种常见 Cache-Aside 策略，不等于绝对强一致性。
- 缓存删除失败、并发读写竞争、旧数据回填、数据库复制延迟都可能带来一致性风险。
- 关键交易价格可以在下单环节读取或校验权威数据，不能只信任展示阶段的缓存值。

此处仅验证对 TTL / 缓存一致性的理解，没有实施真实并发实验或证明某个强一致方案已落地。

## 九、本日形成的可复用架构分析方法

以后遇到分层设计问题，可以依次检查：

~~~text
1. 明确需求：哪个功能或质量属性正在发生变化？
       ↓
2. 划分职责：每个模块/层真正应该负责什么？
       ↓
3. 分析依赖：业务逻辑是否不必要地依赖 HTTP、MQ 等接入细节？
       ↓
4. 检查复用：相同规则是否在多个入口重复实现？
       ↓
5. 比较方案：保留严格分层还是允许特定跨层调用？
       ↓
6. 识别代价：耦合、修改范围、性能开销、复杂度是否变化？
       ↓
7. 验证约束：是否有可观测证据，满足业务与质量要求？
~~~

### 今日关键判断对照

| 现象 | 不充分的判断 | 更严谨的架构判断 |
|---|---|---|
| Controller 写很多业务代码 | “代码太长” | 接入层与业务职责混杂，变化影响范围扩大 |
| Service 参数是 HttpServletRequest | “有 Service 就算分层” | 业务层仍耦合 HTTP 接入模型 |
| 增加许多空转发层 | “分层越多越好” | 需权衡维护收益与额外开销 |
| 查询由 100ms 变 300ms | “可用性下降” | 已知主要是性能退化，其他影响待验证 |
| Controller 直接查 Repository | “绝对错误或绝对更好” | 需结合业务规则、入口数量与长期耦合评估 |
| 10 个入口重复同一规则 | “反正都能跑” | 修改成本高且存在规则不一致风险 |
| Redis TTL = 10 秒 | “10 秒内实时一致” | 只限制缓存条目寿命，不能保证实时一致 |

## 十二、参考资料与事实边界

1. [Microsoft Learn — Architecture Styles](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/)  
   用于对照架构风格的基本定位及不同风格的收益、约束与权衡。

2. [Microsoft Learn — N-tier Architecture Style](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/n-tier)  
   用于对照逻辑分层与物理分级、职责和依赖、严格/宽松分层、样板层与额外开销。特别注意：物理 tier 的网络延迟不能等同于同进程 Java 方法调用开销。

3. [Martin Fowler — Layering Principles](https://martinfowler.com/bliki/LayeringPrinciples.html)  
   讨论层间低耦合、层内高内聚、职责分离、业务层不依赖 UI 等常见设计原则；这是设计讨论而不是所有 Java 项目的强制规范。

4. [CMU/SEI — Attribute-Driven Design (ADD), Version 2.0](https://www.sei.cmu.edu/library/attribute-driven-design-add-version-20/)  
   用于进一步理解质量属性需求如何驱动软件架构设计。

5. [Microsoft Learn — Cache-Aside Pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside)  
   对照 Day 105 间隔回忆中的 TTL、缓存失效和一致性风险。
