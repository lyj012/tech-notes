# 后端工程化每日训练 Day 40：Redis 缓存与数据库一致性、Cache Aside 与最终一致性

## 一、今天学习的知识点

今天学习的是：

**Redis 缓存与数据库一致性、Cache Aside（旁路缓存）模式、数据库与缓存的更新顺序、缓存删除失败后的最终一致性、TTL 兜底、热点 Key 重建，以及 `@Transactional` 与 Redis 的事务边界。**

一句话理解：

> 数据库通常是业务真实数据源，Redis 是为了提高读取性能而存在的副本；缓存一致性设计的核心不是幻想 Redis 和数据库每一个瞬间都绝对相等，而是控制不一致发生的概率、持续时间、业务影响和自动恢复能力。

前面已经学习过：

```text
Redis 缓存穿透 / 击穿 / 雪崩
↓
数据库事务
↓
乐观锁 / 悲观锁
↓
事务隔离
↓
死锁
↓
数据库原子更新
↓
大事务拆分
↓
数据库 UNIQUE
```

今天把这些知识进一步串起来：

```text
数据库
→ 负责真实业务状态

Redis
→ 负责加速读取

数据库修改以后
→ 如何让 Redis 中的旧副本尽快失效

删除失败以后
→ 如何自动恢复

热点缓存失效以后
→ 如何避免数据库被回源流量打垮
```

今天真正需要建立的是：

```text
缓存不是第二个真相源
```

而是：

```text
可失效
可重建
可过期
可恢复
```

的数据副本。

## 二、什么叫缓存与数据库不一致

假设商品价格原来是：

```text
MySQL = 100
Redis = 100
```

管理员把价格修改成：

```text
80
```

数据库已经成功：

```text
MySQL = 80
```

但 Redis 仍然保存：

```text
Redis = 100
```

用户查询商品时：

```text
先查 Redis
↓
命中 100
↓
直接返回
```

结果用户一直看到旧价格。

这属于：

```text
缓存与数据库不一致
```

不是：

```text
缓存穿透
缓存击穿
缓存雪崩
```

需要区分：

```text
缓存穿透
→ 查一个本来就不存在的数据，Redis 和 DB 都没有

缓存击穿
→ 一个热点 Key 失效，大量请求同时回源数据库

缓存雪崩
→ 大量 Key 同时失效，大量流量一起回源数据库

缓存与数据库不一致
→ Redis 中有数据，但它已经不是数据库中的最新业务状态
```

今天第一题已经能够直接判断：

```text
MySQL = 80
Redis = 100
```

就是典型的数据不一致。

## 三、Cache Aside 是什么

Java 后端中最常见的一种缓存模式是：

```text
Cache Aside Pattern
旁路缓存模式
```

它的核心职责划分是：

```text
数据库
→ 最终真实数据源

Redis
→ 缓存副本
```

### 查询流程

```text
请求
↓
查询 Redis
↓
命中
→ 直接返回

未命中
↓
查询 MySQL
↓
把结果写入 Redis
↓
返回
```

Java 代码大致可以理解为：

```java
public Product getProduct(Long id) {
    String key = "product:" + id;

    Product product = redisTemplate.opsForValue().get(key);
    if (product != null) {
        return product;
    }

    product = productMapper.selectById(id);

    if (product != null) {
        redisTemplate.opsForValue()
                .set(key, product, 30, TimeUnit.MINUTES);
    }

    return product;
}
```

这里最重要的思想不是代码，而是：

```text
Redis 没有数据
↓
可以从数据库重新构建
```

所以 Redis 不需要自己成为不可丢失的真实数据源。

## 四、为什么修改时通常是“更新数据库 + 删除缓存”

假设商品价格：

```text
100 → 80
```

有两个方案。

### 方案 A

```text
UPDATE MySQL
↓
UPDATE Redis
```

### 方案 B

```text
UPDATE MySQL
↓
DELETE Redis
```

今天练习中已经能够明确选择：

```text
方案 B
```

原因是：

> **删除缓存比维护 Redis 中第二套业务状态更简单，也更不容易被并发写入顺序反转造成旧值覆盖。**

---

## 五、为什么“更新数据库 + 更新 Redis”存在并发覆盖风险

假设两个线程同时修改商品价格。

线程 A：

```text
100 → 80
```

线程 B：

```text
80 → 70
```

数据库执行顺序：

```text
A：MySQL = 80
B：MySQL = 70
```

最终数据库正确状态是：

```text
70
```

但 Redis 写入是独立网络操作，执行顺序可能变成：

```text
B：Redis = 70
A：Redis = 80
```

最终：

```text
MySQL = 70
Redis = 80
```

旧请求反而覆盖了新缓存。

这就是今天练习中已经能够说出的核心问题：

```text
数据库操作顺序
和
Redis 网络写入完成顺序
不一定完全一致
```

如果为了强行维护两个系统的写入顺序，又需要继续增加：

```text
版本控制
锁
事件顺序
分布式协调
```

复杂度会快速上升。

而删除缓存的逻辑更简单：

```text
数据库改成最新值
↓
旧缓存删除
↓
下一次查询 Redis miss
↓
重新查数据库最新值
↓
重新构建缓存
```

因此 Cache Aside 中常见写策略是：

> **更新数据库，然后让旧缓存失效。**

---

## 六、为什么通常不推荐“先删除 Redis，再更新数据库”

假设初始状态：

```text
MySQL = 100
Redis = 100
```

线程 A 要修改：

```text
100 → 80
```

方案：

```text
先 DELETE Redis
↓
再 UPDATE MySQL
```

并发时可能出现：

```text
A：DELETE Redis
```

此时 Redis 已经没有数据，但 A 还没更新数据库。

线程 B 突然查询：

```text
B：Redis miss
↓
B：查询 MySQL
```

因为 A 还没完成数据库更新，所以 B 读到：

```text
100
```

然后：

```text
B：SET Redis = 100
```

最后 A 才执行：

```text
A：UPDATE MySQL = 80
```

最终：

```text
MySQL = 80
Redis = 100
```

今天已经能够准确指出本质：

> **先删除缓存和数据库真正更新完成之间存在一个时间窗口，查询请求可能在窗口中读到数据库旧值，并把旧值重新写回 Redis。**

所以相比：

```text
DELETE Redis
↓
UPDATE DB
```

更常见的是：

```text
UPDATE DB
↓
DELETE Redis
```

---

## 七、“更新数据库，再删除缓存”也不是绝对一致

今天练习里一个需要纠正的表达是：

```text
“这样操作简单，而且准确，不会出现问题”
```

这个说法过于绝对。

正确表达应该是：

> **先更新数据库，再删除缓存，可以显著降低常见并发不一致风险，但数据库和 Redis 是两个独立系统，仅靠两条普通操作不能提供严格的跨系统原子性。**

例如：

```text
UPDATE MySQL = 80
↓
成功
↓
DELETE Redis
↓
Redis 网络异常
↓
失败
```

最终：

```text
MySQL = 80
Redis = 100
```

所以：

```text
update DB
↓
delete cache
```

不是：

```text
绝对强一致
```

而是：

```text
一种常用的最终一致性基础方案
```

真正的工程问题应该继续追问：

```text
删除失败怎么办？
多久能恢复？
失败会不会被发现？
错误缓存最长存在多久？
```

---

## 八、Redis 删除失败后如何恢复

今天一开始对这部分没有思路。

其实本质很简单：

```text
MySQL = 80
Redis = 100
```

要恢复一致，只需要最终把：

```text
Redis 中的旧缓存
```

删除掉。

所以第一层保护是：

```text
失败重试
```

例如：

```text
数据库更新成功
↓
Redis DELETE 失败
↓
记录缓存失效任务 / 发送失效消息
↓
MQ / 延迟任务 / 定时任务
↓
再次 DELETE Redis
```

假设 5 秒后重试成功：

```text
Redis 被删除
↓
下一次用户查询
↓
Redis miss
↓
查询 MySQL = 80
↓
SET Redis = 80
```

最终：

```text
MySQL = 80
Redis = 80
```

今天已经能够重新解释这条链路：

> MQ 消费者删除旧 Redis 成功以后，Redis 中已经没有错误副本；下一次查询回源数据库，数据库中的正确值 80 会重新缓存到 Redis，所以系统最终恢复一致。

这里有一个关键认知：

> **删除缓存不是直接把正确数据写进 Redis，而是清除错误副本，让系统重新从真实数据源构建缓存。**

## 九、TTL 是什么，为什么它是兜底而不是主要方案

TTL：

```text
Time To Live
```

可以理解为：

```text
缓存存活时间 / 有效期
```

例如：

```text
TTL = 30 分钟
```

表示这个缓存 Key 到达有效期后会自动过期。

TTL 的一个重要价值是：

```text
限制错误缓存存在的最长时间
```

例如极端情况：

```text
DB 更新成功
↓
Redis 删除失败
↓
MQ 重试也失败
↓
异常任务也没恢复
```

如果 Redis 永不过期：

```text
旧数据可能长期甚至永久存在
```

如果：

```text
TTL = 30 分钟
```

则缓存最终会自动失效：

```text
Redis 自动过期
↓
下一次查询回源 MySQL
↓
重新构建最新缓存
```

因此：

```text
主动重试
→ 主动修复

TTL
→ 被动兜底
```

---

## 十、为什么不能说“有 TTL，所以缓存错 30 分钟也没事”

今天对这一题的判断是正确的：

```text
TTL 时间
必须和业务重要性、风险、允许的不一致窗口挂钩
```

TTL 能保证的是：

```text
错误缓存不会无限期存在
```

它不能保证：

```text
错误缓存存在期间不会造成业务损失
```

例如：

### 商品详情描述

```text
新描述已经发布
Redis 仍然是旧描述
```

短时间错误可能可以接受。

### 用户权限

```text
数据库已经撤销管理员权限
Redis 仍然认为是管理员
```

短时间错误都可能产生安全风险。

### 支付状态

```text
数据库已经支付成功
Redis 仍显示未支付
```

如果业务设计不严谨，用户可能再次发起支付。

### 用户账户余额

```text
真实余额 = 1000
缓存显示 = 10000
```

用户看到错误的资金状态，会产生非常严重的信任和业务风险。

所以最终结论不是：

```text
TTL 没用
```

也不是：

```text
TTL 能解决一致性
```

而是：

> **TTL 是一致性故障的最后兜底之一，业务越敏感，越不能把“等 TTL 自动过期”当作主要恢复策略。**

---

## 十一、不是所有业务都应该采用完全相同的缓存策略

今天比较了两个业务：

```text
业务 A：商品详情描述
业务 B：用户账户余额
```

两者不应该机械地使用完全相同的一致性策略。

### 商品详情

一般属于：

```text
读多写少
短时间旧数据影响有限
```

可以接受一定程度的：

```text
最终一致性
```

### 账户余额

属于：

```text
高敏感业务数据
```

最终资金判断通常不能简单相信 Redis 中的一个缓存值。

核心业务判断应该依赖：

```text
真实账本 / 数据库真实状态
+
可靠的并发控制
+
幂等
+
事务边界
```

Redis 可以参与：

```text
加速查询
预计算
辅助展示
```

但不能因为缓存快，就默认让它成为资金最终真相。

今天需要形成：

> **缓存策略必须服从业务风险，而不是所有数据统一“缓存 30 分钟”。**

## 十二、热点 Key 被删除以后为什么会缓存击穿

假设：

```text
product:1001
```

是一个热点商品。

缓存刚被删除：

```text
Redis miss
```

瞬间来了：

```text
5000 个请求
```

如果所有请求都执行：

```text
Redis miss
↓
查 MySQL
```

就可能变成：

```text
5000 个请求同时打数据库
```

这就是：

```text
缓存击穿
```

这里说明了一个很重要的系统设计规律：

```text
为了解决缓存一致性
↓
删除热点缓存
↓
又可能产生缓存击穿
```

一个问题的方案可能制造另一个问题。

---

## 十三、缓存击穿怎么处理

今天忘记了具体处理方式，需要重新建立最小模型。

最核心的思路是：

> **不要让所有请求同时回源数据库，只让一个或少量请求负责重建热点缓存。**

### 方案一：互斥锁 / 分布式锁

```text
请求 A：Redis miss
↓
抢到重建锁
↓
查 MySQL
↓
写 Redis
↓
释放锁
```

其他请求：

```text
Redis miss
↓
没有拿到重建锁
↓
短暂等待 / 重试
↓
A 已经完成缓存重建
↓
直接读取 Redis
```

这样可以从：

```text
5000 次 DB 查询
```

降低到：

```text
极少量 DB 查询
```

### 方案二：逻辑过期

缓存物理上暂时不删除，而是在缓存内容中记录：

```text
逻辑过期时间
```

请求发现逻辑过期：

```text
一个线程负责后台重建
其他线程暂时继续读旧值
```

优点：

```text
避免热点 Key 物理失效瞬间大量回源
```

代价：

```text
允许短时间读取旧数据
```

### 方案三：请求合并

同一个 Key 的大量并发请求：

```text
只触发一次真正的 DB 查询
↓
其他请求共享重建结果
```

三种方案本质都是：

```text
热点缓存失效
↓
不要让所有请求一起重建
```

## 十四、QPS 和 RT 是什么

今天排查题中对 `QPS` 没有概念，因此需要单独记住。

### QPS

```text
Queries Per Second
```

可以简单理解为：

```text
每秒处理多少次请求 / 查询
```

例如：

```text
数据库 QPS = 3000
```

表示数据库每秒大约承受 3000 次请求。

### RT

```text
Response Time
```

即：

```text
响应时间
```

例如：

```text
RT = 80ms
```

表示接口响应大约需要 80 毫秒。

这两个指标在排障中经常结合看。

## 十五、Redis 命中率下降、DB QPS 上升、RT 上升怎么分析

线上出现：

```text
Redis 命中率：95% → 40%
数据库 QPS：3000 → 20000
接口 RT：80ms → 900ms
```

Redis 服务本身没有宕机。

最先建立的因果链应该是：

```text
Redis 命中率下降
↓
更多请求 Redis miss
↓
更多请求回源 MySQL
↓
数据库 QPS 暴涨
↓
数据库压力增加
↓
查询变慢
↓
接口 RT 上升
```

因此第一怀疑方向是：

```text
缓存链路出了问题
```

例如：

```text
大量 Key 同时过期
大量 Key 被批量删除
缓存写入失败
缓存 Key 规则修改错误
新版本读写 Key 不一致
Redis 内存淘汰大量 Key
```

如果确实是大量 Key 在同一时间集中失效，就可能进一步发展为：

```text
缓存雪崩
```

今天能够重新回答：

> Redis 没挂但命中率大幅下降、数据库 QPS 暴涨时，首先应该怀疑是不是大量缓存同时失效、被删除或没有正常写入，导致大量流量绕过 Redis 回源数据库。

注意不能直接断言：

```text
一定是 TTL 到期
```

因为还有很多其他缓存链路故障。

工程排查应该是：

```text
先根据指标形成最可能假设
↓
再通过日志、监控和数据验证
```

## 十六、为什么大量 Key 不应该完全相同时间过期

系统规模扩大以后，如果大量 Key 都设置：

```text
TTL = 30 分钟
```

并且又在差不多同一时间创建：

```text
30 分钟后
↓
大量 Key 一起过期
↓
大量请求一起 Redis miss
↓
数据库 QPS 瞬间升高
```

所以很多缓存会考虑：

```text
基础 TTL
+
随机抖动
```

例如：

```text
30 分钟 + 随机 0～5 分钟
```

目的不是为了“看起来复杂”，而是：

```text
把大量 Key 的失效时间打散
```

降低同时回源数据库的概率。

这就是今天第 10 题里已经能够主动想到的扩容风险：

> 不要让大量缓存使用完全相同的失效时间，否则系统规模变大以后，集中失效可能让数据库瞬时吃不消。

---

## 十七、`@Transactional` 为什么不能保证 MySQL + Redis 一起成功或失败

今天对这一题已经知道结论：

```text
不行
```

但一开始说不清具体原因。

核心原因是：

> **普通 Spring `@Transactional` 通常管理的是数据库事务，它不会自动把 MySQL 和 Redis 两个独立系统变成一个跨系统原子事务。**

例如：

```java
@Transactional
public void updateProduct(Product product) {
    productMapper.updateById(product);
    redisTemplate.delete("product:" + product.getId());
}
```

代码写在同一个方法中，不代表：

```text
MySQL
+
Redis
```

自动获得：

```text
要么一起成功
要么一起回滚
```

### 场景一：Redis 已删除，数据库后来回滚

```text
开启数据库事务
↓
UPDATE MySQL
↓
DELETE Redis 成功
↓
后续代码抛异常
↓
MySQL ROLLBACK
```

Redis 删除操作不会因为 MySQL 回滚而自动撤销。

最后可能是：

```text
MySQL = 旧数据
Redis = 已删除
```

### 场景二：数据库最终提交，但 Redis 删除失败

```text
UPDATE MySQL
↓
Redis DELETE 失败
↓
数据库最终提交
```

最后可能是：

```text
MySQL = 新数据
Redis = 旧数据
```

因此：

```text
@Transactional
≠
MySQL + Redis 分布式事务
```

## 十八、事务方法里直接删 Redis 还有一个容易忽略的并发窗口

假设：

```java
@Transactional
public void updateProduct(...) {
    updateDb();
    deleteRedis();
}
```

数据库事务真正的执行过程可能是：

```text
BEGIN
↓
UPDATE MySQL
↓
DELETE Redis
↓
方法正常结束
↓
COMMIT MySQL
```

也就是说：

> Redis 被删除的时候，数据库事务可能还没有真正提交。

这时另一个请求 B：

```text
Redis miss
↓
查询 MySQL
```

如果 B 看不到 A 尚未提交的新数据，就可能读取：

```text
旧数据
```

然后重新写入 Redis。

最后 A 再提交：

```text
MySQL = 新数据
Redis = 旧数据
```

所以更严谨的工程实现还会考虑：

```text
数据库事务提交成功以后
↓
再执行缓存失效
```

例如使用：

```text
事务提交后回调
事件监听
可靠消息
Outbox / CDC 等机制
```

但这里仍然需要继续处理：

```text
数据库已经 COMMIT
↓
应用进程突然宕机
↓
缓存失效操作没有执行
```

所以如果业务一致性要求更高，还需要：

```text
可靠事件
重试
监控
TTL
补偿
```

不能只把删除 Redis 从方法里挪到 afterCommit 就认为彻底解决。

## 二十、延迟双删是什么

一种经典思路是：

```text
DELETE Redis
↓
UPDATE DB
↓
等待一小段时间
↓
再次 DELETE Redis
```

也就是：

```text
延迟双删
```

目标是：

```text
如果并发查询在第一次删除以后
把数据库旧值重新写回 Redis
↓
第二次删除再把这个脏缓存清掉
```

但是它不是万能方案。

问题包括：

```text
延迟时间不好精确确定
增加实现复杂度
第二次删除仍然可能失败
仍然无法提供真正的跨系统强一致
```

因此不能形成：

```text
缓存一致性
→ 一律延迟双删
```

正确判断仍然应该基于：

```text
业务一致性要求
并发规模
热点程度
故障成本
实现复杂度
```

## 二十四、今天的面试表达

如果面试官问：

**为什么 Cache Aside 修改数据时通常是更新数据库后删除缓存，而不是直接更新 Redis？**

可以回答：

> 数据库通常作为真实数据源，Redis 只是缓存副本。并发修改时，如果数据库和 Redis 都主动更新，两边网络操作完成顺序可能不同，旧请求可能最后覆盖 Redis 中的新值。删除缓存可以减少维护第二套状态的复杂度，数据库更新成功以后让旧缓存失效，下一次查询再从数据库读取最新值并重建缓存。不过这种方案仍然不是跨系统强一致，缓存删除失败时还需要重试、可靠消息或 TTL 等最终一致性机制。

如果面试官问：

**为什么不能先删 Redis 再更新数据库？**

可以回答：

> 先删缓存以后到数据库更新完成之间存在并发窗口。这个窗口内如果有查询请求 Redis miss，它可能回源数据库读到旧值，再把旧值写回 Redis，随后写请求才把数据库更新成新值，最终就会出现数据库是新值而 Redis 又变成旧值。因此 Cache Aside 中更常见的是先完成数据库更新，再让缓存失效。

如果面试官问：

**数据库更新成功，但是 Redis 删除失败怎么办？**

可以回答：

> 我不会认为一次 delete 调用就是全部保障。可以把缓存失效做成可重试任务，例如通过 MQ、延迟任务或可靠事件再次删除；同时缓存设置合理 TTL 作为最后兜底，避免错误值永久存在。线上还应该监控删除失败、重试和消息积压。业务越敏感，允许的不一致窗口越短，恢复机制就应该越可靠。

如果面试官问：

**`@Transactional` 能不能保证 MySQL 更新和 Redis 删除一起回滚？**

可以回答：

> 普通 Spring `@Transactional` 通常管理的是数据库事务，不会自动把 MySQL 和 Redis 变成一个原子事务。Redis 删除成功以后，即使后续数据库事务回滚，Redis 操作也不会跟着恢复；反过来数据库提交成功但 Redis 删除失败也会不一致。另外如果在数据库事务真正提交前就删 Redis，还可能产生并发读旧值重新构建缓存的窗口。因此需要正确设计事务提交后的缓存失效和失败重试，而不能只靠把两行代码写进同一个 `@Transactional` 方法。

如果面试官问：

**Redis 命中率突然下降，同时数据库 QPS 和接口 RT 暴涨，先查什么？**

可以回答：

> 我会先怀疑大量缓存 miss 导致流量回源数据库，例如大量 Key 同时过期、被批量删除、缓存写入失败、Key 规则变化或 Redis 淘汰。因为命中率下降意味着更多请求绕过缓存，数据库 QPS 随之升高，数据库压力增加以后接口 RT 也会升高。然后再结合缓存失效、写入错误、TTL 分布和数据库指标验证这个假设。

## 二十六、今天的最终总结

今天真正需要建立的不是：

```text
Redis 删除命令怎么写
```

而是一套：

**“数据库是真实数据源，缓存是允许失效和重建的副本；缓存一致性依靠失效、重试、TTL 和故障恢复来控制风险”的工程思维。**

核心链路可以压缩成：

```text
用户查询
↓
先 Redis
↓ miss
查 DB
↓
重建 Redis

数据修改
↓
更新 DB
↓
让旧 Redis 失效
↓
下一次查询重新从 DB 构建
```

但不能停在这里。

继续追问：

```text
Redis 删除失败怎么办？
↓
重试 / MQ / 可靠任务
↓
TTL 兜底

热点 Key 删除怎么办？
↓
防缓存击穿
↓
互斥重建 / 请求合并 / 逻辑过期

大量 Key 一起失效怎么办？
↓
TTL 打散 / 预热 / 限流

Redis 命中率下降怎么办？
↓
结合 DB QPS 和 RT 判断回源压力

@Transactional 能不能兜住 Redis？
↓
不能把两个独立系统自动变成一个事务
```

最终应该形成的条件反射：

```text
看到 DB 和 Redis 同时存一份数据
↓
先明确谁是真实数据源
↓
缓存尽量设计成可删除、可重建
↓
写操作优先考虑更新 DB 后失效缓存
↓
承认跨系统存在失败窗口
↓
用重试 + TTL + 监控控制最终一致性
↓
热点场景继续解决缓存击穿
↓
规模扩大后继续解决雪崩、热点和可观测性
```

而不是：

```text
Redis 和 DB 都主动写一遍
↓
再用 @Transactional 包起来
↓
认为两个系统就绝对一致
```

最终原则：

> **缓存不是为了制造第二份必须实时维护的真实状态，而是为了用可控的一致性成本换取读取性能；设计重点不是追求不存在任何时间窗口，而是让错误概率足够低、错误持续时间足够短、故障能够自动恢复，并且不让恢复过程把数据库打垮。**
