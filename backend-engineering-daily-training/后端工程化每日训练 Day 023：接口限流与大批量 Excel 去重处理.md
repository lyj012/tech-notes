# 后端工程化每日训练 Day 23：接口限流与大批量 Excel 去重处理

## 一、今天学习的知识点

今天学习和复盘了两个实际后端问题：

1. **接口限流（Rate Limiting）**
2. **十万条 Excel 数据的去重与多线程处理**

一句话理解：

> 限流解决的是“系统允许多少请求进入”，批量去重解决的是“如何用较低复杂度处理大量重复数据”，多线程则是在处理逻辑足够重时，通过拆分批次提高 CPU 利用率，但不能盲目增加线程。

---

## 二、为什么系统需要限流

线上系统能够处理的请求量是有限的。

假设 AI 异步任务平台提供：

```http
POST /api/task/create
```

平时 QPS 为：

```text
500
```

突然上涨到：

```text
8000
```

同时出现：

```text
Kafka Lag 持续上涨
数据库连接池接近耗尽
接口响应时间持续增加
```

如果所有请求都直接进入系统，可能形成以下故障链路：

```text
大量请求进入
↓
Tomcat 工作线程被占满
↓
数据库连接池接近上限
↓
Kafka 中任务持续积压
↓
Worker 处理不过来
↓
接口超时和重试增加
↓
流量进一步放大
↓
系统整体不可用
```

限流的目标不是保证每一个请求都成功，而是：

> 在系统超过承载能力时，主动拒绝部分请求，保护核心链路和整体可用性。

---

## 三、限流应该放在哪一层

今天最重要的纠正是：

> Controller 可以做限流，但通常不应该作为第一道流量保护。

请求到达 Controller 之前，通常已经经过：

```text
Client
↓
Nginx
↓
API Gateway
↓
Tomcat 线程池
↓
Filter / Interceptor
↓
Controller
```

如果到 Controller 才拒绝，请求已经消耗了：

```text
网络连接
网关转发资源
Tomcat 工作线程
JVM 内存
请求解析和认证资源
```

因此更合理的是多层限流。

### 1. Nginx 或 CDN 层

适合处理：

```text
单 IP 突发流量
明显恶意请求
网络层流量洪峰
```

### 2. API Gateway 层

适合按照以下维度做分布式限流：

```text
接口
用户 ID
Token
API Key
租户
IP
```

网关层能够在请求进入具体业务服务之前快速拒绝。

### 3. 应用层

应用层负责业务级限制，例如：

```text
单个用户同时最多运行 2 个 AI 任务
单个用户待处理任务最多 20 个
每天最多调用 100 次
每天最高消费 20 元
```

完整结构：

```text
Nginx：拦截明显异常流量
↓
Gateway：限制接口和用户请求速率
↓
Application：限制业务并发、任务额度和成本
```

## 四、常见限流算法

### 1. 固定窗口

例如：

```text
1 秒最多 100 次
```

可以通过 Redis 计数器和 TTL 实现。

缺点是存在窗口边界突刺：

```text
第 1 秒最后 10ms 通过 100 次
第 2 秒最前 10ms 再通过 100 次
```

短时间内可能实际通过 200 次请求。

### 2. 滑动窗口

统计最近一段真实时间范围内的请求：

```text
最近 1000ms 最多 100 次
```

相比固定窗口更加平滑，但实现和存储成本更高。

### 3. 漏桶

请求先进入桶，再按照固定速度流出：

```text
突发请求
↓
桶中排队
↓
固定速度处理
```

适合保护处理能力稳定的下游服务。

### 4. 令牌桶

系统按照固定速率产生令牌，请求取得令牌后才能通过：

```text
有令牌：通过
没有令牌：拒绝或等待
```

令牌桶可以允许一定程度的突发流量，是常见的限流方式。

## 五、Redis 固定窗口限流的原子性问题

简单实现可能写成：

```java
Long count = redisTemplate.opsForValue().increment(key);

if (count != null && count == 1) {
    redisTemplate.expire(key, 1, TimeUnit.SECONDS);
}
```

这个实现存在问题：

```text
INCR 成功
↓
应用在设置 EXPIRE 前宕机
↓
Key 没有过期时间
↓
用户可能被持续限流
```

生产环境中应该使用 Lua 脚本，将计数和设置过期时间作为一个原子操作执行。

示例思路：

```lua
local count = redis.call('INCR', KEYS[1])

if count == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[1])
end

return count
```

然后判断：

```text
count <= limit：放行
count > limit：拒绝
```

数据库、Redis 或网关限流组件只能解决各自层面的问题，不能只靠一个计数器完成完整的流量治理。

## 六、不同用户是否应该使用相同规则

不应该。

可以按照用户身份和套餐设置不同额度：

```text
匿名用户：额度最低，增加 IP 维度限制
普通用户：具有基础请求和任务额度
付费用户：根据套餐提高额度
管理员：额度更高，但仍然需要安全上限
```

管理员不能完全不限流，原因包括：

```text
管理员账号可能被盗
管理后台可能出现循环调用 Bug
批量操作可能误提交大量任务
管理员请求同样会消耗系统资源
```

因此管理员可以拥有更高额度，但仍要受到：

```text
单账号上限
单接口上限
批量操作上限
平台全局容量上限
```

此外还必须有全局限流。

即使每个用户都没有超过个人额度，所有用户加起来的流量仍然可能超过系统容量。

## 七、AI 接口如何控制调用成本

假设一次 AI 调用成本约为：

```text
0.5 元
```

只限制“同一时间只能执行一个任务”是不够的。

因为用户仍然可以顺序调用 1000 次：

```text
1000 × 0.5 = 500 元
```

完整策略至少包括：

### 1. 请求速率限制

```text
每个用户每秒最多提交 1 次
```

防止重复点击和脚本快速提交。

### 2. 并发任务数限制

```text
普通用户同时最多运行 2 个任务
付费用户同时最多运行 5 个任务
```

任务进入以下终态后释放并发名额：

```text
SUCCESS
FAILED
CANCELLED
TIMEOUT
```

不能只在成功时释放，否则失败任务可能永久占用额度。

### 3. 每日次数或金额预算

```text
免费用户每天最多 2 次
普通用户每天最高消费 10 元
企业用户根据套餐配置额度
```

金额预算通常比单纯次数限制更准确，因为不同模型和任务的成本不同。

### 4. 平台全局预算

```text
达到预算 80%：告警
达到预算 90%：降低免费用户额度
达到预算 100%：停止非核心调用
```

### 5. 预占和结算

任务提交前：

```text
检查余额或额度
↓
预估成本
↓
预占额度
↓
创建任务
```

任务结束后：

```text
根据实际 Token 或实际金额结算
↓
多退少补
```

同时需要幂等，防止网络重试或重复点击导致重复调用和重复扣费。

## 八、异步任务为什么返回 taskId

今天的疑问是：

> 用户最终还是需要等待 AI 执行完成，立即返回 taskId 有什么意义？

关键结论：

> 异步任务不一定缩短 AI 的计算时间，但可以让提交请求快速结束，释放 Web 线程，并让后台 Worker 按照受控并发独立执行。

同步执行：

```text
用户请求
↓
Tomcat 线程调用 AI
↓
等待 30 秒
↓
保存结果
↓
返回响应
```

这 30 秒中，会持续占用：

```text
Tomcat 工作线程
HTTP 连接
第三方客户端连接
网关和反向代理超时额度
```

异步执行：

```text
用户提交任务
↓
创建任务记录
↓
发送 MQ
↓
立即返回 taskId
```

后台 Worker：

```text
消费任务
↓
调用 AI
↓
保存结果
↓
更新任务状态
```

用户通过以下方式获取结果：

```text
轮询 GET /task/{taskId}
SSE
WebSocket
完成通知
```

用户等待的总时间可能相同，但系统获得了以下能力：

```text
快速释放 Web 线程
任务排队
控制 Worker 并发
失败重试
状态追踪
进度查询
任务取消
用户断线后继续执行
隔离 AI 任务和普通接口
```

可以把 taskId 理解为餐厅的号码牌：

```text
点餐后拿到号码牌
↓
收银台继续服务其他人
↓
后厨独立制作
↓
完成后通知取餐
```

## 九、消息队列、熔断、降级和缓存各自解决什么问题

这些能力不能互相替代。

### 1. 限流

```text
控制允许多少请求进入系统
```

### 2. 消息队列

```text
异步解耦
削峰填谷
任务排队
控制消费速度
失败重试
```

但消息队列不能无限吸收流量。

如果 Kafka Lag 持续上涨，说明：

```text
生产速度长期大于消费速度
```

此时还需要：

```text
Lag 告警
任务准入控制
生产端背压
Worker 扩容
暂停低优先级任务
```

### 3. 熔断

当第三方 AI 服务错误率或超时率持续升高时，临时停止继续调用，避免连接池和线程池被拖垮。

```text
限流：请求太多
熔断：下游已经异常
```

### 4. 降级

系统资源不足时，主动牺牲低优先级功能：

```text
暂停免费用户任务
关闭高成本模型
切换到更便宜的模型
降低最大输出 Token
延迟执行非紧急任务
```

### 5. Redis

在任务创建场景中，Redis 更适合承载：

```text
限流计数器
用户并发任务数
每日额度预检查
幂等 Token
短时间重复提交防护
配置缓存
```

Redis 不能代替核心任务记录、余额扣减和最终结算所需的数据库可靠性。

## 十、面试补充：十万条 Excel 数据如何去重

面试场景：

```text
Excel 中有 10 万条数据
每条记录包含多个字段
如果指定的 10 个字段完全相同，则认为数据重复
```

最直接的处理方式是：

```text
读取一行
↓
对 10 个字段进行标准化
↓
生成唯一 Key
↓
放入 HashSet
↓
add 返回 false，说明重复
```

示例：

```java
Set<String> seen = new HashSet<>();

String uniqueKey = buildUniqueKey(row);

if (seen.add(uniqueKey)) {
    // 第一次出现，保留
} else {
    // 重复数据，跳过或记录
}
```

`HashSet.add()` 的返回值：

```text
true：集合中原来不存在
false：集合中已经存在
```

平均时间复杂度接近：

```text
O(n)
```

十万条数据使用 HashSet 去重通常没有问题。

---

## 十一、生成唯一 Key 时需要注意什么

不能不加处理地直接拼接字段。

例如：

```text
字段 1 = ab，字段 2 = c
字段 1 = a，字段 2 = bc
```

直接拼接都可能得到：

```text
abc
```

可以采用：

```text
明确分隔符
长度编码
稳定序列化
计算 SHA-256 等哈希值
```

在生成 Key 前还应该统一数据格式：

```text
去除首尾空格
统一 null 和空字符串规则
统一大小写规则
统一日期格式
统一数字精度
```

否则：

```text
"Java"
" java "
```

是否重复将取决于业务规则，而不是技术本身。

## 十二、Excel 去重如何使用多线程

核心思路不是创建 100 个线程，而是：

> 将十万条数据拆成多个批次，再由少量固定线程轮流处理这些批次。

例如：

```text
单线程读取 Excel
↓
每 1000 条组成一个批次
↓
10 万条数据得到 100 个批次
↓
4 个工作线程并行处理
```

执行过程：

```text
线程 1：第 1 批
线程 2：第 2 批
线程 3：第 3 批
线程 4：第 4 批

处理完成后：

线程 1：继续领取第 5 批
线程 2：继续领取第 6 批
```

每个工作线程负责：

```text
字段标准化
数据校验
生成唯一 Key
判断是否重复
整理待写入数据
```

不要让多个线程同时操作同一个 Excel 解析对象。

更稳妥的流程是：

```text
一个线程流式读取 Excel
+
固定线程池并行处理批次
+
受控批量写入数据库
```

## 十三、多线程去重为什么不能使用普通 HashSet

普通 `HashSet` 不是线程安全的。

多个线程同时执行：

```java
set.add(uniqueKey);
```

可能出现并发问题。

可以使用：

```java
Set<String> dedupSet = ConcurrentHashMap.newKeySet();
```

判断逻辑：

```java
if (dedupSet.add(uniqueKey)) {
    // 首次出现，保留
} else {
    // 已经存在，重复
}
```

线程池示例：

```java
int processors = Runtime.getRuntime().availableProcessors();

ExecutorService executor = Executors.newFixedThreadPool(processors);
```

但生产中通常不建议直接使用 `Executors` 默认工厂创建无边界队列线程池，而应该使用 `ThreadPoolExecutor` 明确配置：

```text
核心线程数
最大线程数
任务队列容量
线程名称
拒绝策略
```

## 十四、为什么还需要数据库唯一索引

内存中的 Set 只能解决当前这一次导入中的重复数据。

还可能存在：

```text
数据库中已经有相同数据
两个导入任务同时执行
服务重启后再次导入相同文件
多个应用实例并发写入
```

因此需要为 10 个业务字段生成稳定的：

```text
dedup_hash
```

数据库增加唯一索引：

```sql
UNIQUE KEY uk_dedup_hash (dedup_hash)
```

完整方案：

```text
Excel 当前文件内部：Set 去重
↓
批量写入：数据库唯一索引兜底
```

不要针对十万条数据逐条查询数据库：

```text
读取一行
↓
执行一次 SELECT
↓
重复 10 万次
```

这种方式会产生大量数据库网络往返和连接开销。

---

## 十五、多线程一定比单线程快吗

不一定。

如果只是：

```text
简单拼接 10 个字段
+
HashSet.add()
```

十万条数据使用单线程通常已经很快。

多线程会额外产生：

```text
线程调度
上下文切换
共享 Set 竞争
批次拆分和汇总成本
```

多线程更适合以下场景：

```text
字段转换复杂
校验规则很多
需要计算哈希
需要调用 CPU 密集型算法
单线程处理时间已经明显过长
```

如果瓶颈在数据库写入，多开处理线程还可能导致：

```text
数据库连接池耗尽
锁竞争增加
批量插入互相影响
```

因此正确流程应该是：

```text
先测量性能瓶颈
↓
确认 CPU 处理阶段较慢
↓
再按批次并行
↓
控制数据库写入并发
```

## 十六、面试中可以怎么回答

### 1. 接口限流

> 对于 `/api/task/create` 这类高成本接口，我会优先在 Nginx 或 API Gateway 层限制请求速率，尽早拒绝异常流量，避免请求进入 Tomcat、数据库和 Kafka。应用层还需要限制单个用户的并发任务数、待处理任务数、每日次数和金额预算。匿名用户、普通用户、付费用户和管理员可以有不同额度，但管理员仍需要安全上限，同时还要设置平台全局限流。

### 2. 异步任务

> 返回 taskId 不一定能缩短 AI 的实际执行时间，但可以让提交请求快速结束，释放 Web 线程。任务由 Worker 异步执行，用户通过轮询、SSE 或 WebSocket 获取状态。这样可以支持排队、削峰、失败重试、任务状态追踪和并发控制，避免大量长任务占满 Tomcat 线程。

### 3. Excel 去重

> 我会先将 10 个字段按照业务规则标准化，再生成稳定的唯一 Key，使用 HashSet 判断当前文件中的重复数据，整体平均时间复杂度接近 O(n)。如果处理逻辑较重，可以单线程流式读取 Excel，每 1000 条拆成一个批次，交给固定线程池并行处理。多个线程共享去重集合时使用 `ConcurrentHashMap.newKeySet()`，最后批量入库，并通过数据库唯一索引防止历史数据和并发导入造成重复。

## 十七、今天的核心复盘

今天需要记住的不是某一个 API，而是三个工程处理模板。

### 模板一：流量保护

```text
入口尽早限流
↓
应用层业务额度
↓
消息队列削峰
↓
Worker 受控消费
↓
熔断和降级保护下游
↓
监控告警发现容量变化
```

### 模板二：异步任务

```text
快速接收任务
↓
返回 taskId
↓
后台独立执行
↓
状态持久化
↓
轮询或推送结果
```

### 模板三：大批量数据处理

```text
流式读取
↓
按批次拆分
↓
并行校验和转换
↓
线程安全去重
↓
批量入库
↓
唯一索引兜底
```

最后需要明确区分：

```text
限流：控制进入多少请求
并发控制：控制同时执行多少任务
消息队列：异步执行并缓冲突发流量
熔断：下游异常时停止继续调用
降级：资源不足时牺牲低优先级功能
缓存：减少重复读取或承载高频状态
幂等：重复请求不会重复执行
Set 去重：过滤当前批次或文件中的重复数据
唯一索引：从数据库层阻止最终重复写入
```
