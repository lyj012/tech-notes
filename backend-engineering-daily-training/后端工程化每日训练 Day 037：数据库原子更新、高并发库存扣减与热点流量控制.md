# 后端工程化每日训练 Day 37：数据库原子更新、高并发库存扣减与热点流量控制

## 一、今天学习的知识点

今天学习的是：

**数据库原子更新（Atomic Update）、条件 UPDATE、affected rows 业务判断、库存扣减、热点行，以及限流、Redis、MQ 在极端高并发库存场景中的职责。**

一句话理解：

> 对于简单的并发库存扣减，如果数据库能够用一条带业务条件的 UPDATE 同时完成“判断 + 修改”，就优先让数据库原子完成，而不是先 SELECT、再由 Java 判断、最后 UPDATE。

前几天连续学习了：

```text
乐观锁
↓
悲观锁
↓
事务隔离级别
↓
数据库死锁
```

今天进一步解决一个非常实际的问题：

```text
扣库存一定要 SELECT ... FOR UPDATE 吗？
```

答案是：

**很多简单场景不需要。**

今天重点解决以下问题：

```text
为什么 SELECT + Java 判断 + UPDATE 存在并发时间窗口
什么是数据库条件原子更新
为什么 stock > 0 必须写进 SQL
为什么 affected rows 可以直接代表业务并发结果
一次购买 N 件商品时 SQL 应该怎么写
为什么原子 UPDATE 能防超卖却不代表数据库扛得住无限并发
什么是热点行
限流、Redis、MQ 在秒杀场景中分别负责什么
Redis 预扣成功但后续失败为什么需要补偿
为什么并发控制不是叠得越多越安全
```

## 二、先看最典型的库存超卖问题

假设：

```text
product_id = 1001
stock = 1
```

两个请求同时购买。

一种很自然的业务代码可能是：

```text
请求 A：SELECT stock → 1
请求 B：SELECT stock → 1

请求 A：判断 stock > 0
请求 B：判断 stock > 0

请求 A：UPDATE stock = 0
请求 B：UPDATE stock = 0
```

从两个请求自己的视角看：

```text
我查询时库存还有 1
所以我可以买
```

但问题是：

```text
SELECT
和
UPDATE
```

是两个独立动作。

两个动作之间存在一个并发时间窗口：

```text
查询库存
↓
Java 判断
↓
真正执行更新
```

在这段时间里，其他请求可能已经修改了库存。

所以：

> **“我刚才查询到库存足够”不等于“我真正修改数据库时库存仍然足够”。**

---

## 三、用一条 SQL 同时完成“判断 + 修改”

对于简单库存扣减，可以直接写：

```sql
UPDATE product_stock
SET stock = stock - 1
WHERE product_id = 1001
  AND stock > 0;
```

这里最重要的变化是：

```text
原来：
SELECT
↓
Java 判断
↓
UPDATE

现在：
数据库一条 UPDATE
同时完成条件判断和库存修改
```

也就是把：

```text
检查库存
+
扣减库存
```

交给数据库一次完成。

这就是今天学习的核心：

**条件原子更新。**

---

## 四、100 个请求抢最后 1 件商品会发生什么

假设：

```text
stock = 1
```

100 个请求同时执行：

```sql
UPDATE product_stock
SET stock = stock - 1
WHERE product_id = 1001
  AND stock > 0;
```

最终理论上：

```text
1 个请求：affected rows = 1
99 个请求：affected rows = 0
```

原因是：

第一个成功执行更新的请求：

```text
stock = 1
↓
满足 stock > 0
↓
stock = 0
↓
affected rows = 1
```

后面的请求再轮到执行时：

```text
stock = 0
↓
stock > 0 不成立
↓
不更新任何记录
↓
affected rows = 0
```

所以不会出现：

```text
100 个请求都认为自己抢到了最后一个商品
```

---

## 五、affected rows 不只是 SQL 结果，也是业务结果

今天一个非常重要的认识是：

```text
affected rows = 0
```

**不等于数据库异常。**

例如：

```sql
UPDATE product_stock
SET stock = stock - 1
WHERE product_id = 1001
  AND stock > 0;
```

如果库存已经为 0：

```text
SQL 执行本身是成功的
只是 WHERE 条件没有匹配到记录
```

因此业务层应该解释成：

```text
商品已售罄 / 库存不足
```

而不是：

```text
数据库异常
SQL 执行失败
死锁
```

Java 可以直接这样判断：

```java
int rows = stockMapper.decrease(productId);

if (rows == 0) {
    throw new SoldOutException("库存不足");
}
```

因此可以形成一个非常实用的后端思维：

```text
不要先假设业务一定成功
↓
把业务条件写进 UPDATE
↓
让数据库执行条件更新
↓
根据 affected rows 判断最终业务结果
```

这个思想和前面学习的乐观锁很接近。

例如乐观锁：

```sql
UPDATE task
SET status = 'SUCCESS',
    version = version + 1
WHERE id = ?
  AND version = ?;
```

本质也是：

```text
条件满足
→ affected rows = 1
→ 更新成功

条件不满足
→ affected rows = 0
→ 发生业务并发冲突
```

## 六、为什么 stock > 0 不能漏掉

错误写法：

```sql
UPDATE product_stock
SET stock = stock - 1
WHERE product_id = 1001;
```

如果连续有请求进来：

```text
1 → 0 → -1 → -2
```

数据库不会自动知道：

```text
库存不能小于 0
```

所以：

```sql
stock > 0
```

不是可有可无的优化条件，而是：

**业务约束的一部分。**

正确性来自：

```text
修改动作
+
业务条件
```

被放在同一条 SQL 中原子执行。

## 七、一次购买 3 件商品时怎么写

如果用户一次购买：

```text
quantity = 3
```

不能只把：

```text
stock - 1
```

改成：

```text
stock - 3
```

同时还必须修改判断条件。

正确写法：

```sql
UPDATE product_stock
SET stock = stock - 3
WHERE product_id = 1001
  AND stock >= 3;
```

为什么必须是：

```sql
stock >= 3
```

假设现在库存：

```text
stock = 2
```

用户要买：

```text
3 件
```

如果仍然写：

```sql
stock > 0
```

条件仍然成立：

```text
2 > 0
```

最终可能变成：

```text
2 - 3 = -1
```

所以通用写法应该是：

```sql
UPDATE product_stock
SET stock = stock - #{quantity}
WHERE product_id = #{productId}
  AND stock >= #{quantity};
```

对应的最小判断模型：

```text
要扣 N 件
↓
SET stock = stock - N
↓
WHERE stock >= N
```

## 八、原子 UPDATE 和事务不是互相替代关系

如果业务只有：

```text
扣库存
```

一条 SQL，那么数据库已经能够把这个动作原子执行。

但真实下单业务可能包含：

```text
扣库存
↓
创建订单
↓
记录订单明细
↓
记录流水
```

这时原子 UPDATE 只能解决：

```text
库存这一条数据怎么避免并发超卖
```

它不能自动保证：

```text
库存扣成功
但订单创建失败
```

这种跨多步业务的一致性。

所以需要区分：

```text
原子 UPDATE
→ 解决单个条件更新动作的并发正确性

事务
→ 解决多个数据库操作之间的原子性和一致性
```

如果进一步跨越：

```text
数据库
MQ
第三方支付
外部系统
```

则还可能需要：

```text
本地消息表
Outbox Pattern
补偿机制
最终一致性
```

## 九、原子 UPDATE 保证正确性，不代表无限吞吐

今天一开始对于：

```text
100 万请求同时购买同一个商品
```

最初的理解是：

```text
数据量太大，数据库承受不了
```

这个方向接近，但更准确的说法应该是：

> **并发请求量太大，而且大量请求都在竞争同一行库存数据。**

假设：

```text
库存 = 1000
请求 = 100 万
```

即使所有请求都执行正确的原子 UPDATE：

```sql
UPDATE product_stock
SET stock = stock - 1
WHERE product_id = 1001
  AND stock > 0;
```

数据库仍然可能面对：

```text
大量 SQL 请求
↓
大量数据库连接竞争
↓
大量事务执行
↓
大量请求竞争同一库存行
↓
锁等待增加
↓
数据库吞吐下降
```

这时真正的问题不是：

```text
SQL 会不会把库存扣成负数
```

而是：

```text
数据库有没有能力在短时间内处理这么多请求
```

因此必须明确区分：

```text
正确性问题
≠
性能问题
```

原子 UPDATE 主要解决：

```text
正确性
```

它并不自动解决：

```text
极端流量下的吞吐和系统容量问题
```

## 十、什么是热点行

假设 100 万请求都购买：

```text
product_id = 1001
```

那么它们最终都要修改同一行：

```text
product_stock(product_id = 1001)
```

即使整张表只有这一行最忙，这一行也可能成为：

**热点行（Hot Row）。**

可以理解成：

```text
大量并发请求
↓
集中争抢同一个数据库资源
↓
大量等待
↓
数据库处理速度下降
```

所以：

```text
数据行数很少
```

不代表：

```text
数据库压力就一定小
```

有时候最危险的反而是：

```text
所有请求都集中修改同一条数据
```

## 十一、限流在秒杀场景中的作用

假设：

```text
库存只有 1000 件
瞬间来了 100 万请求
```

没有必要让 100 万请求全部进入数据库。

原因有两个：

第一：

```text
系统本身可能承受不了这么大的瞬时并发
```

第二：

```text
库存只有 1000
绝大多数请求最终注定失败
```

如果仍然让 100 万请求全部进入后端：

```text
Web 线程被大量占用
↓
连接池被占用
↓
数据库收到大量 UPDATE
↓
同一库存行产生严重竞争
↓
响应时间上升
↓
请求继续堆积
↓
可能形成雪崩
```

所以 Day 23 学习的限流，在这里负责：

> **控制真正允许进入系统的请求数量，保护应用线程、连接池和数据库。**

可以简化成：

```text
100 万请求
↓
限流
↓
只允许系统可承受的流量继续进入
↓
其余请求快速失败或返回“系统繁忙”
```

因此：

```text
原子 UPDATE → 保证扣减正确性
限流        → 保护系统容量
```

两者解决的不是同一个问题。

---

## 十二、MQ 在这里负责削峰

如果所有请求都必须在同一时刻被同步处理：

```text
瞬时压力非常大
```

Day 2 学习的 MQ 可以把瞬时流量变成排队处理：

```text
大量请求瞬间到达
↓
进入 MQ
↓
消费者按照系统能够承受的速度消费
↓
逐步写入数据库
```

这就是：

**削峰填谷。**

MQ 在这里主要解决：

```text
瞬时并发过高
```

而不是直接负责：

```text
库存不能超卖
```

所以不能混淆：

```text
MQ
≠
库存锁
```

它更像是：

```text
把一瞬间冲进来的洪峰
变成系统能够逐步处理的队列
```

---

## 十三、Redis 可以把大量失败请求挡在数据库之前

极端秒杀场景下，可以把可用库存预先放入 Redis。

请求先经过 Redis：

```text
100 万请求
↓
Redis 判断 / 预扣库存
↓
只有少量成功请求继续进入后续流程
↓
数据库最终落库
```

Redis 主要价值是：

> **在数据库之前完成高吞吐的库存判断或预扣，减少大量无效请求直接访问数据库。**

所以 Day 22 Redis 在这个场景中的职责可以理解成：

```text
前置库存判断
+
预扣库存
+
减少数据库压力
```

但这里必须注意：

```text
Redis 预扣成功
≠
整个订单最终一定成功
```

后面可能还有：

```text
订单创建失败
数据库写入失败
支付失败
消息消费失败
```

所以 Redis 只是高并发链路中的一层，不是整个业务一致性的终点。

---

## 十四、Redis 预扣成功但后续失败，需要补偿

假设 Redis：

```text
stock = 1
```

请求预扣成功：

```text
1 → 0
```

但是后续：

```text
数据库创建订单失败
```

如果什么都不做：

```text
Redis 认为库存少了 1
但数据库里没有对应订单
```

长期下来就会产生：

```text
Redis 库存
和
真实业务库存
不一致
```

所以需要根据业务设计补偿：

```text
Redis 预扣成功
↓
后续业务失败
↓
执行补偿
↓
库存恢复
```

例如：

```text
stock + 1
```

这再次说明：

> **高并发方案不仅要考虑成功路径，还必须设计失败路径和补偿路径。**

## 十五、限流、Redis、MQ、原子 UPDATE 分别负责什么

今天最终把几个经常混在一起的技术拆开了。

### 原子 UPDATE

负责：

```text
数据库层库存扣减正确
防止库存被并发扣成负数
```

核心：

```sql
UPDATE product_stock
SET stock = stock - #{quantity}
WHERE product_id = #{productId}
  AND stock >= #{quantity};
```

---

### 限流

负责：

```text
控制入口流量
保护应用和数据库
```

---

### Redis

负责：

```text
前置库存判断 / 预扣
挡住大量注定失败的请求
减少数据库访问
```

---

### MQ

负责：

```text
削峰
把瞬时高并发摊开处理
```

因此可以形成：

```text
原子 UPDATE → 正确性
限流        → 控制入口
Redis       → 前置过滤 / 预扣
MQ          → 削峰排队
补偿机制    → 处理后续失败造成的不一致
```

注意：

这不是说所有库存系统都必须同时使用这些组件。

只有流量和业务复杂度真正达到相应级别时，才需要逐步引入。

## 十六、为什么不能无脑叠加所有并发控制手段

普通商城每秒只有几十个下单请求，如果一条 SQL：

```sql
UPDATE product_stock
SET stock = stock - #{quantity}
WHERE product_id = #{productId}
  AND stock >= #{quantity};
```

已经能够稳定解决库存并发问题，就没有必要立刻叠加：

```text
Redis 分布式锁
+
SELECT FOR UPDATE
+
version 乐观锁
+
Redis 预扣
+
MQ
```

今天最终确认的判断是：

> **并发控制不是越多越安全。每增加一层，复杂度、故障点和性能成本都会增加。**

例如 Redis 分布式锁会带来：

```text
锁超时
锁续期
锁误释放
Redis 故障
网络分区
```

MQ 会带来：

```text
消息可靠性
重复消费
积压
消费失败
最终一致性
```

Redis 预扣会继续带来：

```text
Redis 和数据库库存一致性
失败补偿
库存回滚
```

所以技术选型应该遵循：

> **在满足业务正确性的前提下，优先选择最简单、故障面最小、维护成本最低的可靠方案。**

---

## 十七、今天形成的并发控制选择顺序

今天最终建立的核心判断顺序：

```text
简单并发修改
↓
先看数据库能否用一条条件 UPDATE 原子完成

涉及多个数据库操作
↓
再考虑事务

必须串行、高冲突临界区
↓
再考虑悲观锁

跨实例、跨资源的复杂临界区
↓
再考虑分布式锁

极端瞬时高并发
↓
再根据瓶颈考虑限流、Redis、MQ 等方案
```

这个顺序的核心不是：

```text
永远不用锁
```

而是：

```text
不要一遇到并发问题就先上最复杂的锁方案
```

应该先问：

```text
数据库本身能不能用一个更小、更简单的原子操作解决？
```

## 十八、面试怎么表达

如果面试官问：

**高并发扣库存怎么避免超卖？**

可以这样回答：

> 对于简单库存扣减，我会优先考虑数据库条件原子更新，例如 `UPDATE product_stock SET stock = stock - ? WHERE product_id = ? AND stock >= ?`，把库存判断和扣减放在同一条 SQL 中执行，并根据 affected rows 判断扣减是否成功。这样可以避免先 SELECT 再 UPDATE 中间的并发时间窗口。对于普通并发场景，这通常比额外引入分布式锁更简单。如果是秒杀这类极端热点场景，虽然原子 UPDATE 能保证不超卖，但同一库存行仍可能成为热点，因此还要结合限流、Redis 预扣和 MQ 削峰保护数据库，并处理 Redis 与数据库之间的最终一致性和失败补偿。

如果面试官继续问：

**为什么不用 SELECT FOR UPDATE？**

可以回答：

> 如果业务只是对单行库存执行一个能够通过条件 UPDATE 表达的原子扣减，就不一定需要先查询再悲观锁定。条件 UPDATE 已经可以让数据库完成判断和修改，并通过 affected rows 返回并发结果。只有业务临界区包含多个必须串行处理的步骤，单条 SQL 无法完整覆盖时，我才会进一步考虑悲观锁。

如果面试官问：

**为什么不用分布式锁？**

可以回答：

> 如果数据库的一条原子条件更新已经能够保证业务正确性，就没有必要再引入分布式锁。分布式锁会增加 Redis 依赖、锁超时、锁续期、异常释放等复杂度。技术方案应该优先选择满足一致性要求的最简单可靠实现。

## 十九、今天练习中的关键纠正

### 1. “数据量太大”不够准确

极端库存场景中，更准确的是：

```text
并发请求量太大
+
所有请求都竞争同一库存行
```

即：

```text
热点行竞争
```

---

### 2. affected rows = 0 不是数据库异常

对于带库存条件的 UPDATE：

```text
affected rows = 0
```

通常应该解释为：

```text
库存不足 / 商品已售罄
```

---

### 3. 原子 UPDATE 正确，不代表性能一定没问题

```text
SQL 正确性
和
系统吞吐能力
```

必须分别分析。

---

### 4. Redis 预扣不是最终成功

如果后续业务失败：

```text
需要根据业务设计补偿
```

否则 Redis 和真实业务数据可能不一致。

---

### 5. 并发控制不是越多越安全

真正正确的工程思路是：

```text
先明确问题
↓
选择最小可行并发控制手段
↓
确认正确性
↓
再根据真实容量瓶颈增加限流、缓存、MQ 等组件
```

而不是：

```text
看到并发
↓
所有锁和中间件全部叠上
```

---

## 二十、今天的最小记忆模型

### 模型一：单件库存扣减

```sql
UPDATE product_stock
SET stock = stock - 1
WHERE product_id = ?
  AND stock > 0;
```

```text
rows = 1
→ 成功

rows = 0
→ 库存不足
```

### 模型二：一次购买 N 件

```sql
UPDATE product_stock
SET stock = stock - #{quantity}
WHERE product_id = #{productId}
  AND stock >= #{quantity};
```

### 模型三：技术职责

```text
原子 UPDATE
→ 防止超卖

限流
→ 控制入口流量

Redis
→ 前置判断 / 预扣

MQ
→ 削峰排队

补偿
→ 处理失败后的不一致
```

### 模型四：方案选择

```text
能用一条条件 UPDATE
→ 先用原子更新

单条 SQL 不够，需要多个数据库操作一致
→ 事务

高冲突且必须串行
→ 悲观锁

跨实例复杂临界区
→ 分布式锁

极端热点流量
→ 再增加限流 / Redis / MQ
```

## 二十一、今天的最终总结

今天真正需要掌握的不是：

```text
背一条库存 SQL
```

而是形成下面这套判断能力：

```text
不要先查出来再在 Java 里判断
如果条件能够写进 SQL
就让数据库直接做条件原子更新
```

以及：

```text
原子 UPDATE 保证正确性
≠
数据库拥有无限吞吐
```

面对真实业务时，应该分别分析：

```text
第一层：业务正确性
库存会不会超卖？

第二层：事务一致性
订单、库存、流水能不能保持一致？

第三层：容量问题
系统和数据库能不能承受当前并发？

第四层：极端流量治理
是否真的需要限流、Redis、MQ、补偿机制？
```

最终原则：

> **能条件更新，就尽量不要“先查出来 → Java 判断 → 再更新”；满足业务正确性的前提下，优先选择最简单、故障面最小的方案。**
