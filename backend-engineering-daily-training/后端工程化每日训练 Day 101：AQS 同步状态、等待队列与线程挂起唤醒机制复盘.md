## 三、先教学：为什么线程竞争锁失败后需要等待？

### 1. 一个订单处理场景

假设订单服务使用 `ReentrantLock` 保护一段临界区：

~~~java
ReentrantLock lock = new ReentrantLock();

public void processOrder() {
    lock.lock();

    try {
        updateOrder();
    } finally {
        lock.unlock();
    }
}
~~~

先理解三个操作：

| 操作 | 含义 |
|---|---|
| `lock.lock()` | 尝试获取锁；获取失败时需要等待 |
| `updateOrder()` | 执行受锁保护的业务逻辑 |
| `lock.unlock()` | 释放当前线程持有的锁 |

`finally` 用于确保代码正常执行或抛出异常时，都能执行释放锁的逻辑。这里假设当前线程已经成功获取锁。

### 2. 两个线程竞争同一把锁

假设：

~~~text
线程 A
   ↓
lock.lock()
   ↓
成功获取锁
   ↓
执行 updateOrder()
   ↓
尚未释放锁


线程 B
   ↓
lock.lock()
   ↓
发现锁已被 A 持有
   ↓
无法立即获取锁
~~~

此时 B 不能直接进入 `updateOrder()`，否则两个线程就可能同时进入本应受同一把锁保护的临界区。

### 3. 今天的第一个核心问题

线程 A 已经成功获取锁，正在执行 `updateOrder()`，尚未执行 `unlock()`。

线程 B 调用同一把锁的 `lock.lock()`：

- B 能不能立即进入 `updateOrder()`？
- 如果不能，需要等待什么？
- A 释放锁后，B 是否一定能马上获取？

### 实际回答（按口述整理）

用户回答：

> 那肯定不能。它得等线程 A 执行完并且释放之后，线程 B 才能继续。A 释放后，B 不一定能获取，因为还要看有没有其他线程。

**评估：基础判断通过。**

回答中正确识别了两个边界：

1. A 仍然持有锁时，B 不能进入受保护的临界区。
2. A 释放锁后，B 也不一定立即获得锁，因为还可能有其他线程参与竞争。

### 纠正与补充：释放锁不等于指定 B 获胜

例如默认非公平的 `ReentrantLock`：

~~~text
A 持有锁
   ↓
B 获取失败，开始等待
   ↓
C 也来竞争
   ↓
A 释放锁
   ↓
B 被唤醒，准备重新竞争
   ↓
C 可能先一步获取锁
~~~

因此，B 不能把“ A 已经释放锁”理解为“锁已经直接交给 B”。

默认构造的 `new ReentrantLock()` 使用非公平策略。非公平竞争下，新到来的线程可能先于已经等待的线程获得锁。

**核心结论：线程等待的是获取锁的机会；锁释放后仍然需要竞争，不能仅凭等待时间判断一定由哪个线程获得。**

## 四、AQS 等待队列：线程获取锁失败后怎么办？

### 1. AQS 解决什么问题？

如果线程获取同步资源失败，系统需要一种方式管理这些等待线程。

AQS 可以把获取同步资源失败的线程组织到等待队列中，并协调它们后续的等待、唤醒和重新竞争。

对今天的 `ReentrantLock` 场景，可以先建立下面的简化理解：

~~~text
线程 A 获取锁
       ↓
线程 B 获取失败
       ↓
B 进入 AQS 等待队列
       ↓
B 在适当条件下挂起等待
       ↓
A 释放锁
       ↓
AQS 唤醒等待线程
       ↓
被唤醒的线程重新尝试获取锁
~~~

**AQS 不只是记录同步资源是否被占用，还负责协调获取资源失败的等待线程。**

### 2. AQS 的两个基础组成

今天的学习资料先把 AQS 理解为两个部分：

**同步状态（state）**

用于表示同步资源当前的状态。

对于普通 `ReentrantLock`，可以先做如下简化理解：

| state | 含义 |
|---:|---|
| 0 | 当前没有线程持有锁 |
| 1 | 锁已被获取一次 |
| 大于 1 | 可重入持有次数大于一次 |

`ReentrantLock` 是可重入锁，同一个线程可以重复获取同一把锁，因此持有次数可能大于 1。这里的 state 解释是针对当前 `ReentrantLock` 场景的直观模型，不代表所有 AQS 子类都采用完全相同的状态语义。

**等待队列（Queue）**

当线程暂时无法获取同步资源时，AQS 可以将等待线程组织起来，协调它们后续重新尝试获取资源。

今天没有展开队列节点结构、CAS 入队细节或 AQS 源码。

## 五、线程被唤醒，不代表已经获得锁

### 1. 场景

假设：

- A 持有锁；
- B 获取锁失败，进入 AQS 等待队列；
- A 执行 `unlock()`；
- AQS 唤醒 B。

问题：

**B 被唤醒之后，是不是就一定已经获得锁？**

### 实际回答（按口述整理）

用户回答：

> AQS 把线程 B 唤醒了，并不代表 B 已经获得锁。B 还是需要重新尝试获取锁，获取成功之后才能执行后续代码。如果没有竞争成功，就只能再次等待。

**评估：通过。**

用户已经明确区分：

- 被唤醒；
- 成功获取锁；
- 进入临界区执行代码。

这三个不是同一个动作。

### 2. 正确过程

~~~text
A 持有锁
   ↓
B 获取失败，进入等待队列
   ↓
B 挂起等待
   ↓
A unlock()
   ↓
AQS 唤醒 B
   ↓
B 重新尝试获取锁
   ├── 获取成功 → 执行后续代码
   └── 获取失败 → 继续等待
~~~

### 3. 为什么唤醒不等于锁交接？

`unpark` 的作用是让等待线程恢复运行或具备继续运行的条件，并不是把锁对象直接交给它。

B 被唤醒后，还要经过锁实现中的获取逻辑。只有真正获取成功，才能进入受保护的临界区。

如果此时有其他线程先获取了锁，B 仍然不能进入业务代码。

**可复用结论：唤醒是重新参与竞争的机会，不是获取锁成功的结果。**

## 六、为什么需要等待队列？自旋与挂起的区别

这是今天用户最初表示“不知道为什么需要等待队列”的知识点，经过一个最小反例后建立了理解。

### 1. 如果一直循环尝试，会发生什么？

假设 A 持有锁，B 获取锁失败。如果不进入等待机制，而是持续执行：

~~~java
while (!tryLock()) {
    // 一直尝试获取锁
}
~~~

这类持续尝试可以称为忙等待（Busy Waiting）；如果线程反复检查锁状态，则属于自旋式等待的一种表现。

问题在于：

1. A 还在执行订单业务，锁暂时不可用。
2. B 不断尝试获取锁，持续消耗 CPU 时间。
3. 如果有很多线程同时竞争，它们可能一起消耗 CPU 资源。
4. 这些 CPU 时间被用于反复检查锁，而不是执行有实际进展的业务工作。

### 2. 用户的实际回答

用户回答：

> 我感觉有点浪费性能。因为线程 A 获取了锁还在执行，线程 B 一直循环获取锁，无疑是浪费时间、浪费性能。如果很多线程都在执行这个操作，我觉得就非常浪费性能。

**评估：核心判断通过。**

用户独立指出了持续循环尝试带来的 CPU 资源浪费，并且注意到多个线程同时竞争时问题会放大。

### 3. AQS 如何协调等待？

在 `ReentrantLock` 的典型实现路径中，获取锁失败的线程会进入同步队列；当它暂时无法继续获取时，可以通过 `LockSupport.park()` 挂起等待。

锁释放后，等待线程会在适当时机被唤醒，例如通过 `LockSupport.unpark()` 使其恢复运行，再重新尝试获取锁。

~~~text
A 持有锁
   ↓
B 获取失败
   ↓
B 进入 AQS 等待队列
   ↓
B park 挂起
   ↓
B 不再持续执行无效的自旋循环
   ↓
A unlock()
   ↓
等待线程得到唤醒机会
   ↓
B 重新尝试获取锁
~~~

这里需要区分：

| 操作 | 作用 |
|---|---|
| `LockSupport.park()` | 挂起当前线程，等待后续许可或唤醒 |
| `LockSupport.unpark(thread)` | 为指定线程提供许可，使其能够恢复运行 |
| 重新获取锁 | 被唤醒后仍要执行获取逻辑，竞争同步资源 |

`park/unpark` 是 `LockSupport` 提供的线程阻塞与唤醒机制，AQS 在同步器实现中使用这类机制协调等待线程。

### 4. 自旋是不是任何时候都不好？

不是。

如果预计等待时间非常短，自旋可能避免线程挂起和恢复所涉及的额外成本。但如果等待可能持续较长时间，或者竞争线程很多，持续自旋通常会浪费 CPU。

因此，不能简单地把自旋说成永远错误，也不能认为挂起在任何场景下都更快。

**本日掌握的核心取舍：持续无效自旋会消耗 CPU；等待队列配合线程挂起，可以避免线程长期运行无意义的获取锁循环。**

## 七、把 AQS 基础等待机制串起来

综合今天的三个问题，可以得到下面的基本过程：

~~~text
线程 A 调用 lock()
       ↓
成功获取锁
       ↓
执行 updateOrder()
       ↓
线程 B 调用 lock()
       ↓
获取锁失败
       ↓
进入 AQS 同步等待队列
       ↓
在适当条件下 park 挂起
       ↓
线程 A 调用 unlock()
       ↓
释放同步状态
       ↓
AQS 协调后继等待线程恢复运行
       ↓
线程 B 被唤醒
       ↓
重新尝试获取锁
       ├── 成功 → 进入临界区
       └── 失败 → 继续等待
~~~

今天需要牢牢记住的三个结论：

1. **获取锁失败，不应该让线程无限制地消耗 CPU 进行无效循环。**
2. **AQS 通过等待队列协调获取同步资源失败的线程。**
3. **线程被唤醒不等于获得锁，仍然需要重新尝试获取。**

## 八、非公平锁与等待线程的竞争边界

今天第一题中，用户已经主动指出：A 释放锁后，B 不一定能获得，因为还可能有其他线程竞争。

以默认非公平 `ReentrantLock` 为例：

- B 可能已经在等待队列中；
- A 释放锁后，B 获得重新竞争的机会；
- 新到来的 C 也可能参与竞争；
- C 可能先于 B 获得锁。

这说明：

**等待队列中的先后顺序，不等于非公平锁下最终获得锁的严格顺序。**

今天只建立了这个基础认识，没有系统比较公平锁与非公平锁的源码实现、吞吐量、公平性和调度边界。

### 3. 完整查询条件

对于排序：

~~~sql
ORDER BY create_time DESC, id DESC
~~~

上一页最后一条记录是：

~~~text
(10:00:02, 104)
~~~

下一页查询条件：

~~~sql
SELECT id, create_time
FROM orders
WHERE create_time < '10:00:02'
   OR (
       create_time = '10:00:02'
       AND id < 104
   )
ORDER BY create_time DESC, id DESC
LIMIT 10;
~~~

两个分支分别表示：

1. 查询创建时间更早的记录；
2. 查询创建时间相同、但 ID 更小的记录。

如果只写：

~~~sql
WHERE create_time < '10:00:02'
~~~

那么创建时间同为 10:00:02、但 ID 小于 104 的记录也会被跳过，造成遗漏。

## 十二、可复用的 AQS 等待机制判断模型

以后遇到线程竞争锁的问题，可以按下面的顺序分析：

~~~text
1. 当前锁是否已经被其他线程持有？
   ↓
2. 当前线程能否立即获取同步资源？
   ↓
3. 如果获取失败，是否需要进入等待队列？
   ↓
4. 线程是持续自旋，还是被挂起等待？
   ↓
5. 持锁线程释放同步资源后，哪些等待线程会得到唤醒机会？
   ↓
6. 被唤醒的线程是否已经获得锁？
   ↓
7. 如果没有获得，是否需要重新竞争或继续等待？
   ↓
8. 公平性策略和其他竞争线程是否会影响最终获取顺序？
~~~

**一句话总结：** AQS 通过同步状态和等待队列协调线程竞争同步资源；获取失败的线程可以进入队列并挂起，资源释放后等待线程得到唤醒机会，但唤醒不代表锁已经交给它，最终仍要重新竞争。

## 十三、训练节奏与后续方向

本日按照“先解释机制，再一次问一道题”的方式完成了三个递进问题：

1. 持锁期间，其他线程为什么不能进入？
2. 等待线程被唤醒后，是否已经获得锁？
3. 为什么需要等待队列，而不是持续自旋？

用户在第三题开始时明确表示不知道等待队列的必要性。通过忙等待的最小示例，用户能够独立推导出持续循环尝试会消耗 CPU，多个线程竞争时问题会放大。

这说明教学顺序应当是：**先建立问题，再解释机制，最后验证理解；不能在用户还不知道概念时直接要求猜答案。**

后续可以继续学习：

- AQS 获取锁与释放锁的基本源码路径；
- CAS 与同步队列入队的关系；
- 公平锁与非公平锁的差异；
- 可重入锁的 state 变化；
- 中断与超时获取锁；
- Condition 等待队列与同步队列的区别。

以上是后续候选方向，不代表本日已经掌握。
