# 后端工程化每日训练 Day 31：数据库连接池、连接泄漏与连接池耗尽排障

## 一、今天学习的知识点

今天学习的是：

**数据库连接池（Connection Pool）设计、连接容量规划、连接长期占用与连接泄漏排查，以及线上连接池耗尽时的故障定位思路。**

一句话理解：

> 数据库连接池不是“连接越多性能越高”，而是用有限的数据库连接承接应用并发；真正需要控制的是连接总预算和单个连接的持有时间。如果慢 SQL、长事务、锁等待、第三方调用或连接泄漏让连接长期不能归还，即使数据库 CPU 很低，应用也可能因为拿不到连接而整体超时。

今天重点解决以下问题：

```text
为什么 Java 应用需要数据库连接池
数据库 CPU 不高，为什么应用仍然可能拿不到连接
多实例部署时 maximumPoolSize 应该如何规划
为什么 4 个实例 × 80 个连接不能只理解成“多出来的连接浪费”
慢 SQL 为什么会进一步拖满连接池
大表 JOIN 条件错误为什么可能产生巨量中间结果甚至接近笛卡尔积
长事务和事务内第三方调用为什么会长期占用连接
连接长期占用和真正的连接泄漏有什么区别
线上 active connections 长期接近上限时应该按什么顺序排查
连接池扩容为什么不能代替根因治理
```

---

## 二、数据库连接池到底解决什么问题

如果每次请求访问数据库都重新建立连接：

```text
收到请求
↓
建立数据库连接
↓
执行 SQL
↓
关闭连接
```

那么每次请求都需要重复承担：

```text
TCP 建连
数据库认证
会话初始化
连接销毁
```

高并发下成本很高。

所以实际 Java 项目通常使用连接池，例如 Spring Boot 中常见的 HikariCP。

应用启动以后维护一批可复用连接：

```text
应用启动
↓
创建 / 维护数据库连接
↓
请求到来
↓
从连接池借一个连接
↓
执行数据库操作
↓
归还连接
↓
下一个请求继续复用
```

连接池除了减少建连成本，还有一个更重要的作用：

> **限制应用同时向数据库施加的并发压力。**

数据库连接本身也是有限资源。

如果应用可以无限创建连接，那么大量请求到来时可能直接把数据库拖垮。

所以连接池本质上也是一种：

```text
资源池
+
并发上限
+
反压边界
```

---

## 三、连接池里最重要的三种状态

可以先用最简单的模型理解连接池：

```text
Idle Connections
空闲连接

Active Connections
正在被业务占用的连接

Pending / Waiting Threads
正在等待连接的线程
```

正常情况下：

```text
请求到来
↓
拿到空闲连接
↓
执行 SQL
↓
快速归还
```

如果所有连接都被占用：

```text
maximumPoolSize = 30

30 个连接全部 Active
↓
第 31 个需要数据库的线程无法立即拿到连接
↓
进入等待
```

如果等待超过 `connectionTimeout`：

```text
获取连接失败
↓
抛出超时异常
```

所以连接池故障常见的演化过程是：

```text
连接持有时间变长
↓
Active 持续升高
↓
Idle 接近 0
↓
Pending / Waiting 增加
↓
获取连接耗时增加
↓
connection timeout 增加
↓
接口整体变慢甚至不可用
```

---

## 四、几个核心连接池参数

以常见连接池的概念为例，需要重点理解：

### 1. maximumPoolSize

```text
单个应用实例最多允许同时拥有多少个数据库连接
```

它不是越大越好。

过小可能导致：

```text
正常并发下大量线程等待连接
```

过大则可能导致：

```text
多个应用实例一起把数据库连接数打满
数据库上下文切换和资源压力增加
其他服务或运维连接没有余量
```

---

### 2. minimumIdle

表示连接池希望维持的最小空闲连接数量。

它的作用主要是：

```text
提前保留可复用连接
降低突发请求到来时临时创建连接的开销
```

但同样不能脱离数据库整体连接预算单独设置。

---

### 3. connectionTimeout

表示：

```text
业务线程从连接池获取连接
最多愿意等待多久
```

例如：

```text
connectionTimeout = 3000ms
```

连接池持续没有可用连接时：

```text
等待 3 秒
↓
仍然没有连接
↓
快速失败
```

它解决的是：

> 不允许业务线程为了数据库连接无限等待。

---

### 4. maxLifetime

表示池中连接允许存活的最长生命周期。

连接池会在合适的时间淘汰过老连接并重新建立连接。

它主要用于避免：

```text
数据库 / 网络设备已经准备关闭老连接
但应用仍继续长期复用它
```

具体值需要结合数据库、代理、网络环境的连接生命周期设置，而不是机械复制一个固定值。

---

### 5. idleTimeout

用于控制空闲连接长时间不用以后何时回收。

核心思想仍然是：

```text
连接数量
连接生命周期
连接等待时间
```

都应该受控。

## 五、多实例场景下为什么不能只看单个连接池

今天的练习场景：

```text
AI 平台：4 个应用实例
每个实例 maximumPoolSize = 80
数据库 max_connections = 200
```

应用理论最大连接需求：

```text
4 × 80 = 320
```

但数据库允许的最大连接数只有：

```text
200
```

所以：

```text
应用总连接需求 320
>
数据库最大连接数 200
```

这种设计明显不合理。

但问题不应该只理解成：

```text
多出来 120 个连接没有作用，所以浪费了
```

真正的风险是：

```text
4 个实例会竞争有限的数据库连接资源
```

极端情况下可以理解成：

```text
实例 A → 拿到很多连接
实例 B → 拿到很多连接
实例 C → 只能拿到剩余一部分
实例 D → 新建连接频繁失败或等待
```

最终可能出现：

```text
不同实例获取连接能力不稳定
连接建立失败
请求等待
接口超时
故障实例进一步被上游重试放大
```

并且：

> 数据库 `max_connections = 200` 也不代表这 200 个连接都应该全部分给当前 Java 应用。

还需要为下面资源留余量：

```text
数据库管理员 / 运维排障连接
监控系统
定时任务
其他应用
数据同步任务
临时管理脚本
故障恢复操作
```

因此连接池规划应该从：

```text
数据库总连接能力
↓
扣除其他系统使用量
↓
预留安全余量
↓
得到当前业务应用连接预算
↓
再分配给各个应用实例
```

例如仅用于理解：

```text
数据库上限：200
业务应用预算：160
应用实例：4

160 / 4 = 40
```

那么单实例可能从 30～40 一类的范围开始压测，而不是直接配置 80。

注意：

> 40 只是示例，不是标准答案。

真正的数值还需要结合：

```text
实际并发
SQL 平均耗时
P95 / P99 SQL 延迟
事务时间
数据库 CPU / IO 能力
数据库连接成本
实例数量
流量峰值
压测结果
```

共同确定。

## 六、为什么数据库 CPU 不高，应用仍然拿不到连接

这是今天最重要的认知之一。

错误直觉是：

```text
数据库 CPU 不高
↓
数据库应该很空闲
↓
应用不应该拿不到连接
```

但：

> **CPU 只是数据库的一种资源，连接也是独立资源。**

假设当前 30 个连接全部被业务占着：

```text
30 个 Active Connections
30 个全部没有归还
```

第 31 个请求仍然需要数据库连接时：

```text
连接池里没有 Idle Connection
↓
只能等待
```

这些已占用连接可能并没有持续消耗大量数据库 CPU。

例如：

### 情况一：长事务中等待第三方 AI

```text
事务开始
↓
执行一条 SQL
↓
连接已经被事务持有
↓
调用 AI
↓
等待 20 秒
```

这 20 秒里数据库可能没有执行复杂计算，CPU 很低。

但：

```text
数据库连接仍被应用事务占着
```

---

### 情况二：锁等待

```text
事务 A 持有锁
↓
事务 B 等锁
↓
事务 C 等锁
```

大量连接处于等待状态时：

```text
CPU 不一定很高
```

但连接依然不能被快速归还。

---

### 情况三：连接泄漏

业务代码拿到连接以后由于异常路径没有正确释放：

```text
连接一直没有归还池中
```

数据库甚至可能没有多少实际工作负载，但应用连接池仍然会越来越少。

因此：

> **数据库 CPU 低，不代表连接池健康。**

线上必须同时看：

```text
CPU / IO
+
数据库当前会话
+
连接池 Active / Idle / Pending
+
慢 SQL
+
锁等待
+
长事务
```

---

## 七、慢 SQL 为什么会拖满连接池

今天首先想到的原因是：

> SQL 执行特别慢，导致当前请求一直持有数据库连接。

这个判断成立。

正常 SQL：

```text
借连接
↓
SQL 执行 20ms
↓
归还连接
```

连接周转非常快。

如果某条 SQL 执行：

```text
20 秒
```

那么同一个连接会被当前请求持续占用 20 秒。

高并发时：

```text
请求 1 → 慢 SQL → 占连接
请求 2 → 慢 SQL → 占连接
请求 3 → 慢 SQL → 占连接
...
```

很快就可能演变成：

```text
Active 接近 maximumPoolSize
↓
Idle = 0
↓
后续线程等待
↓
connection timeout
```

所以：

> **慢 SQL 不只是“某一个接口慢”，它还会降低连接周转率，进一步演变成整个连接池的容量问题。**

---

## 八、真实开发中的大表 JOIN 与笛卡尔积风险

今天提到了一个实际开发中遇到过的场景：

```text
两个几十万数据量的大表
进行 JOIN / UPDATE JOIN
SQL 执行非常缓慢
```

这里需要把概念说准确。

并不是：

```text
LEFT JOIN / RIGHT JOIN 本身就会产生笛卡尔积
```

而是：

> **如果 JOIN 条件缺失、关联条件写错、关联字段选择错误，或者一个条件产生大量多对多匹配，就可能产生巨大的中间结果；极端情况下可能接近笛卡尔积。**

例如：

```text
表 A：10 万行
表 B：10 万行
```

完全笛卡尔积理论组合数量：

```text
100000 × 100000
=
100 亿
```

实际数据库优化器不一定真的把 100 亿条完整物化出来，但这种错误关联仍然可能造成极高的：

```text
扫描量
JOIN 计算量
临时数据量
内存消耗
磁盘临时空间
锁持有时间
SQL 执行时间
```

如果这还是 `UPDATE ... JOIN ...`：

```text
执行时间变长
+
可能持有更多行锁
+
事务持续时间变长
```

最终故障链可能是：

```text
错误 / 低效的大表关联
↓
SQL 长时间执行
↓
事务长期不结束
↓
数据库连接长期被占用
↓
连接池周转率下降
↓
Active 接近上限
↓
新请求获取连接超时
```

因此排查大表关联 SQL 时除了看有没有索引，还应该看：

```text
JOIN 条件是否正确
是否出现不必要的多对多匹配
执行计划是否合理
扫描行数
索引是否命中
锁范围
事务大小
是否一次更新过多数据
```

## 九、除了慢 SQL，还有哪些原因会让连接长期不释放

### 1. 长事务

例如：

```text
@Transactional
↓
查询数据库
↓
执行大量 Java 业务逻辑
↓
继续更新数据库
↓
最终提交
```

事务持续越久，连接就可能被持有越久。

核心原则：

> 数据库事务应该尽可能短，只包住真正需要原子性的一组数据库操作。

---

### 2. 事务中调用第三方服务

这是 Day 28 和 Day 29 已经学习过的问题。

错误链路：

```text
@Transactional
↓
查询数据库
↓
调用 AI / HTTP / OSS / OBS
↓
等待 20 秒
↓
更新数据库
↓
提交事务
```

如果第一条数据库操作以后事务已经拿到连接，那么：

```text
外部服务等待 20 秒
=
数据库连接也可能跟着被占 20 秒
```

更合理的是：

```text
短事务读取 / 更新必要状态
↓
提交事务
↓
释放连接
↓
事务外调用第三方
↓
再开启短事务保存结果
```

涉及跨系统一致性时，再结合：

```text
状态机
Outbox Pattern
MQ
幂等
补偿
```

而不是简单扩大事务范围。

---

### 3. 锁等待 / 死锁相关等待

某个事务长时间持锁：

```text
事务 A
↓
持有目标行锁
```

其他事务：

```text
事务 B → 等待
事务 C → 等待
事务 D → 等待
```

这些等待请求同样会持续占用应用线程和数据库连接。

因此连接池耗尽时不能只看：

```text
慢 SQL
```

还要看：

```text
当前锁等待
长事务
阻塞链
```

---

### 4. 大结果集 / 大批量处理

例如：

```text
一次查询百万数据
↓
在业务线程中慢慢循环处理
```

如果整个处理期间 ResultSet、Session 或事务一直没有结束，就可能长期占用连接。

更合理的思路通常是：

```text
分页 / 游标 / 分批读取
↓
控制每批处理规模
↓
避免一个请求无限扩大数据库资源持有时间
```

具体方案要结合 ORM、事务和游标实现判断。

---

### 5. 真正的连接泄漏

例如手动 JDBC：

```java
Connection connection = dataSource.getConnection();
```

执行过程中发生异常：

```text
Exception
↓
异常路径没有 close
```

连接可能没有正确归还连接池。

所以手动管理资源时应该使用：

```java
try (Connection connection = dataSource.getConnection()) {
    // execute sql
}
```

或确保在 `finally` 中正确释放。

在 Spring + MyBatis / JPA 的标准事务管理路径中，框架通常会代管连接生命周期，但自定义 JDBC、错误的资源管理、特殊异步使用等场景仍然需要注意连接泄漏。

---

## 十、连接长期占用和连接泄漏不是一回事

这两个概念需要明确区分。

### 连接长期占用

例如：

```text
SQL 执行 30 秒
事务等待第三方 20 秒
锁等待 40 秒
```

连接最终还是可能被正确归还。

只是：

```text
归还得太慢
```

---

### 连接泄漏

连接泄漏是：

```text
业务已经不需要连接
↓
但因为代码路径错误
↓
连接一直没有被正确归还
```

随着请求不断发生：

```text
可用连接越来越少
↓
最终连接池永久性地接近耗尽
```

所以排查时不能看到：

```text
Active 很高
```

就立即下结论：

```text
一定是连接泄漏
```

还可能只是：

```text
慢 SQL
锁等待
长事务
第三方调用
业务峰值
```

导致正常连接长期被占用。

## 十一、线上 Active Connections 长期接近上限时怎么排查

今天最开始的排障思路是：

```text
先看日志
↓
看看哪些服务一直占着连接
↓
看耗时和报错
↓
再进一步定位
```

这个方向有价值，但需要形成更稳定的排障顺序。

### 第一步：先确认连接池确实已经成为瓶颈

先看：

```text
Active Connections
Idle Connections
Pending / Waiting Threads
获取连接耗时
connectionTimeout 次数
```

典型连接池耗尽特征：

```text
Active ≈ maximumPoolSize
Idle ≈ 0
Pending 持续增加
获取连接耗时明显上升
connection timeout 开始出现
```

这一步解决的是：

> 先确认问题真的是连接资源紧张，而不是看到接口慢就直接猜数据库。

---

### 第二步：看应用日志和 TraceId

优先搜索：

```text
Connection is not available
connection timeout
SQL timeout
transaction timeout
数据库异常
接口耗时异常
```

再通过：

```text
traceId
接口路径
方法耗时
SQL 日志
```

定位：

```text
到底是哪些接口在异常时间段大量占用数据库资源
```

只看数据库日志通常不足以直接映射到具体业务接口，因此应用日志和链路信息非常重要。

---

### 第三步：直接查看数据库当前会话和正在执行的 SQL

目标不是只看：

```text
数据库有没有报错
```

而是找：

```text
哪些连接现在正在干什么
已经执行 / 等待了多久
```

例如可能看到：

```text
SQL A → 20ms
SQL B → 80ms
SQL C → 已执行 45s
SQL D → 锁等待 30s
```

那么：

```text
SQL C
SQL D
```

就是优先调查对象。

对于 MySQL 一类数据库，实际排障会进一步查看：

```text
当前会话
执行中的 SQL
慢 SQL
锁等待
事务状态
执行计划
```

---

### 第四步：沿着“为什么连接不归还”继续查根因

建议优先按下面几个方向判断：

```text
1. 慢 SQL / 执行计划异常
2. 锁等待 / 长事务
3. @Transactional 范围是否过大
4. 事务内是否包含 AI / HTTP / OSS 等外部调用
5. 是否存在连接泄漏
6. 是否存在大结果集或一次性批量处理
```

这一步的核心问题只有一句：

> **哪些连接被谁占着、占了多久、正在执行什么、为什么迟迟不归还？**

---

### 第五步：最后再判断是不是容量确实不足

如果确认：

```text
SQL 正常
事务正常
无明显锁等待
无连接泄漏
连接持有时间正常
```

但业务并发已经稳定超过当前设计能力，再考虑：

```text
重新计算连接预算
调整连接池
数据库扩容
优化 SQL
增加缓存
限流
读写分离
拆分高消耗业务
```

不能一看到连接池满就立即：

```text
maximumPoolSize 30 → 300
```

因为这可能只是：

> 把应用侧排队转移成数据库侧过载。

---

## 十二、连接池监控应该看哪些指标

如果线上只监控：

```text
CPU
内存
```

远远不够。

连接池至少应该关注：

```text
Active Connections
Idle Connections
Total Connections
Pending / Waiting Threads
Connection Acquire Time
Connection Timeout Count
Connection Usage Time / Hold Time
```

数据库侧继续关注：

```text
当前连接数
活跃会话
慢 SQL
长事务
锁等待
死锁
数据库 CPU
IO
Buffer Pool / Cache 状态
```

业务侧则要同时看：

```text
接口 QPS
接口 P95 / P99
错误率
超时率
哪些接口流量突然上涨
是否发生重试放大
```

最终才能把完整链路串起来：

```text
业务流量变化
↓
接口请求增加 / 某接口变慢
↓
SQL / 事务连接持有时间增加
↓
Active Connections 上升
↓
Pending 增加
↓
接口超时
```

## 十三、连接池和线程池之间的关系

连接池和线程池都是：

```text
有限资源池
```

但保护的对象不同。

### 线程池

控制：

```text
同时可以运行多少任务 / 请求
```

### 数据库连接池

控制：

```text
同时允许多少数据库会话被应用占用
```

如果：

```text
Tomcat 工作线程 = 200
数据库连接池 = 30
```

这并不意味着系统错误。

因为：

```text
并不是所有 200 个请求都在同一时刻访问数据库
```

真正重要的是连接周转率。

如果每次数据库操作只需要：

```text
20ms
```

30 个连接可能已经能够承载很高的业务吞吐。

反过来，即使配置：

```text
80 个连接
```

如果每个连接都被长事务占 30 秒，仍然会很快耗尽。

所以连接池设计的核心不是单纯看请求线程数量，而是理解：

```text
并发数据库需求
×
单次连接持有时间
```

---

## 十四、连接池扩容为什么不是第一解决方案

遇到：

```text
连接池经常满
```

最简单的操作是：

```text
maximumPoolSize = 30
↓
maximumPoolSize = 100
```

短期可能看起来：

```text
等待线程减少
```

但如果根因是：

```text
慢 SQL
长事务
锁等待
错误 JOIN
第三方调用放在事务里
```

那么扩容只是让更多慢请求同时进入数据库。

可能形成：

```text
更多连接
↓
更多并发 SQL
↓
数据库 IO / 锁竞争进一步加重
↓
SQL 更慢
↓
连接持有时间更长
↓
连接池再次耗尽
```

所以正确思路通常是：

```text
先定位连接为什么长期占用
↓
治理根因
↓
再根据压测和容量模型决定是否调整池大小
```

---

## 十五、今天思考题的回答与修正

### 问题一：为什么数据库 CPU 不高，但应用仍然获取不到连接

最开始的回答思路：

```text
4 个实例每个最大 80
数据库最大连接数只有 200
如果请求很多，连接被长时间占用
剩余请求只能等待
```

方向正确，需要补充两个关键点。

第一：

```text
4 × 80 = 320
```

只是应用理论最大连接需求，并不代表数据库真的能够同时提供 320 个连接。

数据库只有：

```text
200
```

所以应用实例之间本身就会竞争有限连接资源。

第二：

> CPU 不高并不代表连接资源充足。

如果连接正在：

```text
等锁
等长事务结束
事务中等待第三方调用
因为泄漏没有归还
```

那么数据库未必持续做大量计算，但连接池仍然可能被占满。

最终答案：

> 数据库 CPU 和数据库连接是两种不同资源。4 个实例理论连接需求已经达到 320，超过数据库 200 的上限；同时如果已有连接又被慢 SQL、长事务、锁等待或第三方调用长期占用，新请求就会因为没有可用连接而等待甚至超时，即使数据库 CPU 并不高。

---

### 问题二：每个实例配置 80 是否合理

原回答核心：

```text
4 × 80 = 320
数据库只能 200
所以 80 不合理
```

这个结论正确。

但不能只说：

```text
多出来 120 个连接浪费了
```

更准确的是：

> 多实例连接池总和超过数据库连接预算，会导致实例之间竞争连接、连接建立失败和不可预测的超时风险。

连接池应该按照：

```text
数据库总连接预算
-
其他系统和运维连接
-
安全余量
↓
当前业务可用预算
÷
应用实例数量
```

再结合实际压测确定。

---

### 问题三：哪些原因会导致连接长期不释放

首先想到的是实际开发中遇到过的：

```text
大表 JOIN / UPDATE JOIN SQL 很慢
↓
SQL 长时间执行
↓
连接长期被占用
```

这个判断成立。

其中需要修正术语：

```text
LEFT JOIN / RIGHT JOIN 本身不会天然产生笛卡尔积
```

真正需要警惕的是：

```text
JOIN 条件缺失 / 写错
多对多关联范围异常
大表扫描
索引失效
```

造成巨量中间结果，极端情况下接近笛卡尔积。

除此之外还包括：

```text
长事务
锁等待
事务中调用第三方 AI / HTTP / OBS
连接泄漏
大结果集处理
```

---

### 问题四：Active Connections 长期接近上限时怎么排查

最开始的排查思路：

```text
先看日志
↓
看哪些服务长时间占连接
↓
看耗时和报错
↓
继续定位
```

需要把它工程化成下面的顺序：

```text
1. 看连接池指标
   Active / Idle / Pending / Acquire Time / Timeout

2. 看应用日志和 TraceId
   找异常接口、连接超时、SQL 超时、事务超时

3. 看数据库当前会话
   找长时间执行 SQL、锁等待、长事务

4. 找连接为什么不归还
   慢 SQL / 锁 / 长事务 / 第三方调用 / 泄漏

5. 根因正常以后
   再判断是不是连接容量本身不足
```

核心排障问题：

> **哪些连接被谁占着、占了多久、正在执行什么、为什么迟迟没有归还？**

## 十六、面试时怎么表达

可以这样回答：

> 数据库连接池主要用于复用连接，同时限制应用访问数据库的并发。连接池大小不能只看单个实例，而要按照数据库总连接预算、应用实例数量、其他服务占用和安全余量统一规划。例如数据库最大连接数 200，但 4 个实例都配置 80，那么理论连接需求达到 320，明显超过数据库上限。
>
> 如果线上发现 Active Connections 长期接近 maximumPoolSize，我不会先直接扩大连接池，而是先看 Active、Idle、Pending、获取连接耗时和超时次数，再结合应用日志、TraceId 和数据库当前会话定位慢 SQL、锁等待、长事务、事务中的第三方调用以及真正的连接泄漏。因为数据库 CPU 不高也可能出现连接池耗尽，瓶颈可能是连接被长期占用，而不是数据库计算能力不足。

如果结合实际项目经历，还可以补充：

> 我遇到过大数据量表关联更新非常慢的情况。大表 JOIN 如果关联条件、索引或执行计划不合理，会产生大量扫描和中间结果，极端情况下可能接近笛卡尔积，导致 SQL 和事务长时间执行。这个问题不仅影响单条 SQL，也会延长数据库连接持有时间，高并发时进一步拖满连接池。

## 十七、把 Day 28、Day 29、Day 31 串起来

这几天的知识其实是一条完整故障链。

### Day 28：事务边界

```text
事务不要包含不可控的外部调用
```

否则：

```text
事务时间变长
↓
连接持有时间变长
```

### Day 29：超时

```text
外部调用必须设置等待上限
```

否则：

```text
线程 / HTTP 连接 / 事务资源长期不释放
```

### Day 31：连接池

当大量请求都长时间占连接：

```text
Active 接近上限
↓
Pending 增加
↓
获取连接超时
↓
接口雪崩
```

所以稳定的数据库访问链路应该尽量做到：

```text
短 SQL
+
短事务
+
事务外外部调用
+
合理超时
+
连接池容量预算
+
慢 SQL / 锁 / 连接池监控
```

这不是几个独立知识点，而是一套共同的资源治理逻辑：

> **系统稳定性的核心之一，就是让有限资源能够快速周转，并且在下游异常时有明确的等待上限。**

## 十八、今天最终建立的核心认知

### 1. 数据库连接是有限资源

```text
连接池不是越大越好
```

它必须服从数据库整体容量。

### 2. 多实例必须看总连接预算

```text
单实例 maximumPoolSize
×
应用实例数量
```

才是应用理论总需求。

### 3. CPU 低不代表数据库没有瓶颈

```text
锁
连接
IO
长事务
```

都可能成为独立瓶颈。

### 4. 连接池耗尽不等于连接泄漏

```text
慢 SQL
长事务
锁等待
第三方调用
```

都可能让正常连接长期占用。

### 5. 排障要先找“连接为什么不归还”

而不是第一时间：

```text
把连接池调大
```

### 6. 慢 SQL 会形成资源级联故障

```text
SQL 变慢
↓
连接周转率下降
↓
连接池耗尽
↓
请求等待
↓
接口整体变慢
```

### 7. 连接池、事务、超时、线程池必须一起理解

它们共同决定：

```text
一个请求会占用多少资源
占用多久
故障时能否快速释放
```

数据库连接池并不只是记住：

maximumPoolSize

真正有工程价值的是能够回答：
